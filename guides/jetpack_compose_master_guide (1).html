النموذج الفكري لـ Jetpack Compose

The Compose Mental Model
🔄
Declarative vs Imperative UI

يمثل Jetpack Compose تحولاً جذرياً في طريقة بناء واجهات المستخدم على Android. فبدلاً من التعامل مع View Tree قابل للتعديل (Imperative)، نصف واجهة المستخدم كدالة رياضية تحول State إلى UI.

⚠️ Imperative (النمط القديم)
  • تعديل Views مباشرةً عبر المراجع (findViewById)
  • إدارة State يدوية داخل كل View
  • صعوبة التزامن بين البيانات والعرض
  • كود متكرر ومعقد عند التغييرات
✅ Declarative (Jetpack Compose)
  • وصف UI كدالة من State
  • State-driven: تغيير البيانات = تغيير الواجهة
  • إدارة State مركزية ومتنبؤة
  • كود أقصر وأكثر قابلية للصيانة
💡
المبدأ الأساسي

في Compose، واجهة المستخدم ليست "شيئاً" يتم تعديله، بل هي "نتيجة" يتم إعادة حسابها. كل Composable Function هي دالة نقية (Pure Function) تقبل State وتُنتج UI Tree.

⬇️
Unidirectional Data Flow (UDF)

يعتمد Compose على نمط تدفق البيانات الأحادي الاتجاه، حيث تتدفق الـ State من الأعلى إلى الأسفل، وتتدفق الأحداث (Events) من الأسفل إلى الأعلى.

Unidirectional Data Flow Architecture
ViewModel / State Holder
Single Source of Truth
⬇️ State Flows Down
Composable Parent
⬇️
Composable Child A
Composable Child B
⬆️ Events Flow Up
onClick, onValueChange
Lambda Callbacks
✅
فوائد UDF

تبسيط تتبع البيانات، إمكانية اختبار الواجهة بسهولة، تقليل الأخطاء المتعلقة بالتزامن، وتحسين قابلية إعادة الاستخدام للمكونات.

🧠
State Management Basics
remember & mutableStateOf

تُستخدم remember للاحتفاظ بقيمة عبر Recompositions، بينما mutableStateOf تُنشئ State قابلاً للملاحظة (Observable) يُطلق Recomposition عند تغيره.

var count by remember { mutableStateOf(0) }

@Composable
fun Counter() {
    var count by remember { mutableStateOf(0) }

    Button(onClick = { count++ }) {
        Text("Count: $count")
    }
}
State Hoisting

نمط رفع الـ State إلى أعلى مستوى ممكن في شجرة المكونات (Composable Tree) لجعل المكونات Stateless وقابلة لإعادة الاستخدام.

// Stateless Composable - يستقبل State و Event كمعاملات
@Composable
fun StatelessCounter(
    count: Int,
    onIncrement: () -> Unit
) {
    Button(onClick = onIncrement) {
        Text("Count: $count")
    }
}

// Stateful Wrapper - يدير الـ State
@Composable
fun StatefulCounter() {
    var count by remember { mutableStateOf(0) }
    StatelessCounter(
        count = count,
        onIncrement = { count++ }
    )
}
derivedStateOf vs remember

استخدم derivedStateOf عندما تكون القيمة المشتقة (Derived Value) تتغير بمعدل أقل من الـ State المصدر. هذا يمنع Recompositions غير الضرورية.

// ❌ سيُسبب Recomposition عند كل تغيير في list
val isEmpty = list.isEmpty()

// ✅ سيُسبب Recomposition فقط عندما يتغير ناتج isEmpty
val isEmpty by derivedStateOf { list.isEmpty() }
⚠️
متى تستخدم rememberUpdatedState؟

عندما تحتاج إلى الوصول إلى أحدث قيمة لـ Lambda أو State داخل LaunchedEffect أو DisposableEffect دون إعادة تشغيل الـ Effect. تُستخدم بشكل شائع في الـ Callbacks التي تستمر عبر Recompositions.

@Composable
fun Timer(onTimeout: () -> Unit) {
    // يضمن الوصول إلى أحدث onTimeout داخل LaunchedEffect
    val currentOnTimeout by rememberUpdatedState(onTimeout)

    LaunchedEffect(Unit) {
        delay(3000)
        currentOnTimeout() // دائماً تستخدم أحدث قيمة
    }
}

إدارة التأثيرات الجانبية والتخطيط

Side-Effects & Layout Architecture
⚡
Side-Effects API Masterclass

التأثيرات الجانبية (Side Effects) هي العمليات التي تؤثر على العالم الخارجي (مثل الـ Coroutines، الـ Listeners، أو الـ Callbacks). يوفر Compose API متكاملاً لإدارتها بأمان.

الـ API الاستخدام الدورة الحياتية
LaunchedEffect تشغيل Coroutine مرتبطة بـ Composable تُلغى عندما يتغير الـ key أو يُزال المكون
DisposableEffect إعداد وإلغاء Resources (Listeners, Subscriptions) يستدعى onDispose عند التغيير أو الإزالة
SideEffect تشغيل كود بعد كل Recomposition ناجحة يُنفذ بعد كل Composition Commit
rememberCoroutineScope إنشاء CoroutineScope مرتبط بـ Composable يُلغى عند خروج المكون من الـ Composition
produceState تحويل State من مصدر خارجي إلى Compose State يدير الـ Producer Coroutine تلقائياً
snapshotFlow تحويل Compose State إلى Kotlin Flow يلتقط تغييرات الـ Snapshot System 
// LaunchedEffect: تشغيل Coroutine عند تغيير الـ key
@Composable
fun UserProfile(userId: String) {
    LaunchedEffect(userId) {
        // يُلغى ويُعاد تشغيله عندما يتغير userId
        val user = repository.fetchUser(userId)
        userState.value = user
    }
}

// DisposableEffect: إدارة Resources مع التنظيف
@Composable
fun BackHandler(onBack: () -> Unit) {
    val callback = rememberUpdatedState(onBack)

    DisposableEffect(Unit) {
        val dispatcher = requireActivity().onBackPressedDispatcher
        val backCallback = object : OnBackPressedCallback(true) {
            override fun handleOnBackPressed() { callback.value() }
        }
        dispatcher.addCallback(backCallback)

        onDispose { backCallback.remove() }
    }
}

// produceState: تحويل Flow/Callback إلى State
@Composable
fun NetworkState(): State<Boolean> = produceState(initialValue = false) {
    val callback = NetworkCallback { isAvailable ->
        value = isAvailable
    }
    connectivityManager.registerDefaultNetworkCallback(callback)
    awaitDispose {
        connectivityManager.unregisterNetworkCallback(callback)
    }
}

// snapshotFlow: مراقبة State كـ Flow
@Composable
fun ScrollToTop(listState: LazyListState) {
    LaunchedEffect(listState) {
        snapshotFlow { listState.firstVisibleItemIndex }
            .filter { it > 0 }
            .collect { index ->
                showScrollToTop.value = true
            }
    }
}

التوقيع المُحوّل للـ Composable Function

يقوم الـ Plugin بإضافة معاملين سريين: $composer (Composer) و $changed (Bitmask) لتتبع التغييرات وتحسين Recomposition.

// ما تكتبه أنت:
@Composable
fun Greeting(name: String) {
    Text("Hello, $name")
}

// ما يُنتجه الـ Compiler (مبسط):
fun Greeting(
    name: String,
    $composer: Composer?,  // يُضاف تلقائياً
    $changed: Int           // Bitmask للمعاملات
) {
    $composer?.startRestartGroup(...)
    // ... group logic for tracking
    $composer?.endRestartGroup()
}
🔍
Bitmask & $changed Parameter

يستخدم الـ Compiler Bitmask (مثلاً 0b0001 أو 0b0010) لتحديد أي المعاملات قد تغيرت. إذا لم يتغير أي معامل، يتخطى Compose الـ Recomposition لهذا المكون.

The Compose Runtime & The Slot Table
ما هو Slot Table؟

الـ Slot Table هو بنية بيانات داخلية تعمل كـ Gap Buffer Array يخزن معاملات الـ Composables، والـ States، والقيم المُحفوظة (Memoized Values). يمثل "ذاكرة" الـ Composition.

Slot Table Architecture

[1] Key: 100
[2] Data: Modifier
[3] Group Start: "Text"
[4] Key: 200
[5] Data: "Hello"
[6] Group End
[7] Group End
Gap Buffer
[Active] [Active] [GAP] [Active]
↑ يتم إعادة استخدام المساحة الفارغة

O(1) Insert/Delete
O(n) Gap Movement
🧠
Positional Memoization

يستخدم Compose Positional Memoization حيث يُستخدم موقع استدعاء الدالة في شجرة التنفيذ (Execution Tree) كهوية (Identity) لتخزين واسترجاع القيم المُحفوظة. هذا هو السبب في أهمية استقرار شجرة الـ Composition.

// كل استدعاء لـ remember يُخزن في Slot Table
// بناءً على موقعه في الـ Call Tree
@Composable
fun Example() {
    val a = remember { "Value A" }  // Slot [0]
    if (condition) {
        val b = remember { "Value B" }  // Slot [1] - مشروط
    }
    val c = remember { "Value C" }  // Slot [2] أو [1]
}

// ⚠️ تحذير: الشروط تُغير المواقع وتُسبب فقدان الـ State!

// Smart Recomposition: يتخطى المكونات غير المتأثرة
@Composable
fun Parent() {
    var count by remember { mutableStateOf(0) }

    Column {
        ExpensiveWidget()        // ✅ لا يُعاد تركيبه
        CounterDisplay(count)  // ✅ يُعاد تركيبه فقط
        Button({ count++ })    // ✅ لا يُعاد تركيبه
    }
}

🛡️
Stability System (@Stable & @Immutable)
قواعد Smart Recomposition

يقوم Compose بتحليل استقرار (Stability) أنواع البيانات لتحديد ما إذا كان المكون يحتاج إلى Recomposition. الأنواع @Stable و @Immutable تُعلم الـ Compiler بأن النوع آمن للمقارنة بالمرجع (Referential Equality).

الـ Annotation المعنى الاستخدام
@Stable النوع قابل للتغيير لكنه يُعلم Compose عند التغيير Classes مع mutableStateOf داخلها
@Immutable النوع غير قابل للتغيير نهائياً بعد الإنشاء Data Classes مع val فقط
بدون Annotation الـ Compiler يفترض أن النوع غير مستقر (Unstable) قد يُسبب Recompositions غير ضرورية 
// ❌ غير مستقر - سيُسبب Recomposition دائماً
data class User(var name: String)

// ✅ Immutable - Compose يثق بأنها لا تتغير
@Immutable
data class User(val name: String)

// ✅ Stable - يُعلم Compose عند التغيير عبر State
@Stable
class UserViewModel {
    var name by mutableStateOf("")
}

// ✅ استخدام Immutable Collections
import kotlinx.collections.immutable.ImmutableList
import kotlinx.collections.immutable.persistentListOf

@Composable
fun UserList(users: ImmutableList<User>) { ... }
⚠️
مشكلة Multi-Module Data Models

عندما تكون Data Models في modules منفصلة، قد لا يستطيع الـ Compose Compiler تحليل استقرارها. الحلول: استخدام @Stable أو @Immutable، أو تفعيل strongSkipping mode في Compose Compiler 1.5.0+.

Performance Optimization & Metrics
⚡
Deferred State Reading

يتيح Deferred State Reading تجاوز مرحلة الـ Composition والانتقال مباشرة إلى مراحل الـ Layout أو Draw. يُستخدم بشكل شائع في الـ Scroll Animations والـ Gestures.

Lambda-based Modifiers

عند استخدام Lambda-based modifiers مثل Modifier.offset { ... } أو Modifier.drawWithContent { ... }، يتم قراءة الـ State داخل الـ Lambda بدلاً من الـ Composition، مما يتجنب Recomposition.

// ❌ سيُسبب Recomposition عند كل تغيير في scroll
val offset = scrollState.value.toFloat()
Box(modifier = Modifier.offset(y = offset.dp))

// ✅ يتجنب Recomposition - يقرأ State في Layout Phase
Box(
    modifier = Modifier.offset {
        IntOffset(0, scrollState.value) // قراءة مؤجلة
    }
)

// ✅ Modifier.drawWithContent - قراءة مؤجلة في Draw Phase
Box(
    modifier = Modifier.drawWithContent {
        val progress = animationState.value // قراءة في Draw
        drawRect(
            color = Color.Red,
            alpha = progress
        )
        drawContent()
    }
)

Custom Graphics & Animations

Custom Layouts

يتيح Layout Composable إنشاء تخطيطات مخصصة بتحديد منطق القياس (Measure) والوضع (Place) يدوياً. 

@Composable
fun CustomLayout(
    modifier: Modifier = Modifier,
    content: @Composable () -> Unit
) {
    Layout(
        content = content,
        modifier = modifier
    ) { measurables, constraints ->
        // Measure children
        val placeables = measurables.map { measurable ->
            measurable.measure(constraints)
        }

        // Calculate layout size
        val width = placeables.maxOfOrNull { it.width } ?: 0
        val height = placeables.sumOf { it.height }

        // Place children
        layout(width, height) {
            var yPosition = 0
            placeables.forEach { placeable ->
                placeable.placeRelative(x = 0, y = yPosition)
                yPosition += placeable.height
            }
        }
    }
}

@Composable
fun CustomChart(dataPoints: List<Float>) {
    Canvas(modifier = Modifier.fillMaxSize()) {
        val path = Path()
        val widthStep = size.width / (dataPoints.size - 1)

        dataPoints.forEachIndexed { index, value ->
            val x = index * widthStep
            val y = size.height - (value * size.height)

            if (index == 0) {
                path.moveTo(x, y)
            } else {
                path.lineTo(x, y)
            }
        }

        drawPath(
            path = path,
            color = Color(0xFF4285F4),
            style = Stroke(width = 4f)
        )
    }
}

updateTransition متوسط تنسيق Animations متعددة لنفس الـ Target State
InfiniteTransition متوسط Animations تكرارية لا نهائية (Pulsing, Rotation)
Animatable منخفض تحكم كامل في Animation مع Snap, AnimateTo
AnimationController منخفض أدنى مستوى - تحكم يدوي في كل Frame 
// animate*AsState - High Level
val alpha by animateFloatAsState(
    targetValue = if (visible) 1f else 0f,
    animationSpec = tween(durationMillis = 300)
)

// updateTransition - Coordinated Animations
val transition = updateTransition(targetState = expanded, label = "card")
val width by transition.animateDp(label = "width") { state ->
    if (state) 300.dp else 100.dp
}
val cornerRadius by transition.animateDp(label = "radius") { state ->
    if (state) 0.dp else 16.dp
}

// Animatable - Low Level Control
val offset = remember { Animatable(Offset.Zero, Offset.VectorConverter) }

LaunchedEffect(target) {
    offset.animateTo(
        targetValue = target,
        animationSpec = spring(dampingRatio = Spring.DampingRatioMediumBouncy)
    )
}

Best Practices Checklist

✅ افعل

  • ارفع الـ State (State Hoisting) قدر الإمكان
  • استخدم derivedStateOf للقيم المشتقة
  • استخدم key و contentType في Lazy Lists
  • استخدم Lambda-based Modifiers للـ Animations
  • أضف @Stable / @Immutable لـ Data Models
  • استخدم DisposableEffect للتنظيف
  • فعل تقارير الـ Compiler لتحليل الأداء

❌ لا تفعل

  • لا تُمرر State غير مستقر إلى Composables
  • لا تستخدم remember مع Objects متغيرة
  • لا تُجري Side Effects مباشرة في Composable Body
  • لا تقس Child مرتين في Custom Layout
  • لا تستخدم mutableStateOf في غير Composable
  • لا تُنشئ Objects جديدة في Modifiers Chain
  • لا تهمل معامل key في Dynamic Lists
🏛️ توجيهات معمارية للمستوى Senior

يُعد Jetpack Compose ليس مجرد مكتبة UI، بل هو نظام Declarative Runtime كامل. لبناء تطبيقات قابلة للتطوير (Scalable) وأداءً عالياً:

  • 1. افهم الـ Three-Phase Pipeline: Composition → Layout → Drawing. كل مرحلة لها تكلفتها، ومهمتك تقليل الـ Work غير الضروري في كل مرحلة.
  • 2. احترم Stability Contracts: الأنواع غير المستقرة (Unstable) هي السبب الرئيسي لـ Recompositions غير الضرورية. استخدم @Immutable و @Stable بشكل واعٍ.
  • 3. استثمر في Deferred State Reading: في Animations والـ Gestures، استخدم Lambda-based Modifiers لتجاوز Composition Phase بالكامل.
  • 4. عالج Multi-Module Boundaries: في المشاريع الكبيرة، استخدم strongSkipping mode أو عرّف Stability Contracts واضحة عبر الحدود.
  • 5. راقب باستمرار: استخدم Compiler Reports و Layout Inspector لتحديد نقاط الضعف قبل أن تُصبح مشاكل أداء حقيقية.

"Compose ليس عن كتابة UI أقل، بل عن كتابة UI أكثر وعياً — كل Composable هو قرار معماري، وكل State Read هو تكلفة يجب تبريرها."
