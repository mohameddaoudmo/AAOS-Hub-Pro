046
Dynamic Dispatch على مستوى JVM Vtable

الفكرة: عند استدعاء method على object، الـ JVM لازم يعرف أنهي نسخة من الميثود ينفذ، خصوصًا لو فيه inheritance و overriding.

الـ Vtable: كل class عنده جدول (array) بيحتوي على pointers لكل virtual method. كل subclass بيرث الـ vtable ويستبدل pointers اللي عملها override. كل object بيحمل hidden pointer لـ vtable بتاع class.

الخطوات: الكومبايلر بيحدد index → Runtime: object → class reference → vtable → index → method pointer → تنفيذ.

Kotlin
open class Shape { open fun draw() = println("Shape") }
class Circle : Shape() { override fun draw() = println("Circle") }
val s: Shape = Circle()
s.draw() // JVM يلاقي vtable بتاع Circle وينفذ نسختها
JVM بيستخدم invokevirtual bytecode instruction للـ lookup الديناميكي. أما final أو static أو private فبتستخدم invokestatic/invokespecial — ده اسمه static binding.

047
Double Dispatch و Visitor Pattern

المشكلة: Dynamic Dispatch العادي هو single dispatch — بيتحدد بناءً على نوع object واحد فقط. لكن أحيانًا محتاجين نحدد السلوك بناءً على نوعين من objects في نفس الوقت.

الحل: استدعاءين polymorphic: الأول بيحدد نوع Element، والتاني بيحدد نوع Visitor.

Kotlin
interface Visitor {
    fun visit(c: Circle)
    fun visit(s: Square)
}
interface Shape { fun accept(v: Visitor) }
class Circle : Shape {
    override fun accept(v: Visitor) = v.visit(this) // dispatch 1
}
class AreaVisitor : Visitor {
    override fun visit(c: Circle) = println("مساحة دائرة") // dispatch 2
}

049
ليه الـ Casting (as) بيكسر الـ Polymorphism؟

Polymorphism الهدف منها التعامل مع objects من خلال abstraction عامة من غير ما تعرف النوع الحقيقي. لما تعمل casting، بترجع تكسر الـ abstraction وتقول "أنا لازم أعرف النوع الحقيقي" — الكود بقى coupled بكل subtype (بيخالف Open/Closed Principle).

البديل: polymorphic method → Visitor Pattern → sealed class + when

وجود casting كتير في الكود هو code smell بيقول لك "محتاج تعيد تصميم الـ hierarchy أو تستخدم Visitor/Strategy pattern".

Visitor Pattern لحل Expression Problem (AST)
Kotlin
sealed class Expr {
    abstract fun <R> accept(visitor: ExprVisitor<R>): R
}
class NumberExpr(val value: Double) : Expr() {
    override fun <R> accept(v: ExprVisitor<R>) = v.visitNumber(this)
}
interface ExprVisitor<R> {
    fun visitNumber(e: NumberExpr): R
    fun visitAdd(e: AddExpr): R
}
class EvalVisitor : ExprVisitor<Double> { ... }
class PrintVisitor : ExprVisitor<String> { ... }

لإضافة operation جديدة: class جديد يـ implement ExprVisitor — من غير ما تلمس Expr classes. لكن لو ضفت نوع جديد لـ Expr، لازم تعدل كل Visitors.

059
Covariance و Contravariance في Parameters و Return Types

Covariance: يرجع نوع أضيق (subtype) في return type. Contravariance: يقبل نوع أوسع (supertype) في parameters — مدعوم في generics و function types.

Kotlin
// Covariance في Generics
class Container<out T>(val item: T)
val anyContainer: Container<Any> = Container("hello") // ✅

// Contravariance في Generics
interface Consumer<in T> { fun consume(item: T) }

// PECS: Producer Extends (out), Consumer Super (in)

060
تأثير Generics/Templates على Polymorphism

Generics بتضيف طبقة parametric polymorphism مع الحفاظ على type safety وقت الكومبايل.

  • Type Erasure (JVM): List<String> و List<Int> بيبقوا List عادي runtime. مينفعش تعمل is List<String> runtime.
  • Bounded Type Parameters: fun <T : Comparable<T>> max(a: T, b: T): T — بيدمج parametric مع subtype polymorphism.

061
Performance Implications للـ Virtual Method Calls

التكلفة:

  • Indirect call: vtable lookup خطوات إضافية (object → class → vtable → method → call).
  • CPU Branch Prediction: virtual calls بتقلل قدرة التنبؤ بمسار التنفيذ → pipeline stalls.
  • منع Inlining: JIT صعب يعمل inline لـ virtual methods لأن الهدف مش معروف وقت الكومبايل.

التحسين: JIT بيعمل Monomorphic Inline Caching — لو نفس النقطة بتنادي نفس النوع دايمًا، بيحولها لـ direct call مؤقتًا مع fallback لو اتغير.

نصيحة: خلّي الميثودز final أو private لو معرفش إنها محتاجة override — ده بيدي الكومبايلر فرصة يحسّن الأداء.

065
Leaky Abstraction: 3 أمثلة من Android

التعريف: لما التفاصيل الداخلية (implementation details) للطبقة المفروض تكون "مخفية" بتظهر وتأثر على المستخدم — رغم إن الهدف من الـ abstraction إنها تخفيها.

1. RecyclerView.ViewHolder و View Recycling: المفروض يخفي تفاصيل إعادة استخدام Views، لكن لو مانضفتش الـ state القديم في onBindViewHolder، هتلاقي views "بتفتكر" حالة عنصر تاني.

2. Bitmap و Memory Management: الـ Bitmap API بيوهمك إنه object عادي (garbage collected)، لكن الـ pixel data بتتخزن في native memory في Android أقدم — لو مانديتش bitmap.recycle() يدويًا، ممكن OutOfMemoryError.

3. LiveData/Flow و Lifecycle: المفروض تخفي تعقيد ربط observers بالـ lifecycle، لكن لو استخدمت observeForever من غير removeObserver، هتسرب memory.

Joel Spolsky's Law: "All non-trivial abstractions, to some degree, are leaky."

Law of Demeter (LoD)

"Talk only to your immediate friends, don't talk to strangers." — object يتفاعل بس مع: نفسه، parameters، objects عمله، fields المباشرة.

مايجوزش: chain calls عميقة (Train Wreck) زي userManager.getUser().getAddress().getCity().getName()

069
Cohesion و Coupling

Cohesion (التماسك): مدى ارتباط المسؤوليات جوه نفس الـ class. High cohesion = كلاس بيعمل حاجة واحدة واضحة.

Coupling (الترابط): مدى اعتماد class على classes تانية. Loose coupling = التغيير في class واحد مايأثرش على التانية.

ليه High Cohesion + Loose Coupling؟ أسهل للفهم والصيانة (SRP) + أسهل للاختبار والتوسيع (mock للـ interfaces).

070
Abstraction Layer بين ViewModel ومكتبة Third-party

الاستراتيجية: Adapter/Facade Pattern عن طريق Interface خاص بيك (مش بتاع المكتبة).

  1. اعمل interface خاص بيك يعبّر عن احتياجات الـ ViewModel فقط.
  2. اعمل implementation بيستخدم المكتبة جوه ويحوّل بياناتها لموديلز خاصة بيك (Domain Models).
  3. الـ ViewModel يعتمد بس على الـ interface عن طريق DI.
Kotlin
interface AuthProvider {
    suspend fun login(email: String, password: String): AppUser
}
class FirebaseAuthProvider(private val firebaseAuth: FirebaseAuth) : AuthProvider {
    override suspend fun login(...) = ... // تحويل من Firebase لموديلك
}
class LoginViewModel(private val authProvider: AuthProvider) : ViewModel() { ... }

لو حبيت تستبدل Firebase بـ AWS Cognito: بس class CognitoAuthProvider : AuthProvider جديد + تغيير DI binding — الـ ViewModel صفر تعديل.

074
Stable Dependencies Principle وتصميم Abstractions مستقرة

SDP: "Depend in the direction of stability." — modules اللي بتتغير كتير تعتمد على modules أكتر استقرارًا. الـ abstractions المفروض تكون أكتر حاجة مستقرة.

  • اعتمد على السلوك مش التفاصيل.
  • Interface Segregation: interfaces صغيرة ومركزة.
  • Dependency Inversion: الطبقات العليا (Domain) تعرّف interfaces، والطبقات الأدنى (Data) تعمل implement.
  • قِس الاستقرار: I = Ce / (Ca + Ce) — كل ما الـ module اعتمد عليه modules تانية كتير (Afferent Coupling عالي)، كل ما بقى أكتر استقرارًا.

077
Default Methods في الـ Interfaces وتأثيراتها

من Java 8، interfaces تقدر تحط implementation افتراضي. الفايدة: تضيف method جديدة لـ interface موجود من غير ما تكسر الـ classes اللي بتعمل implement (backward compatibility).

التداعيات:

  • Diamond Problem: لو class عمل implement لـ interfaceين وكل واحد عنده default method بنفس الاسم، لازم يعمل override صريح.
  • بيبوظ جزء من فكرة interfaces (contract بحت) — سبب جدل بين المصممين.
  • مفيدة لعمل Mixins (سلوك مشترك بدون inheritance تقليدي).
Kotlin
interface A { fun greet() = println("A") }
interface B { fun greet() = println("B") }
class C : A, B {
    override fun greet() {
        super<A>.greet() // لازم تحدد صراحة
        super<B>.greet()
    }
}

078
Versioning لما تضيف Methods لـ Interfaces

لو عندك interface منشور (public API) وناس عاملة implement ليه، وضفت method جديدة abstract، كل الـ implementations هتكسر (compile error).

استراتيجيات الحل:

  1. Default Methods: أشيع وأفضل حل — backward compatible.
  2. Extension Interface: interface PaymentProcessorV2 : PaymentProcessor — interface جديد بدل تعديل القديم.
  3. Semantic Versioning: Major Version Bump لو التغيير breaking فعلاً.
  4. Deprecation: @Deprecated قبل الحذف بفترة كافية.

  • Vtable: array of method pointers لكل class — JVM بيستخدم invokevirtual للـ dynamic dispatch.
