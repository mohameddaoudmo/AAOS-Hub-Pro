Inheritance Pitfalls (#025 - #045)

#025 – استدعاء open method من الـ constructor

لو نادينا method مفتوحة (open) جوه constructor الأب، وكانت الابن (subclass) عامل override ليها، فـ Kotlin/JVM هيستدعوا نسخة الابن قبل ما الابن يخلص تهيئة الـ properties بتاعته. النتيجة: الـ method بتتنفذ على object لسه "نص متكوّن" (partially constructed)، فأي property في الابن لسه مالهاش قيمة بتظهر null أو default value غلط.

open class Parent {
    init { printInfo() } // بينادي نسخة الـ Child!
    open fun printInfo() = println("Parent")
}

class Child : Parent() {
    val name = "Kotlin"
    override fun printInfo() = println("Child name length = ${name.length}")
}

fun main() { Child() }
// النتيجة: Child name length = 0  (مش الطول الحقيقي، لأن name لسه null وقت النداء)

الحل: متعملش override لدوال بتتنادى من الـ init/constructor، أو خلي الدالة final، أو استخدم factory method بدل ما تعتمد على virtual dispatch جوه الـ constructor.

#026 – ليه Kotlin بيمنع نداء non-final methods على object نص متكون

الـ JVM بيبني الـ object على مراحل: تخصيص الذاكرة (allocate) → تنفيذ constructor الأب بالكامل → تنفيذ constructor الابن. لو نادينا method قابلة للـ override في مرحلة constructor الأب، الـ vtable بيوجّه النداء لنسخة الابن (لأن الـ dynamic dispatch بيعتمد على النوع الحقيقي runtime)، لكن حقول الابن لسه معملتلهاش initialize. Kotlin مبيمنعش ده صراحة بالـ compiler (لسه ممكن يحصل)، لكنه بيقلل الخطر لأن الكلاسات والدوال final by default، فمعظم الحالات دي مش بتحصل غصب عنك زي Java.

#027 – Constructor chaining: this() و super()

  • •this(...): بينادي constructor تاني في نفس الكلاس.
  • •super(...): بينادي constructor في الكلاس الأب.

ترتيب التنفيذ دايمًا: الأب الأقدم أولًا، نزولًا للابن.

open class A(x: Int) { init { println("A($x)") } }
open class B(x: Int) : A(x) { init { println("B($x)") } }
class C(x: Int) : B(x) { init { println("C($x)") } }

fun main() { C(5) }
// A(5)
// B(5)
// C(5)

لو استخدمنا this() جوه C علشان ينده constructor تاني في C، هو برضو في الآخر لازم يوصل لـ super() قبل ما ينفذ أي كود تاني.

#028 – abstract override vs open override

  • •open override: بتفتح الدالة تاني عشان أي subclass جاي يقدر يعمل override زيادة.
  • •الدالة اللي already implemented متقدرش "تتحول" لـ abstract تاني في نفس الكلاس، لكن ممكن كلاس abstract intermediate يعيد تعريفها كـ abstract (re-abstraction) لو احتاج يجبر الفروع الجاية إنها تدي implementation جديدة، وده بيتعمل بصيغة abstract override fun foo() في كلاس abstract وسيط.
abstract class Base { open fun foo() = println("Base") }
abstract class Middle : Base() { abstract override fun foo() }
class Leaf : Middle() { override fun foo() = println("Leaf") }

#029 – Deep inheritance (5+ levels) وكابوس الصيانة

كل تعديل في أي مستوى ممكن يكسر سلوك المستويات الأعمق (fragile base class)، وصعب تتوقع مين بيعمل override لإيه، وصعب تتبع تدفق التنفيذ (yo-yo problem). الحل المعتمد في OOP الحديث: Composition over Inheritance — بدل ما تعمل هرم طويل، اعمل interfaces صغيرة + كلاسات تتجمع مع بعض (has-a بدل is-a)، أو استخدم Strategy/Decorator Pattern لإضافة سلوك بدل وراثة جديدة.

#030 – sealed class subclass ممكن تكون open؟

أيوه، subclass لكلاس sealed ممكن تتعرف كـ open عادي، وده بيسمح إن حد يعمل وراثة تانية منها (لكن لازم تبقى في نفس الـ module/package زي قيود sealed classes). الفايدة: بتقدر تعمل hierarchy مرنة جوه مجموعة محدودة معروفة (exhaustive when). الخطر: لو فتحت subclass كتير للتوريث الإضافي، ممكن تفقد الفايدة الأساسية من sealed (إنك عارف كل الأنواع الممكنة وقت الـ compile) لو الأنواع الجديدة دي بتتعرف بعيد عن الملف الأصلي.

#031 – Yo-yo Problem

لما تقرا كود مبني على هرم وراثة عميق، بتضطر "تلف" بين الكلاسات (فوق تحت زي اليويو) عشان تفهم مين بينفذ إيه فعليًا، لأن الـ method ممكن تتعرف في كلاس وتتنفذ فعليًا في تاني. في Android ده بيظهر بوضوح في هرم Activity/Fragment القديم: BaseActivity → BaseAuthActivity → BaseToolbarActivity → MainActivity، وأي lifecycle method زي onCreate ممكن تتلف بين 4 كلاسات عشان تفهم مين عمل super.onCreate() وفين. الحل الحديث: Composition عبر delegates/Fragments صغيرة، أو Jetpack Compose بدل هرم الـ Activity.

#032 – final و fragile base class problem

لما الكلاس final، مفيش حد يقدر يعمل subclass ليها ويعتمد على تفاصيل internal ممكن تتغير مستقبلًا. فالكلاس الأب حر يغيّر implementation جواه من غير ما يخاف يكسر كود ورثه منها؛ العلاقة الوحيدة المسموحة هي عبر الـ public API المعلن، مش عبر افتراضات داخلية. في Kotlin، كل كلاس final by default، فالمشكلة دي بتتحل من الأساس إلا لو انت قررت تفتح الكلاس بـ open عن قصد.

#033 – Behavioral subtyping vs Syntactic subtyping

  • •Syntactic: الابن بس لازم يديه نفس الـ method signatures (بيتأكد منه الـ compiler).
  • •Behavioral (Liskov Substitution Principle): الابن لازم كمان يحافظ على نفس "العقد السلوكي" (preconditions ماتتشددش، postconditions ماتضعفش) بحيث تقدر تستبدل الأب بالابن من غير ما تكسر الكود.

Kotlin الـ compiler بيتأكد بس من الـ syntactic subtyping. الـ behavioral جزء من مسؤولية المبرمج، ومفيش أداة تلقائية تضمنهولك بالكامل.

#034 – تعارض default methods بين اتنين interfaces

لو Interface A و Interface B عندهم نفس اسم الدالة بـ default implementation مختلف، وكلاس C بيعمل implement للاتنين، الـ Kotlin compiler بيرفض الترجمة ويجبرك إنك تعمل override صريح في C وتحدد أنهي implementation تستخدم (أو تدمجهم):

interface A { fun greet() = println("A") }
interface B { fun greet() = println("B") }
class C : A, B {
    override fun greet() { super<A>.greet(); super<B>.greet() }
}

على مستوى الـ bytecode، الـ JVM (Java 8+) بيعامل default methods كـ static-ish invokespecial calls على الـ interface، والـ compiler بيولّد method جديدة في C بتنادي A.super.greet() و B.super.greet() بشكل صريح.

#035 – تضييق visibility للـ override

لأ، متقدرش. في OOP وفي Kotlin تحديدًا، الـ override لازم يحافظ على نفس مستوى الـ visibility أو أوسع، مش أضيق، لأن ده بيكسر الـ Liskov Substitution Principle: لو حد شغال على الأب واستخدم method عمومية، وبعدين استبدلها بالابن، لازم يقدر ينده نفس الـ method. تضييقها هيكسر التوافق (substitutability).

#036 – Mixin Inheritance

الـ Mixin هو وسيلة "تحقن" سلوك جاهز (implementation) لأكتر من كلاس من غير علاقة وراثة is-a حقيقية. Kotlin interfaces مع default methods بتقرب من الفكرة دي: كلاس يقدر يعمل implement لعدة interfaces، كل واحدة معاها سلوك جاهز.

القيود: الـ interface متقدرش تحمل state حقيقي (بس ممكن abstract/computed properties)، لسه لازم تحل تعارضات الـ default methods يدويًا (زي #034)، ومفيش تحكم كامل زي Ruby mixins أو Traits في لغات تانية.

#037 – Diamond Problem

لو كلاس D بيرث من B و C، واللي هما الاتنين وارثين من A، وعند D استدعاء method موروثة من A بس اتعدلت في B و C كل واحدة بشكل مختلف، مين الـ implementation اللي هتشتغل؟ الغموض ده اسمه Diamond Problem.

  • •C++: بيسمح بالـ multiple inheritance لكن بيحتاج virtual inheritance تتحكم فيه يدوي.
  • •Java/Kotlin: بيمنعوا multiple inheritance للكلاسات خالص؛ بيسمحوا بس بتعدد الـ interfaces، وأي تعارض في default methods لازم يتحل صراحة (زي #034/#045).
  • •Python: بيستخدم C3 Linearization (MRO) عشان يحدد ترتيب واضح ومحدد لحل التعارض.

#038 – Composition vs Inheritance

  • •Inheritance (is-a): مناسب لما فيه علاقة نوعية حقيقية وثابتة (Dog is-a Animal) وسلوك مشترك مستقر.
  • •Composition (has-a): الكلاس بيحتوي object تاني ويفوض له السلوك. مرن أكتر، بيقلل fragile base class، وبيسمح بتغيير السلوك runtime (عبر تغيير الـ object المحتوى).

القاعدة الشائعة: "Favor composition over inheritance" — استخدم وراثة بس لما تحتاج فعلًا polymorphism حقيقي (تعامل مع الأنواع الفرعية كأب بشكل موحد)، واستخدم composition لإعادة استخدام الكود في باقي الحالات.

#039 – Method Resolution Order (MRO)

هو الترتيب اللي بيه اللغة بتقرر أنهي implementation تستخدم لما فيه أكتر من مصدر محتمل لنفس الـ method (زي لما كلاس بيرث من أكتر من أب في Python، أو بيعمل implement لأكتر من interface). أهميته إنه بيدي سلوك متوقع وقابل للتكرار بدل غموض؛ من غيره كل تشغيل ممكن يختار implementation مختلفة أو يديك تعارض compile-time.

#040 – مشاكل الـ Deep Inheritance Hierarchies

  • •Fragile base class: أي تعديل بسيط فوق بيكسر حاجات تحت.
  • •Yo-yo problem: صعوبة تتبع التنفيذ.
  • •Tight coupling: الفروع مرتبطة بتفاصيل داخلية للأب.
  • •صعوبة الاختبار (testing) لأن كل مستوى بيحمل حالة من اللي فوقه.
  • •صعوبة إعادة استخدام جزء من السلوك من غير ما تجر الهرم كله معاك.

#041 – Fragile Base Class Problem

لما تغيّر تفصيلة داخلية (implementation detail) في كلاس أب، وده يكسر سلوك subclasses حتى لو الـ public API متغيرش. بيحصل لأن الابن بيعتمد (يعمل implicit assumption) على تفاصيل داخل الأب مش موثقة كعقد رسمي.

الحل: خلي الكلاسات final بشكل افتراضي (زي Kotlin)، افتح للـ extension بس النقط اللي فعلًا متعمولها design كـ extension points (template methods واضحة)، وفضّل composition/interfaces عن الوراثة العميقة.

#042 – Overriding exceptions 

class Child : Parent() {
    // ✅ نفس الاستثناء أو subclass منه أو من غير استثناء أو أي Unchecked
    override fun method() { }
}

القاعدة: الـ override يقدر يرمي نفس الاستثناء، subclass منه، أو مفيش استثناء خالص، أو أي RuntimeException (unchecked) في أي وقت — لكن مايقدرش يوسّع (throws a broader checked exception) عن الأب. ملحوظة: Kotlin أصلًا معندوش checked exceptions زي Java، فالقيد ده بيفرق لو انت بتنادي كود Java من Kotlin.

#043 – Overriding vs Hiding

  • •Overriding: بيحصل مع instance methods، ويتحدد runtime (dynamic/late binding) بناءً على النوع الحقيقي للـ object.
  • •Hiding: بيحصل مع static methods، ويتحدد compile-time (static/early binding) بناءً على نوع المتغير المعلن.
Parent p = new Child();
p.staticMethod(); // بينادي نسخة Parent لأن static methods بتتحدد بنوع الـ reference مش الـ object
p.instanceMethod(); // بينادي نسخة Child (لو فيه override) لأن ده runtime polymorphism

#044 – هل الـ Constructors ممكن تتعمللها override؟

لأ. الـ constructors مش موروثة أصلًا (each class defines its own) ومالهاش اسم بيتشارك بين الأب والابن بالمعنى البوليمورفي، فمش بتشارك في آلية الـ dynamic dispatch. كل كلاس بيعرف الـ constructors بتاعته، والابن بيستدعي constructor الأب صراحة عبر super()، مش بيعمل override له.

#045 – حل Diamond Problem في Java

Java مبتسمحش بالوراثة المتعددة للكلاسات من الأساس، فمفيش diamond problem حقيقي على مستوى الكلاسات. المشكلة بتظهر بس مع الـ interfaces اللي عندها default methods متعارضة، وفي الحالة دي Java بتجبر الكلاس الوارث إنه يعمل override صريح ويحدد أنهي implementation يستخدم، زي:

class C implements A, B {
    public void method() { A.super.method(); }
}

#161 – Race Condition على مستوى الـ Object

بتحصل لما اكتر من thread بيقروا/يكتبوا في نفس الـ mutable state جوه object في نفس الوقت من غير تزامن (synchronization)، فالنتيجة النهائية بتعتمد على ترتيب تنفيذ عشوائي (timing) بدل منطق محدد.

class Counter {
    var count = 0
    fun increment() { count++ } // مش atomic: read → add → write
}

fun main() = runBlocking {
    val counter = Counter()
    val jobs = List(1000) {
        launch(Dispatchers.Default) { counter.increment() }
    }
    jobs.forEach { it.join() }
    println(counter.count) // غالبًا أقل من 1000 بسبب lost updates
}

#162 – Monitor Pattern و @Synchronized

الـ Monitor Pattern هو تصميم بيضمن إن thread واحد بس يقدر ينفذ جوه block معين من الكود في نفس الوقت، عن طريق ربط الكود بـ "قفل" (lock) مرتبط بالـ object نفسه.

@Synchronized في Kotlin بتعمل بالظبط كده: بتاخد الـ intrinsic lock بتاع الـ object (أو الكلاس لو static) قبل ما تنفذ الدالة، وتسيبه بعد ما تخلص.

العيوب: أداء أبطأ (thread contention)، ممكن يعمل deadlock لو استخدمته مع locks تانية بترتيب مختلف، وبيمنع أي تحكم دقيق زي timeout أو try-lock، وبيقفل الـ object كله مش جزء بس منه.

#163 – volatile vs AtomicInteger vs Mutex

  • •volatile: بيضمن الـ visibility بس (كل thread هيشوف آخر قيمة اتكتبت فورًا)، لكنه مش بيضمن atomicity للعمليات المركبة زي count++ (اللي هي read-modify-write). يفشل لو عندك أكتر من عملية مترابطة.
  • •AtomicInteger: بيضمن atomicity لعمليات بسيطة (increment, compareAndSet) عبر CAS (Compare-And-Swap) من غير حاجة لـ lock كامل. يفشل لو محتاج تعمل أكتر من عملية atomic مترابطة مع بعض كوحدة واحدة (compound actions).
  • •Mutex (coroutines) / synchronized: بيضمن atomicity لأي block كامل من الكود، حتى لو معقد. أبطأ نسبيًا، وممكن يعمل deadlock لو استخدامه غلط.

#164 – Actor Model في Kotlin Coroutines

الـ Actor بيحل مشكلة الـ race condition من غير locks عن طريق إن الـ state بتاعته معزولة تمامًا وبتتعدل بس من جوه الـ actor نفسه، والتواصل بيتم عبر رسائل (channel) بتتعالج واحدة ورا التانية بالتسلسل. مفيش اتنين thread بيلمسوا نفس الـ state في نفس اللحظة لأن كل حاجة بتمر عبر channel واحد متسلسل.

التشبيه في OOP: الـ Actor زي object بيطبق encapsulation صارم جدًا — مفيش حد بره الـ object يقدر يلمس الـ state مباشرة، وأي تفاعل لازم يكون عبر "رسالة" (method call تتعامل معاملة queue)، بالظبط زي فكرة الـ message passing الأصلية في OOP كما تخيلها Alan Kay.

#165 – StateFlow vs MutableStateFlow (Encapsulation)

  • •MutableStateFlow: بيسمح بالقراءة والكتابة (value = x)، وده زي الـ private/internal field.
  • •StateFlow: read-only view، وده زي public getter من غير setter.

النمط ده هو information hiding: الكلاس بيحتفظ بـ MutableStateFlow كـ private، وبيكشف بس StateFlow كـ public property، بحيث المستهلكين (UI) يقدروا يقروا ويعملوا observe بس، ومايقدروش يعدلوا الحالة من بره. ده نفس فكرة LiveData مقابل MutableLiveData بالظبط — نفس pattern الـ encapsulation، بس StateFlow بيدعم coroutines وعنده initial value إجباري.

#166 – ليه viewModelScope آمن من الـ memory leaks

viewModelScope هو CoroutineScope مربوط بـ Job مخزن جوه الـ ViewModel نفسها عبر CloseableCoroutineContext. لما الـ ViewModel توصل لـ onCleared() (بتتنادى تلقائيًا من الـ ViewModelStore لما الـ Activity/Fragment تتدمر نهائيًا)، فريموورك Android بينده clear() على كل الـ Closeable objects المسجلة، وده بيعمل job.cancel() تلقائيًا على كل الـ coroutines الشغالة جوه الـ scope ده. فالسلسلة: Activity destroyed → ViewModelStore.clear() → ViewModel.clear() → CloseableCoroutineContext.close() → Job.cancel() → كل الـ coroutines بتتوقف، فمفيش thread أو callback فاضل شغال يمسك reference لـ View اتمسحت.

#167 – Deadlock بين Objects

بيحصل لما Object A بياخد lock بتاعه وبعدين بينتظر lock بتاع Object B، في نفس الوقت اللي Object B ماسك lock بتاعه وبينتظر lock بتاع A — كل واحد واقف ينتظر التاني للأبد.

class Account(val name: String) {
    @Synchronized
    fun transferTo(other: Account) {
        Thread.sleep(50)
        other.receive()
    }
    @Synchronized
    fun receive() { println("received by $name") }
}

fun main() {
    val a = Account("A")
    val b = Account("B")
    Thread { a.transferTo(b) }.start() // A locked, waiting for B
    Thread { b.transferTo(a) }.start() // B locked, waiting for A -> Deadlock
}

الحل التقليدي: ترتيب ثابت للـ locks (مثلًا حسب hashCode أو ID) بحيث كل الـ threads بتاخد الأقفال بنفس الترتيب دايمًا.

#168 – Producer-Consumer بمبادئ OOP 

class SafeQueue<T>(private val capacity: Int) {
    private val items = ArrayDeque<T>()
    private val lock = Object()

    fun produce(item: T) = synchronized(lock) {
        while (items.size == capacity) (lock as java.lang.Object).wait()
        items.addLast(item)
        (lock as java.lang.Object).notifyAll()
    }

    fun consume(): T = synchronized(lock) {
        while (items.isEmpty()) (lock as java.lang.Object).wait()
        val item = items.removeFirst()
        (lock as java.lang.Object).notifyAll()
        item
    }
}

تصميميًا: الـ Queue نفسها object مسؤول عن حماية حالتها الداخلية (encapsulation + thread-safety مع بعض)، والـ Producers والـ Consumers مجرد كلاسات بتستخدم الـ API العام من غير ما تعرف تفاصيل التزامن جوه. في الكود الحقيقي، الأفضل تستخدم Channel في coroutines بدل wait/notify اليدوي.

#169 – Task Scheduling System

تصميم مقترح باستخدام Design Patterns:

  • •Strategy Pattern: لأنواع الجدولة المختلفة (FIFO, Priority, Cron-based).
  • •Composite/Dependency Graph: لتمثيل الـ dependencies بين المهام (task لازم تخلص قبل التانية تبدأ) — DAG structure.
  • •Observer Pattern: لإعلام أي جزء في النظام لما مهمة تخلص أو تفشل.
  • •Command Pattern: كل Task تتمثل كـ Command قابلة للتنفيذ/الإلغاء/الإعادة.
data class Task(val id: String, val priority: Int, val dependsOn: List<String> = emptyList(), val action: suspend () -> Unit)

class Scheduler {
    private val queue = java.util.PriorityQueue<Task>(compareByDescending { it.priority })
    private val completed = mutableSetOf<String>()

    fun submit(task: Task) = queue.add(task)

    suspend fun runReady() {
        val ready = queue.filter { it.dependsOn.all { d -> d in completed } }
        ready.forEach { task ->
            queue.remove(task)
            task.action()
            completed += task.id
        }
    }
}

النقطة الأهم في الـ system design هنا: فصل "جدولة إيه يشتغل امتى" (scheduler) عن "المهمة نفسها بتعمل إيه" (task action) — ده Single Responsibility واضح.

Data Management Patterns (#202 - #204)

#202 – Offline-First Apps

استخدم Repository Pattern + Cache-Aside (Single Source of Truth): الـ Repository دايمًا بيرجع بياناته من الـ local database (زي Room)، وده هو الـ SSOT اللي الـ UI بيعمل عليه observe. أي بيانات جاية من الـ network بتتخزن في الـ DB الأول، وبعدين الـ UI بيتحدث تلقائيًا لأنه observing على الـ DB مش على الـ network call مباشرة.

class ProductRepository(private val dao: ProductDao, private val api: ProductApi) {
    fun observeProducts(): Flow<List<Product>> = dao.getAll() // SSOT

    suspend fun refresh() {
        val remote = api.fetchProducts()
        dao.insertAll(remote) // الداتا بتتحدث محليًا، والـ Flow بيبعت التحديث تلقائي
    }
}

لو مفيش نت، الـ observeProducts() بيفضل شغال عادي من الـ cache المحلي.

#203 – إدارة إعدادات التطبيق

  • •لإعدادات بسيطة (theme, language, notifications toggle): Singleton بسيط زي PreferencesManager فوق DataStore/SharedPreferences.
  • •لإعدادات معقدة (متعددة المصادر، محتاجة sync، أو منطق تحقق معقد): Repository Pattern كامل بحيث تقدر تستبدلها/تختبرها بسهولة.

النقطة المهمة: استخدم DI عشان تحقن الـ instance بدل ما تنادي PreferencesManager.getInstance() في كل مكان، عشان تحافظ على قابلية الاختبار.

#204 – مزامنة البيانات بين local و remote

استخدم Sync Manager بيعتمد على Observer Pattern + WorkManager:

  • •أي تعديل محلي (add/edit/delete) بيتسجل كـ "pending change" في جدول منفصل أو flag.
  • •WorkManager بيشغل periodic/triggered work بيقرا الـ pending changes ويبعتها للسيرفر (push)، وبعدين يجيب أحدث نسخة من السيرفر (pull) ويحدث الـ local DB.
  • •أي conflict (تعديل حصل في الاتنين) بيتحل بسياسة واضحة (زي Last-Write-Wins أو timestamp-based merge).
class SyncWorker(context: Context, params: WorkerParameters) : CoroutineWorker(context, params) {
    override suspend fun doWork(): Result {
        syncManager.pushPendingChanges()
        syncManager.pullRemoteUpdates()
        return Result.success()
    }
}

الميزة الأساسية: الـ UI مش عارف ولا مهتم إن فيه مزامنة شغالة أصلًا — هو بس بيعمل observe على الـ local DB زي الحالة العادية (offline-first)، والمزامنة بتحصل في الخلفية.

️ Navigation Patterns (#205 - #206)

#205 – Navigation معقدة (Multi-step flows)

استخدم State Pattern فوق Navigation Component: كل خطوة في الـ flow (مثلًا Checkout: Cart → Address → Payment → Confirm) بتتمثل كـ state، وكل state عارف بس "أنا أروح فين بعدين" حسب قرار المستخدم، من غير ما تكتب منطق if/else ضخم في مكان واحد.

sealed interface CheckoutState {
    object Cart : CheckoutState
    object Address : CheckoutState
    object Payment : CheckoutState
    object Confirm : CheckoutState
}

fun CheckoutState.next(): CheckoutState = when (this) {
    CheckoutState.Cart -> CheckoutState.Address
    CheckoutState.Address -> CheckoutState.Payment
    CheckoutState.Payment -> CheckoutState.Confirm
    CheckoutState.Confirm -> CheckoutState.Confirm
}

#206 – Deep Linking

استخدم Chain of Responsibility Pattern: كل handler متخصص في نوع لينك معين، وبيتفحص هل هو ده اللي يقدر يتعامل مع الرابط ده، لو أيوه بيتعامل معاه، لو لأ بيمرره لل handler التالي في السلسلة.

interface DeepLinkHandler {
    var next: DeepLinkHandler?
    fun handle(uri: Uri): Boolean
}

class ProductLinkHandler : DeepLinkHandler {
    override var next: DeepLinkHandler? = null
    override fun handle(uri: Uri): Boolean {
        if (uri.pathSegments.firstOrNull() == "product") {
            openProduct(uri.pathSegments[1]); return true
        }
        return next?.handle(uri) ?: false
    }
}

الميزة: إضافة نوع لينك جديد = handler جديد جوه السلسلة، من غير ما تلمس الـ handlers القديمة (Open/Closed Principle).

️ Best Practices & Mistakes (#212 - #214)

#212 – مشكلة الـ God Objects في Android

الـ God Object (زي Activity ضخمة بتعمل كل حاجة: UI + networking + business logic + navigation) بيكسر Single Responsibility Principle، وبيبقى صعب الاختبار والصيانة والتوسعة لأن أي تعديل بسيط ممكن يأثر على حاجات تانية كتير جوه نفس الكلاس.

الحل: فكك الكلاس لمسؤوليات أصغر — استخدم Fragments لتقسيم الـ UI، ViewModels لمنطق العرض، Repositories للداتا، وFacade Pattern لو لسه محتاج واجهة موحدة بسيطة فوق أنظمة فرعية معقدة.

#213 – تجنب Memory Leaks في الـ Listeners

  • •استخدم WeakReference لما تحتاج تحتفظ بمرجع لـ Context/View من كلاس عمره أطول (زي Singleton أو background service).
  • •الأفضل: استخدم Lifecycle-Aware Components (LifecycleObserver, viewLifecycleOwner.lifecycleScope) بحيث الـ listener بيتنضف تلقائيًا.
  • •لو استخدمت listener يدوي، لازم تعمل unregister/removeListener صراحة في onDestroy()/onPause() المناسبة، خصوصًا في Fragments لازم تستخدم viewLifecycleOwner مش this عشان تتفادى leak لما الـ view تتدمر بس الـ Fragment instance لسه موجود.

#214 – امتى متستخدمش Singleton

تجنب الـ Singleton لما:

  • •الـ object بيحمل reference لـ Context/Activity (بيمنع الـ garbage collection ويسبب leak).
  • •محتاج نسخ مختلفة بإعدادات مختلفة (مثلًا اتصال بأكتر من بيئة/سيرفر في نفس الوقت).
  • •بتحتاج تعمل اختبار (unit testing) — الـ Singleton صعب تستبدله بـ mock/fake لأنه global state ثابت.

البديل: Dependency Injection — بتاخد نفس فايدة "instance واحدة مشتركة" (عبر تسجيله كـ singleton scope في الـ DI container)، بس بتفضل قادر تستبدله في الاختبارات وتتحكم في lifecycle بتاعه بوضوح.

interface EvictionPolicy<K> { fun onAccess(key: K); fun evictKey(): K? }
class LRUCache<K, V>(private val capacity: Int) {
    private val map = LinkedHashMap<K, V>(capacity, 0.75f, true)
    @Synchronized
    fun get(key: K): V? = map[key]
    @Synchronized
    fun put(key: K, value: V) {
        if (map.size >= capacity && !map.containsKey(key)) {
            val eldest = map.keys.first()
            map.remove(eldest)
        }
        map[key] = value
    }
}

#226 – نداء virtual method من الـ constructor

#228 – تبعات overriding equals() من غير hashCode()

لو عدّلت equals() من غير ما تعدّل hashCode() بنفس المنطق، بتكسر الـ contract الأساسي: أي كائنين متساويين بـ equals() لازم يكون عندهم نفس hashCode(). النتيجة: الكائنات دي هتتصرف بشكل غلط جوه HashMap/HashSet — ممكن كائن "متساوي" منطقيًا يتحط في bucket مختلف، فـ contains() أو get() يرجع نتيجة غلط (بيدور في bucket غلط بناءً على hash قديم).

class Point(val x: Int, val y: Int) {
    override fun equals(other: Any?) = other is Point && x == other.x && y == other.y
    // نسيان override hashCode() هنا = باج خطير مع HashSet/HashMap
}

#229 – التعامل مع Circular Dependencies بين كلاسات

الحلول الشائعة:

  • •Dependency Inversion: خلي الاتنين يعتمدوا على interface مشترك بدل ما يعتمدوا على بعض مباشرة.
  • •Mediator Pattern: كلاس ثالث بيتوسط بينهم بدل ما يكلموا بعض مباشرة.
  • •Lazy initialization: استخدام lazy { } أو Dependency Injection عشان تأجل حل الـ dependency لحد ما تحتاجه فعليًا.
  • •إعادة تصميم المسؤوليات (refactor) بحيث المنطق المشترك ينتقل لكلاس تالت مستقل، وكل كلاس يعتمد عليه هو بس.

#230 – تأثير Garbage Collection على قرارات تصميم الـ Objects

  • •تجنب إنشاء objects كتير قصيرة العمر (churn) جوه loops حساسة للأداء — كل object بيزود ضغط على الـ GC.
  • •الحذر من الـ memory leaks المنطقية: الاحتفاظ بمراجع (references) لعمر أطول من اللازم (listeners مسجلين، static references لـ Context) بيمنع الـ GC من تحرير الذاكرة حتى لو الـ object منطقيًا "خلص شغله".
  • •immutable objects بتسهل حياة الـ GC وبتقلل الأخطاء المرتبطة بمشاركة الحالة، لكن ممكن تزود عدد الـ allocations لو كل تعديل بيعمل نسخة جديدة.
  • •استخدام WeakReference/SoftReference بقصد لما تحتاج cache ممكن يتفضّى تلقائيًا لو الذاكرة قلّت.

#231 – تبعات استخدام الـ Reflection في تصميم OOP

  • •بيكسر encapsulation لأنه بيسمح بالوصول لـ private members من بره.
  • •بيبطئ الأداء بشكل ملحوظ مقارنة بالنداء المباشر (لأنه بيتجاوز الـ compile-time type checking).
  • •بيصعّب الـ refactoring: أدوات الـ IDE مش دايمًا بتلاقي كل الاستخدامات لأن الاسم بيتحدد كـ string أحيانًا.
  • •بيكسر ضمانات الـ type-safety اللي الـ compiler المفروض يديهالك.

بيستخدم بحذر في حالات محددة زي: frameworks (dependency injection, serialization)، أو annotation processing، لكن مش كحل عام في الكود التطبيقي العادي.

#232 – تأثير الـ Generics/Templates على الـ Polymorphism

الـ Generics بتديك polymorphism إضافي على مستوى الـ compile-time (parametric polymorphism) منفصل عن الـ runtime polymorphism التقليدي (inheritance-based). أهم نقطة في Kotlin/Java: بسبب Type Erasure، معلومات الـ generic type بتتشال وقت الـ runtime، فمينفعش تعمل is List<String> مباشرة، ومينفعش تعمل overload لدالتين باختلاف الـ generic type بس.

Variance (out/in في Kotlin) بتتحكم في العلاقة بين List<Dog> و List<Animal> — بدونها، الـ generics ممكن تكسر type-safety الـ polymorphism العادي لو استخدمتها غلط (زي مشكلة array covariance الشهيرة في Java).
