01

لماذا Fragment ولماذا Navigation؟

Fragment هو وحدة UI قابلة لإعادة الاستخدام ولها دورة حياة خاصة بها، تعيش داخل Activity مضيفة. Navigation Component هو الطبقة التي تدير التنقل بين هذه الأجزاء بشكل معياري وآمن.

المشكلة قبل Navigation Component

التعامل اليدوي مع FragmentManager و FragmentTransaction يعني إدارة الـ back stack يدويًا، تمرير بيانات عبر Bundle بدون فحص نوع، وتكرار كود معالجة الأخطاء في كل مكان.

مصدر واحد للحقيقة

Navigation Graph (ملف XML) يمثّل كل شاشات التطبيق ومساراتها في مكان واحد مرئي.

Back stack تلقائي

NavController يدير الـ back stack نيابة عنك، متوافقًا مع زر الرجوع في النظام.

Safe Args

توليد كود آمن النوع لتمرير البيانات بين الوجهات، بدل Bundle خام.

تكامل مع Jetpack

يعمل بسلاسة مع ViewModel، Hilt، BottomNavigationView، و Drawer.

02

دورة حياة Fragment

دورة حياة Fragment أكثر تعقيدًا من Activity لأنها مرتبطة بدورتين متوازيتين: دورة حياة الـ Fragment نفسه، ودورة حياة الـ View الخاص به.

onAttach()

يُستدعى عند ربط الـ Fragment بالـ Context المضيف. أول نقطة وصول لـ Context.

onCreate()

تهيئة المكونات غير المرتبطة بالـ View — مثل ViewModel أو استرجاع Arguments.

onCreateView()

تضخيم (inflate) الـ layout وإرجاع الـ View الجذري. لا تُنفّذ منطق UI هنا بعد.

onViewCreated()

الـ View أصبح جاهزًا بالكامل — المكان الصحيح لإعداد الـ Listeners والمراقبة (observe).

onStart() / onResume()

الـ Fragment مرئي وتفاعلي، متزامن مع دورة حياة الـ Activity المضيفة.

onPause() / onStop()

الـ Fragment يفقد التفاعل أو الظهور — وقت مناسب لحفظ الحالة المؤقتة.

onDestroyView()

الـ View يُدمَّر لكن الـ Fragment instance نفسه قد يبقى حيًا (خصوصًا في back stack). يجب تحرير الـ Binding هنا لتفادي تسرّب الذاكرة.

onDestroy() / onDetach()

تدمير الـ Fragment بالكامل وفصله عن الـ Context المضيف.

أهم فرق يجب فهمه

دورة حياة الـ View (getViewLifecycleOwner()) أقصر من دورة حياة الـ Fragment نفسه. عند وضع Fragment في back stack، الـ View يُدمَّر بينما الـ Fragment instance يبقى موجودًا في الذاكرة.

override fun onViewCreated(view: View, savedInstanceState: Bundle?) {
    super.onViewCreated(view, savedInstanceState)

    // استخدم viewLifecycleOwner وليس this عند المراقبة داخل الـ Fragment
    viewModel.uiState.observe(viewLifecycleOwner) { state ->
        binding.title.text = state.title
    }
}
03

إنشاء Fragment و ViewBinding

class HomeFragment : Fragment(R.layout.fragment_home) {

    private var _binding: FragmentHomeBinding? = null
    private val binding get() = _binding!!

    private val viewModel: HomeViewModel by viewModels()

    override fun onCreateView(
        inflater: LayoutInflater, container: ViewGroup?, savedInstanceState: Bundle?
    ): View {
        _binding = FragmentHomeBinding.inflate(inflater, container, false)
        return binding.root
    }

    override fun onViewCreated(view: View, savedInstanceState: Bundle?) {
        super.onViewCreated(view, savedInstanceState)
        binding.startButton.setOnClickListener {
            findNavController().navigate(R.id.action_home_to_details)
        }
    }

    override fun onDestroyView() {
        super.onDestroyView()
        _binding = null // تفادي تسرّب الذاكرة
    }
}
نصيحة

استخدم Fragment(R.layout.fragment_home) constructor مباشرة بدلًا من inflate يدوي في onCreateView عند عدم الحاجة لـ ViewBinding — أبسط وأقل كودًا.

04

التواصل بين Fragments

التواصل المباشر بين Fragment وآخر (مراجع مباشرة) يخلق ترابطًا ضارًا. الطرق الصحيحة الحديثة:

1. Shared ViewModel (بين Fragments في نفس الـ Activity)

class SharedViewModel : ViewModel() {
    private val _selectedItem = MutableLiveData<Item>()
    val selectedItem: LiveData<Item> = _selectedItem

    fun select(item: Item) { _selectedItem.value = item }
}

// في كل Fragment
private val shared: SharedViewModel by activityViewModels()

2. Fragment Result API (للاستجابة لمرة واحدة، عبر back stack)

// الشاشة المستقبِلة تسجّل مستمعًا
setFragmentResultListener("requestKey") { _, bundle ->
    val result = bundle.getString("resultKey")
}

// الشاشة المرسِلة (مثلًا BottomSheet) ترسل النتيجة قبل الرجوع
setFragmentResult("requestKey", bundleOf("resultKey" to "value"))
الطريقةالاستخدام المناسب
Shared ViewModelمشاركة حالة مستمرة بين شاشتين تعيشان في نفس نطاق الـ Activity/Nav Graph.
Fragment Result APIإرسال نتيجة واحدة عند الرجوع (مثل اختيار من BottomSheet أو Dialog).
Safe Argsتمرير بيانات أولية عند الانتقال إلى شاشة جديدة (forward navigation).
تجنّب

لا تستخدم (parentFragment as? Listener) أو استدعاء دوال مباشرة على Fragment آخر — هذا يكسر مبدأ الفصل بين المكونات ويصعّب إعادة الاستخدام والاختبار.

05

FragmentManager والـ Transactions اليدوية

قبل Navigation Component، كانت إدارة الشاشات تتم عبر FragmentManager مباشرة. فهمها ضروري لأنها الأساس الذي يعمل فوقه Navigation Component داخليًا، ولا تزال تُستخدم في حالات خاصة.

supportFragmentManager.commit {
    setReorderingAllowed(true)
    replace(R.id.container, DetailsFragment())
    addToBackStack("details")
}
  • add / replace: إضافة Fragment جديد أو استبدال الموجود في الـ container.
  • addToBackStack: يجعل العملية قابلة للتراجع عبر زر الرجوع.
  • setReorderingAllowed(true): يسمح بتحسين ترتيب تنفيذ العمليات المتزامنة (موصى به دائمًا).
متى تحتاجها رغم وجود Navigation؟

حالات خاصة مثل عرض Fragment داخل Fragment آخر بشكل ديناميكي بالكامل (child fragment manager)، أو مكتبات قديمة لا تدعم Navigation Component.

06

Navigation Component: الأساسيات

ثلاثة عناصر أساسية: NavGraph (خريطة الشاشات)، NavHostFragment (الحاوية)، NavController (المتحكم في التنقل).

Navigation Graph (XML)

<navigation xmlns:android="..."
    android:id="@+id/nav_graph"
    app:startDestination="@id/homeFragment">

    <fragment
        android:id="@+id/homeFragment"
        android:name=".ui.HomeFragment"
        android:label="Home">
        <action
            android:id="@+id/action_home_to_details"
            app:destination="@id/detailsFragment" />
    </fragment>

    <fragment
        android:id="@+id/detailsFragment"
        android:name=".ui.DetailsFragment"
        android:label="Details">
        <argument
            android:name="itemId"
            app:argType="long" />
    </fragment>
</navigation>

الاستضافة في الـ Activity

<androidx.fragment.app.FragmentContainerView
    android:id="@+id/nav_host"
    android:name="androidx.navigation.fragment.NavHostFragment"
    app:navGraph="@navigation/nav_graph"
    app:defaultNavHost="true"
    android:layout_width="match_parent"
    android:layout_height="match_parent" />

التنقل برمجيًا

findNavController().navigate(R.id.action_home_to_details)

// أو عبر الرجوع للخلف
findNavController().popBackStack()

// أو الرجوع لوجهة محددة مع مسح ما بعدها
findNavController().popBackStack(R.id.homeFragment, false)
أداة مهمة

استخدم Navigation Editor المرئي في Android Studio لبناء الـ graph ورؤية كل المسارات بصريًا بدل كتابة XML يدويًا بالكامل.

07

Safe Args — تمرير البيانات بأمان

Gradle plugin يولّد أصناف Kotlin آمنة النوع من تعريفات الـ argument في الـ Nav Graph، بدل التعامل مع Bundle خام.

plugins {
    id("androidx.navigation.safeargs.kotlin")
}
// الإرسال من HomeFragment
val action = HomeFragmentDirections.actionHomeToDetails(itemId = 42L)
findNavController().navigate(action)

// الاستقبال في DetailsFragment
private val args: DetailsFragmentArgs by navArgs()

override fun onViewCreated(view: View, savedInstanceState: Bundle?) {
    val id = args.itemId // Long، بدون أي cast يدوي
}
لماذا هذا أفضل من Bundle مباشرة؟

أي خطأ في اسم المفتاح أو النوع يُكتشف وقت الترجمة (compile-time) بدلًا من انهيار التطبيق وقت التشغيل بسبب ClassCastException أو مفتاح مفقود.

08

Nested Graphs و Bottom Navigation

التطبيقات الكبيرة تُقسَّم إلى Nested Graphs — كل قسم رئيسي (مثل تبويب في BottomNavigationView) له graph مستقل بـ back stack خاص به.

bottomNavigationView.setupWithNavController(navController)

// كل عنصر في BottomNavigationView.menu يجب أن يطابق
// id لأحد الـ nested graphs في nav_graph.xml
Multiple Back Stacks

منذ Navigation 2.4، يدعم setupWithNavController الاحتفاظ بـ back stack منفصل لكل تبويب تلقائيًا — عند التبديل والعودة لتبويب سابق، تجد حالته كما تركتها.

Include graph مستقل

<include app:graph="@navigation/profile_graph" />
09

Deep Links

تسمح بفتح وجهة محددة داخل التطبيق مباشرة من رابط خارجي (إشعار، متصفح، تطبيق آخر).

<fragment android:id="@+id/detailsFragment" ...>
    <deepLink app:uri="myapp://details/{itemId}" />
</fragment>
// إنشاء PendingIntent لإشعار يفتح الوجهة مباشرة
val pendingIntent = NavDeepLinkBuilder(context)
    .setGraph(R.navigation.nav_graph)
    .setDestination(R.id.detailsFragment)
    .setArguments(bundleOf("itemId" to 42L))
    .createPendingIntent()
تذكّر

يجب تسجيل الـ <intent-filter> المناسب في AndroidManifest أيضًا (أو استخدام <nav-graph> tag) حتى يعرف النظام أن التطبيق يستجيب لهذا الرابط.

10

الانتقالات و Shared Elements

val extras = FragmentNavigatorExtras(
    imageView to "transitionName_image"
)
findNavController().navigate(
    HomeFragmentDirections.actionHomeToDetails(itemId),
    extras
)

عنصر الـ View في الوجهة الهدف يجب أن يحمل نفس android:transitionName ليعمل الانتقال المشترك (Shared Element Transition) بسلاسة.

Custom Animations عبر NavOptions

val navOptions = navOptions {
    anim {
        enter = R.anim.slide_in_right
        exit = R.anim.slide_out_left
        popEnter = R.anim.slide_in_left
        popExit = R.anim.slide_out_right
    }
}
findNavController().navigate(R.id.action_home_to_details, null, navOptions)
11

DialogFragment مع Navigation

Navigation Component يدعم DialogFragment كوجهة مباشرة داخل الـ graph — يظهر كطبقة فوق الوجهة الحالية دون استبدالها.

<dialog
    android:id="@+id/confirmDeleteDialog"
    android:name=".ui.ConfirmDeleteDialogFragment" />
findNavController().navigate(R.id.confirmDeleteDialog)

// الـ DialogFragment يرسل النتيجة قبل الإغلاق
setFragmentResult("delete_confirmed", bundleOf())
dismiss()
12

أخطاء شائعة وأفضل الممارسات

خطأ 01

عدم تحرير الـ ViewBinding في onDestroyView — يسبب تسرّب ذاكرة لأن الـ View يبقى محتجزًا حتى بعد تدميره.

خطأ 02

استخدام this بدل viewLifecycleOwner عند مراقبة LiveData/Flow داخل Fragment — قد يسبب استدعاءات على View مُدمَّر بالفعل.

خطأ 03

التنقل المتكرر بنقرة سريعة مزدوجة (double navigation) يضيف نفس الوجهة مرتين للـ back stack — استخدم debounce أو launchSingleTop.

خطأ 04

تمرير كائنات كبيرة أو غير قابلة للتسلسل عبر Safe Args بدل تمرير معرّف (ID) فقط وجلب البيانات من مصدر واحد للحقيقة (Repository/ViewModel).

خطأ 05

نسيان setReorderingAllowed(true) عند استخدام FragmentManager يدويًا مع عمليات متزامنة، ما قد يسبب حالات غير متوقعة في ترتيب التنفيذ.

قاعدة ذهبية

اجعل كل Fragment "غبيًا" قدر الإمكان — لا منطق أعمال بداخله، فقط عرض حالة قادمة من ViewModel والاستجابة لأحداث المستخدم. هذا يجعل الاختبار والصيانة أسهل بكثير.
