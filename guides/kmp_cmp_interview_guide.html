01 src/commonMain/

أساسيات Kotlin Multiplatform

المفهوم الأساسي، لماذا KMP، والفرق عن الحلول التانية

5 أسئلة

KMP مش framework بيرسم UI، هو بالأساس امتداد لـ compiler الـ Kotlin بيسمحلك تكتب الـ business logic (زي networking، caching، validation، domain models) مرة واحدة في source set اسمه commonMain، وبعدين الكود ده يترجم (compile) لكل platform بشكل native: JVM bytecode للـ Android، LLVM/native binary للـ iOS عن طريق Kotlin/Native، وJS/Wasm للويب. الفرق الجوهري عن Flutter إنك مش بتشغل VM أو rendering engine إضافي (زي Skia engine اللي بيرسم كل حاجة من الصفر في Flutter) فوق الـ native platform؛ الـ UI في KMP التقليدي بيفضل native 100% (SwiftUI على iOS و Jetpack Compose على Android)، يعني تجربة المستخدم والأداء والـ accessibility بيبقوا native حقيقي. React Native بيستخدم Bridge (أو JSI في الإصدارات الجديدة) للتواصل بين JS والـ native، أما KMP فمفيش bridge أصلاً لأن الكود بيتحول native فعلي وقت الـ compilation، فمفيش overhead في الـ runtime marshalling.

KMP هي الـ umbrella الأشمل: مشاركة أي كود Kotlin (منطق، data layer، networking...) بين المنصات مع سيبان الـ UI native لكل platform. CMP هي مكتبة UI declarative مبنية فوق نفس الـ Compose compiler و runtime اللي بيستخدمه Jetpack Compose، لكن بتوسّع الرسم (rendering) عن طريق Skia بحيث تشتغل على iOS وDesktop (JVM) وWeb (Wasm/JS) مش بس Android. يعني CMP بيسمحلك كمان تشارك الـ UI layer نفسه مش بس الـ logic. الاختيار العملي: لو عايز أقصى درجة native feel وaccessibility مطابقة 100% للمنصة، تسيب الـ UI native وتستخدم KMP للـ logic بس (زي إستراتيجية JetBrains نفسها في IntelliJ/Android Studio قبل ما يتحولوا لـ Compose في بعض الأجزاء). لو عايز سرعة تطوير وconsistency بصرية بين المنصات وuser base متقارب، CMP هي الخيار.

الـ Source Set هو مجلد كود مربوط بـ target معين أو مجموعة targets بيتشارك فيهم نفس الكود. الأساسي هو commonMain اللي فيه الكود المشترك، ومقابله commonTest للاختبارات المشتركة. تحت كل target فيه source set مخصص زي androidMain وiosMain وdesktopMain وwasmJsMain، وده اللي بتحط فيه الـ platform-specific implementations. لو عندك مجموعة targets قريبة من بعض زي iosX64 وiosArm64 وiosSimulatorArm64، بتقدر تعمل intermediate source set زي iosMain يبقى parent ليهم عشان تتفادى تكرار كود الـ actual الخاص بـ iOS في كل target لوحده. الـ hierarchy ده بيتحدد في build.gradle.kts عن طريق kotlin { sourceSets { ... } } وبيدعم الـ Default Hierarchy Template اللي JetBrains وفروه عشان يبسط الإعداد اليدوي.

أول تحدي هو فصل الـ business logic عن أي حاجة Android-specific زي Context أو Android SDK APIs، وده بيتطلب إعادة هيكلة الـ layers لو الكود مكتوب أصلاً بطريقة متشابكة. تاني حاجة هي الـ dependencies: مكتبات كتير في عالم Android (زي Retrofit أو Room بشكلها التقليدي) مش KMP-ready، فمحتاج تستبدلها بـ multiplatform alternatives زي Ktor بدل Retrofit وSQLDelight أو Room KMP (بقت متاحة تجريبياً) بدل Room التقليدي. كمان فيه تعقيد في الـ build configuration، خصوصاً لو المشروع بيستخدم Gradle plugins قديمة أو build logic معقدة. وأخيراً، لو الهدف يوصل لـ iOS، لازم فريق يكون عنده خبرة Swift/Xcode كافية للـ integration، وده تحدي تنظيمي مش تقني بس.

بقول إن الفكرة زي ما تكتب وصفة أكل بلغة عالمية، وكل مطبخ (Android أو iOS) عنده أدواته الخاصة بيحضر بيها نفس الوصفة بطريقته الأمثل - النتيجة طبق يليق بذوق أهل البلد ده، مش نسخة معلبة واحدة اتوزعت على الكل. الفايدة التجارية إن الفريق بيكتب الـ business rules والـ validation والـ networking مرة واحدة، فبيقلل الأخطاء الناتجة عن اختلاف التنفيذ بين الفريقين (Android bug مش موجود في iOS والعكس)، وبيسرّع وقت الوصول للسوق، مع الحفاظ على إحساس الأداء والتصميم الأصلي لكل منصة.

02 src/buildSystem/

Gradle وبنية المشروع

إعداد المشروع، الـ targets، والـ Kotlin/Native toolchain

5 أسئلة

بتستخدم الـ kotlin block وجواه بتعرّف كل target عايز تدعمه، مثلاً androidTarget() لدعم Android، وiosX64() / iosArm64() / iosSimulatorArm64() لدعم أجهزة وsimulators iOS المختلفة (أو ببساطة iosMain hierarchy)، وjvm('desktop') لدعم Desktop، وwasmJs { browser() } لدعم الويب عبر WebAssembly. كل target بيتربط تلقائياً بـ source set مخصوص ليه. الميزة إن نفس الملف بيتحكم في كل حاجة: dependencies، compiler options، وحتى framework configuration للـ iOS زي اسم الـ XCFramework الناتج وهل هو static ولا dynamic.

kotlin {
    androidTarget()
    jvm("desktop")
    listOf(iosX64(), iosArm64(), iosSimulatorArm64()).forEach {
        it.binaries.framework {
            baseName = "shared"
            isStatic = true
        }
    }
}

expect/actual آلية على مستوى الـ compiler: بتعرّف 'توقيع' (signature) في commonMain بكلمة expect، وكل platform بيوفر التنفيذ الفعلي بكلمة actual، والـ compiler هو اللي بيربط بينهم وقت البناء لكل target، يعني مفيش أي runtime overhead والربط بيحصل statically. أما الـ DI (زي Koin) فهو حل runtime: بتعرّف interface عادي في commonMain، وكل platform module بيسجل الـ implementation بتاعه في الـ container، والـ resolution بيحصل وقت التشغيل. عملياً، expect/actual أنسب للحاجات البسيطة والمباشرة زي الحصول على اسم المنصة أو platform-specific utility function، أما الـ DI أنسب للـ dependencies المعقدة اللي محتاجة lifecycle management أو lazy initialization أو scoping.

قبل Kotlin 1.7.20 كان فيه الـ 'strict/old memory model' اللي كان بيفرض قيود صارمة على مشاركة الـ objects بين الـ threads؛ أي object اتعمله freeze() كان بيبقى immutable تماماً وأي محاولة تعديل عليه من thread تاني كانت بترمي InvalidMutabilityException، وده كان بيخلي التعامل مع الـ coroutines والـ concurrency معقد جداً وغير بديهي بالنسبة لمطور جاي من عالم JVM. الـ 'New Memory Model' (بقى default من Kotlin 1.9.20) قرّب السلوك من الـ JVM: مفيش freezing إجباري، وبتقدر تشارك الـ objects بين threads بحرية أكبر مع الاعتماد على نفس آليات الـ synchronization المعتادة، وده خلى مكتبات زي kotlinx.coroutines تشتغل على iOS بسلوك متوقع أقرب لسلوكها على Android.

لما بتبني مكتبة KMP وتصدرها كـ framework لاستخدامها في مشروع iOS، عندك طريقتين للتوزيع. الأولى CocoaPods: بتستخدم الـ Kotlin CocoaPods Gradle plugin اللي بيولّد podspec تلقائي، وده مناسب لو الفريق أصلاً شغال بـ CocoaPods كـ dependency manager. الثانية SPM، اللي بقى الاتجاه الرسمي الحديث من Apple وبقى JetBrains بيدعمه بشكل رسمي عن طريق بناء XCFramework وربطه كـ binary target في Package.swift. عملياً، SPM بقى الخيار المفضل في المشاريع الجديدة لأنه مدمج في Xcode من غير أدوات خارجية، وأسرع في الـ resolution، وأقرب لتوجه Apple المستقبلي، لكن الفرق التقنية القديمة أو اللي عندها dependencies تانية بـ CocoaPods ممكن تفضل مستمرة عليه لتفادي الخلط بين نظامين.

الـ commonizer أداة بتشتغل خلف الكواليس وقت الـ build عشان توحّد الـ platform libraries (زي POSIX أو Foundation APIs بتاعة iOS) اللي مختلفة شكلياً بين iosX64 وiosArm64 وiosSimulatorArm64 رغم إنها بتمثل نفس الـ API منطقياً. بدل ما تكتب expect/actual يدوي لكل حاجة، الـ commonizer بيولّد 'commonized' API موحدة تقدر تستخدمها مباشرة من جوه intermediate source set زي iosMain، وده اللي بيخلي كتابة كود مشترك بين أجهزة iOS المختلفة أسهل بكتير من غير ما تكرر نفس الـ actual تلاتة مرات.

03 src/expectActual/

آلية expect / actual

أساس الربط بين الكود المشترك والكود الخاص بكل منصة

3 أسئلة

بتعرّف في commonMain 'توقيع' من غير تنفيذ باستخدام expect، وده ممكن يكون function أو class أو property أو حتى annotation. وبعدين في كل platform source set، لازم توفر actual implementation مطابق تماماً للتوقيع (نفس الاسم، نفس الـ parameters، نفس النوع الراجع)، وإلا الـ compiler هيرفض البناء. الـ compiler بيتأكد وقت البناء إن كل expect ليه actual مقابل في كل target مفعّل، فمفيش احتمال تنسى تنفيذ منصة وتكتشف الغلط في الـ runtime زي ما ممكن يحصل مع الـ reflection-based solutions.

// commonMain
expect fun getPlatformName(): String

expect class SecureStorage {
    fun save(key: String, value: String)
    fun read(key: String): String?
}

// androidMain
actual fun getPlatformName(): String = "Android"

actual class SecureStorage(private val context: Context) {
    private val prefs = EncryptedSharedPreferences.create(...)
    actual fun save(key: String, value: String) { prefs.edit().putString(key, value).apply() }
    actual fun read(key: String): String? = prefs.getString(key, null)
}

// iosMain
actual class SecureStorage {
    actual fun save(key: String, value: String) {
        KeychainWrapper.set(value, forKey = key)
    }
    actual fun read(key: String): String? = KeychainWrapper.stringForKey(key)
}

لأن expect/actual بتربط الكود المشترك بشكل مباشر (tight coupling) بكل target وقت الـ compile time، وده بيصعّب اختبار الكود بمعزل عن المنصة، وبيصعّب إضافة target جديد لاحقاً (لازم تضيف actual جديد في كل مكان مستخدم فيه). البديل المفضّل هو تعريف interface عادي في commonMain (زي PlatformContext أو Clock) وحقن الـ implementation بتاعه بـ constructor injection أو عن طريق DI framework زي Koin. الطريقة دي أسهل للـ testing (تقدر تعمل fake implementation بسهولة)، وأنضف من ناحية الـ architecture لأنها بتفصل الـ 'العقد' (contract) عن التنفيذ زي أي dependency inversion عادي، وبتسيب expect/actual للحالات البسيطة جداً زي قراءة اسم المنصة أو الوصول لـ low-level platform API مالوش abstraction مناسب.

أول حاجة، الـ expect declarations لازم توفر default values في الـ common side بس، مش في الـ actual، عشان يفضل التوقيع موحد. تاني حاجة، لغاية إصدارات قريبة، expect/actual functions ماكانوش بيدعموا default parameter values بشكل كامل في كل السيناريوهات، وكان فيه قيود على استخدام inline functions مع reified type parameters عبر expect/actual. كمان، الـ expect classes ماكانتش بتقدر implement interface بشكل مباشر بسهولة في كل الحالات القديمة (اتحسنت الميزة دي لاحقاً بمسمى 'expect/actual classes' اللي كانت experimental فترة طويلة). وأخيراً، كتر استخدامها بيخلي الـ commonMain مليان 'توقيعات فاضية' يصعب فهم سلوكها الفعلي من غير ما تفتح كل target لوحده، وده بيأثر على قابلية القراءة (readability) للكود.

04 src/concurrency/

Coroutines والـ Concurrency

الفروق بين JVM وNative، والـ threading model

4 أسئلة

على Android (JVM)، الـ coroutines بتشتغل فوق thread pool حقيقي، والـ Dispatchers.Default وDispatchers.IO بيستخدموا threads فعلية متوازية استفادة من الـ multi-core. على iOS، الوضع كان مختلف تاريخياً بسبب الـ old memory model، لكن مع الـ new memory model، الـ coroutines بقت بتقدر تستخدم multiple native threads فعلاً بنفس الفلسفة الموجودة على JVM. الفرق العملي الأهم اللي لازم تعرفه إن Dispatchers.Main على iOS لازم يشتغل جوه الـ main run loop زي أي UI framework تاني، وإن أي تعديل على الـ UI لازم يرجع للـ main thread زي بالظبط ما بيحصل في Compose على Android.

في الـ old memory model، عشان تشارك object بين threads على Kotlin/Native كان لازم تستدعي freeze() عليه، وده كان بيحوّله لـ immutable بشكل نهائي، وأي محاولة تعديل بعد كده كانت بترمي exception وقت الـ runtime، وده كان بيسبب bugs صعبة الاكتشاف لأنها بتظهر بس وقت التنفيذ الفعلي مش وقت الـ compile. مع الـ new memory model اللي بقى default، مفيش حاجة اسمها freezing إجباري خالص، ومشاركة الـ state بين threads بقت بتعتمد على نفس أدوات التزامن العادية (زي Mutex أو Atomic references أو الاعتماد على immutability الطبيعي للـ data classes)، فمفهوم freeze() بقى قديم (deprecated) دلوقتي وموجود بس للتوافق مع كود قديم.

المشكلة إن Swift مالوش فهم طبيعي لـ Kotlin's StateFlow، فمحتاج طبقة تحويل. الحل الشائع هو استخدام مكتبة زي KMP-NativeCoroutines أو SKIE اللي بتولّد wrappers تلقائية تحول الـ Flow/StateFlow لـ async sequences أو Combine publishers قابلة للاستخدام مباشرة من Swift بشكل idiomatic. البديل اليدوي (قبل ظهور المكتبات دي) كان بتعمل function زي fun observe(scope: CoroutineScope, onEach: (T) -> Unit): Closeable بتستخدم .onEach { }.launchIn(scope) وترجع كائن تقدر تلغي بيه الـ subscription من الـ Swift side. النقطة المهمة في المقابلة إنك تفهم إن الـ StateFlow نفسه Kotlin-native ومحتاج جسر (bridge) صريح للتعامل معاه من عالم Swift.

// SKIE أو KMPNativeCoroutines بتولد تلقائيًا استخدام زي ده في Swift:
// for await state in viewModel.uiState {
//     self.state = state
// }

على JVM/Android، Dispatchers.Default مخصص للـ CPU-intensive work وبيستخدم thread pool بعدد يساوي عدد الـ CPU cores، بينما Dispatchers.IO مخصص للـ blocking I/O operations وعنده thread pool أكبر بكتير (limit افتراضي 64 على الأقل) عشان يقدر يستوعب عدد كبير من الـ blocking calls المتزامنة من غير ما يستنزف الـ cores. على Kotlin/Native، الاتنين كانوا بيستخدموا نفس الآلية الأساسية لإدارة الـ worker threads بس بفلسفة مختلفة شوية لأن مفيش JVM thread pool تحتهم، والـ runtime بيدير الـ threads بنفسه. عملياً في الكود المشترك، أهم حاجة إنك تستخدم Dispatchers.Default للحسابات التقيلة وDispatchers.IO (أو حتى custom dispatcher لو محتاج تحكم أدق) للعمليات اللي فيها انتظار زي الشبكة أو قاعدة البيانات، بغض النظر عن الاختلافات الداخلية بين المنصات.

05 src/cmpUi/

Compose Multiplatform (UI)

الرسم عبر Skia، الموارد، والتنقل بين المنصات

5 أسئلة

على Android، Compose Multiplatform بيستخدم نفس Jetpack Compose الأصلي اللي بيرسم فوق الـ Android Canvas/RenderNode العادي، يعني مفيش أي فرق عن مشروع Compose تقليدي. على المنصات التانية (iOS، Desktop، وWeb عبر Wasm)، الرسم بيتم عن طريق مكتبة Skia (نفس الـ rendering engine اللي Flutter وChrome بيستخدموه) اللي بترسم كل الـ pixels بنفسها من غير الاعتماد على UIKit أو AppKit widgets، وبعدين بتوصل الناتج (buffer) لـ native view واحدة بسيطة (زي UIView على iOS) بتستضيف الرسمة دي. ده معناه إن الـ layout والـ styling بيبقوا متطابقين تماماً بكسل بكسل بين المنصات، بعكس الـ UI الـ native الصرف اللي بيختلف شكله حسب فلسفة كل منصة، وده trade-off مهم لازم تعرفه: consistency بصرية مقابل native look-and-feel.

JetBrains وفروا مكتبة رسمية اسمها compose.components.resources بتسمحلك تحط الملفات في composeResources/ (زي drawable/ وvalues/ وfont/) في commonMain، وبعدين بتولّد accessors آمنة النوع (type-safe) تلقائياً زي Res.drawable.logo أو Res.string.app_name تقدر تستخدمها مباشرة جوه أي @Composable في أي platform، والمكتبة بتتكفل بتحميلها بالطريقة المناسبة لكل target (asset loading على Android، bundle resource على iOS، إلخ) من غير ما تكتب expect/actual يدوي. قبل ظهور المكتبة دي كانت الحلول بديلة زي moko-resources، لكن الحل الرسمي بقى الخيار الافتراضي في المشاريع الجديدة.

// commonMain/composeResources/drawable/logo.xml
// وبعدين في أي composable:
Image(
    painter = painterResource(Res.drawable.logo),
    contentDescription = stringResource(Res.string.logo_description)
)

فيه خيارين رئيسيين: الأول استخدام Jetpack Navigation Compose نفسها اللي بقت multiplatform-ready من الإصدارات الحديثة، وبتديك نفس الـ NavHost/NavController اللي معتاد عليهم في Android لكن شغالة على كل المنصات. الخيار التاني هو مكتبات navigation مبنية خصيصاً للـ multiplatform زي Voyager أو Decompose، اللي بتوفر مميزات إضافية زي better state preservation عبر configuration changes، ودعم أوضح لـ Compose Multiplatform-specific concerns زي التعامل مع الـ back gesture على iOS (اللي مختلف تماماً عن نظام الـ back button في Android). الاختيار العملي بيعتمد على مدى تعقيد التطبيق: لو التطبيق بسيط، Jetpack Navigation الرسمية كافية، لو عندك متطلبات معقدة في الـ state management أو تحتاج تحكم أدق في الـ lifecycle، مكتبة زي Decompose بتوفر مرونة أكبر لأنها مبنية على مبدأ component-based architecture مش screen-based.

لازم تفهم إن CMP بيديك نفس الـ pixels على كل منصة، لكن مش بيديك تلقائياً نفس الـ interaction patterns، فده مسؤوليتك كمطور. على Android، النظام بيعطيك predictive back gesture callback عن طريق OnBackPressedCallback، وممكن تستخدمه مع BackHandler composable. على iOS، المفهوم مختلف: مفيش نظام back button، وبدل كده المستخدم بيعمل swipe من حافة الشاشة، ولو عايز تحاكي السلوك ده جوه CMP لازم تتعامل مع الـ UIKit gesture recognizers من الـ native layer وتوصل الحدث للـ Compose layer عن طريق interop. الممارسة الأفضل عملياً إنك تستخدم مكتبة navigation بتجرد (abstracts) الفرق ده عنك زي Decompose بدل ما تعيد اختراعه يدوياً، لكن المهم في المقابلة إنك توضح إنك واعي إن 'نفس الكود' مش معناه 'نفس تجربة المستخدم' تلقائياً.

لو محتاج تستخدم native iOS component معندوش مقابل جاهز في CMP (زي MapKit view أو camera picker أصلي، أو حتى SwiftUI view جاهزة من الفريق)، بتقدر تستضيف الـ Compose UI بتاعتك جوه UIViewController من خلال ComposeUIViewController، وده هو نقطة الدخول الأساسية اللي مشروع iOS بيستخدمها. للاتجاه المعاكس (استضافة native view جوه شجرة Compose)، فيه UIKitView composable بيسمحلك تحط أي UIView جواه، مع التحكم في كيفية تحديثه (update block) وربط الـ lifecycle بتاعه بشكل صحيح. المهم تفهم إن ده hybrid approach: مش كل التطبيق لازم يبقى CMP بالكامل، وده أحد أهم نقاط قوة الحل إن التبني ممكن يكون تدريجي (incremental adoption).

Networking و Data Layer

Ktor، SQLDelight، kotlinx.serialization

5 أسئلة

Retrofit مبني أساساً على JVM annotation processing وOkHttp، وده بيخليه محصور في targets اللي عندها JVM (زي Android وDesktop)، ومش شغال على iOS أو Wasm. Ktor Client، بالعكس، مبني بفلسفة multiplatform من الأساس، وعنده engine مختلف لكل platform: OkHttp أو CIO على Android/JVM، وDarwin (اللي بيستخدم NSURLSession تحت السطح) على iOS، وJs engine للويب. الـ API نفسه (HttpClient, request builders, plugins زي ContentNegotiation وLogging وAuth) موحد وبيتكتب مرة واحدة في commonMain، والـ engine بس هو اللي بيتغير حسب الـ platform عن طريق dependency injection بسيطة في الـ Gradle configuration.

// commonMain
val client = HttpClient {
    install(ContentNegotiation) { json() }
}

// androidMain build.gradle.kts
implementation("io.ktor:ktor-client-okhttp:$ktorVersion")

// iosMain build.gradle.kts
implementation("io.ktor:ktor-client-darwin:$ktorVersion")

SQLDelight بتاخد نهج مختلف عن Room: بتكتب استعلامات SQL خام في ملفات .sq، والـ Gradle plugin بتاعها بيقرا الملفات دي وقت الـ build ويولّد Kotlin classes وfunctions آمنة النوع (type-safe) تمثل كل query، بما فيها الـ result types. المميز إن الـ driver (طبقة التنفيذ الفعلية اللي بتتكلم مع SQLite) قابل للتبديل حسب المنصة: AndroidSqliteDriver على Android بيستخدم SQLite المدمج في النظام، NativeSqliteDriver على iOS بيستخدم SQLite.framework المدمج في iOS، وJdbcSqliteDriver على Desktop. زي Ktor، الكود اللي بتكتبه وبتستدعيه (الـ generated Queries object) موحد 100% في commonMain، والاختلاف بيقتصر بس على تهيئة الـ driver في كل platform module.

Gson وMoshi بيعتمدوا على الـ Java reflection API عشان يقرأوا الـ classes وقت الـ runtime ويحولوها لـ JSON، والـ reflection ده مش متاح أصلاً على Kotlin/Native أو Wasm، فالمكتبتين دول مش هيشتغلوا برة الـ JVM. kotlinx.serialization بتحل المشكلة دي بطريقة مختلفة تماماً: بدل الـ reflection، فيه compiler plugin (kotlinx-serialization-plugin) بيشتغل وقت الـ compile time وبيولّد كود serialization فعلي (serializer) لكل data class معمول عليه @Serializable، فمفيش أي اعتماد على reflection في الـ runtime، وده بيخليها تشتغل بنفس الكفاءة على أي target مدعوم من Kotlin، بالإضافة لكونها أسرع من الحلول اللي بتعتمد على reflection حتى على JVM نفسها.

@Serializable
data class UserDto(
    val id: Int,
    val name: String,
    @SerialName("email_address") val email: String? = null
)

val json = Json { ignoreUnknownKeys = true }
val user = json.decodeFromString<UserDto>(jsonString)

الباترن الشائع (زي ما هو معروف في Android من مكتبة Sunflower/Now-in-Android) بيتطبق بنفس الفلسفة في KMP: الـ repository بيرجع دايماً Flow من الـ SQLDelight database كـ single source of truth للـ UI layer، وبيعمل sync مع الـ remote API (عن طريق Ktor) في الخلفية، وبيكتب أي نتيجة جديدة في نفس الـ database بدل ما يرجعها مباشرة للـ UI. الفايدة إن الـ UI بيفضل reactive وconsistent حتى لو مفيش إنترنت، لأنه بيقرا من DB مش من الـ network مباشرة، وSQLDelight بيديك .asFlow().mapToList() جاهزة عشان تحول أي query لـ Flow<List<T>> تلقائياً، وده بيتكامل بشكل طبيعي جداً مع StateFlow في الـ ViewModel المشترك.

SharedPreferences هي Android API بحتة مش متاحة على iOS، فلو محتاج تخزين key-value بسيط (زي flags أو user preferences أو tokens) في الكود المشترك، بتستخدم مكتبة زي multiplatform-settings (من Touchlab) اللي بتوفر واجهة موحدة (Settings interface) في commonMain، وبتنفذها فعلياً باستخدام SharedPreferences على Android وNSUserDefaults على iOS. المكتبة كمان بتوفر إصدار Coroutines-friendly (ObservableSettings) بيسمحلك تعمل .listen() أو تحوّل قيمة لـ Flow، وده مفيد جداً لو محتاج الـ UI يعمل react تلقائياً لتغيير setting معين.

07 src/architecture/

Architecture و DI

MVVM/MVI multiplatform، Koin، وClean Architecture

4 أسئلة

المبدأ الأساسي نفسه: طبقات Presentation وDomain وData، مع اعتماد الطبقات الخارجية على الداخلية مش العكس (Dependency Rule). الفرق الجوهري إن في KMP، الـ Domain layer بالكامل (use cases، entities، repository interfaces) والـ Data layer بالكامل (repository implementations، Ktor، SQLDelight) بيعيشوا في commonMain، يعني بيتشاركوا 100% بين Android وiOS. الـ Presentation layer هو نقطة الانقسام: الـ ViewModel (لو بتستخدم مكتبة زي Voyager أو حتى androidx.lifecycle.ViewModel اللي بقت multiplatform) ممكن كمان يتشارك في commonMain، لكن شجرة الـ UI الفعلية بتفترق: Jetpack Compose على Android وSwiftUI (أو CMP لو مستخدمها) على iOS. النقطة اللي بتتسأل عنها كتير في المقابلات: 'فين بتوقف مشاركة الكود؟' والإجابة الناضجة إنها بتوصل غالباً لحد الـ ViewModel/State، وبعدها الـ rendering بيبقى platform-specific إلا لو مستخدمين CMP.

Dagger وHilt بيعتمدوا بشكل جوهري على الـ Java Annotation Processing Tool (APT) أو KAPT/KSP بطريقة مرتبطة بـ JVM tooling، ومش مصممين أصلاً للعمل على Kotlin/Native targets، فمحاولة استخدامهم في commonMain مليانة عوائق تقنية حقيقية. Koin، بالعكس، حل DI بسيط بيعتمد على Kotlin DSL عادي وservice locator pattern بيشتغل وقت الـ runtime من غير أي code generation أو annotation processing، فهو multiplatform بطبيعته من الأول. التريد أوف (trade-off) اللي لازم تعرفه: Koin بيفقد بعض الـ compile-time safety اللي Dagger بيوفرها (يعني ممكن تكتشف dependency ناقصة وقت الـ runtime مش وقت الـ compile)، لكن المميزات دي بتتعوض بسهولة الإعداد والسرعة في التطوير. فيه كمان مكتبة Kotlin-Inject بتحاول توفر compile-time safety زي Dagger لكن بفلسفة KSP متوافقة مع multiplatform، وده اتجاه بيكبر تدريجياً.

// commonMain
val commonModule = module {
    single { HttpClient { install(ContentNegotiation) { json() } } }
    single<UserRepository> { UserRepositoryImpl(get(), get()) }
    factory { GetUserUseCase(get()) }
}

// androidMain
val androidModule = module {
    single { DatabaseDriverFactory(androidContext()) }
}

من Kotlin/Jetpack بقى فيه androidx.lifecycle:lifecycle-viewmodel متاحة كـ multiplatform artifact، فبتقدر تكتب class بيرث من ViewModel() في commonMain نفسه، وتستخدم viewModelScope اللي متاح كمان multiplatform (مبني فوق نفس المفهوم بتاع Coroutines المرتبط بـ lifecycle). التحدي الحقيقي مش في تعريف الـ ViewModel نفسه لكن في التكامل مع lifecycle كل منصة: على Android، النظام بيدير الـ ViewModel tied لـ Activity/Fragment scope تلقائياً عن طريق ViewModelStoreOwner. على iOS مفيش مفهوم مطابق، فمحتاج تدير الـ instance creation والـ clearing يدوياً (أو عن طريق مكتبة زي Voyager/Moko-MVVM اللي بتوفر لك helper)، وده معناه إنك المسؤول عن استدعاء onCleared() في الوقت المناسب (زي وقت اختفاء الـ SwiftUI view) عشان تتجنب memory leaks أو استمرار الـ coroutines شغالة من غير داعي.

MVVM بيعتمد على تعدد الـ states والـ events المنفصلة (زي عدة StateFlow/LiveData لكل جزء من الشاشة)، وده مريح ومباشر لكن ممكن يبقى صعب التتبع لما الشاشة تكبر وتتعقد. MVI بيفرض state واحد غير قابل للتغيير (immutable single state) بيتمثل غالباً في sealed class أو data class شامل، وكل تفاعل من المستخدم بيتحول لـ 'Intent' واضح بيتعالج بشكل مركزي وبينتج state جديد كامل، وده بيخلي الـ debugging والـ testing أسهل جداً لأن كل تغيير قابل للتتبع (predictable state transitions) وده مهم جداً في بيئة multiplatform لأنك عايز الـ Presentation logic يبقى متوقع بنفس الشكل تماماً سواء استهلكه Jetpack Compose أو SwiftUI. عملياً، فرق كتير بيميلوا لـ MVI في مشاريع KMP بالذات لأن الـ single state object بيبقى أسهل تحويله (mapping) وقراءته من طرف Swift عن طريق KMP-NativeCoroutines أو SKIE.

08 src/iosInterop/

Kotlin/Native و iOS Interop

Swift interop، إدارة الذاكرة، وأداء الـ Native binary

5 أسئلة

Kotlin/Native عنده الـ garbage collector بتاعه الخاص (tracing GC، بقى بيستخدم default الـ Concurrent Mark and Sweep من الإصدارات الحديثة) بيدير objects اللي اتعملها من كود Kotlin، بينما Objective-C/Swift بيستخدموا Automatic Reference Counting (ARC) لإدارة الذاكرة بتاعتهم. لما الكائنات دي تتفاعل مع بعض عبر الـ interop layer، Kotlin/Native بيولّد Objective-C headers للكلاسات بتاعته، وأي Kotlin object بيتم تمريره لـ Swift/Obj-C بيتغلف في ref-counted wrapper بيتكامل مع ARC بحيث لو الـ Swift side مسكه بـ strong reference، الـ Kotlin GC مش هيجمعه (collect) لغاية ما الـ ARC refcount يوصل للصفر. التحدي الحقيقي بيظهر في الـ retain cycles: لو عندك Kotlin object ماسك closure أو delegate من Swift والعكس صحيح، ممكن يحصل memory leak حقيقي محتاج انتباه خاص، وده سبب شائع لأسئلة الـ debugging في المقابلات.

من ناحية تنفيذ الكود نفسه، Kotlin/Native بيتحول لـ LLVM IR وبعدين لـ native machine code زي بالظبط Swift، يعني مفيش interpreter أو VM overhead في تنفيذ منطق الأعمال نفسه، والأداء الخام (raw execution) قريب جداً من Swift. الفرق الحقيقي بيظهر في نقطتين: الأولى startup time، لأن الـ Kotlin/Native runtime (بما فيه الـ GC والـ Kotlin standard library) بيضيف حجم إضافي للـ binary وبيحتاج تهيئة (initialization) بسيطة وقت إطلاق التطبيق. التانية هي الـ interop overhead عند كل استدعاء بيعدي الحدود (boundary) بين Kotlin وSwift، لأن فيه تكلفة تحويل أنواع البيانات (type marshalling) وإدارة الـ reference counting المتبادل، فلو عندك كود بيعمل استدعاءات كتيرة جداً ومتكررة عبر الـ boundary دي (زي حلقة (loop) بتستدعي دالة Kotlin آلاف المرات)، ده ممكن يبقى أبطأ من نفس الكود لو كان Swift خالص، فالممارسة الأفضل تقليل عدد الـ boundary crossings وتصميم الـ API بحيث تمرر بيانات مجمعة (batched) بدل استدعاءات صغيرة متكررة.

Kotlin/Native بيولّد debug symbols (dSYM) لو الـ framework اتبنى بـ debug configuration، وده بيسمح لـ Xcode's LLDB debugger إنه يقف على breakpoints جوه ملفات .kt نفسها زي أي ملف Swift عادي، تقدر تتفحص فيها الـ variables وتعمل step-through للكود. المهم عملياً إنك تتأكد إن الـ Gradle build بتاع الـ framework شغال في Debug mode (مش Release) عشان الـ symbols تتولد صح، وإن مسار الملفات المصدرية (source paths) متاح للـ Xcode. في حالة تعقيدات أكتر، أدوات زي Kotlin/Native Memory Tool بتساعد في تتبع الـ memory leaks، وLLDB نفسه بيقدر يعرض قيم الـ Kotlin objects بشكل مقروء لو الـ debug info متظبطة صح.

الـ Static Framework (isStatic = true) بيتضمن الكود مباشرة جوه الـ binary بتاع تطبيق iOS النهائي وقت الـ linking، وده الخيار الموصى بيه من JetBrains حالياً لمعظم الحالات لأنه بيقلل مشاكل الـ App Store validation وبيبسط عملية الـ distribution، خصوصاً مع SPM. الـ Dynamic Framework بيفضل ملف منفصل بيتحمل وقت الـ runtime، وكان أنسب لو محتاج تشارك نفس الـ framework بين أكتر من target جوه نفس مشروع iOS (زي main app وextension) من غير ما تكرر الكود في كل واحد، لكنه بيزود وقت الإطلاق (launch time) شوية بسبب dynamic linking، وبيحتاج إعداد أدق في مشروع Xcode. القرار الشائع في الشركات دلوقتي: static افتراضياً إلا لو فيه حاجة صريحة تستلزم dynamic.

قبل كده، أي Kotlin API بيتصدّر لـ iOS كان لازم يعدي على 'Objective-C bridge' الأول، يعني حتى لو الفريق كله Swift، الـ types والـ generics والـ sealed classes بتاعة Kotlin كانت بتتحول لصيغة Objective-C-compatible أولاً وده كان بيفقد كتير من التعبيرية (زي sealed classes بتتحول لـ enum-like structure أقل قوة، أو الـ default arguments مش بتتدعم مباشرة). Swift Export هي ميزة جديدة (لسه بتتطور) بتسمح بتوليد Swift APIs مباشرة من Kotlin من غير المرور بالـ Objective-C bridge، وده بيحافظ على تعبيرية أكتر من ناحية الـ generics والـ null-safety وnamed parameters، وبيخلي تجربة استهلاك مكتبة KMP من Swift أقرب بكتير لإحساس مكتبة Swift أصلية 100%.

09 src/testing/

Testing في KMP

kotlin.test، fakes، وplatform-specific test runners

3 أسئلة

بتستخدم مكتبة kotlin.test اللي هي abstraction طبقة فوق أطر الاختبار المختلفة لكل منصة: بتتحول لـ JUnit على JVM/Android، وXCTest تلقائياً على iOS، وnodejs test runner على JS/Wasm. بتكتب الاختبار مرة واحدة في commonTest باستخدام @Test وassertEquals وباقي assertions المتاحة، والـ Gradle plugin بيتكفل بتشغيله لكل target عند تنفيذ ./gradlew allTests أو ./gradlew iosSimulatorArm64Test مثلاً. الميزة الكبيرة إنك بتضمن إن الـ business logic بيشتغل صح فعلياً على كل platform runtime مش بس على JVM، لأن فيه فروق دقيقة أحياناً في سلوك بعض الـ APIs (زي التعامل مع الـ floating point precision أو الـ date/time) بين الـ runtimes المختلفة.

// commonTest
class UserValidatorTest {
    @Test
    fun `email بدون @ لازم يفشل`() {
        val result = UserValidator.isValidEmail("invalid-email")
        assertFalse(result)
    }
}

لو الكود مصمم صح (يعني بيعتمد على interfaces بدل expect/actual مباشرة زي ما اتكلمنا قبل كده)، بتقدر ببساطة تعمل fake class عادي بيطبق نفس الـ interface وتحقنه في الـ constructor، وده الأسلوب الأنظف للـ testability. لو مضطر تتعامل مع expect/actual class فعلاً (لحالات نادرة)، الممارسة الشائعة إنك تعمل actual implementation خاص بـ commonTest source set نفسه (لو الـ target بيدعم كده) أو تستخدم fake عادي جواه wrapper interface بحيث الـ expect/actual يفضل thin layer بس، والمنطق الحقيقي كله بيتحط جواه class تاني قابل لل mocking بسهولة، وده بيرجعنا لنفس المبدأ: قلل الاعتماد المباشر على expect/actual في الأماكن اللي محتاجة اختبار مكثف.

لأ، Mockito وMockK الاتنين مبنيين على آليات JVM-specific (زي bytecode manipulation عن طريق Java's dynamic proxy أو ByteBuddy)، فمش هيشتغلوا في commonTest لأنه لازم يكون portable لكل target. البديل المستخدم في مشاريع KMP هو مكتبة multiplatform حقيقية زي MockKMP أو ببساطة كتابة manual fakes/stubs (يعني تعمل class بسيط بيطبق الـ interface ويرجعلك قيم ثابتة أو بيسجل الاستدعاءات في list يدوي عشان تتحقق منها بعدين). كتير من الفرق المحترفة بتفضل فعلياً الـ manual fakes حتى لو كانوا بيستخدموا Mockito على JVM، لأنها أوضح وأسهل صيانة على المدى الطويل، وده اتجاه معروف حتى في مجتمع Android بشكل عام مش بس KMP.

10 src/advancedComparisons/

أسئلة متقدمة ومقارنات

قرارات معمارية، أداء، ومقارنة مع Flutter/RN، وسيناريوهات مقابلات فعلية

5 أسئلة

الإجابة الناضجة مش 'KMP أفضل مطلقاً' لكن توضيح الـ trade-offs: KMP بيسيبلك حرية الـ native UI الكامل (لو مش مستخدم CMP)، فده مثالي لو الشركة عندها فريقين Android/iOS ناضجين وعايزة تحافظ على أعلى درجة native feel وaccessibility وperformance للـ UI، مع تقليل تكرار منطق الأعمال بس. Flutter بالعكس بيديك consistency بصرية كاملة وسرعة تطوير أعلى من البداية لأن الـ UI نفسه مشترك 100% دايماً، وده أنسب لشركة ناشئة عايزة تطلق منتج بفريق واحد بسرعة، أو منتج شكله البصري أهم من مطابقته الكاملة لكل platform convention. عيب Flutter الأساسي إنه بيجيب معاه الـ Dart runtime كامل وبيرسم كل حاجة بنفسه (حتى الـ text rendering)، وده بيسبب أحياناً اختلافات دقيقة عن سلوك النظام (زي text selection أو IME behavior) لازم تتحل يدوياً. القرار الصح بيعتمد على نضج الفريق، حجم المنتج، ومدى أهمية الـ native fidelity بالنسبة للمنتج.

أكبر خطر هو 'leaky abstraction' في اتجاه عكسي: إنك تكتب commonMain code بس فعلياً بيفترض سلوك platform معين (زي الاعتماد الضمني على إن الـ threading model زي Android بالظبط، أو استخدام مكتبة JVM-only من غير الانتباه)، وده بيتكشف متأخر جداً وقت محاولة إضافة target جديد أو حتى وقت اختبار الكود على iOS لأول مرة، وبيكون التصحيح مكلف جداً في المرحلة دي. الحل العملي إنك من أول يوم تشغّل CI على كل الـ targets المستهدفة (مش بس Android)، حتى لو iOS UI لسه مش جاهز، عشان تكتشف مشاكل الـ compilation والـ runtime behavior بدري. كمان مهم جداً وضع 'حدود' واضحة (architectural boundaries) من الأول لمين مسؤول عن الـ platform-specific concerns زي permissions أو navigation، بدل ما الفريق يكتشفها بالتجربة والخطأ مع كل feature جديد.

React Native حتى بعد الـ New Architecture لسه بيعتمد أساساً على تشغيل JavaScript على محرك (JS engine زي Hermes)، والـ JSI (JavaScript Interface) بس قلّلت الـ overhead في التواصل بين JS والـ native code (بدل الـ old bridge اللي كان async وبطيء نسبياً وبيحول كل حاجة لـ JSON)، لكن الـ business logic نفسه لسه بيتفسر (interpreted/JIT-compiled) عن طريق الـ JS engine وقت الـ runtime. KMP مختلف جذرياً: مفيش JS engine ولا تفسير وقت التشغيل خالص، الكود بيتحول (compiled) لـ native machine code وقت البناء نفسه (ahead-of-time)، سواء JVM bytecode أو LLVM-based native binary، يعني مفيش أي 'محرك تفسير' وسيط بين الكود ومنطق التشغيل، وده الفرق الأساسي في نقطة الأداء والـ startup time، حتى لو الـ New Architecture قربت React Native كتير من ناحية سرعة الـ interop.

أول خطوة عملية إنك تدور على multiplatform alternative موجودة فعلاً (المجتمع بقى كبير نسبياً: Ktor بدل Retrofit، SQLDelight بدل Room التقليدي، kotlinx-datetime بدل java.time المباشر، kotlinx.serialization بدل Gson). لو مفيش بديل، الخيار التاني إنك تعزل استخدام المكتبة دي جوه الـ platform-specific source set (androidMain مثلاً) وتوفر abstraction (interface) في commonMain بحيث باقي الكود المشترك مش بيعرف تفاصيل المكتبة دي، وتكتب actual implementation منفصل لكل platform حتى لو ده معناه تكرار جزء من المنطق. الخيار الأخير والأصعب هو المساهمة (contribution) في المكتبة نفسها أو كتابة KMP wrapper بنفسك حواليها، وده قرار بيتاخد لو المكتبة استراتيجية جداً للمنتج ومفيش بديل مقبول.

خبرة الـ AOSP والـ VHAL بتعطيك حس عملي بمفاهيم زي الـ HAL abstraction layers، الـ Binder IPC، وإدارة الـ process boundaries، وده نفس المنطق الذهني المستخدم في فهم إزاي KMP بيعزل الـ platform-specific behavior عن طريق expect/actual، أو إزاي Kotlin/Native بيتفاعل مع ARC عبر حدود process/memory مختلفة. كمان فهمك العميق لـ ART (Android Runtime) وbytecode compilation بيدّيك أساس قوي لفهم الفرق الجوهري بين إزاي Kotlin بيتحول لـ JVM bytecode مقابل إزاي بيتحول لـ LLVM IR ثم native binary على Kotlin/Native، وده تحديداً النوع من الفهم اللي بيميّزك في مقابلة senior/staff عن مطور بيتعامل مع KMP كـ 'framework' بس من غير فهم لطبقات الـ runtime تحته.
