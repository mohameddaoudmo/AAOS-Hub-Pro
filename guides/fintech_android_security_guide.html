FinTech & Payment Security

المرجع ده بيشرح كل حاجة متعلقة بعالم الـ FinTech وأمان أنظمة الدفع (PCI، EMV، ISO 8583، التشفير بأنواعه) وبيربطها بشكل مباشر بتطبيقات Android — يعني مش بس نظرية، كل موضوع فيه إزاي تطبّقه في Kotlin، وإزاي يستخدم Android Keystore و JCA/JCE، وإيه العلاقة بـ NFC/EMV في تطبيقات الدفع.

1

ما هو FinTech (Financial Technology)

FinTech هو استخدام التكنولوجيا عشان تحسّن أو تُتمتة الخدمات المالية: الدفع، التحويلات، الإقراض، إدارة الاستثمار، والبنوك الرقمية. بدل ما العميل يروح فرع بنك، بقى يقدر يدفع بموبايله أو يفتح حساب من التطبيق.

🧩 أهم مجالات FinTech

  • Payments: محافظ إلكترونية، تحويلات فورية، NFC payments (زي Google Pay).
  • Digital Banking: بنوك بدون فروع (Neobanks).
  • Lending: قروض رقمية بتقييم ائتماني آلي.
  • InsurTech: تأمين رقمي.
  • RegTech: أدوات الامتثال والمراقبة ضد الاحتيال (AML/KYC).
📱 علاقتها بـ Android كمطوّر Android في مجال FinTech، غالبًا هتشتغل على: تطبيقات محافظ، قراءة كروت عبر NFC (EMV)، تخزين مفاتيح تشفير آمن عبر Android Keystore، وتكامل مع أجهزة POS عبر Bluetooth/Serial باستخدام بروتوكول ISO 8583.
2

PCI DSS (Payment Card Industry Data Security Standard)

معيار أمان عالمي أنشأته Visa وMasterCard وAmex وغيرهم، بيحدد إزاي أي شركة أو تطبيق بيتعامل مع بيانات الكروت (رقم الكارت PAN، تاريخ الانتهاء، CVV) لازم يحميها.

🔑 أهم متطلبات PCI DSS

  1. عدم تخزين CVV نهائيًا بعد إتمام العملية.
  2. تشفير رقم الكارت (PAN) أثناء التخزين والنقل.
  3. Firewall وتحكم صارم في الوصول للأنظمة.
  4. مراقبة وتسجيل كل عملية وصول لبيانات الكروت (Logging).
  5. اختبار أمان دوري (Penetration Testing).
⚠️ تحذير مهم لمطوري Android: ممنوع تخزّن PAN كامل أو CVV في SharedPreferences أو حتى في Room DB بدون تشفير قوي — ده مخالفة مباشرة لـ PCI DSS وممكن يعرّض التطبيق للرفض من متاجر التطبيقات أو من البنك المُصدر. الحل: استخدم Tokenization بدل تخزين البيانات الحقيقية.
3

Card Acceptance

Card Acceptance هو مصطلح بيوصف قدرة نظام (تاجر، تطبيق، أو جهاز POS) على قبول كارت كوسيلة دفع. فيه أنواع قبول مختلفة حسب طريقة إدخال بيانات الكارت:

النوعالوصفمستوى الأمان
Chip & PIN (EMV)إدخال الكارت في الشريحة + كتابة الرقم السريالأعلى
Contactless / NFCتقريب الكارت أو الموبايل من الجهازعالي
Magnetic Stripeتمرير الشريط المغناطيسيمنخفض (قديم)
Card Not Present (CNP)إدخال البيانات يدويًا أونلاينمتوسط (يحتاج 3D-Secure)
📱 علاقتها بـ Android تطبيقات الـ mPOS (Mobile POS) على Android بتستخدم NFC API عشان تقرأ الكروت Contactless، وبتتواصل مع قارئ EMV خارجي (Reader) عبر Bluetooth لو الدفع بـ Chip & PIN.

EMV (Europay, MasterCard, Visa)

EMV هو المعيار العالمي للكروت الذكية (Chip Cards) اللي بيحل محل الشريط المغناطيسي. بدل ما بيانات الكارت تكون ثابتة (سهلة النسخ)، الشريحة بتولّد Cryptogram فريد لكل عملية، فحتى لو حد سرق البيانات مش هيقدر يستخدمها تاني.

الفرق الأساسي بين EMV والشريط المغناطيسي: EMV بيستخدم تشفير غير متماثل (Asymmetric) بين الشريحة والبنك عشان يتأكد إن الكارت أصلي (Card Authentication) وإن الـ PIN صحيح بدون ما يبعته Plain Text.

📱 علاقتها بـ Android قراءة كارت EMV عبر NFC في Android بتتم باستخدام IsoDep class من حزمة android.nfc.tech، وبيتم تبادل أوامر APDU (Application Protocol Data Unit) مباشرة مع شريحة الكارت. 
// مثال مبسّط لقراءة كارت EMV عبر NFC في Android
val isoDep = IsoDep.get(tag)
isoDep.connect()
val selectAidCommand = byteArrayOf(
    0x00, 0xA4.toByte(), 0x04, 0x00,
    0x07, 0xA0.toByte(), 0x00, 0x00,
    0x00, 0x03, 0x10, 0x10
)
val response = isoDep.transceive(selectAidCommand) // APDU response
isoDep.close()
5

ISO 8583

هو المعيار الدولي لتبادل رسائل المعاملات المالية بين الأنظمة (POS ↔ Acquirer ↔ Network ↔ Issuer). كل رسالة ISO 8583 بتتكون من: MTI (Message Type Indicator) + Bitmap + Data Elements.

🧱 تركيب الرسالة

الجزءالوصفمثال
MTIنوع الرسالة (4 أرقام)0200 = طلب معاملة مالية
Bitmapيحدد أي Data Elements موجودة64 أو 128 بت
Data Elements (DE)الحقول الفعلية للبياناتDE2=PAN, DE3=Processing Code, DE55=Chip Data

📋 أشهر الـ Data Elements

  • DE2: رقم الكارت (PAN)
  • DE3: كود المعالجة (Processing Code)
  • DE4: مبلغ العملية
  • DE35: Track 2 Data
  • DE52: PIN Block
  • DE55: بيانات الشريحة (EMV Data)
MTI بيتقرأ كـ 4 أرقام: الرقم الأول = إصدار المعيار، الثاني = فئة الرسالة (0=Auth, 2=Financial...)، الثالث = دالة الرسالة (طلب/رد)، الرابع = من بدأ الرسالة.
📱 علاقتها بـ Android لو بتبني تطبيق mPOS، هتحتاج تبني/تقرأ رسائل ISO 8583 بنفسك (أو تستخدم مكتبة زي jPOS إذا الجزء ده على السيرفر)، وتبعتها عبر Socket TCP للـ Acquirer. في Kotlin غالبًا بتبني الـ Bitmap والـ DE يدويًا بـ ByteArray processing.

Prepaid & Postpaid Cards

💳 Prepaid

الرصيد بيتشحن مقدمًا. مفيش ائتمان — العميل بيصرف من فلوسه بس. مثالي لتطبيقات المحافظ الإلكترونية والكروت المؤقتة (Gift Cards).

🧾 Postpaid

الشراء الأول والدفع لاحقًا (زي كروت الائتمان). البنك بيحدد حد ائتماني (Credit Limit) والعميل بيسدد شهريًا.

📱 علاقتها بـ Android تطبيقات المحافظ الرقمية (زي Vodafone Cash، InstaPay) غالبًا بتشتغل بمنطق Prepaid: بتتحقق من الرصيد محليًا/عبر API قبل ما تسمح بالعملية، وده بيقلل الحاجة لعمليات Authorization المعقدة.

Visa & MasterCard

Visa وMasterCard مش بنوك — هما شبكات دفع (Payment Networks) بتربط بين البنك المُصدر للكارت (Issuer) والتاجر/البنك المستقبل (Acquirer). هما اللي بيحددوا المعايير الفنية زي شكل رقم الكارت وبروتوكولات EMV الخاصة بيهم.

🔢 تمييز الكارت من رقمه (BIN/IIN)

يبدأ بـالشبكة
4Visa
51-55 أو 2221-2720MasterCard
34 أو 37American Express

أول 6-8 أرقام من الكارت بتُسمى BIN (Bank Identification Number) وبتحدد البنك المُصدر ونوع الكارت.

POS Devices (Point of Sale)

جهاز أو تطبيق بيستقبل عملية الدفع من العميل ويبعتها للشبكة المصرفية. أنواعه:

  • Traditional POS: جهاز مستقل بشاشة وقارئ كارت خاص فيه.
  • mPOS (Mobile POS): قارئ صغير بيتوصل بموبايل/تابلت عبر Bluetooth أو Audio Jack.
  • SoftPOS / Tap to Phone: الموبايل نفسه بيبقى جهاز الدفع باستخدام NFC، من غير هارد وير إضافي.
📱 علاقتها بـ Android SoftPOS هو أكتر اتجاه حالي بيهم مطور Android — بيعتمد على HostApduService (Host Card Emulation) و NFC APIs، ولازم يمر باعتماد PCI CPoC (Contactless Payments on COTS) قبل الإطلاق.

Encoding vs Encryption vs Hashing

ده أهم فرق لازم أي مطور FinTech يفهمه صح، لأن كتير بيخلطوا بينهم:

الخاصيةEncodingEncryptionHashing
الهدفتحويل شكل البيانات للنقلحماية سرية البياناتالتحقق من سلامة البيانات
يحتاج مفتاح؟لانعملا (عادة)
عكسه ممكن؟نعم دايمًا (Decode)نعم بالمفتاح الصح (Decrypt)لا — عملية باتجاه واحد
مثالBase64, URL EncodingAES, RSASHA-256, MD5
قاعدة ذهبية: Encoding مش تشفير. لو حد شافك بتـ Base64 كلمة سر وتقول "مشفرة" — ده غلط، لأن أي حد يقدر يعمل Decode ليها فورًا بدون أي مفتاح.
10

Encoding بالتفصيل

Encoding بيحوّل البيانات لصيغة تانية عشان تتنقل بأمان عبر أنظمة مختلفة (شبكة، ملفات نصية...) — مثلاً تحويل صورة Binary لنص عشان تتبعت في JSON. 

// Base64 Encoding في Kotlin
val original = "4111111111111111"
val encoded = Base64.encodeToString(original.toByteArray(), Base64.DEFAULT)
val decoded = String(Base64.decode(encoded, Base64.DEFAULT))
// أي حد معاه الـ encoded string يقدر يرجعها زي ما هي، مفيش سرية هنا
في الشرائح السابقة كان فيه سؤال "ماذا يحدث لو الرسالة مش Encoded أثناء النقل؟" — الإجابة: ممكن تتلف البيانات (Binary data جوه بروتوكولات نصية زي HTTP)، مش مشكلة أمان لكن مشكلة توافقية (Compatibility).
11

Encryption بالتفصيل

Encryption بيحوّل البيانات لصيغة غير مفهومة (Ciphertext) باستخدام مفتاح، ومينفعش ترجعها للأصل غير بنفس المفتاح (أو المفتاح المقابل له في التشفير الغير متماثل).

نوعين أساسيين

🔑 Symmetric Encryption

نفس المفتاح للتشفير وفك التشفير. أسرع، مثال: AES.

🔐 Asymmetric Encryption

مفتاحين: عام (Public) وخاص (Private). أبطأ، مثال: RSA.

ماذا يحدث لو مفيش Encryption؟ أي حد على الشبكة (Man-in-the-middle) يقدر يقرأ بيانات الكارت كاملة كـ Plain Text — ده أخطر سيناريو ممكن يحصل في تطبيق دفع، وسبب مباشر لرفض PCI DSS Compliance.
12

Hashing بالتفصيل

Hashing بيحوّل أي بيانات لبصمة (Hash) ثابتة الطول، وعملية باتجاه واحد يعني مينفعش ترجع البيانات الأصلية من الـ Hash. بيُستخدم للتحقق من سلامة البيانات (Integrity) أو تخزين كلمات السر بأمان.

أي تغيير بسيط جدًا في البيانات (حتى حرف واحد) بيغيّر الـ Hash بالكامل — ده بيُسمى Avalanche Effect.
// Hashing باستخدام SHA-256 في Kotlin
fun sha256(input: String): String {
    val bytes = MessageDigest.getInstance("SHA-256").digest(input.toByteArray())
    return bytes.joinToString("") { "%02x".format(it) }
}
13

SHA-256

خوارزمية Hashing من عائلة SHA-2، بتنتج بصمة طولها ثابت 256 بت (64 حرف Hex) مهما كان طول المدخل. بتُستخدم في التحقق من سلامة رسائل ISO 8583، توليد MAC، وفي Blockchain.

📱 استخدامها في Android بتستخدمها للتحقق من سلامة ملف تم تنزيله، أو عمل Hash لمفتاح API قبل تخزينه، أو التحقق من صحة توقيع (Signature verification) على APK وقت الـ Runtime.
14

SecretKey

الـ SecretKey هو المفتاح المستخدم في التشفير المتماثل (Symmetric). في Android، أفضل وأأمن طريقة لتوليده وتخزينه هي عبر Android Keystore System — المفتاح بيتولد ويتخزن جوه Hardware-backed area ومستحيل يتسحب برة الجهاز حتى لو التطبيق نفسه اتعمله Reverse Engineering. 

// توليد SecretKey داخل Android Keystore
val keyGenerator = KeyGenerator.getInstance(
    KeyProperties.KEY_ALGORITHM_AES, "AndroidKeyStore"
)
keyGenerator.init(
    KeyGenParameterSpec.Builder("paymentKey",
        KeyProperties.PURPOSE_ENCRYPT or KeyProperties.PURPOSE_DECRYPT)
        .setBlockModes(KeyProperties.BLOCK_MODE_GCM)
        .setEncryptionPaddings(KeyProperties.ENCRYPTION_PADDING_NONE)
        .setKeySize(256)
        .build()
)
val secretKey = keyGenerator.generateKey()
مبدأ أساسي: SecretKey ما ينفعش يتخزن Hardcoded في الكود — لو حد عمل Decompile للـ APK هيلاقيه فورًا.
15

AES Encryption (Advanced Encryption Standard)

خوارزمية تشفير متماثل (نفس المفتاح للتشفير وفك التشفير)، بتشتغل بحجم مفتاح 128/192/256 بت. هي المعيار العالمي حاليًا لتشفير البيانات الحساسة (بيانات الكارت، الجلسات، ملفات). 

// تشفير بيانات باستخدام AES/GCM في Kotlin (JCA)
val cipher = Cipher.getInstance("AES/GCM/NoPadding")
cipher.init(Cipher.ENCRYPT_MODE, secretKey)
val iv = cipher.iv // لازم تخزن الـ IV مع الـ ciphertext
val encryptedBytes = cipher.doFinal(cardData.toByteArray())
استخدم دايمًا GCM mode بدل ECB أو حتى CBC العادي، لأن GCM بيوفر Authenticated Encryption يعني بيتأكد كمان إن البيانات ما اتغيرتش (Integrity) مش بس سرية.
16

AES Behind The Scenes

AES بيشتغل على كتل بيانات (Blocks) حجم كل واحدة 128 بت، وبيمر بعدة جولات (Rounds) حسب طول المفتاح:

حجم المفتاحعدد الجولات
128-bit10 جولات
192-bit12 جولة
256-bit14 جولة

كل جولة فيها 4 خطوات رئيسية:

SubBytes
→
ShiftRows
→
MixColumns
→
AddRoundKey
  • SubBytes: استبدال كل بايت بقيمة من جدول ثابت (S-Box) لإضافة عدم خطية.
  • ShiftRows: تحريك الصفوف في المصفوفة لخلط البيانات مكانيًا.
  • MixColumns: خلط الأعمدة رياضيًا (باستثناء الجولة الأخيرة).
  • AddRoundKey: عملية XOR بين البيانات ومفتاح الجولة (Round Key) المشتق من المفتاح الأساسي.
كل ده بيخلي أي تغيير بسيط في المدخل أو المفتاح ينتج Ciphertext مختلف تمامًا — ومفيش طريقة عملية لكسره بالقوة الغاشمة (Brute Force) بمفتاح 256-bit بالتقنية الحالية.
17

RSA Algorithm

خوارزمية تشفير غير متماثل (Asymmetric) بتعتمد على الصعوبة الرياضية لتحليل حاصل ضرب عددين أوليين كبيرين (Integer Factorization). بتُستخدم غالبًا مش لتشفير البيانات الكبيرة نفسها (بطيئة) لكن لـ:

  • تبادل مفتاح AES بأمان (Key Exchange).
  • التوقيع الرقمي (Digital Signature) للتأكد من هوية المرسل.
  • تشفير TLS/HTTPS في مرحلة الـ Handshake.
// توليد زوج مفاتيح RSA وتشفير بيانات في Kotlin
val keyPairGen = KeyPairGenerator.getInstance("RSA")
keyPairGen.initialize(2048)
val keyPair = keyPairGen.generateKeyPair()

val cipher = Cipher.getInstance("RSA/ECB/OAEPWithSHA-256AndMGF1Padding")
cipher.init(Cipher.ENCRYPT_MODE, keyPair.public)
val encrypted = cipher.doFinal(aesKeyBytes) // تشفير مفتاح AES بمفتاح RSA العام
18

RSA with AES Encryption (Hybrid Encryption)

النظام الأمثل عمليًا هو دمج الاتنين — ده اللي بيحصل فعليًا في TLS/HTTPS وفي أنظمة الدفع:

1. توليد مفتاح AES عشوائي (Session Key)
←
2. تشفير البيانات الفعلية بـ AES (سريع)
←
3. تشفير مفتاح AES نفسه بـ RSA Public Key
←
4. إرسال الاثنين معًا للطرف الآخر

الطرف المستقبل بيفك تشفير مفتاح AES باستخدام RSA Private Key بتاعه، وبعدين يستخدم مفتاح AES ده عشان يفك باقي البيانات. كده استفدنا من سرعة AES وأمان RSA في تبادل المفتاح.

📱 استخدامها في Android نفس المبدأ ده بيُستخدم لما التطبيق بيحتاج يبعت بيانات حساسة للسيرفر بدون الاعتماد الكامل على HTTPS (Defense in depth) — أو في تشفير End-to-End داخل التطبيق نفسه.

PIN Block in Payment Systems

الـ PIN مينفعش يتبعت زي ما هو أبدًا — لازم يتحط جوه هيكل يُسمى PIN Block بعدين يتشفر (تقليديًا بـ 3DES، وحديثًا AES) قبل ما يترسل من الـ POS أو الـ Reader للـ Acquirer.

تركيب PIN Block (فورمات ISO-0 الأشهر)

Field 1: طول الـ PIN + الـ PIN نفسه + Padding (F)
XOR
Field 2: آخر 12 رقم من الـ PAN (بدون check digit)

ناتج الـ XOR ده هو الـ PIN Block اللي بيتشفر بمفتاح خاص (PIN Encryption Key) قبل الإرسال ضمن DE52 في رسالة ISO 8583.

مهم: الـ PIN مينفعش أبدًا يتخزن أو يُعرض حتى داخليًا — الأجهزة المعتمدة (PIN Pads) بتكون معزولة هاردوير (Tamper-resistant) وبتشفّر الـ PIN فورًا جوه نفس الجهاز.

PAN Parser

الأداة/المنطق المسؤول عن قراءة رقم الكارت (Primary Account Number) من مصادر مختلفة (Track 1/2 Data, Chip Data) واستخراج المعلومات منه: BIN، طول الرقم، Check Digit عبر خوارزمية Luhn. 

// التحقق من صحة رقم الكارت بخوارزمية Luhn
fun isValidLuhn(cardNumber: String): Boolean {
    var sum = 0
    var alternate = false
    for (i in cardNumber.length - 1 downTo 0) {
        var n = cardNumber[i].digitToInt()
        if (alternate) { n *= 2; if (n > 9) n -= 9 }
        sum += n
        alternate = !alternate
    }
    return sum % 10 == 0
}
📱 في Android نفس اللوجيك ده بتستخدمه في validation فوري لحقل رقم الكارت في UI (Compose TextField) قبل ما تبعت أي حاجة للسيرفر.

DE55 (Data Element 55) — Chip Data

Data Element رقم 55 في رسالة ISO 8583 بيحمل بيانات EMV الكاملة الجاية من شريحة الكارت — وده بيشمل Tags متعددة (زي TLV - Tag Length Value) منها:

Tagالوصف
9F26Application Cryptogram
9F27Cryptogram Information Data
9F10Issuer Application Data
95Terminal Verification Results
9F37Unpredictable Number

الـ Issuer بيستخدم الـ Cryptogram ده عشان يتأكد إن الكارت الفعلي (مش نسخة/محاكاة) هو اللي عمل العملية.

Sniffing

عملية اعتراض ومراقبة البيانات وهي بتتنقل عبر شبكة أو داخل جهاز (Traffic interception)، مثلاً باستخدام أدوات زي Wireshark أو Proxy tools زي Burp Suite لالتقاط الطلبات بين التطبيق والسيرفر.

لو التطبيق مش عامل Certificate Pinning، أي حد يقدر يستخدم Proxy (زي mitmproxy) عشان يشوف كل الـ HTTPS requests وbodies كاملة — حتى لو كانت "مشفرة بـ HTTPS"، لأن الـ Proxy بيبقى Man-in-the-middle موثوق فيه من الجهاز.

Prevent Sniffing

🛡️ طرق الحماية في Android

  • Certificate/Public Key Pinning: التطبيق يرفض أي اتصال SSL ما كانتش شهادته مطابقة للمتوقعة.
  • Network Security Config: منع Cleartext traffic بالكامل.
  • Root/Debug detection: كشف لو الجهاز فيه Proxy CA مثبت أو الجهاز Rooted.
  • تشفير إضافي على مستوى الـ Application layer فوق HTTPS للبيانات شديدة الحساسية.
// مثال Certificate Pinning عبر OkHttp
val certificatePinner = CertificatePinner.Builder()
    .add("api.mybank.com", "sha256/AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA=")
    .build()

val client = OkHttpClient.Builder()
    .certificatePinner(certificatePinner)
    .build()
// network_security_config.xml - منع الاتصال الغير مشفر
<network-security-config>
    <base-config cleartextTrafficPermitted="false">
        <trust-anchors>
            <certificates src="system" />
        </trust-anchors>
    </base-config>
</network-security-config>

Prevent Copy & Paste

في تطبيقات الدفع، لازم تمنع نسخ بيانات حساسة (رقم كارت، CVV، PIN) من حقول الإدخال أو الشاشة — عشان تقلل خطر إن الـ Clipboard (اللي أي تطبيق تاني ممكن يقراه على أندرويد القديم) يسرب البيانات دي. 

// منع النسخ من EditText في Android (View system)
editText.customSelectionActionModeCallback = object : ActionMode.Callback {
    override fun onPrepareActionMode(mode: ActionMode?, menu: Menu?): Boolean {
        menu?.clear() // يشيل خيارات Copy/Cut/Share
        return true
    }
    override fun onCreateActionMode(m: ActionMode?, menu: Menu?) = true
    override fun onActionItemClicked(m: ActionMode?, item: MenuItem?) = false
    override fun onDestroyActionMode(mode: ActionMode?) {}
}
editText.isLongClickable = false
// في Jetpack Compose - منع التحديد/النسخ
BasicTextField(
    value = cardNumber,
    onValueChange = { cardNumber = it },
    modifier = Modifier.pointerInteropFilter { true } // يمنع الـ long press selection
