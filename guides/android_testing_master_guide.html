فلسفة وهرم الاختبارات في أندرويد (Android Test Pyramid & Strategy)

مبدأ الهرم الاختباري (The Android Test Pyramid)

يُعد هرم الاختبارات (Test Pyramid) الإطار الاستراتيجي الأساسي لتحديد توزيع الاختبارات في مشروعك. يقوم المبدأ على توزيع الاختبارات بحيث تكون الأكثر سرعةً واستقراراً في القاعدة، والأكثر تكلفةً في القمة.

Unit Tests
Integration Tests
End-to-End / UI Tests
70% Unit Tests — سريعة، منخفضة التكلفة، عالية الاستقرار
20% Integration Tests — متوسطة السرعة، تتحقق من التفاعل بين المكونات
10% E2E / UI Tests — بطيئة، مكلفة، عرضة للـ Flakiness
💡
القاعدة الذهبية

كلما صعدت في الهرم، زادت تكلفة الصيانة (Maintenance Cost) وقلت السرعة (Execution Speed) وزاد احتمال الفشل العشوائي (Flakiness). لذلك، اجعل غالبية اختباراتك في طبقة Unit Tests.

نوع الاختبار السرعة التكلفة الاعتمادية Flakiness
Unit Tests مللي ثوانٍ منخفضة جداً عالية جداً نادر
Integration Tests ثوانٍ متوسطة عالية منخفض
E2E / UI Tests دقائق عالية متوسطة شائع

Architecture for Testability

لا يمكن بناء اختبارات نظيفة دون بنية نظيفة. يتيح لك Clean Architecture و Dependency Injection (عبر Hilt أو Koin) فصل منطق الأعمال (Business Logic) عن واجهات برمجة تطبيقات إطار عمل أندرويد (Android Framework APIs)، مما يجعل اختبار الوحدات ممكناً دون الحاجة إلى Emulator أو Device.

🏗️

Clean Architecture

فصل الطبقات إلى Domain و Data و Presentation يضمن أن منطق الأعمال خالٍ من أي تبعية لـ Android SDK.

💉

Dependency Injection

استخدام Hilt أو Koin لحقن التبعيات (Dependencies) يتيح لك استبدال Implementations الحقيقية بـ Test Doubles بسهولة.

Test Doubles Taxonomy

عند اختبار وحدة معزولة، نحتاج إلى استبدال تعاونياتها (Collaborators) بكائنات وهمية. يُعد فهم الفرق بين أنواع Test Doubles أمراً حاسماً لكتابة اختبارات نظيفة وغير هشة (Non-Brittle).

النوع الوصف متى تستخدمه
Dummy كائن يُمرر فقط لإرضاء التوقيع (Signature) دون استخدامه فعلياً عندما يتطلب المُنشئ parameter لا يُستخدم في الاختبار
Stub يوفر رداً جاهزاً مُبرمج مسبقاً على استدعاء معين عندما تحتاج إلى تحكم في القيم المُرجعة (Return Values)
Spy يسجل استدعاءات الطرق (Method Calls) للتحقق لاحقاً عندما تحتاج إلى التحقق من Side Effects الداخلية
Mock كائن وهمي يُحقق التوقعات (Expectations) على التفاعلات عندما تحتاج إلى التحقق من أن تفاعلاً محدداً قد حدث
Fake تنفيذ حقيقي مُبسط (In-Memory DB، Fake Server) يُفضل في طبقة البيانات بدلاً من Mocks
⚠️
تفضيل Fakes على Mocks في طبقة البيانات

في طبقة البيانات (Data Layer)، يُفضل دائماً استخدام Fake Implementations (مثل In-Memory Room Database أو Fake Retrofit Service) بدلاً من Mocks. الفيكس يُحاكي السلوك الحقيقي بشكل أقرب، ويقلل من هشاشة الاختبارات (Brittleness) عند تغيير التفاصيل الداخلية للتنفيذ.

اختبارات الوحدات والـ Coroutines والـ Flows (Unit Testing & Coroutines/Flows)

JUnit 4 vs JUnit 5 في أندرويد

على الرغم من أن JUnit 4 لا يزال المستخدم افتراضياً في مشاريع أندرويد، إلا أن JUnit 5 (Jupiter) يوفر ميزات متقدمة مثل Nested Tests و Dynamic Tests و Extension Model الأكثر مرونة. يمكن دمج JUnit 5 في مشروعك عبر android-junit5 plugin.

4️⃣

JUnit 4

@Test · @Before · @After · @Rule · @RunWith
النموذج القديم المبني على Annotations و Rules.

5️⃣

JUnit 5 (Jupiter)

@Test · @BeforeEach · @AfterEach · @ParameterizedTest · @ExtendWith
Extension Model مرن ودعم Nested Tests.

@ExtendWith(MainDispatcherExtension::class)
class UserViewModelTest {

    @BeforeEach
    fun setUp() {
        // Initialize test dependencies
    }

    @ParameterizedTest
    @ValueSource(strings = ["user1", "user2"])
    fun `should validate username`(username: String) {
        // Test logic
    }
}

Mocking مع MockK

MockK هو إطار العمل الأفضل لمحاكاة الكائنات في Kotlin. يدعم Coroutines بشكل أصلي ويوفر DSL نظيفاً وقوياً. 

val repository = mockk<UserRepository>()

// Mocking regular functions
every { repository.getUser("123") } returns mockUser

// Mocking suspend functions
coEvery { repository.fetchUserAsync("123") } returns mockUser

// Verification
verify(exactly = 1) { repository.getUser("123") }

// Capturing arguments with slot
val slot = slot<String>()
verify { repository.getUser(capture(slot)) }
assertEquals("123", slot.captured)

// Mocking static / singleton (object)
mockkObject(NetworkUtils)
every { NetworkUtils.isConnected() } returns true
🎯
نصيحة MockK

استخدم relaxed = true عند إنشاء Mock إذا كنت لا تهتم بالقيم المُرجعة لبعض الطرق. استخدم relaxedUnitFun = true للدوال التي تُرجع Unit.

Testing Coroutines

اختبار الكوروتينات يتطلب التحكم في المُجدول (Dispatcher) لتجنب التنفيذ غير المتزامن في الاختبارات. يوفر kotlinx-coroutines-test الأدوات اللازمة. 

class MainDispatcherRule(
    val testDispatcher: TestDispatcher = StandardTestDispatcher()
) : TestWatcher() {
    override fun starting(description: Description) {
        Dispatchers.setMain(testDispatcher)
    }
    override fun finished(description: Description) {
        Dispatchers.resetMain()
    }
}

// Usage in test
@get:Rule
val mainDispatcherRule = MainDispatcherRule()

@Test
fun `should emit loading then success`() = runTest {
    viewModel.loadData()
    mainDispatcherRule.testDispatcher.scheduler.advanceUntilIdle()
    // Assert state
}
⚡

StandardTestDispatcher

يتطلب advanceUntilIdle() أو runCurrent() لتنفيذ المهام المعلقة. يمنحك تحكماً كاملاً في التوقيت.

🌊

UnconfinedTestDispatcher

ينفذ المهام فوراً دون الحاجة إلى تقديم الوقت (Time Advancement). سريع لكن أقل تحكماً في التسلسل الزمني.

Testing Kotlin Flows مع Turbine

Turbine هي مكتبة من Square تُبسط اختبار Flows بشكل متزامن (Synchronous). تتيح لك استهلاك القيم (Emissions) واحدة تلو الأخرى والتحقق من حالات الإكمال والأخطاء. 

@Test
fun `should emit states in correct order`() = runTest {
    viewModel.uiState.test {
        // Initial state
        assertEquals(UiState.Idle, awaitItem())

        // Trigger action
        viewModel.fetchUser("123")

        // Loading state
        assertEquals(UiState.Loading, awaitItem())

        // Success state
        assertEquals(UiState.Success(user), awaitItem())

        // Ensure no more emissions
        awaitComplete()
    }
}

// Testing SharedFlow events (One-time events)
viewModel.events.test {
    viewModel.showError()
    assertEquals(Event.ShowError, awaitItem())
    cancelAndConsumeRemainingEvents()
}

ViewModel Unit Testing — خطوة بخطوة

يُعد ViewModel حجر الزاوية في طبقة Presentation. يجب اختبار تحديثات حالة واجهة المستخدم (UI State Updates) والتأثيرات الجانبية (Side Effects) بشكل منفصل وواضح. 

class LoginViewModelTest {

    @get:Rule
    val mainDispatcherRule = MainDispatcherRule()

    private val loginUseCase = mockk<LoginUseCase>()
    private lateinit var viewModel: LoginViewModel

    @Before
    fun setUp() {
        viewModel = LoginViewModel(loginUseCase)
    }

    @Test
    fun `should update state to success on valid login`() = runTest {
        // Given
        coEvery { loginUseCase.invoke("user", "pass") } returns Result.Success

        // When
        viewModel.login("user", "pass")
        advanceUntilIdle()

        // Then
        assertEquals(LoginUiState.Success, viewModel.uiState.value)
    }
}

اختبار طبقة البيانات والـ Room (Data Layer & Integration Testing)

Testing Room Database

يُعد Room جزءاً أساسياً من طبقة البيانات المحلية. يمكن اختباره باستخدام قاعدة بيانات In-Memory تُنشأ وتُدمَّر مع كل اختبار، مما يضمن عزل الاختبارات (Test Isolation). 

@RunWith(AndroidJUnit4::class)
class UserDaoTest {

    private lateinit var database: AppDatabase
    private lateinit var userDao: UserDao

    @Before
    fun createDb() {
        val context = ApplicationProvider.getApplicationContext<Context>()
        database = Room.inMemoryDatabaseBuilder(
            context, AppDatabase::class.java
        ).build()
        userDao = database.userDao()
    }

    @After
    fun closeDb() {
        database.close()
    }

    @Test
    fun `should insert and retrieve user`() = runTest {
        val user = UserEntity(id = 1, name = "Ahmed")
        userDao.insertUser(user)

        val result = userDao.getUserById(1).first()
        assertEquals("Ahmed", result.name)
    }

    @Test
    fun `should emit flow updates on insert`() = runTest {
        userDao.getAllUsers().test {
            assertEquals(emptyList<UserEntity>(), awaitItem())

            userDao.insertUser(UserEntity(1, "Ahmed"))
            assertEquals(1, awaitItem().size)

            cancelAndIgnoreRemainingEvents()
        }
    }
}
✅
أفضل ممارسة Room Testing

استخدم inMemoryDatabaseBuilder دائماً لاختبارات DAO. لا تستخدم قاعدة البيانات الحقيقية على القرص (Disk) لأنها تُبطئ الاختبارات وتُسبب تبعيات بينها.

Testing Repository Pattern

يجب اختبار Repository باستخدام Fake Data Sources (Remote و Local) للتحقق من منطق التنسيق بين المصادر (Single Source of Truth) دون الاعتماد على الشبكة أو قاعدة البيانات الحقيقية. 

class FakeLocalDataSource : LocalDataSource {
    private val users = MutableStateFlow<List<User>>(emptyList())
    override fun getUsers() = users.asStateFlow()
    override suspend fun saveUsers(list: List<User>) { users.value = list }
}

class FakeRemoteDataSource : RemoteDataSource {
    var usersToReturn: List<User> = emptyList()
    var shouldThrowError = false

    override suspend fun fetchUsers(): List<User> {
        if (shouldThrowError) throw IOException("Network error")
        return usersToReturn
    }
}

// Test: Repository should fetch from remote and cache locally
@Test
fun `should cache remote data locally`() = runTest {
    val remote = FakeRemoteDataSource().apply { 
        usersToReturn = listOf(User("1", "Ahmed")) 
    }
    val local = FakeLocalDataSource()
    val repo = UserRepository(remote, local)

    repo.syncUsers()

    assertEquals("Ahmed", local.getUsers().value.first().name)
}

Testing Network Requests مع MockWebServer

MockWebServer من OkHttp يتيح لك اختبار Retrofit APIs بشكل حقيقي دون الحاجة إلى الإنترنت. يُنشئ خادماً وهمياً (Local HTTP Server) يستجيب للطلبات بردود مُبرمجة. 

class UserApiTest {
    private val mockWebServer = MockWebServer()
    private lateinit var api: UserApi

    @Before
    fun setUp() {
        mockWebServer.start()
        val retrofit = Retrofit.Builder()
            .baseUrl(mockWebServer.url("/"))
            .addConverterFactory(GsonConverterFactory.create())
            .build()
        api = retrofit.create(UserApi::class.java)
    }

    @After
    fun tearDown() {
        mockWebServer.shutdown()
    }

    @Test
    fun `should parse user response correctly`() = runTest {
        val response = MockResponse()
            .setBody("""{"id":"1","name":"Ahmed"}""")
            .setResponseCode(200)
        mockWebServer.enqueue(response)

        val user = api.getUser("1")
        assertEquals("Ahmed", user.name)
    }

    @Test
    fun `should throw on 500 error`() = runTest {
        mockWebServer.enqueue(MockResponse().setResponseCode(500))

        assertThrows<HttpException> {
            api.getUser("1")
        }
    }
}

اختبار واجهات المستخدم والـ Compose (UI & Instrumentation Testing)

Espresso UI Testing (Legacy View System)

Espresso هو إطار العمل الرسمي لاختبار واجهات المستخدم المبنية على نظام العرض التقليدي (View System). يعتمد على ثلاثة مكونات أساسية: ViewMatchers للعثور على العناصر، وViewActions للتفاعل معها، وViewAssertions للتحقق من حالتها. 

@Test
fun `should navigate to detail on item click`() {
    // Match
    Espresso.onView(ViewMatchers.withId(R.id.recyclerView))
        .perform(RecyclerViewActions.actionOnItemAtPosition<RecyclerView.ViewHolder>(
            0, ViewActions.click()
        ))

    // Assert
    Espresso.onView(ViewMatchers.withId(R.id.detailTitle))
        .check(ViewAssertions.matches(ViewMatchers.isDisplayed()))
}

// Custom Matcher
fun withDrawable(@DrawableRes id: Int): Matcher<View> {
    return object : BoundedMatcher<View, ImageView>(ImageView::class.java) {
        override fun describeTo(description: Description) {
            description.appendText("with drawable: $id")
        }
        override fun matchesSafely(view: ImageView): Boolean {
            return view.drawable != null
        }
    }
}
⏳
IdlingResource للعمليات غير المتزامنة

عندما يحتوي تطبيقك على عمليات غير متزامنة (Network, Database, Animations)، استخدم IdlingResource لإبلاغ Espresso بأن التطبيق في حالة خمول (Idle) قبل المتابعة. هذا يمنع Flaky Tests الناتجة عن Race Conditions.

Jetpack Compose UI Testing (Modern UI)

يقدم Jetpack Compose نظام اختبار خاصاً به يعتمد على Semantics Tree بدلاً من View Hierarchy. يتيح لك ComposeTestRule إنشاء واجهات Compose في عزلة (Isolation) والتفاعل معها. 

class LoginScreenTest {

    @get:Rule
    val composeTestRule = createComposeRule()

    @Test
    fun `should show error when fields are empty`() {
        composeTestRule.setContent {
            LoginScreen(viewModel = fakeViewModel)
        }

        // Find and interact
        composeTestRule.onNodeWithText("Login")
            .performClick()

        // Assert
        composeTestRule.onNodeWithText("Fields cannot be empty")
            .assertIsDisplayed()
    }

    @Test
    fun `should navigate on successful login`() {
        composeTestRule.setContent {
            val navController = rememberNavController()
            LoginScreen(navController = navController)
        }

        composeTestRule.onNodeWithTag("email_field")
            .performTextInput("user@example.com")

        composeTestRule.onNodeWithTag("password_field")
            .performTextInput("password123")

        composeTestRule.onNodeWithText("Login")
            .performClick()

        // Verify navigation occurred
        assertEquals("home_route", navController.currentBackStackEntry?.destination?.route)
    }
}

State Restoration Testing

عند تغيير إعدادات الجهاز (مثل تدوير الشاشة Screen Rotation)، يجب أن يحتفظ Compose UI بحالته. يوفر StateRestorationTester أداة لمحاكاة هذه العملية في الاختبارات. 

@Test
fun `should restore state after configuration change`() {
    val restorationTester = StateRestorationTester(composeTestRule)

    restorationTester.setContent { CounterScreen() }

    // Increment counter
    composeTestRule.onNodeWithText("+").performClick()
    composeTestRule.onNodeWithText("Count: 1").assertIsDisplayed()

    // Simulate configuration change
    restorationTester.emulateSavedInstanceStateRestore()

    // Verify state persisted
    composeTestRule.onNodeWithText("Count: 1").assertIsDisplayed()
}

تقنيات الاختبار المتقدمة (Advanced Testing Paradigms)

Robolectric — اختبارات Android على JVM

Robolectric يسمح بتشغيل اختبارات تعتمد على Android Framework APIs مباشرة على JVM دون الحاجة إلى Emulator أو جهاز حقيقي. هذا يُسرع الاختبارات بشكل كبير، لكنه قد يفتقر إلى بعض الدقة (Fidelity) مقارنةً بالأجهزة الحقيقية. 

@RunWith(RobolectricTestRunner::class)
@Config(sdk = [33], manifest = Config.NONE)
class MainActivityTest {

    @Test
    fun `should show correct title`() {
        val activity = Robolectric.buildActivity(MainActivity::class.java)
            .create()
            .resume()
            .get()

        val title = activity.findViewById<TextView>(R.id.title)
        assertEquals("Welcome", title.text)
    }
}
⚡

Speed

تشغيل على JVM بدون Emulator. اختبارات أسرع بمئات المرات مقارنةً بـ Instrumented Tests.

⚠️

Fidelity

قد تختلف سلوكيات Robolectric قليلاً عن الجهاز الحقيقي. استخدمه للاختبارات السريعة، وتحقق من السلوكيات الحرجة على أجهزة حقيقية.

Hilt in Integration Tests

عند اختبار المكونات التي تستخدم Hilt للحقن، يمكنك استبدال الوحدات (Modules) باختباراتها باستخدام @UninstallModules و @BindValue. 

@HiltAndroidTest
class ProfileFragmentTest {

    @get:Rule
    val hiltRule = HiltAndroidRule(this)

    @get:Rule
    val composeTestRule = createAndroidComposeRule<MainActivity>()

    @BindValue
    @JvmField
    val fakeRepository: UserRepository = FakeUserRepository()

    @Test
    fun `should display user profile`() {
        fakeRepository.setUser(User("1", "Ahmed"))

        composeTestRule.onNodeWithText("Ahmed")
            .assertIsDisplayed()
    }
}

Screenshot Testing — Roborazzi & Paparazzi

اختبار لقطات الشاشة (Screenshot Testing) يُكتشف تغييرات واجهة المستخدم على مستوى البكسل (Pixel-Level). أدوات حديثة مثل Roborazzi و Paparazzi تُبسط هذه العملية بشكل كبير.

📸

Roborazzi

يعمل مع Compose Test Rule و Robolectric. يلتقط لقطات من الاختبارات البرمجية ويقارنها مع المرجع (Reference).

Test Driven Development (TDD) Workflow

TDD هو نهج تطوير يعتمد على كتابة الاختبار أولاً قبل كتابة الكود الإنتاجي. يتبع دورة Red-Green-Refactor.

🔴

Red

اكتب اختباراً يفشل (Failing Test) يُحدد السلوك المطلوب. يجب أن يفشل لأن الكود غير موجود بعد.

🟢

Green

اكتب أقل كود ممكن لإجبار الاختبار على النجاح (Pass). لا تُبالغ في التصميم.

🔵

Refactor

حسّن الكود مع الحفاظ على اجتياز الاختبارات. أعد تسمية المتغيرات، واستخرج الدوال، وحسّن الأداء.

Flaky Tests Mitigation

الاختبارات غير المستقرة (Flaky Tests) هي التي تنجح أحياناً وتفشل أحياناً دون تغيير في الكود. إنها عدو الاعتمادية (Reliability) في CI/CD.

  • عزل التبعيات الخارجية: استخدم Fake Implementations بدلاً من Network/Database الحقيقية.
  • تجنب Race Conditions: استخدم IdlingResource في UI Tests و TestDispatcher في Unit Tests.
  • تجنب الاعتماد على الوقت: لا تستخدم Thread.sleep() أبداً. استخدم آليات التزامن (Synchronization) بدلاً منها.
  • تجنب Shared State: كل اختبار يجب أن يكون مستقلاً تماماً. لا تشارك Mutable State بين الاختبارات.
  • Retry Mechanism: في CI، يمكن تفعيل إعادة تشغيل الاختبارات الفاشلة مرة واحدة فقط للتمييز بين Flakiness و Failures الحقيقية.

قياس التغطية والـ CI/CD (Code Coverage & CI Integration)

Code Coverage Tools: Jacoco vs Kover

قياس تغطية الكود (Code Coverage) يُظهر النسبة المئوية من الكود الذي يتم اختباره. يُعد مؤشراً مفيداً لكنه ليس المقياس الوحيد لجودة الاختبارات.

المعيار Jacoco Kover
اللغة Java-first، يدعم Kotlin عبر Agent Kotlin-native، مُصمم خصيصاً لـ Kotlin
Compose Coverage دعم محدود لـ Composable Functions دعم ممتاز لـ Compose و Inline Functions
Gradle Integration Plugin تقليدي Plugin رسمي من JetBrains
HTML Reports ✅ متاح ✅ متاح مع تنسيق XML/IC
Line vs Branch Coverage يدعم Line و Branch و Instruction يدعم Line و Branch و Declaration 
// build.gradle.kts — Kover setup
plugins {
    id("org.jetbrains.kotlinx.kover") version "0.7.0"
}

kover {
    reports {
        total {
            xml { onCheck = true }
            html { onCheck = true }
        }
    }
}

// Set minimum coverage threshold
kover {
    verify {
        rule("Minimum Line Coverage") {
            bound {
                minValue = 80
                metric = MetricType.LINE
            }
        }
    }
}

CI/CD Integration

يجب أن يتم تشغيل الاختبارات تلقائياً عند كل Pull Request. يوفر GitHub Actions و GitLab CI pipelines آليات قوية لذلك. 

// .github/workflows/android-test.yml
name: Android Tests

on: [push, pull_request]

jobs:
  unit-tests:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Set up JDK 17
        uses: actions/setup-java@v4
        with:
          java-version: '17'
          distribution: 'temurin'
      - name: Run Unit Tests
        run: ./gradlew testDebugUnitTest
      - name: Generate Coverage Report
        run: ./gradlew koverXmlReport
      - name: Upload Coverage
        uses: codecov/codecov-action@v3
        with:
          files: build/reports/kover/report.xml

  instrumentation-tests:
    runs-on: macos-latest
    steps:
      - uses: actions/checkout@v4
      - name: Run Instrumented Tests
        uses: reactivecircus/android-emulator-runner@v2
        with:
          api-level: 33
          script: ./gradlew connectedCheck
🚀
أفضل ممارسة CI

افصل Unit Tests (سريعة) عن Instrumented Tests (بطيئة) في Pipeline منفصلة. اجعل Unit Tests شرطاً إلزامياً (Required) لدمج PR، بينما اجعل Instrumented Tests اختيارية أو تتم في الليل (Nightly Builds).

Test Reporting & Thresholds

يجب أن يتضمن كل Pull Request تقريراً واضحاً بتغطية الكود. يمكن استخدام أدوات مثل Codecov أو SonarQube لعرض التغطية بشكل مرئي ومنع دمج PRs التي تقل تغطيتها عن الحد الأدنى.

  • الحد الأدنى العام: 70-80% Line Coverage كهدف أولي.
  • Branch Coverage: لا تقل عن 60% للتأكد من اختبار جميع مسارات الشرط (Condition Paths).
  • Diff Coverage: يجب أن تغطي كل PR 100% من الأسطر المُضافة (New Lines).
  • Fail on Drop: إذا انخفضت التغطية عن PR السابق، يجب منع الدمج.

توجيهات معمارية Senior QA / Architecture

اختبر السلوك، لا التفاصيل التنفيذية (Test Behavior, Not Implementation Details).

الاختبارات التي تتحقق من كيفية عمل الكود (How) بدلاً من ما يفعله (What) تصبح هشة (Brittle) بسرعة. عند إعادة هيكلة الكود (Refactoring)، يجب ألا تفشل الاختبارات ما دام السلوك الخارجي لم يتغير.

  • تجنب التحقق من استدعاءات الطرق الداخلية (Private Methods) — اختبر الواجهة العامة (Public API).
  • استخدم Fakes في طبقة البيانات و Mocks في طبقة Presentation.
  • اجعل أسماء الاختبارات وصفية: shouldDoSomethingWhenCondition.
  • اتبع ترتيب Given-When-Then في كل اختبار لزيادة القراءة.
  • لا تختبر Framework Code — لا تختبر Retrofit أو Room أو Hilt نفسها.
