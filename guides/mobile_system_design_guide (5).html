ما هو تصميم أنظمة الهواتف؟

What is Mobile System Design?
🎯
تعريف System Design ببساطة

System Design هو فن وعلم بناء الأنظمة البرمجية القادرة على التعامل مع متطلبات العمل (Functional Requirements) وقيود التشغيل (Non-Functional Requirements) بكفاءة. في سياق Mobile System Design، نركز على تصميم تطبيقات العميل (Client-Side Applications) التي تعمل على أجهزة المستخدم النهائي، مقابل Backend System Design الذي يهتم ببناء الخوادم والخدمات السحابية (Server-Side Monoliths/Microservices).

الفرق الجوهري: Backend يتحكم في البيئة (Environment) بالكامل — يمكنك إضافة خوادم، تحديث الـ OS، وتحسين الشبكة. أما Mobile فأنت تُرسل كود إلى "جهاز غريب" لا تملكه، لا تتحكم في موارده، ولا تعرف حالته.
💼
لماذا تسأل الشركات الكبرى أسئلة System Design؟

عند تقييم مرشحين لمناصب Senior/Staff Engineer، لا يبحث المقابلون عن إجابة "صحيحة" واحدة، بل عن طريقة تفكير منظمة. إليك ما يتم تقييمه فعلياً:

1
Scalability Thinking

قدرة المهندس على التفكير في النمو — ماذا يحدث عندما يصبح التطبيق لديه مليون مستخدم؟ عشرة ملايين؟

2
Trade-offs Analysis

هل يستطيع المرشح توضيح التضحيات (Trade-offs) بين السرعة والموثوقية، أو بين الذاكرة والشبكة؟

3
Edge-Case Handling

كيف يتعامل النظام مع السيناريوهات النادرة؟ انقطاع الشبكة، نفاد البطارية، أو قتل النظام للتطبيق؟

4
Systems Thinking

رؤية النظام ككل متكامل — ليس فقط كود، بل بيانات، شبكة، أجهزة، وسياسات أمنية.

مصفوفة البروتوكولات — APIs & Protocols Matrix

اختيار البروتوكول المناسب هو قرار معماري حاسم. لا يوجد "أفضل" بروتوكول مطلق — كل بروتوكول له سياق استخدامه الأمثل:

REST

When to use:

  • عمليات CRUD بسيطة
  • Caching عبر HTTP (Cache-Control, ETag)
  • APIs عامة وثابتة
  • Debugging سهل عبر cURL/Postman
GET / POST / PUT / DELETE HTTP Caching Stateless
GraphQL

When to use:

  • منع Over-fetching / Under-fetching
  • شاشات ديناميكية متعددة البيانات
  • Mobile Apps مع بيانات معقدة ومتداخلة
  • Product Catalogs، Social Feeds
Single Endpoint Type Safety Apollo Client
WebSocket / SSE

When to use:

  • Real-time feeds (Chat, Notifications)
  • Live tracking (Maps, Delivery apps)
  • Collaborative editing
  • Live sports scores
Bidirectional Persistent Connection Low Latency
gRPC

When to use:

  • Binary serialization (Protobuf)
  • High throughput microservices
  • Service-to-service communication
  • Low latency internal APIs
HTTP/2 Streaming Strongly Typed

🔋 تأثير حجم البيانات على البطارية

⚠️ JSON vs Protobuf

JSON: Text-based، حجم أكبر (+30-50%)، parsing أبطأ، Battery drain أعلى.

Protobuf: Binary، حجم أصغر، parsing أسرع 5-10x، Battery أكثر كفاءة.

📉 Payload Size Impact:
كل 1KB إضافي في الـ Response يستهلك طاقة راديو إضافية. في 3G، الـ Tail Latency (~10s) يعني أن الراديو يبقى نشطاً بعد انتهاء الطلب!
⚡
التنفيذ المتزامن vs. غير المتزامن — Synchronous vs. Asynchronous Execution
🚫 Main Thread Freezing (ANR)

أي عملية ثقيلة على Main/UI Thread تتجاوز 5 ثوانٍ تؤدي إلى ANR (Application Not Responding). الحلول:

  • Thread Pools (Coroutine Dispatchers، GCD Queues)
  • Non-blocking I/O (Kotlin Coroutines، Swift async/await)
  • WorkManager / Background Tasks
Kotlin Coroutines Example 
// ❌ BAD: Blocking the Main Thread
val data = api.fetchData() // ANR Risk!

// ✅ GOOD: Offload to IO Dispatcher
lifecycleScope.launch(Dispatchers.IO) {
    val data = api.fetchData()
    withContext(Dispatchers.Main) {
        uiState.update { data }
    }
}

// ✅ BETTER: Reactive Streams with Flow
viewModelScope.launch {
    repository.getDataStream()
        .flowOn(Dispatchers.IO)
        .collect { data ->
            _uiState.value = data
        }
}

قابلية التوسع على جانب العميل — Scalability on the Client Side

Scalability في Mobile لا تعني "إضافة خوادم" — بل تعني قدرة الكود على النمو دون أن ينهار تحت ضغط الميزات والبيانات:

1
Codebase Scale

Modularization — فصل التطبيق إلى Feature Modules مستقلة. Dynamic Delivery لتقليل حجم الـ APK.

2
Feature Modularization

Plugin Architecture، Feature Flags، A/B Testing Frameworks. كل ميزة يمكن تفعيلها/تعطيلها دون إعادة بناء.

3
Heavy Data Volume

Pagination (Offset vs Cursor)، Lazy Loading، Image Compression، Delta Sync بدلاً من Full Sync.

4
Form Factor Adaptation

Responsive Layouts، Foldable Support، Tablet Optimization، Multi-window Mode.

قيود وبيئة عمل الهواتف الخاصة

Mobile-Specific Constraints
🔧
اختناقات العتاد — Hardware Bottlenecks
🔋 Limited Battery — البطارية المحدودة

الراديو اللاسلكي (Cellular Radio) هو أكبر مستهلك للبطارية. فهم حالاته ضروري:

Radio Stateالحالةاستهلاك البطارية
Full Power نقل البيانات بنشاط عالي جداً
Low Power انتظار (Idle) مع اتصال متوسط
Standby غير متصل منخفض

Doze Mode: Android يعلق الوصول إلى الشبكة عندما يكون الجهاز ساكناً وغير موصول بالشاحن.
App Standby: تقييد التطبيقات غير المستخدمة بشكل متكرر.
Wakelocks: تجنب الاحتفاظ بالجهاز مستيقظاً دون داعٍ.

🧠 Memory Constraints — قيود الذاكرة

الهواتف لديها ذاكرة محدودة، والـ OS يقتل التطبيقات عند الضغط:

  • Out of Memory (OOM): تخصيص Bitmap كبير بدون downsample
  • GC Pauses: Garbage Collection يتسبب في Jank (تقطيع UI)
  • Large Heap: يمكن طلبه لكنه يؤثر على Multitasking
  • Memory Leaks: Activity/Fragment references في Listeners
💡 نصيحة: استخدم inSampleSize للصور، WeakReference للـ Callbacks، و onTrimMemory() لتحرير الموارد.
🌡️ CPU & Thermal Throttling — خنق الحرارة

عندما يسخن الجهاز (Gaming، Video processing)، يقلل الـ OS سرعة الـ CPU (Thermal Throttling). هذا يعني:

  • Background tasks تُعلق أو تُؤجل
  • Heavy computation يجب نقله إلى Background Thread أو Cloud
  • تجنب العمليات الحسابية المستمرة في Foreground
💾 Local Storage Limits — قيود التخزين المحلي

التخزين على الهاتف محدود ومشترك بين جميع التطبيقات. استراتيجيات الإدارة:

  • LRU Cache: إزالة أقل البيانات استخداماً
  • Cache Eviction: سياسات مسح ذكية (TTL, Size-based)
  • Disk Space Monitoring: التحقق من المساحة المتوفرة قبل التخزين
  • Encrypted Storage: DataStore / Keychain للبيانات الحساسة
📶
الشبكات غير الموثوقة — Unreliable Networks

تطبيقك سيعمل على 2G في المصعد، و 5G في المنزل، و Wi-Fi ضعيف في المقهى. التصميم يجب أن يتكيف مع كل هذه الحالات:

🔄 التبديل بين الشبكات

[Wi-Fi Connected] ───► High Quality Images │ │ User enters elevator ▼ [Wi-Fi Lost] ───► Queue Requests │ ▼ [4G/5G Available] ───► Resume Sync │ │ Signal drops to 2G ▼ [2G/Edge] ───► Low-res Images, Batch Requests │ │ No signal at all ▼ [Offline Mode] ───► Local DB + Queue + Retry

🏗️ استراتيجيات Offline-First Architecture

📦 Queue-Based Sync

تخزين العمليات (Create/Update/Delete) في Queue محلي وتنفيذها عند عودة الشبكة.

⚡ Optimistic UI

عرض التغييرات فوراً على UI قبل تأكيد الخادم، مع إمكانية Rollback عند الفشل.

🔄 Conflict Resolution

استخدام Timestamps (Last-Write-Wins) أو Operational Transform (OT) للبيانات المتزامنة.

آليات دورة حياة التطبيق — App Lifecycle Mechanics

📱 Android Lifecycle States

┌─────────────────────────────────────────────┐ │ ANDROID ACTIVITY LIFECYCLE │ └─────────────────────────────────────────────┘ [Created] ──onStart()──► [Started] │ ──onResume()──► [Resumed] ◄── User Interacting │ ──onPause()──► [Paused] ◄── Partially Visible │ ──onStop()──► [Stopped] ◄── Background │ ──onDestroy()──► [Destroyed] ◄── Killed by OS ⚠️ onSaveInstanceState() → Save UI state before destruction

🍎 iOS Lifecycle States

┌─────────────────────────────────────────────┐ │ iOS APP LIFECYCLE │ └─────────────────────────────────────────────┘ [Not Running] ──launch──► [Inactive] │ ──didBecomeActive──► [Active] ◄── Foreground │ ──willResignActive──► [Inactive] │ ──didEnterBackground──► [Background] │ ──system kills──► [Suspended] ◄── No code execution ⚠️ applicationDidEnterBackground() → Save critical state
⚠️ Process Death / Killed by OS — القتل بواسطة النظام

عندما يكون الجهاز منخفض الذاكرة، يقتل الـ OS التطبيقات في الخلفية دون سابق إنذار. لا يمكنك منع هذا — لكن يمكنك التعافي منه:

State Restoration Strategies:
  • SavedInstanceState: Bundle صغير (< 1MB) للبيانات البسيطة
  • Local DB: Room / Core Data للبيانات المعقدة
  • SharedPreferences / DataStore: الإعدادات والتفضيلات
Graceful Recovery:
  • استعادة الـ Navigation Stack من الـ DB
  • إعادة تحميل البيانات من Cache
  • عرض Splash/Loading screen أثناء الاستعادة
  • تجنب Crash loops عند البيانات الفاسدة

لماذا تصميم Mobile مختلف جوهرياً عن Backend؟

Mobile System Design يمثل تحولاً نموذجياً (Paradigm Shift) في التفكير الهندسي. الفروقات ليست تقنية فقط، بل فلسفية:

!
Uncontrollable Environment

لا تملك الجهاز، لا تملك الـ OS، لا تملك الشبكة. أنت "ضيف" على جهاز المستخدم.

!
User-Driven UI Thread

المستخدم يتوقع استجابة فورية. أي تأخير > 16ms يُدرك كـ "بطء".

!
Offline is the Default

في Backend، Offline = خطأ. في Mobile، Offline = حالة طبيعية يجب التصميم لها.

!
Hardware Diversity

آلاف الأجهزة، أحجام شاشات مختلفة، إصدارات OS متفرقة، قدرات معالجة متباينة.

خطة مقابلة System Design للموبايل — 45 دقيقة

45-Minute Mobile System Design Interview Structure
🎯
Senior Mobile Architect Interview Tips

في مقابلة Mobile System Design لمدة 45 دقيقة، الهدف ليس إكمال التصميم، بل إظهار طريقة تفكير منظمة. اتبع هذا الإطار الزمني:

0:00 → 0:10 (10 دقائق)
1. Clarification — توضيح المتطلبات

لا تبدأ بالحل! اسأل أولاً: DAU/MAU؟ Offline support؟ Target platforms (Android/iOS/Both)؟ Real-time requirements؟ Data sensitivity (GDPR/PII)؟ اكتب المتطلبات Functional و Non-Functional على السبورة.

0:10 → 0:20 (10 دقائق)
2. High-Level Architecture — البنية المعمارية العليا

ارسم Data Flow Diagram: Mobile App → API Gateway → Backend Services → DB. حدد Client-Server Boundaries، اختر البروتوكول (REST/GraphQL/WebSocket)، وحدد Caching Strategy (Memory → Disk → Network).

0:20 → 0:35 (15 دقيقة)
3. Deep-Dives — الغوص في التفاصيل

اختر 2-3 مجالات للتعمق: Offline-First Sync (Queue + Conflict Resolution)، State Management (MVI + Unidirectional Data Flow)، Image Loading Pipeline (Downsample + Cache + Cancel). اشرح الـ Trade-offs بوضوح.

0:35 → 0:45 (10 دقائق)
4. Edge Cases & Bottlenecks — الحالات الطرفية

ناقش: ماذا يحدث عند Process Death؟ كيف تتعامل مع Network Switching (WiFi → 2G)؟ ما هي Battery implications للـ Sync strategy؟ كيف تضمن Data consistency عند الـ Offline mode؟ اختتم بـ Summary واضح.

✅ DO — افعل
  • اسأل عن المتطلبات قبل الحل
  • فكر بصوت عالٍ (Think Aloud)
  • ناقش Trade-offs لكل قرار
  • استخدم أرقام (Latency, Size, Count)
  • اختر بروتوكول وبرر اختيارك
❌ DON'T — لا تفعل
  • لا تبدأ بالكود مباشرة
  • لا تتجاهل قيود Mobile (Battery, Memory)
  • لا تفترض شبكة مثالية
  • لا تنسى Offline mode
  • لا تتردد في طلب توضيح
💡 KEY PHRASES — عبارات مفتاحية
  • "Let me clarify the requirements first..."
  • "The trade-off here is..."
  • "For mobile, we need to consider battery..."
  • "In the offline scenario..."
  • "Let me quantify that..."

🚀 استمر في التعلم

هذا الدليل هو الجزء الأول من سلسلة Mobile System Design. استمر في التعمق في كل موضوع، وبنِ تطبيقات تجريبية لتطبيق هذه المفاهيم عملياً. التصميم الجيد ليس معرفة — بل ممارسة.
