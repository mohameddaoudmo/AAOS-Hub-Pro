نظرة عامة على المرجع

يُعدّ فهم خدمات النظام (System Services) في Android Framework من أهم الركائز التي يجب على أي مطوّر نظام (System Developer) أو مهندس إطار عمل (Framework Engineer) إتقانها. هذه الخدمات هي العمود الفقري الذي ترتكز عليه جميع وظائف النظام — من إدارة الطاقة والبطارية، إلى إدارة النافذة والعرض، مرورًا بالشبكات والاتصال.

في هذا المرجع الشامل، سنقوم بتتبع الرحلة الكاملة لخدمة النظام بدءًا من لحظة إقلاع الجهاز (Boot Sequence)، مرورًا بتسجيلها في ServiceManager، وانتهاءً بكيفية وصول التطبيقات إليها عبر Context.getSystemService().

🎯 الأهداف التعليمية لهذا المرجع
  • فهم تسلسل الإقلاع الكامل: Init → Zygote → SystemServer
  • إتقان ميكانيكية ServiceManager كسجلّ عالمي (Global Registry) لخدمات Binder
  • تحليل دورة حياة SystemService ومراحل الإقلاع (Boot Phases)
  • تتبع end-to-end لـ BatteryService كنموذج واقعي
  • فهم نمط Manager Pattern من جانب التطبيق
  • تعلم أفضل الممارسات لإضافة خدمة نظام مخصصة في AOSP

تسلسل الإقلاع وبنية SystemServer

١.١ نظرة شاملة على عملية إقلاع Android

عند الضغط على زر التشغيل، تبدأ رحلة معقّدة تمر بعدة طبقات برمجية وعتادية. يُعدّ تسلسل الإقلاع في Android فريدًا من نوعه لأنه يجمع بين نواة Linux التقليدية وآلية Java Runtime المخصصة.

١.٢ دور SystemServer.java كقلب الإطار

يقع الملف SystemServer.java في المسار frameworks/base/services/java/com/android/server/SystemServer.java وهو النقطة المحورية التي تبدأ منها معظم خدمات النظام. يعمل SystemServer في عملية منفصلة تُسمى system_server تحمل UID 1000 (SYSTEM_UID).

لماذا SystemServer منفصل عن Zygote؟
يتم فصل system_server عن Zygote لأسباب أمنية واستقرارية: إذا تعطّلت إحدى خدمات النظام، فإن عملية system_server قد تُعاد تشغيلها دون الحاجة إلى إعادة إطلاق Zygote بأكمله — مما يحافظ على استقرار التطبيقات العاملة.

١.٣ الفئات الثلاث لخدمات النظام

داخل دالة run() في SystemServer.java، يتم بدء الخدمات في ثلاث فئات رئيسية، كل منها يخدم غرضًا محددًا في تسلسل الإقلاع:

الفئة الغرض أمثلة الأولوية
Bootstrap Services خدمات أساسية لا يمكن للنظام العمل بدونها. يجب أن تبدأ قبل أي خدمة أخرى. ActivityManagerService, PowerManagerService, PackageManagerService, DisplayManagerService عالية جدًا
Core Services خدمات أساسية للوظائف الأساسية للنظام، تعتمد على Bootstrap Services. BatteryService, UsageStatsService, WebViewUpdateService عالية
Other Services خدمات إضافية توفّر وظائف متخصصة، تعتمد على الخدمات الأساسية. CameraService, AlarmManagerService, InputManagerService, VibratorService متوسطة 
// frameworks/base/services/java/com/android/server/SystemServer.java
public final class SystemServer {

    private SystemServiceManager mSystemServiceManager;

    public static void main(String[] args) {
        new SystemServer().run();
    }

    private void run() {
        // 1. إنشاء SystemServiceManager — المدير الرئيسي لدورة حياة الخدمات
        mSystemServiceManager = new SystemServiceManager(mSystemContext);
        LocalServices.addService(SystemServiceManager.class, mSystemServiceManager);

        // ───────────────────────────────────────────────
        // الفئة الأولى: Bootstrap Services
        // ───────────────────────────────────────────────
        Installer installer = mSystemServiceManager.startService(Installer.class);
        mSystemServiceManager.startService(ActivityManagerService.Lifecycle.class);
        mSystemServiceManager.startService(PowerManagerService.class);
        mSystemServiceManager.startService(LightsService.class);
        mSystemServiceManager.startService(DisplayManagerService.class);

        // ───────────────────────────────────────────────
        // الفئة الثانية: Core Services
        // ───────────────────────────────────────────────
        mSystemServiceManager.startService(BatteryService.class);
        mSystemServiceManager.startService(UsageStatsService.class);
        mSystemServiceManager.startService(WebViewUpdateService.class);

        // ───────────────────────────────────────────────
        // الفئة الثالثة: Other Services
        // ───────────────────────────────────────────────
        mSystemServiceManager.startService(CameraService.class);
        mSystemServiceManager.startService(AlarmManagerService.class);
        // ... ~90 خدمة إضافية
    }
}
💡 رؤية معمارية: لماذا ثلاث فئات؟

التقسيم إلى ثلاث فئات ليس عشوائيًا — فهو يعكس التبعيات (Dependencies) بين الخدمات. على سبيل المثال، BatteryService (Core) يحتاج إلى ActivityManagerService (Bootstrap) لإرسال broadcast عند تغيّر مستوى الشحن. وCameraService (Other) يحتاج إلى BatteryService لمعرفة ما إذا كان مستوى البطارية منخفضًا جدًا.

٢

ميكانيكية عمل ServiceManager

٢.١ ما هو ServiceManager؟

ServiceManager هو سجلّ Binder العالمي (Global Binder Registry) — يُشبه "نظام DNS" للإطار. عندما تُسجّل خدمة نظام نفسها، فإنها تُضيف واجهة Binder الخاصة بها إلى هذا السجلّ تحت اسم فريد (مثل "battery" أو "power"). عندما يحتاج تطبيق أو خدمة أخرى إلى التواصل مع تلك الخدمة، فإنه يبحث عنها في ServiceManager ليحصل على وكيل Binder (Binder Proxy).

٢.٢ تسجيل الخدمة: addService()

عندما تستدعي خدمة النظام publishBinderService() (من الفئة الأساسية SystemService)، فإنها في الواقع تستدعي ServiceManager.addService() لتسجيل واجهة Binder الخاصة بها. 

// frameworks/base/core/java/android/os/ServiceManager.java
public final class ServiceManager {

    private static IServiceManager sServiceManager;

    /**
     * تسجيل خدمة Binder في السجلّ العالمي.
     * @param name اسم الخدمة الفريد (مثل "battery", "power")
     * @param service واجهة Binder التي تُنفّذ الخدمة
     */
    public static void addService(String name, IBinder service) {
        try {
            IServiceManager sm = getIServiceManager();
            sm.addService(name, service, false /* allowIsolated */);
        } catch (RemoteException e) {
            Log.e(TAG, "error in addService", e);
        }
    }

    /**
     * البحث عن خدمة Binder في السجلّ العالمي.
     * @param name اسم الخدمة المطلوبة
     * @return وكيل Binder (Binder Proxy) أو null إذا لم تُوجد
     */
    public static IBinder getService(String name) {
        try {
            IServiceManager sm = getIServiceManager();
            return sm.getService(name);
        } catch (RemoteException e) {
            Log.e(TAG, "error in getService", e);
            return null;
        }
    }
}

٢.٣ استرجاع الخدمة: getService()

من جانب التطبيق، عند استدعاء Context.getSystemService(Context.BATTERY_SERVICE)، فإن السلسلة تمر بعدة طبقات حتى تصل إلى ServiceManager.getService("battery"):

1
Context.getSystemService(String name)
تُستدعى من التطبيق — تبحث في SystemServiceRegistry عن المدير (Manager) المقابل.
2
SystemServiceRegistry.getSystemService()
يُرجع كائن Manager (مثل BatteryManager) مُغلّفًا لوكيل Binder.
3
ServiceManager.getService("battery")
يُرجع IBinder proxy يشير إلى BatteryService العامل في system_server.
4
IBinder.transact()
يُرسل استدعاء IPC عبر Binder driver إلى system_server حيث يُنفّذ BatteryService العملية.

٢.٤ طبقة الأمان: SELinux Context

لا يمكن لأي عملية تسجيل خدمة في ServiceManager دون امتلاك السياق الأمني (SELinux Context) المناسب. يتم التحقق من ذلك في طبقة native عبر selinux_check_access(). 

// frameworks/native/cmds/servicemanager/ServiceManager.cpp
status_t ServiceManager::addService(const String16& name,
                                    const sp<IBinder>& service,
                                    bool allowIsolated,
                                    int dumpsysPriority) {
    // التحقق من SELinux context قبل السماح بالتسجيل
    const char* context = selinux_lookup(name.string());
    if (!selinux_check_access(getpidcon(), context, "add")) {
        return PERMISSION_DENIED;
    }

    AutoMutex _l(mLock);
    mNameToService[name] = service;
    return NO_ERROR;
}
⚠️ تحذير أمني

محاولة تسجيل خدمة باسم موجود مسبقًا (مثل "battery") من قِبل عملية غير موثوقة ستفشل بسبب فحص SELinux. فقط العمليات التي تحمل السياق u:r:system_server:s0 يمكنها تسجيل خدمات النظام الرئيسية.

دورة حياة خدمات النظام

٣.١ الفئة الأساسية: SystemService

جميع خدمات النظام في Android ترث من الفئة المجردة com.android.server.SystemService. هذه الفئة تُوفّر هيكلًا موحدًا لدورة الحياة، وتُتيح لـ SystemServiceManager إدارة جميع الخدمات بشكل متسق. 

// frameworks/base/services/core/java/com/android/server/SystemService.java
public abstract class SystemService {

    private final Context mContext;

    public SystemService(Context context) {
        mContext = context;
    }

    /**
     * يُستدعى مرة واحدة عند بدء الخدمة.
     * هنا يجب تسجيل الـ Binder interface في ServiceManager.
     */
    public abstract void onStart();

    /**
     * يُستدعى عند الوصول إلى مرحلة إقلاع معينة.
     * تُتيح للخدمة الاستجابة لأحداث مراحل الإقلاع المختلفة.
     */
    public void onBootPhase(int phase) {}

    /**
     * يُستدعى عندما يصبح مستخدم جديد نشطًا.
     */
    public void onUserStarting(int userId) {}

    /**
     * يُستدعى عند اكتمال بدء المستخدم.
     */
    public void onUserStarted(int userId) {}

    /**
     * يُستدعى عند توقف المستخدم.
     */
    public void onUserStopped(int userId) {}

    // ─── أدوات مساعدة محمية ───

    protected final void publishBinderService(String name, IBinder service) {
        ServiceManager.addService(name, service);
    }

    protected final IBinder getBinderService(String name) {
        return ServiceManager.getService(name);
    }
}

٣.٢ مراحل الإقلاع (Boot Phases)

تُعرّف الفئة SystemService ثوابتًا تمثّل مراحل الإقلاع المختلفة. يقوم SystemServiceManager بإشعار جميع الخدمات عند الوصول إلى كل مرحلة، مما يُتيح لها تهيئة المكونات التي تعتمد على خدمات أخرى.

PHASE_WAIT_FOR_DEFAULT_DISPLAY
تُشير إلى أن الشاشة الافتراضية جاهزة. الخدمات التي تعتمد على DisplayManager يمكنها البدء في هذه المرحلة.
PHASE_LOCK_SETTINGS_READY
إعدادات قفل الشاشة جاهزة. KeyguardManager والخدمات الأمنية تستجيب هنا.
PHASE_SYSTEM_SERVICES_READY
جميع خدمات النظام الأساسية قد بدأت. يمكن للخدمات الآن البحث عن خدمات أخرى بأمان.
PHASE_ACTIVITY_MANAGER_READY
ActivityManagerService جاهز. يمكن إرسال broadcasts وبدء الأنشطة.
PHASE_THIRD_PARTY_APPS_CAN_START
التطبيقات التابعة لجهات خارجية يمكنها البدء. الخدمات التي تتفاعل مع التطبيقات تستعد هنا.
PHASE_BOOT_COMPLETED
الإقلاع اكتمل بالكامل. جميع الخدمات يجب أن تكون جاهزة لاستقبال الطلبات من التطبيقات. 
// frameworks/base/services/core/java/com/android/server/SystemServiceManager.java
public class SystemServiceManager {

    private final ArrayList<SystemService> mServices = new ArrayList<>();

    public <T extends SystemService> T startService(Class<T> serviceClass) {
        try {
            Constructor<T> constructor = serviceClass.getConstructor(Context.class);
            T service = constructor.newInstance(mContext);
            mServices.add(service);
            service.onStart(); // ← استدعاء onStart()
            return service;
        } catch (Exception e) {
            throw new RuntimeException("Failed to create service " + serviceClass, e);
        }
    }

    public void startBootPhase(int phase) {
        for (SystemService service : mServices) {
            TimingsTraceAndSlog.traceBegin("OnBootPhase_" + phase
                + "_" + service.getClass().getName());
            try {
                service.onBootPhase(phase); // ← إشعار كل خدمة
            } catch (Exception ex) {
                Slog.wtf(TAG, "Failure passing boot phase " + phase
                    + " to " + service, ex);
            } finally {
                TimingsTraceAndSlog.traceEnd();
            }
        }
    }
}
🔧 لماذا Boot Phases مهمة جدًا؟

بدون مراحل الإقلاع، كانت الخدمات ستضطر إلى "الانتظار العشوائي" (busy-waiting) حتى تصبح الخدمات التي تعتمد عليها جاهزة. مراحل الإقلاع توفر آلية إشعار مركزية تضمن أن كل خدمة تبدأ عملها في الوقت الصحيح دون تبعيات دائرية أو سباقات (race conditions).

تتبع دورة حياة خدمة حقيقية: BatteryService

٤.١ لماذا BatteryService كنموذج؟

BatteryService خدمة مثالية للدراسة لأنها: (1) تتفاعل مباشرة مع طبقة HAL (Hardware Abstraction Layer)، (2) تُسجّل Binder interface، (3) تستجيب لمراحل الإقلاع، و(4) تُوفّر واجهة واضحة للتطبيقات عبر BatteryManager.

في الإصدارات الحديثة من AOSP، يتم استخدام mSystemServiceManager.startService(BatteryService.class) بدلاً من الإنشاء المباشر. هذا يضمن أن SystemServiceManager يتتبع دورة الحياة الكاملة للخدمة.

٤.٣ الخطوة 2: onStart() — تسجيل Binder Interface

عند استدعاء onStart()، تقوم BatteryService بإنشاء كائن BinderService داخلي (يُنفّذ واجهة IBatteryStats) وتسجيله في ServiceManager. 

// frameworks/base/services/core/java/com/android/server/BatteryService.java
public final class BatteryService extends SystemService {

    private final IBatteryStats mBatteryStats;
    private final BinderService mBinderService;

    public BatteryService(Context context) {
        super(context);
        mBatteryStats = BatteryStatsService.getService();
        mBinderService = new BinderService();

        // الاستماع إلى أحداث HAL عبر healthd
        initHealthInfo();
    }

    @Override
    public void onStart() {
        Slog.d(TAG, "Starting BatteryService...");

        // تسجيل BinderService في ServiceManager تحت الاسم "battery"
        publishBinderService(Context.BATTERY_SERVICE, mBinderService);

        // تسجيل مستقبل لأحداث البطارية من HAL
        registerHealthCallback();
    }

    // ─── الفئة الداخلية التي تُنفّذ واجهة Binder ───
    private final class BinderService extends IBatteryStats.Stub {

        @Override
        public int getBatteryLevel() {
            return mHealthInfo.batteryLevel;
        }

        @Override
        public boolean isCharging() {
            return mHealthInfo.batteryStatus == BatteryManager.BATTERY_STATUS_CHARGING;
        }

        @Override
        public void getBatteryState(BatteryState state) {
            synchronized (mLock) {
                state.set(mHealthInfo);
            }
        }
    }
}

٤.٤ الخطوة 3: الاستماع إلى أحداث العتاد (HAL Events)

BatteryService لا تستقبل أحداث البطارية مباشرة من النواة. بدلاً من ذلك، تستخدم Health HAL (Hardware Abstraction Layer) التي تُوفّر واجهة موحدة للتفاعل مع برامج تشغيل البطارية المختلفة. 

// BatteryService.java — تسجيل callback لأحداث HAL
private void registerHealthCallback() {
    try {
        IHealth healthService = IHealth.getService(true /* retry */);
        if (healthService != null) {
            healthService.registerCallback(new HealthCallback());
        }
    } catch (RemoteException e) {
        Slog.e(TAG, "Failed to register health callback", e);
    }
}

private final class HealthCallback extends IHealthInfoCallback.Stub {
    @Override
    public void healthInfoChanged(HealthInfo info) {
        synchronized (mLock) {
            mHealthInfo = info;
            processValuesLocked();
        }
    }
}

٤.٥ الخطوة 4: الاستجابة لمراحل الإقلاع onBootPhase()

عندما يصل SystemServiceManager إلى مرحلة PHASE_BOOT_COMPLETED، يتم إشعار BatteryService لإرسال broadcast أولي يُخبر التطبيقات بحالة البطارية الحالية. 

@Override
public void onBootPhase(int phase) {
    if (phase == PHASE_BOOT_COMPLETED) {
        Slog.d(TAG, "Boot completed — sending initial battery broadcast");

        synchronized (mLock) {
            // إرسال Intent.ACTION_BATTERY_CHANGED الأولي
            Intent intent = new Intent(Intent.ACTION_BATTERY_CHANGED);
            intent.addFlags(Intent.FLAG_RECEIVER_REGISTERED_ONLY
                | Intent.FLAG_RECEIVER_FOREGROUND);
            updateBatteryIntentLocked(intent);
            mContext.sendStickyBroadcastAsUser(intent, UserHandle.ALL);
        }
    }
}
أفضل الممارسات من BatteryService
  • استخدام synchronized blocks: جميع العمليات على mHealthInfo تتم داخل synchronized (mLock) لتجنب race conditions.
  • Sticky Broadcast: يستخدم ACTION_BATTERY_CHANGED sticky broadcast لضمان أن أي تطبيق يسجّل BroadcastReceiver يستلم آخر قيمة فورًا.
  • فصل Binder Interface: BinderService فئة داخلية منفصلة تُنفّذ واجهة AIDL — هذا يُبقي منطق الخدمة منفصلًا عن منطق IPC.

واجهة التطبيقات: نمط التغليف Manager Pattern

٥.١ لماذا لا يتعامل التطبيق مباشرة مع Binder؟

التطبيقات العادية لا يجب أن تتعامل مباشرة مع كائنات Binder الخام. بدلاً من ذلك، يوفر Android Framework طبقة تغليف (Wrapper Layer) تُسمى Managers — فئات في حزمة android.app تُبسّط الوصول إلى خدمات النظام.

٥.٢ تتبع Context.getSystemService()

عندما يستدعي التطبيق getSystemService(Context.BATTERY_SERVICE)، تبدأ رحلة تمر بعدة طبقات: 

// frameworks/base/core/java/android/app/ContextImpl.java
class ContextImpl extends Context {

    @Override
    public Object getSystemService(String name) {
        ServiceFetcher<?> fetcher = SystemServiceRegistry.getServiceFetcher(name);
        return fetcher != null ? fetcher.getService(this) : null;
    }
}

٥.٣ SystemServiceRegistry — مصنع المدراء

SystemServiceRegistry هو "مصنع" مركزي يُسجّل جميع المدراء (Managers) ويُدير تخزينهم المؤقت (Caching). يتم تسجيل كل خدمة عبر registerService() أثناء تحميل الفئة (static initializer). 

// frameworks/base/core/java/android/app/SystemServiceRegistry.java
final class SystemServiceRegistry {

    private static final Map<String, ServiceFetcher<?>> SYSTEM_SERVICE_FETCHERS =
        new ArrayMap<>();

    static {
        // ─── تسجيل BatteryManager ───
        registerService(Context.BATTERY_SERVICE, BatteryManager.class,
            new CachedServiceFetcher<BatteryManager>() {
                @Override
                public BatteryManager createService(ContextImpl ctx) {
                    return new BatteryManager();
                }
            });

        // ─── تسجيل PowerManager ───
        registerService(Context.POWER_SERVICE, PowerManager.class,
            new CachedServiceFetcher<PowerManager>() {
                @Override
                public PowerManager createService(ContextImpl ctx) {
                    IBinder b = ServiceManager.getService(Context.POWER_SERVICE);
                    IPowerManager service = IPowerManager.Stub.asInterface(b);
                    return new PowerManager(ctx.getOuterContext(), service,
                        ctx.getDisplayNoVerify(Display.DEFAULT_DISPLAY));
                }
            });

        // ... تسجيل ~50+ خدمة أخرى
    }

    private static <T> void registerService(String serviceName,
                                          Class<T> serviceClass,
                                          ServiceFetcher<T> serviceFetcher) {
        SYSTEM_SERVICE_NAMES.put(serviceClass, serviceName);
        SYSTEM_SERVICE_FETCHERS.put(serviceName, serviceFetcher);
    }
}

٥.٤ BatteryManager — المدير كوكيل (Proxy)

BatteryManager هو الفئة التي يتعامل معها المطوّرون مباشرة. هي تُغلّف الوصول إلى IBatteryStats Binder interface وتُوفّر واجهة Java نظيفة. 

// frameworks/base/core/java/android/os/BatteryManager.java
public class BatteryManager {

    public static final String EXTRA_LEVEL = "level";
    public static final String EXTRA_SCALE = "scale";
    public static final String EXTRA_STATUS = "status";

    public static final int BATTERY_PROPERTY_CAPACITY = 4;

    /**
     * يُرجع قيمة خاصية البطارية المطلوبة.
     * هذه الدالة تتواصل مع BatteryService عبر Binder IPC.
     */
    public int getIntProperty(int id) {
        try {
            return IBatteryStats.Stub.asInterface(
                ServiceManager.getService(Context.BATTERY_SERVICE)
            ).getIntProperty(id);
        } catch (RemoteException e) {
            return Integer.MIN_VALUE;
        }
    }

    /**
     * يُرجع نسبة الشحن الحالية (0-100).
     */
    public int getBatteryPercent() {
        return getIntProperty(BATTERY_PROPERTY_CAPACITY);
    }
}

٥.٥ آلية التخزين المؤقت (Caching)

SystemServiceRegistry يستخدم نمط CachedServiceFetcher لضمان أن كل Manager يُنشأ مرة واحدة فقط لكل Context، مما يُقلل من حمل إنشاء كائنات Binder proxy. 

// SystemServiceRegistry.java — آلية التخزين المؤقت
static abstract class CachedServiceFetcher<T> implements ServiceFetcher<T> {
    private final int mCacheIndex;

    CachedServiceFetcher() {
        mCacheIndex = sServiceCacheSize++;
    }

    @Override
    public final T getService(ContextImpl ctx) {
        final Object[] cache = ctx.getServiceCache();
        synchronized (cache) {
            Object service = cache[mCacheIndex];
            if (service == null) {
                service = createService(ctx); // ← إنشاء مرة واحدة فقط
                cache[mCacheIndex] = service;
            }
            return (T) service;
        }
    }

    public abstract T createService(ContextImpl ctx);
}
📊 أداء Manager Pattern

بدون التخزين المؤقت، كل استدعاء لـ getSystemService() سيُنشئ Binder proxy جديد — وهذا مكلف. بفضل CachedServiceFetcher، يتم إنشاء كل Manager مرة واحدة فقط لكل Context، مما يُقلل من:

  • حمل GC (Garbage Collection) بسبب إنشاء كائنات مؤقتة
  • استدعاءات IPC المتكررة إلى ServiceManager
  • استهلاك الذاكرة بسبب proxies مكررة

٦.١ الخطوات الكاملة لإضافة خدمة نظام مخصصة

إضافة خدمة نظام مخصصة في AOSP تتطلب تعديلات في عدة طبقات. فيما يلي الخطوات المنهجية:

1
تعريف واجهة AIDL
أنشئ ملف ICustomService.aidl في frameworks/base/core/java/android/os/ICustomService.aidl
2
كتابة خدمة النظام
أنشئ CustomService.java في frameworks/base/services/core/java/com/android/server/CustomService.java واجعلها ترث SystemService.
3
تسجيل الخدمة في SystemServer
أضف mSystemServiceManager.startService(CustomService.class) في SystemServer.run().
4
إنشاء Manager للتطبيقات
أنشئ CustomManager.java في frameworks/base/core/java/android/app/CustomManager.java تُغلّف الوصول إلى AIDL interface.
5
تسجيل Manager في SystemServiceRegistry
أضف registerService(Context.CUSTOM_SERVICE, CustomManager.class, ...) في SystemServiceRegistry.

// frameworks/base/services/core/java/com/android/server/CustomService.java
package com.android.server;

public class CustomService extends SystemService {

    private final BinderService mBinderService;
    private int mValue = 0;

    public CustomService(Context context) {
        super(context);
        mBinderService = new BinderService();
    }

    @Override
    public void onStart() {
        publishBinderService(Context.CUSTOM_SERVICE, mBinderService);
    }

    private final class BinderService extends ICustomService.Stub {
        @Override
        public int getCustomValue() {
            return mValue;
        }

        @Override
        public void setCustomValue(int value) {
            mValue = value;
        }
    }
}

الخطوة 3: Manager للتطبيقات

// frameworks/base/core/java/android/app/CustomManager.java
package android.app;

public class CustomManager {
    private final ICustomService mService;

    CustomManager(ICustomService service) {
        mService = service;
    }

    public int getValue() {
        try {
            return mService.getCustomValue();
        } catch (RemoteException e) {
            throw e.rethrowFromSystemServer();
        }
    }
}

٦.٣ قائمة مراجعة (Checklist) قبل الدمج

قائمة التحقق من جودة خدمة النظام
  • Thread Safety: هل جميع العمليات على الحالة المشتركة محمية بـ synchronized أو Locks؟
  • Deadlock Prevention: هل هناك تبعيات دائرية بين خدمات النظام؟
  • SELinux: هل تم تحديث سياسات SELinux للسماح بالتسجيل في ServiceManager؟
  • Permission Checks: هل تتحقق الخدمة من الأذونات (Permissions) قبل تنفيذ العمليات الحساسة؟
  • Memory Leaks: هل تُسجّل الخدمة BroadcastReceivers أو Listeners دون إلغاء تسجيلها؟
  • Boot Time: هل عملية onStart() خفيفة بما يكفي؟ (تجنب I/O_blocking في onStart)
  • RemoteException: هل يتم التعامل مع RemoteException في جميع استدعاءات Binder؟
⚠️ تحذيرات هامة
  • لا تُنفّذ I/O_blocking في onStart(): هذا سيُبطئ إقلاع النظام بأكمله. استخدم Threads أو Handlers للعمليات الثقيلة.
  • لا تفترض ترتيب بدء الخدمات: استخدم onBootPhase() بدلاً من الافتراض بأن خدمة أخرى قد بدأت.
  • اجتنب التبعيات الدائرية: إذا كانت الخدمة A تعتمد على B وB تعتمد على A، فسيتسبب ذلك في Deadlock.
