🔐1. هيكلية أمان أندرويد: DAC مقابل MAC

تعتمد أنظمة أندرويد الحديثة على نموذج أمان مزدوج يجمع بين آليتين أساسيتين: Discretionary Access Control (DAC) و Mandatory Access Control (MAC). يُعدّ فهم الفرق بينهما حجر الزاوية لأي مهندس نظام يعمل على مستوى AOSP.

1.1 التحكم التقديري بالوصول (DAC — Discretionary Access Control)

في أنظمة Linux التقليدية، يتحكم UID (User ID) و GID (Group ID) في صلاحيات الوصول إلى الملفات والموارد. يُطلق على هذا النموذج "تقديري" لأن مالك المورد (Owner) يملك صلاحية تعديل صلاحيات الوصول إليه باستخدام أوامر مثل chmod و chown.

┌─────────────────────────────────────────────────────────────┐ │ نموذج DAC التقليدي │ ├─────────────────────────────────────────────────────────────┤ │ │ │ ┌─────────────┐ ┌─────────────┐ │ │ │ Process │ │ File │ │ │ │ UID=1000 │────────▶│ UID=1000 │ │ │ │ (system) │ read │ mode=644 │ │ │ └─────────────┘ └─────────────┘ │ │ │ │ ┌─────────────┐ ┌─────────────┐ │ │ │ Process │ │ File │ │ │ │ UID=0 │────────▶│ UID=0 │ │ │ │ (root) │ ALL │ mode=600 │ │ │ └─────────────┘ └─────────────┘ │ │ │ │ ⚠️ المشكلة: إذا امتلكت صلاحية root، فأنت تملك كل شيء! │ │ │ └─────────────────────────────────────────────────────────────┘
⚠️ نقطة ضعف DAC: في نموذج DAC، إذا تمكن تطبيق أو خدمة ما من الحصول على صلاحيات root (مثلاً عبر ثغرة أمان)، فإنه يكتسب صلاحية غير محدودة على كامل موارد النظام. هذا يجعل النموذج غير كافٍ لأنظمة التشغيل الحديثة التي تتطلب عزلًا دقيقًا للموارد.

1.2 التحكم الإلزامي بالوصول (MAC — Mandatory Access Control)

لمعالجة قصور DAC، أُدخل SELinux (Security-Enhanced Linux) كطبقة MAC إضافية. في MAC، لا يقرر مالك المورد من يمكنه الوصول إليه، بل السياسة المركزية (Policy) هي التي تحدد ذلك بشكل إلزامي. حتى المستخدم root يخضع لقيود SELinux.

┌─────────────────────────────────────────────────────────────┐ │ نموذج MAC مع SELinux │ ├─────────────────────────────────────────────────────────────┤ │ │ │ ┌─────────────┐ ┌──────────────┐ ┌─────────────┐│ │ │ Process │ │ SELinux │ │ File ││ │ │ UID=0 │─────▶│ Policy │───▶│ u:object_r:││ │ │ (root) │ │ (MAC Layer) │ │ system_file:s0│ │ └─────────────┘ └──────────────┘ └─────────────┘│ │ │ ▲ │ │ │ │ │ │ └──────────────────────┘ │ │ يتم رفض الوصول إذا لم تُصرّح السياسة │ │ │ │ ✅ حتى root يخضع للقيود! لا يوجد "تجاوز" للسياسة │ │ │ └─────────────────────────────────────────────────────────────┘

1.3 أوضاع SELinux: Enforcing مقابل Permissive

يعمل SELinux في أحد الوضعين، ويمكن التبديل بينهما عبر أوامر setenforce و getenforce:

الوضع الوصف الأمر اللون
Enforcing يتم تطبيق السياسة بشكل فعلي ورفض أي وصول غير مصرّح به setenforce 1 ●
Permissive يتم تسجيل المخالفات فقط دون رفضها (مفيد للتصحيح) setenforce 0 ●
🚨 تحذير أمني: يجب ألا يُترك وضع Permissive في الأجهزة الإنتاجية (Production Devices). يُستخدم هذا الوضع حصريًا أثناء مرحلة التطوير والتصحيح (Debugging) لالتقاط سجلات avc: denied وتحليلها قبل توليد القواعد المناسبة. 
# التحقق من الوضع الحالي لـ SELinux
$ getenforce
Enforcing

# التبديل إلى وضع Permissive للتصحيح (مؤقتًا فقط)
$ setenforce 0

# العودة إلى وضع Enforcing
$ setenforce 1

# التحقق من سياق العملية الحالية
$ id -Z
u:r:shell:s0

⭐2. التطبيقات المُميزة (Privileged Apps) وتثبيتها في النظام

في هيكلية أندرويد، لا يتمتع جميع التطبيقات المثبتة في قسم /system بنفس المستوى من الصلاحيات. هناك تمييز حاسم بين التطبيقات العادية و التطبيقات المُميزة (Privileged Apps).

2.1 الفرق بين /system/app و /system/priv-app

المسار النوع الصلاحيات الاستخدام
/system/app Normal System App صلاحيات النظام العادية فقط تطبيقات النظام الأساسية (Calculator, Calendar)
/system/priv-app Privileged App صلاحيات signatureOrSystem المحمية تطبيقات النظام المتقدمة (Settings, SystemUI, TeleService)
💡 ملاحظة هندسية: التطبيقات المُميزة (Privileged Apps) هي التطبيقات الوحيدة التي يمكنها الحصول على أذونات signatureOrSystem دون توقيعها بمفتاح المنصة (Platform Key). هذا يمنحها وصولًا أعمق إلى واجهات برمجة النظام المحمية.

2.2 بناء Privileged App باستخدام Android.bp

لتحويل تطبيق إلى Privileged App في AOSP، يجب تعديل ملف Android.bp ليشمل الخصائص privileged: true و certificate: "platform":

// system/priv-app/MyPrivilegedApp/Android.bp
// ==========================================
// ملف بناء تطبيق مُميز (Privileged Application)
// يجب وضع هذا التطبيق في المسار: system/priv-app/MyPrivilegedApp/

android_app {
    name: "MyPrivilegedApp",

    // تمكين وضع التطبيق المُميز — إلزامي للوصول إلى signatureOrSystem
    privileged: true,

    // توقيع التطبيق بشهادة المنصة (Platform Certificate)
    // هذا يُمنحه معرف UID=1000 (system) ويُمكّنه من الوصول إلى APIs المحمية
    certificate: "platform",

    // مسار ملف AndroidManifest.xml
    manifest: "AndroidManifest.xml",

    // مصادر التطبيق
    srcs: ["src/**/*.java"],

    // الموارد
    resource_dirs: ["res"],

    // المكتبات المطلوبة
    libs: [
        "framework",
    ],

    // تحسين التطبيق
    optimize: {
        enabled: true,
        shrink: true,
    },
}

2.3 إلزامية ملف privapp-permissions.xml

بدءًا من Android 8.0 (Oreo)، فرضت Google شرطًا صارمًا: كل تطبيق مُميز يجب أن تكون أذوناته مدرجة في قائمة بيضاء (Whitelist) داخل ملف privapp-permissions.xml. إذا حاول تطبيق مُميز استخدام إذن signatureOrSystem دون وجوده في القائمة البيضاء، فإن النظام يرفض منحه الإذن، وقد يتسبب ذلك في حلقة إعادة تشغيل (Boot Loop) إذا كان التطبيق حيويًا.

<!-- system/etc/permissions/privapp-permissions.xml -->
<!-- ============================================== -->
<!-- قائمة الأذونات البيضاء للتطبيقات المُميزة       -->
<!-- يجب تضمين هذا الملف في build عبر Android.bp    -->

<?xml version="1.0" encoding="utf-8"?>
<permissions>

    <!-- تطبيقنا المُميز: MyPrivilegedApp -->
    <privapp-permissions package="com.example.myprivilegedapp">

        <!-- إذن الوصول إلى إعدادات النظام المحمية -->
        <permission name="android.permission.WRITE_SECURE_SETTINGS" />

        <!-- إذن إدارة الحزم -->
        <permission name="android.permission.INSTALL_PACKAGES" />

        <!-- إذن الوصول إلى شبكة الاتصال -->
        <permission name="android.permission.CONNECTIVITY_INTERNAL" />

        <!-- إذن إدارة الطاقة -->
        <permission name="android.permission.DEVICE_POWER" />

        <!-- إذن الوصول إلى إشعارات النظام -->
        <permission name="android.permission.MANAGE_NOTIFICATIONS" />

    </privapp-permissions>

</permissions>
🚨 تحذير حلقة الإقلاع (Boot Loop): إذا نسيت إضافة إذن signatureOrSystem إلى privapp-permissions.xml، وكان التطبيق المُميز يُنفّذ عملية حيوية أثناء الإقلاع (مثل SystemUI أو Telephony)، فسيحاول النظام تشغيله، ويفشل، ويعيد الإقلاع — مما يؤدي إلى حلقة إعادة تشغيل لا نهائية. تحقق دائمًا من اكتمال القائمة البيضاء قبل تثبيت النظام. 
// system/etc/permissions/Android.bp — تضمين ملف الأذونات
prebuilt_etc {
    name: "privapp-permissions-com.example.myprivilegedapp",
    src: "privapp-permissions.xml",
    sub_dir: "permissions",
    filename_from_src: true,
}

🛡️3. أساسيات SELinux وقواعد Type Enforcement (.te)

تُعدّ قواعد Type Enforcement (TE) جوهر سياسة SELinux. تستند هذه القواعد إلى مفهوم تسمية (Labeling) كل كيان في النظام (عملية، ملف، جهاز، مأخذ شبكة) بـ سياق أمان (Security Context) محدد.

3.1 فهم سياقات الأمان (Security Contexts)

كل كيان في النظام يحمل تسمية (Label) تتبع الصيغة التالية:

┌─────────────────────────────────────────────────────────────┐ │ بنية سياق الأمان (Security Context) │ ├─────────────────────────────────────────────────────────────┤ │ │ │ u:object_r:system_file:s0 │ │ │ │ │ │ │ │ │ │ │ └─ Range (مستوى MLS/MCS) │ │ │ │ └─ Type (النوع — الأهم في TE) │ │ │ └─ Role (الدور — غالبًا object_r للملفات) │ │ └─ User (المستخدم — غالبًا u) │ │ │ │ مثال على عملية (Process): │ │ u:r:system_server:s0 │ │ │ │ │ │ │ │ │ │ │ └─ Range │ │ │ │ └─ Domain (النطاق — للعمليات) │ │ │ └─ Role (الدور — غالبًا r للعمليات) │ │ └─ User │ │ │ └─────────────────────────────────────────────────────────────┘ 
# عرض سياقات الملفات في المسار الحالي
$ ls -Z
u:object_r:system_file:s0  init.rc
u:object_r:rootfs:s0       system

# عرض سياق العمليات الجارية
$ ps -Z
u:r:init:s0                    root     1     0  ... init
u:r:system_server:s0           system   1234  1   ... system_server
u:r:platform_app:s0:c512,c768  u0_a10   2345  1234 ... com.android.settings

3.2 تشريح قاعدة Type Enforcement (.te)

تتكون قاعدة TE الأساسية من أربعة عناصر رئيسية:

┌─────────────────────────────────────────────────────────────┐ │ تشريح قاعدة allow في SELinux │ ├─────────────────────────────────────────────────────────────┤ │ │ │ allow source_domain target_type : object_class { perms };│ │ │ │ │ │ │ │ │ │ │ │ │ │ │ │ │ │ │ │ │ │ │ │ └─ الفاصلة المنقوطة (إنهاء القاعدة)│ │ │ │ │ │ │ └─ قائمة الصلاحيات (read, write, open...)│ │ │ │ │ │ └─ فئة الكائن (file, dir, chr_file, socket...)│ │ │ │ │ └─ الفاصل الزمني (:) │ │ │ │ └─ النوع المستهدف (الملف/الجهاز) │ │ │ └─ نطاق المصدر (العملية/الخدمة) │ │ └─ الكلمة المحجوزة (allow أو dontaudit أو neverallow) │ │ │ │ مثال: │ │ allow system_server system_file:file { read write open }; │ │ │ └─────────────────────────────────────────────────────────────┘ 
# system/sepolicy/public/system_server.te (مقتطف)
# ============================================
# هذا الملف يحدد نطاق (Domain) خدمة النظام الرئيسية

# تعريف النطاق (Domain) لـ system_server
type system_server, domain;

# منح system_server صلاحية الوصول إلى ملفات النظام للقراءة
allow system_server system_file:file { read open getattr };

# منح system_server صلاحية الوصول إلى أجهزة العشوائية (random/urandom)
allow system_server random_device:chr_file { read write open };

# السماح لـ system_server بالانتقال (transition) إلى نطاقات أخرى
allow system_server app_domain:process { signal sigkill };

3.3 الفرق بين Domains و Types

المفهوم الاستخدام المثال الملف
Domain يُستخدم لتسمية العمليات (Processes) system_server, platform_app *.te
Type يُستخدم لتسمية الملفات والموارد الثابتة system_file, sysfs file.te, device.te
💡 ملاحظة تصميم: في AOSP، يتم تعريف Domains و Types في ملفات منفصلة ضمن system/sepolicy/. يُفضل فصل تعريفات الأنواع (Type Definitions) عن قواعد الوصول (Access Rules) لتحسين قابلية الصيانة وإعادة الاستخدام.

⚙️4. تطبيق عملي: كتابة سياسة SELinux لخدمة جديدة

في هذا القسم، سنطبق مفاهيم SELinux على سيناريو واقعي: لدينا خدمة أصلية (Native Service) تُسمى custom_hw_service تحتاج إلى الوصول لقراءة وكتابة جهاز محرف (Character Device) موجود في /dev/custom_hw_node.

┌─────────────────────────────────────────────────────────────┐ │ سيناريو: خدمة مخصصة تصل إلى جهاز عتادي │ ├─────────────────────────────────────────────────────────────┤ │ │ │ ┌──────────────────┐ ┌─────────────────────┐ │ │ │ custom_hw_service│─────▶│ /dev/custom_hw_node │ │ │ │ (Native Daemon) │ │ (Character Device) │ │ │ │ Domain: custom_ │ │ Type: custom_hw_ │ │ │ │ hw_service │ │ device │ │ │ └──────────────────┘ └─────────────────────┘ │ │ │ │ المطلوب: │ │ 1. تعريف النوع (Type) للجهاز │ │ 2. تعريف النطاق (Domain) للخدمة │ │ 3. ربط الجهاز بالنوع عبر file_contexts │ │ 4. كتابة قاعدة allow للوصول │ │ │ └─────────────────────────────────────────────────────────────┘
1

تعريف سياق الملف في file_contexts

أول خطوة هي إخبار SELinux بأن الملف /dev/custom_hw_node يجب أن يحمل النوع custom_hw_device عند إنشاء الملفات (Labeling). يتم ذلك في ملف file_contexts:

# device/company/sepolicy/vendor/file_contexts
# ===========================================
# ربط المسار الفعلي بالنوع (Type) في SELinux

# الجهاز العتادي المخصص — يتم تسميته تلقائيًا بنوع custom_hw_device
/dev/custom_hw_node    u:object_r:custom_hw_device:s0

# ملاحظة: يمكن استخدام تعبيرات regex للمسارات المتغيرة
# /dev/custom_hw_node[0-9]*    u:object_r:custom_hw_device:s0
2

تعريف الأنواع في device.te و file.te

يجب تعريف النوع custom_hw_device كـ dev_type (نوع جهاز) في ملف device.te. كما نحتاج لتعريف نطاق الخدمة:

# device/company/sepolicy/vendor/device.te
# ========================================
# تعريف أنواع الأجهزة (Device Types)

# تعريف نوع الجهاز العتادي المخصص
# dev_type: سمة (Attribute) تُستخدم لتجميع جميع أنواع الأجهزة
type custom_hw_device, dev_type;

# ============================================
# device/company/sepolicy/vendor/file.te
# ============================================
# تعريف أنواع الملفات العامة (File Types)

# تعريف نوع ملفات بيانات الخدمة (إذا احتجنا تخزين بيانات)
type custom_hw_data_file, file_type, data_file_type;
3

كتابة قواعد النطاق في custom_hw_service.te

نقوم بتعريف نطاق الخدمة وربطها بعملية init باستخدام وحدات ماكرو مُحسّنة (Optimized Macros) مثل init_daemon_domain():

# device/company/sepolicy/vendor/custom_hw_service.te
# ===================================================
# قواعد SELinux للخدمة المخصصة (Custom Hardware Service)

# ─────────────────────────────────────────────────────
# 1. تعريف النطاق (Domain) للخدمة
# ─────────────────────────────────────────────────────
type custom_hw_service, domain;

# ربط النطاق بعملية init — يُفعّل الانتقال التلقائي (Auto-Transition)
# عندما يبدأ init تشغيل الخدمة، تنتقل العملية إلى نطاق custom_hw_service
init_daemon_domain(custom_hw_service)

# ─────────────────────────────────────────────────────
# 2. منح صلاحيات الوصول إلى الجهاز العتادي
# ─────────────────────────────────────────────────────
# السماح للخدمة بالقراءة والكتابة والفتح والتحكم (ioctl) في الجهاز
allow custom_hw_service custom_hw_device:chr_file { 
    read 
    write 
    open 
    ioctl 
    getattr 
};

# ─────────────────────────────────────────────────────
# 3. صلاحيات إضافية مطلوبة للخدمة
# ─────────────────────────────────────────────────────

# السماح بالوصول إلى مأخذ binder للتواصل مع framework
allow custom_hw_service binder_device:chr_file { read write ioctl open };

# السماح بالاتصال بـ servicemanager لتسجيل الخدمة
allow custom_hw_service servicemanager:service_manager { add find };

# السماح بكتابة السجلات (Logs) إلى logd
allow custom_hw_service logd:unix_stream_socket { connectto read write };

# السماح بالوصول إلى ملفات البيانات الخاصة بالخدمة
allow custom_hw_service custom_hw_data_file:dir { create read write open add_name remove_name };
allow custom_hw_service custom_hw_data_file:file { create read write open append getattr };
4

تسجيل الخدمة في init.rc

يجب تسجيل الخدمة في ملف init.rc (أو init.target.rc) ليتم تشغيلها بواسطة init وانتقالها تلقائيًا إلى النطاق المحدد:

# device/company/init.rc
# ======================
# تسجيل خدمة العتاد المخصصة

service custom_hw_service /system/bin/custom_hw_service
    class core
    user system
    group system
    seclabel u:r:custom_hw_service:s0    # ← سياق SELinux للخدمة
    oneshot disabled

# تشغيل الخدمة عند اكتمال الإقلاع
on property:sys.boot_completed=1
    start custom_hw_service
✅ ملخص التنفيذ: بهذه الخطوات الأربع، نكون قد أنشأنا نطاقًا (Domain) مخصصًا للخدمة، عرّفنا نوعًا (Type) للجهاز العتادي، ربطنا المسار الفعلي بالنوع عبر file_contexts، ومنحنا الصلاحيات الدقيقة عبر قواعد .te. الخدمة الآن تعمل ضمن حدود SELinux دون الحاجة إلى وضع Permissive.

🔍5. استكشاف الأخطاء وتوليد القواعد تلقائيًا (audit2allow)

عندما ترفض SELinux وصولًا غير مصرّح به، فإنها تُنشئ سجلًا يُعرف بـ "AVC Denial". يُعدّ فك شفرة هذه السجلات وتحويلها إلى قواعد .te صالحة مهارة أساسية لكل مهندس أمان أندرويد.

5.1 قراءة سجل avc: denied

تظهر سجلات الرفض في dmesg أو logcat بالصيغة التالية:

AVC DENIAL LOG
avc: denied { read write open } for pid=1234 comm="custom_hw_service" name="custom_hw_node" dev="tmpfs" ino=12345 scontext=u:r:custom_hw_service:s0 tcontext=u:object_r:device:s0 tclass=chr_file permissive=0

5.2 تفكيك السجل (Deconstructing the Log)

الحقل القيمة في المثال الوصف
avc: denied denied نوع الحدث: رفض الوصول
{ ... } read write open الصلاحيات المطلوبة (Permissions)
pid 1234 معرّف العملية (Process ID)
comm "custom_hw_service" اسم العملية (Command Name)
scontext u:r:custom_hw_service:s0 سياق المصدر (Source Context) — النطاق (Domain)
tcontext u:object_r:device:s0 سياق الهدف (Target Context) — النوع (Type)
tclass chr_file فئة الهدف (Target Class) — نوع الكائن
💡 تحليل المثال: في السجل أعلاه، العملية custom_hw_service (نطاقها u:r:custom_hw_service:s0) حاولت الوصول إلى جهاز محرف (chr_file) يحمل النوع device (النوع الافتراضي العام) بصلاحيات read write open. تم الرفض لأن file_contexts لم يُعدّل لربط /dev/custom_hw_node بالنوع custom_hw_device.

5.3 استخدام audit2allow لتوليد القواعد تلقائيًا

أداة audit2allow تقرأ سجلات AVC Denial وتحوّلها إلى قواعد .te جاهزة للاستخدام. تُستخدم بالشكل التالي:

# الخطوة 1: التقاط سجلات AVC من dmesg
$ dmesg | grep "avc: denied" > avc_denials.log

# الخطوة 2: استخدام audit2allow لتوليد القواعد
$ audit2allow -i avc_denials.log

# النتيجة:
# ============= custom_hw_service ==============
allow custom_hw_service device:chr_file { read write open };

# ─────────────────────────────────────────────
# الخطوة 3: توليد قاعدة لنوع مخصص (مع تحديد النوع الصحيح)
# إذا كانت file_contexts مُعدّلة بشكل صحيح، سيولد audit2allow:
allow custom_hw_service custom_hw_device:chr_file { read write open };

# الخطوة 4: توليد ملف .te كامل (مفيد للسياسات المعقدة)
$ audit2allow -i avc_denials.log -p /sepolicy > custom_hw_service_auto.te
⚠️ تحذير هام: لا تستخدم audit2allow بشكل أعمى (Blindly). راجع كل قاعدة مُولدة يدويًا للتأكد من أنها لا تمنح صلاحيات زائدة (Over-Privileging). الهدف هو أقل صلاحية ممكنة (Principle of Least Privilege)، وليس حل المشكلة بأسرع طريقة.

5.4 قواعد neverallow وامتثال CTS

تُعرّف Google في AOSP قواعد neverallow التي تُمنع صراحةً وجود قواعد allow معينة. هذه القواعد غير قابلة للتجاوز ويجب الامتثال لها لاجتياز اختبارات CTS (Compatibility Test Suite).

# system/sepolicy/public/domain.te (مقتطف)
# ===========================================
# قواعد neverallow — لا يمكن تجاوزها أبدًا

# مثال 1: منع أي تطبيق غير موثوق من الوصول إلى kernel
neverallow { appdomain -init } kernel:security *;

# مثال 2: منع التطبيقات من الوصول المباشر إلى أجهزة العتاد
neverallow appdomain dev_type:chr_file { read write };

# مثال 3: منع الوصول إلى ملفات shadow (كلمات المرور)
neverallow { domain -init -installd } shadow_file:file *;
🚨 قيود neverallow: إذا حاولت إضافة قاعدة allow تتعارض مع neverallow، فإن عملية بناء السياسة (Policy Build) ستفشل برسالة خطأ واضحة. لا يمكنك "تجاوز" neverallow حتى بامتلاك root — هذه قيود مُدمجة في السياسة المترجمة (Compiled Policy). الحل الوحيد هو إعادة هيكلة التصميم ليتوافق مع قواعد Google.

5.5 سير عمل التصحيح الموصى به (Recommended Debugging Workflow)

  1. ضع الجهاز في وضع Permissive باستخدام setenforce 0
  2. شغّل السيناريو الذي يُسبب الرفض (Denial)
  3. التقط السجلات باستخدام dmesg | grep avc
  4. حلّل السجلات يدويًا لفهم scontext و tcontext و tclass
  5. استخدم audit2allow كمساعد، وليس كحل نهائي
  6. اكتب القواعد يدويًا مع مراعاة مبدأ أقل الصلاحية (Least Privilege)
  7. أعد بناء السياسة (m sepolicy)
  8. اختبر في وضع Enforcing (setenforce 1)
  9. شغّل cts-tradefed للتحقق من عدم كسر neverallow
