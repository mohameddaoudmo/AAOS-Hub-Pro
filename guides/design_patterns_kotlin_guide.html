أنماط التصميم ومبادئ SOLID في Kotlin

رحلة من الحلول الكلاسيكية إلى التعبيرات الاصطلاحية في لغة حديثة، مع استعراض كامل للمقايضات والفلسفة وراء كل نمط.

يستعرض هذا الدليل سبع محاضرات تقنية مفصلة حول أنماط التصميم الأكثر شيوعًا ومبادئ SOLID، مع التركيز على تطبيقها بلغة Kotlin الحديثة. الهدف ليس مجرد نقل الكود، بل فهم لماذا نشأ كل نمط، وكيف تتيح لنا اللغات الحديثة التعبير عن ذات المبادئ بأدوات أكثر أناقة وقوة.

💡 الفكرة المركزية

المبادئ هي التي تعيش، لا التطبيق الحرفي. مبدأ مثل Composition over Inheritance سيظل صحيحًا، لكن طريقة تحقيقه تتغير مع تطور اللغات. الأنماط يجب أن تكون مصدر إلهام لا قيودًا.

1 Factory Method & Abstract Factory

تبدأ الرحلة من موقف مألوف لكل مبرمج: كود صغير يبدأ ويتوسع فجأة لتجد نفسك أمام Class واحد يحاول عمل كل شيء في نفس الوقت. في مثال المستندات، كان لدينا Class اسمه Document يدير مجموعة عناصر (Paragraphs)، لكنه كان يحمل أيضًا منطق تنسيق كل عنصر لكل صيغة (HTML وMarkdown).

⚠️ المشكلة الأساسية

الـ Document تحول من "مدير تحرير" يُرتب المحتوى فقط إلى "مصمم" يعرف تفاصيل التنسيق الدقيقة لكل صيغة. هذا يربطه بشدة بالتفاصيل ويخالف مبدأ Open-Closed Principle: الكود يجب أن يكون مفتوحًا للإضافة ومغلقًا للتعديل.

Factory Method: الورشة المتخصصة

الخطوة الأولى في الحل الكلاسيكي هي تحويل Document إلى Abstract Class. هذا يغير العقد الأساسي: لم يعد هناك "مستند عام"، بل يجب تحديد النوع بدقة (HTMLDocument أو MarkdownDocument). ثم نضيف دالة Abstract اسمها createParagraph() — وهي الـ Factory Method.

Kotlin 
abstract class Document {
    private val paragraphs = mutableListOf<Paragraph>()
    
    // Factory Method: يسند الإنشاء للوريث
    protected abstract fun createParagraph(text: String): Paragraph
    
    fun addParagraph(text: String) {
        val paragraph = createParagraph(text)
        paragraphs.add(paragraph)
    }
    
    fun render(): String = paragraphs.joinToString("\n") { it.render() }
}

class HTMLDocument : Document() {
    override fun createParagraph(text: String): Paragraph = HTMLParagraph(text)
}

class MarkdownDocument : Document() {
    override fun createParagraph(text: String): Paragraph = MarkdownParagraph(text)
}

🔍 شرح الكود

  • abstract class Document: يحدد الهيكل العام للمستند لكنه لا يعرف كيفية إنشاء الفقرات.
  • protected abstract fun createParagraph: الـ Factory Method. هو "العقد" الذي يُلزم كل مستند متخصص بتوفير طريقته الخاصة في صناعة الفقرات.
  • HTMLDocument و MarkdownDocument: الـ Concrete Creators. كل واحد يمتلك "ورشة صغيرة" تنتج فقرات بتنسيقه.
  • addParagraph: الكود الأساسي يعمل بلا معرفة بالتفاصيل. هو يطلب الفقرة ويثق بأن الوريث المتخصص سيتصرف.

باستخدام مصطلحات Gang of Four: Document هو الـ Creator، والفئات الوراثية هي الـ Concrete Creators. الفقرة كفكرة مجردة هي الـ Product، والفقرات الفعلية (HTMLParagraph، MarkdownParagraph) هي الـ Concrete Products.

Abstract Factory: عائلة المنتجات

عندما نحتاج لإضافة عناصر جديدة مثل العناوين (Heading) والروابط (Link)، يظهر قيد Factory Method: كل Subclass سيحتاج إضافة createHeading و createLink، والأب سيُملأ بدوال Abstract جديدة. هنا ننتقل من مشكلة "إنشاء كائن واحد" إلى مشكلة "إنشاء عائلة متكاملة من الكائنات".

Kotlin 
// العقد: Abstract Factory
interface ElementFactory {
    fun createParagraph(text: String): Paragraph
    fun createHeading(level: Int, text: String): Heading
    fun createLink(url: String, text: String): Link
}

// Concrete Factory للـ HTML
class HTMLElementFactory : ElementFactory {
    override fun createParagraph(text: String) = HTMLParagraph(text)
    override fun createHeading(level: Int, text: String) = HTMLHeading(level, text)
    override fun createLink(url: String, text: String) = HTMLLink(url, text)
}

// Concrete Factory للـ Markdown
class MarkdownElementFactory : ElementFactory {
    override fun createParagraph(text: String) = MarkdownParagraph(text)
    override fun createHeading(level: Int, text: String) = MarkdownHeading(level, text)
    override fun createLink(url: String, text: String) = MarkdownLink(url, text)
}

// الـ Client يستخدم التكوين بدل الوراثة
class Document(private val factory: ElementFactory) {
    private val elements = mutableListOf<Element>()
    
    fun addParagraph(text: String) = elements.add(factory.createParagraph(text))
    fun addHeading(level: Int, text: String) = elements.add(factory.createHeading(level, text))
}

🔍 شرح الكود

  • ElementFactory: الـ Abstract Factory. يضمن أن كل مصنع ينتج عناصر متوافقة مع بعضها (HTML مع HTML، Markdown مع Markdown).
  • HTMLElementFactory و MarkdownElementFactory: الـ Concrete Factories. كل مصنع مسؤول عن عائلة منتجات كاملة.
  • Composition over Inheritance: Document لم يعد يرث نوعًا محددًا. العلاقة أصبحت "has-a" (لديه مصنع) بدل "is-a" (هو نوع من). هذا يتيح تغيير المصنع في وقت التشغيل.

التبسيط الاصطلاحي في Kotlin

تقدم Kotlin أدوات تُغيّر طريقة التفكير. المصانع مثل HTMLFactory هي مجرد حاويات لدوال بلا حالة داخلية (State). بدلًا من كلاسات نُنشئ منها كائنات، نستخدم object لجعلها Singletons:

Kotlin 
// Singleton Factory: نسخة واحدة في البرنامج كله
object HTMLElementFactory : ElementFactory {
    override fun createParagraph(text: String) = HTMLParagraph(text)
    // ...
}

لكن النقلة الأكبر هي استخدام First-class Functions. بدلًا من كلاسات صغيرة لكل منتج، نستطيع استبدالها بـ Lambdas:

Kotlin 
// بدل HTMLParagraph class، نستخدم Lambda للعرض
data class Paragraph(val text: String, val render: (String) -> String)

object HTMLElementFactory : ElementFactory {
    override fun createParagraph(text: String) = 
        Paragraph(text) { "<p>$it</p>" }
}

// لكن هنا تظهر مشكلة: الـ Lambda لا تحتوي على منطق التحقق
// مثلاً Heading يحتاج التأكد من أن المستوى بين 1 و 6
// في هذه الحالة، قد نحتفظ بـ Subclasses للعناصر التي تحتاج قيودًا
🎯 حكمة التطبيق

في مشروع حقيقي، غالبًا ما يُفضل الحل الأقل أناقة إذا كان يحافظ على أمان البيانات. الـ Lambdas رائعة للعرض البسيط، لكن العناصر التي تحتاج تحققًا (Validation) تستحق كلاسًا مستقلًا. الأنماط ليست كتابًا مقدسًا، بل نقطة بداية نُكيّفها حسب احتياجاتنا.

في أبسط صوره، يمكن تقليل الكود لـ 35 سطرًا إذا قبلنا فقدان Type Safety بجعل كل شيء String. لاستعادة الأمان دون ثقل الكلاسات، تقدم Kotlin Value Classes:

Kotlin 
@JvmInline
value class ParagraphString(val value: String)

@JvmInline
value class HeadingString(val value: String)

// لا تكلفة إضافية في الذاكرة، لكن المترجم يفرق بين الأنواع

الوراثة (is-a) تخلق علاقة صلبة: HTMLDocument مرتبط للأبد بأنه "نوع من Document". أما التكوين (has-a) فهو مرن: Document يستطيع العمل مع أي مصنع تُعطيه له. يمكنك تغيير المصنع من HTMLElementFactory إلى MarkdownElementFactory في منتصف البرنامج. هذه المرونة هي جوهر الفرق.

2 Observer Pattern

تخيل جروب واتساب لأصدقاء يُخططون لخروجة: كل دقيقة يقترح أحدهم مكانًا جديدًا ويغير آخر المعاد. لمنع الفوضى، يبلّغ صاحب التغيير "المهتمين" بالجديد. هذه هي فكرة Observer Pattern في جوهرها: فصل المُبلّغ عن المُبلَّغ إليه.

الارتباط الشديد (Tight Coupling)

في المثال الكلاسيكي، لدينا لعبة Game ومعلقين (ScoreAnnouncer و WinnerAnnouncer). في النسخة الأولى، كلما تغيرت النتيجة، كان Class الـ Game يذهب بنفسه لكل معلق ويُبلّغه. هنا يعرف Game تفاصيل دقيقة عن المعلقين — أسماءهم ودوالهم — مما يُنشئ ارتباطًا شديدًا.

⚠️ عواقب الارتباط الشديد

إضافة معلق ثالث (مثل محلل إحصائيات) يتطلب فتح كود Game نفسه وإضافة سطر جديد. الكود يصبح عاملًا كالمبنى الذي كل حوائطه تدعم بعضها: تغيير حائطة واحدة قد يسقط المبنى.

الحل الكلاسيكي: طبقة الوساطة

الحل يقوم على إضافة طبقة وسيطة. نُنشئ نوعين مجردين: Subject (الشيء المراقب) و Observer (المراقب). Game يرث من Subject ويحتفظ بقائمة من المراقبين. المراقبون يسجّلون أنفسهم (subscribe) وينتظرون التبليغ.

Kotlin 
// العقد الكلاسيكي
interface Observer {
    fun update(score: Int)
}

abstract class Subject {
    private val observers = mutableListOf<Observer>()
    
    fun attach(observer: Observer) = observers.add(observer)
    fun detach(observer: Observer) = observers.remove(observer)
    
    fun notifyObservers(score: Int) {
        observers.forEach { it.update(score) }
    }
}

class Game : Subject() {
    var score: Int = 0
        set(value) {
            field = value
            notifyObservers(value) // التبليغ اليدوي
        }
}

🔍 شرح الكود

  • Observer: واجهة العقد. أي شيء يريد الاستماع يجب أن ينفذ update.
  • Subject: يدير قائمة المراقبين ويُبلّغهم عند التغيير.
  • Dependency Inversion: Game لم يعد يعرف المعلقين بالاسم. المعلقون هم الذين يعتمدون على Game، لا العكس.
ℹ️ نقطة ضعف الكلاسيكي

في Kotlin (وJava)، لكي يحصل Game على وظائف إدارة المراقبين، يجب أن يرث من Subject. وبما أن Kotlin تسمح بالوراثة من كلاس واحد فقط، فقد "استهلكنا الجوكر الوحيد". قد يحتاج Game في المستقبل للوراثة من كلاس آخر أهم لأسباب تتعلق بقواعد اللعبة نفسها.

التحديثات الحديثة في Kotlin

أول تحسين هو التخلص من التبليغ اليدوي باستخدام Delegates.observable:

Kotlin 
import kotlin.properties.Delegates

class Game {
    var score: Int by Delegates.observable(0) { _, oldValue, newValue ->
        if (oldValue != newValue) {
            notifyObservers(newValue) // تلقائي!
        }
    }
}

النقلة الفكرية الحقيقية تأتي عندما نسأل: لماذا نحتاج Interface كاملة اسمها Observer؟ كل ما نريده هو سلوك معين يُنفّذ عند التغيير. في Kotlin، الدوال هي مواطنون من الدرجة الأولى (First-class citizens):

Kotlin 
class Game {
    private val listeners = mutableListOf<(Int) -> Unit>() // قائمة من الدوال!
    
    fun addListener(listener: (Int) -> Unit) = listeners.add(listener)
    
    var score: Int by Delegates.observable(0) { _, _, newValue ->
        listeners.forEach { it(newValue) } // Push Model
    }
}

// الاستخدام: لا حاجة لكلاسات!
val game = Game()
game.addListener { score -> println("النتيجة: $score") }
game.addListener { score -> sendPushNotification(score) }

🔍 شرح الكود

  • mutableListOf<(Int) -> Unit>(): قائمة تحتفظ بـ "وصفات" كود بدل كائنات. كل عنصر هو دالة تقبل Int ولا ترجع شيئًا.
  • Push Model: اللعبة تدفع المعلومة (النتيجة الجديدة) مباشرةً كمعامل للدالة. هذا يختلف عن النمط الكلاسيكي (Pull Model) حيث كان المراقب يسأل اللعبة عن النتيجة بعد التبليغ.
  • المرونة: يمكن تسجيل دالة Logging بسيطة، أو دالة إرسال إشعار، دون إنشاء كلاس لكل منها.

التزامن والـ Flow

في تطبيقات الواجهات الرسومية (UI)، قد يكون أحد المراقبين بطيئًا (مثل رسم بياني معقد أو إرسال بيانات للسيرفر). إذا كان الكود يعمل على مسار واحد رئيسي (Main Thread)، سيُجمّد التطبيق. الحل في Kotlin هو Coroutines و Flow:

Kotlin 
import kotlinx.coroutines.flow.MutableStateFlow
import kotlinx.coroutines.flow.StateFlow
import kotlinx.coroutines.yield

class Game {
    private val _score = MutableStateFlow(0)
    val score: StateFlow<Int> = _score
    
    suspend fun updateScoreLoop() {
        repeat(10) { i ->
            _score.value = i
            yield() // يسمح للمراقبين بالتنفس!
        }
    }
}

// الاشتراك: كل مراقب في مساره الخاص
viewModelScope.launch {
    game.score.collect { score ->
        updateComplexChart(score) // بطيء، لكن لا يُجمّد الآخرين
    }
}

🔍 شرح الكود

  • MutableStateFlow: قناة بث تحتفظ بآخر قيمة. أي مشترك جديد يحصل على القيمة الأخيرة فورًا (مثل تطبيق الأسهم).
  • yield(): تُخبر الـ Coroutine الحالي "تنازل عن دورك للحظة". هذا يعطي فرصة لـ Coroutines المراقبين لالتقاط التحديثات الوسطى، لا أول قيمة وآخر قيمة فقط.
  • collect: كل مشترك ينتظر التحديثات في مسار تنفيذ منفصل خاص به.
🎯 الخلاصة

الفكرة الأساسية (فصل المُبلّغ عن المُبلَّغ) بقيت ثابتة، لكن التطبيق تطور من كلاسات متشابكة إلى دوال مستقلة تتواصل عبر قنوات بيانات غير متزامنة. Kotlin تدمج المبادئ العريقة داخل اللغة نفسها عبر First-class Functions و Coroutines.

3 Strategy Pattern

تخيل نموذج إدخال (Form) على الإنترنت: حقل إيميل، حقل اسم مستخدم، حقل باسورد. في البداية، كل حقل له كلاس يحتوي على منطق التحقق (Validation). الكارثة تبدأ عندما يطلب البيزنس تفرقة بين الحقول الإجبارية والـ اختيارية.

الانفجار التوافقي للكلاسات

الحل المباشر: عمل نسخة اختيارية من كل كلاس. إذا بدأنا بثلاثة حقول، فجأة يصبح لدينا 6 كلاسات. هذا ما يُسمى Combinatorial Explosion: كل بُعد جديد (إجباري/اختياري، نص/رقم) يضرب عدد الكلاسات في بعضها. كأنك في مطعم يقدم 3 سندوتشات × 2 نوع عيش × 3 صوصات = 18 صنفًا!

⚠️ الانفجار التوافقي

كل بُعد جديد نضيفه يُضاعف عدد الكلاسات. الكود يتحول لكابوس صيانة مستحيل التعامل معه. المشكلة ليست في عدد الكلاسات فقط، بل في تكرار المنطق وصعوبة تعديله.

الاستراتيجية الكلاسيكية

المبدأ الأساسي: استخرج ما يختلف. إذا نظرنا إلى EmailField و UsernameField، نجد أن الجزء المتغير هو isValid(). نستخرج هذا المنطق إلى Interface:

Kotlin 
// الاستراتيجية المجردة
interface Validator {
    fun isValid(input: String): Boolean
}

// استراتيجيات ملموسة
class EmailValidator : Validator {
    override fun isValid(input: String): Boolean = 
        input.contains("@") && input.contains(".com")
}

class UsernameValidator : Validator {
    override fun isValid(input: String): Boolean = input.isNotBlank()
}

// المدير (Context)
class FormField(private val validator: Validator) {
    var value: String = ""
    fun isValid(): Boolean = validator.isValid(value)
}

🔍 شرح الكود

  • Validator: الاستراتيجية المجردة. تحدد العقد: أي مدقق يجب أن يقدم دالة isValid.
  • EmailValidator و UsernameValidator: استراتيجيات ملموسة. كل واحد يحمل منطق التحقق الخاص به.
  • FormField: الـ Context. لا يعرف تفاصيل التحقق، بل يوظف الخبير (Validator) الذي يُعطى له.

النتيجة: بدل 6 كلاسات، لدينا FormField واحد وعدة Validators. لكن في Kotlin، يمكن الاختصار أكثر. إذا كانت الواجهة تحتوي على دالة واحدة فقط، فهي Functional Interface يمكن استبدالها بـ Lambda:

Kotlin 
// بدل Interface، نستخدم نوع الدالة مباشرة
typealias Validator = (String) -> Boolean

class FormField(private val validator: Validator) {
    var value: String = ""
    fun isValid(): Boolean = validator(value)
}

// الاستخدام: لا حاجة لكلاسات!
val emailField = FormField { input -> input.contains("@") }
val userField = FormField { it.isNotBlank() }

🔍 شرح الكود

  • typealias Validator = (String) -> Boolean: يعرف اسمًا بديلًا لنوع "دالة تأخذ String وترجع Boolean". لا حاجة لـ Interface أو كلاسات.
  • FormField { input -> ... }: نمرر Lambda مباشرة كمعامل. الكلاس يحتفظ بالدالة ويناديها عند الحاجة.
  • it: في Lambda ذي المعامل الواحد، Kotlin توفر اسمًا افتراضيًا it لتبسيط الكود.

لحل مشكلة الحقول الاختيارية، نستخدم Higher-order Function (دالة تُنتج دوال):

Kotlin 
// دالة تُنتج Validator اختياريًا
fun optional(validator: Validator): Validator = { input ->
    if (input.isBlank()) true else validator(input)
}

// الاستخدام
val optionalEmail = optional { input -> input.contains("@") }
val field = FormField(optionalEmail)
field.value = ""        // صحيح (اختياري)
field.value = "a@b.com" // صحيح
field.value = "invalid" // خطأ

🔍 شرح الكود

  • optional: دالة تستقبل Validator وتُعيد Validator جديدًا. الجديد يتحقق أولًا من الفراغ: إذا كان النص فارغًا يرجع true، وإلا ينادي الـ Validator الأصلي.
  • حلّت المشكلة بدون إضافة أي كلاس جديد. الكود أصبح مرنًا بشكل لا يصدق.
🎯 الفكرة النهائية

القوة الحقيقية ليست في حفظ أسماء الأنماط، بل في القدرة على تمييز اللحظة التي تسمح فيها لغتك بالتعبير عن القصد من النمط مباشرةً. الانتقال من التفكير في الأسماء (كلاسات وواجهات) إلى التفكير في الأفعال (دوال وسلوكيات).

4 Decorator Pattern

تخيل كلاس Logger بسيط وظيفته طباعة رسالة في الكونسول. مع الوقت، تُطلب إضافات: طباعة التاريخ، إضافة معرف فريد (UUID)، اسم الـ Thread. الحل المباشر هو إضافة Parameters منطقية (Boolean) في Constructor. لكن هذا يؤدي لـ "كونستركتور المرعب" ذي الـ 20 معاملًا.

مشاكل التصميم الأولي

  • التعقيد المتزايد: كل ميزة جديدة تُضيف Parameter، والاستخدام يصبح غريبًا.
  • الاعتماديات غير الضرورية: لإضافة الوقت، يحتاج الكود Clock Object. حتى لو لم ترد الطباعة بالوقت، ستُجبر على تمرير الـ Clock.
  • عدم المرونة: الكود مصمم للطباعة في الكونسول فقط. لتسجيل في ملف أو إرسال لسيرفر، يجب تعديل الكلاس الأصلي.
⚠️ فخ الوراثة

أول حل قد يخطر على البال هو الوراثة: LoggerWithTimestamp يرث Logger، و LoggerWithUUID يرث Logger. لكن مع 3 ميزات، نحتاج 7 كلاسات لتغطية كل التركيبات. إضافة ميزة رابعة تُضاعف العدد. هذا انفجار الكلاسات (Class Explosion).

التزيين الكلاسيكي

فكرة Decorator: بدل تغيير جوهر الشيء، نُغلّفه من الخارج. نُنشئ Interface مشتركًا، وكل ميزة تصبح كلاسًا منفصلًا يُغلّف Logger آخر:

Kotlin 
// العقد المشترك
interface Logger {
    fun log(message: String)
}

// العامل الأساسي
class ConsoleLogger : Logger {
    override fun log(message: String) = println(message)
}

// المزيّن: يضيف التاريخ والوقت
class DateTimeLogger(private val wrapped: Logger) : Logger {
    override fun log(message: String) {
        val timestamp = java.time.Instant.now()
        wrapped.log("[$timestamp] $message")
    }
}

// المزيّن: يضيف UUID
class UniqueIdLogger(private val wrapped: Logger) : Logger {
    private var counter = 0
    override fun log(message: String) {
        wrapped.log("[${++counter}] $message")
    }
}

// التركيب كطبقات كيكة
val logger = UniqueIdLogger(DateTimeLogger(ConsoleLogger()))
logger.log("خطأ في الاتصال") // [1] [2025-...] خطأ في الاتصال

🔍 شرح الكود

  • Logger: Interface يضمن أن كل مكون (أساسي أو مزيّن) يمكن استبداله بالآخر.
  • DateTimeLogger: يستقبل Logger آخر في Constructor. يضيف الطابع الزمني ثم ينادي الـ wrapped.log.
  • التركيب: كل طبقة تضيف سلوكها ثم تُمرر للطبقة الداخلية. يمكن إعادة الترتيب أو إزالة طبقة دون التأثير على الباقي.

الأسلوب السلس في Kotlin

في Kotlin، يمكن تبسيط الهيكل باستخدام Functional Interface (fun interface) و Extension Functions:

Kotlin 
// واجهة وظيفية: دالة واحدة فقط
fun interface Logger {
    fun log(message: String)
}

// Logger أساسي باستخدام Lambda
val consoleLogger = Logger { println(it) }

// Extension Function: تبدو وكأنها دالة من Logger نفسه
fun Logger.withTimestamp(): Logger = Logger { message ->
    log("[${java.time.Instant.now()}] $message")
}

fun Logger.withUniqueId(): Logger = Logger { message ->
    log("[${java.util.UUID.randomUUID()}] $message")
}

// استخدام سلس (Fluent Style)
val fancyLogger = consoleLogger
    .withTimestamp()
    .withUniqueId()

fancyLogger.log("تم تسجيل الدخول")

🔍 شرح الكود

  • fun interface: يسمح بإنشاء كائن من Interface باستخدام Lambda مباشرةً، دون كلاس منفصل.
  • Logger { println(it) }: ينشئ Logger جديدًا باستخدام Lambda. it هو المعامل الوحيد (الرسالة).
  • withTimestamp(): Extension Function. تبدو كأنها جزء من Logger، لكنها دالة منفصلة تأخذ Logger وتُعيد Logger جديدًا مُغلّفًا.
  • Fluent Style: السلسلة consoleLogger.withTimestamp().withUniqueId() تقرأ كجملة طبيعية: "Logger مع طابع زمني ومعرف فريد".

الأسلوب السلس يُضحي ببعض سهولة التتبع (Debugging). عند وضع Breakpoint، ستجد نفسك تنتقل بين Lambda متداخلة. الكلاسات المنفصلة في النمط الكلاسيكي تُسهّل تتبع الرسالة وهي تنتقل من مزيّن إلى آخر. الاختيار يعتمد على تعقيد الفريق وخبرته.

5 State Pattern

كيف تجعل كائنًا يتصرف بطرق مختلفة حسب حالته؟ المثال الكلاسيكي: طلب شراء أونلاين يمر بمراحل (قيد المراجعة → مؤكد → تم الشحن → تم التسليم). كل حالة لها قواعدها: في "قيد المراجعة" يمكن الإلغاء، لكن في "تم الشحن" تختفي هذه الصلاحية.

جمل when المتكررة

في الكود المبدئي، كل دالة مثل viewContent أو editProfile تكون مليئة بجمل when (أو switch). هذا المنطق المُتفرق يجعل أي تغيير مستقبلي صعبًا:

Kotlin 
// كود هش: when متكررة في كل دالة
class User(val state: UserState) {
    fun viewContent() = when (state) {
        UserState.ANONYMOUS -> "عرض محدود"
        UserState.UNVERIFIED -> "عرض مع إعلان"
        UserState.AUTHENTICATED -> "عرض كامل"
    }

    fun editProfile() = when (state) {
        UserState.ANONYMOUS -> throw IllegalStateException("ممنوع!")
        UserState.UNVERIFIED -> "طلب التحقق أولاً"
        UserState.AUTHENTICATED -> "تعديل البيانات"
    }
}
⚠️ مشكلة التكرار

إضافة حالة جديدة (مثل SUSPENDED) تتطلب تعديل كل جملة when في الكود. نسيان دالة واحدة يُنشئ Bug غريبًا وصعب الاكتشاف.

نمط الحالة الكلاسيكي

المبدأ: Code that grows together, goes together. بدل تنظيم الكود حسب الوظيفة، ننظمه حسب الحالة:

Kotlin 
// واجهة الحالة
interface UserState {
    fun viewContent(): String
    fun editProfile(): String
}

// حالات ملموسة
class AnonymousState : UserState {
    override fun viewContent() = "عرض محدود"
    override fun editProfile() = throw IllegalStateException("ممنوع!")
}

class AuthenticatedState : UserState {
    override fun viewContent() = "عرض كامل"
    override fun editProfile() = "تعديل البيانات"
}

// السياق: يُفوّض لحالته
class User(private var state: UserState) {
    fun viewContent() = state.viewContent()
    fun editProfile() = state.editProfile()
    fun changeState(newState: UserState) { state = newState }
}

🔍 شرح الكود

  • UserState: يحدد كل الأفعال الممكنة. كل حالة جديدة تُنشئ كلاسًا واحدًا فقط.
  • User: أصبح وسيطًا بسيطًا (Delegate). كل طلب يُمرر للحالة الحالية.
  • إضافة SuspendedState تتطلب كلاسًا واحدًا جديدًا فقط، دون تعديل أي كود قديم.

الـ Enum والـ Lambdas

في Kotlin، يمكن استخدام Enum مع خصائص من نوع وظيفي (Function Type) للتخلص من Boilerplate:

Kotlin 
enum class UserState(
    val viewContent: () -> String,
    val editProfile: () -> String
) {
    ANONYMOUS(
        viewContent = { "عرض محدود" },
        editProfile = { throw IllegalStateException("ممنوع!") }
    ),
    UNVERIFIED(
        viewContent = { "عرض مع إعلان" },
        editProfile = { "طلب التحقق أولاً" }
    ),
    AUTHENTICATED(
        viewContent = { "عرض كامل" },
        editProfile = { "تعديل البيانات" }
    )
}

class User(var state: UserState) {
    fun viewContent() = state.viewContent()
    fun editProfile() = state.editProfile()
}

🔍 شرح الكود

  • enum class مع Constructor يأخذ دوال Lambda: كل حالة تحمل سلوكها مباشرةً.
  • اختُصرت 3 كلاسات منفصلة إلى قيم Enum. الكود انكمش لأقل من نصف.
  • الـ Compiler يضمن أن كل الحالات تُعرف كل السلوكيات المطلوبة.

يمكن الاختصار أكثر باستخدام Lambdas with Receivers، حيث يصبح الكود داخل Lambda كأنه جزء من كائن User نفسه:

Kotlin 
enum class UserState(
    val viewContent: User.() -> String,
    val editProfile: User.() -> String
) {
    AUTHENTICATED(
        viewContent = { "مرحبًا $name" }, // this هو User
        editProfile = { changeState(UNVERIFIED); "تم" }
    ),
    // ...
}

class User(var state: UserState, val name: String) {
    fun viewContent() = state.viewContent(this)
    fun editProfile() = state.editProfile(this)
}
ℹ️ الإيجاز مقابل الوضوح

النسخة الأخيرة مضغوطة لدرجة قد تربك المبرمج الجديد. اختفاء المتغيرات الصريحة (مثل user) يجعل الفهم معتمدًا على معرفة ضمنية بـ Lambdas with Receivers. إذا كان الفريق كله خبراء، فهذا قمة الأناقة. إذا كانت مستويات الخبرة متفاوتة، فالكود الأوضح — حتى لو أطول — قد يكون أفضل على المدى الطويل.

6 Builder Pattern

تخيل بناء Object يمثل إعدادات الإشعارات: المستخدم مشترك في ماذا؟ أخبار، تحليلات، تحديثات أمنية؟ كل إشعار يصل كيف؟ فوري، يومي، أسبوعي؟ Constructor التقليدي يريد كل شيء جاهزًا دفعة واحدة، لكن الواقع مليء بالشروط والمنطق الديناميكي.

قيود الـ Constructor

الـ Constructor عامل كخط إنتاج: يأخذ كل المكونات مرة واحدة ويُخرج المنتج. لكن ماذا لو كان المنطق معقدًا؟ "أضف اشتراك الإيميل فقط إذا كان المستخدم لديه إيميل مسجل". لا يمكن كتابة if داخل استدعاء Constructor.

البناء الكلاسيكي

الحل الكلاسيكي (Gang of Four): ورشة عمل منفصلة (Builder) تُجهز كل شيء براحتك، ثم تأمر ببناء المنتج النهائي:

Kotlin 
data class NotificationSettings(
    val subscriptions: List<String>,
    val frequency: String,
    val channels: List<String>
)

class NotificationSettingsBuilder {
    private val subscriptions = mutableListOf<String>()
    private var frequency = "immediate"
    private val channels = mutableListOf<String>()

    fun addSubscription(topic: String) = apply { subscriptions.add(topic) }
    fun setFrequency(freq: String) = apply { frequency = freq }
    fun addChannel(channel: String) = apply { channels.add(channel) }

    fun build(): NotificationSettings {
        return NotificationSettings(subscriptions, frequency, channels)
    }
}

// الاستخدام
val settings = NotificationSettingsBuilder()
    .addSubscription("news")
    .addSubscription("analytics")
    .setFrequency("daily")
    .addChannel("email")
    .build()

🔍 شرح الكود

  • NotificationSettingsBuilder: نسخة طبق الأصل من الكلاس الأصلي، لكن كل خصائصه قابلة للتعديل (Mutable).
  • apply: تُعيد الكائن نفسه، مما يسمح بسلسلة الاستدعاءات (Chaining).
  • build(): الخطوة الأخيرة التي تحول الشيء الفوضوي القابل للتعديل إلى منتج نهائي ثابت (Immutable).

بدائل Kotlin المدمجة

في Kotlin، 80% من الحالات لا تحتاج Builder على الإطلاق:

Kotlin 
// 1. Default + Named Arguments
data class NotificationSettings(
    val subscriptions: List<String> = emptyList(),
    val frequency: String = "immediate",
    val channels: List<String> = emptyList()
)

// استخدام: لا حاجة لـ Builder!
val settings = NotificationSettings(
    subscriptions = listOf("news"),
    frequency = "daily"
)

// 2. Scope Function (run) للمنطق الديناميكي
val dynamicSettings = NotificationSettings(
    subscriptions = mutableListOf<String>().apply {
        if (user.hasEmail) add("news")
        if (user.isPremium) add("analytics")
    }
)

// 3. buildList: صندوق أدوات مخصص للقوائم
val subs = buildList {
    if (user.hasEmail) add("news")
    if (user.isPremium) {
        add("analytics")
        add("security")
    }
}
val settings2 = NotificationSettings(subscriptions = subs)

🔍 شرح الكود

  • Default Arguments: تحل مشكلة "20 معاملًا في الكونستركتور". كل قيمة افتراضية تُقلل الحاجة لتمريرها.
  • Named Arguments: تخليك تحدد أي Parameter تريد دون حفظ الترتيب.
  • buildList: دالة مدمجة تُعطيك بلوكًا داخله add مباشرةً. تتولى Kotlin إنشاء القائمة النهائية غير القابلة للتعديل.

DSL مع Lambdas with Receivers

للحالات المعقدة، يمكن تحويل Builder إلى DSL (لغة مصغرة) باستخدام Lambdas with Receivers:

Kotlin 
// تعريف DSL
class NotificationSettingsDsl {
    val subscriptions = mutableListOf<String>()
    var frequency = "immediate"
    val channels = mutableListOf<String>()

    fun send(topic: String, to: String, freq: String) {
        subscriptions.add(topic)
        channels.add(to)
        frequency = freq
    }
}

fun notificationSettings(block: NotificationSettingsDsl.() -> Unit): NotificationSettings {
    val dsl = NotificationSettingsDsl().apply(block)
    return NotificationSettings(dsl.subscriptions, dsl.frequency, dsl.channels)
}

// الاستخدام: كأنك تكتب جملة إنجليزية!
val settings = notificationSettings {
    send("analytics", to = "email", freq = "daily")
    send("news", to = "mobile", freq = "weekly")
}

🔍 شرح الكود

  • NotificationSettingsDsl.() -> Unit: Lambda with Receiver. داخل البلوك، this هو NotificationSettingsDsl، لذا يمكن استدعاء دواله مباشرةً.
  • send(...): تبدو كأنها كلمة محجوزة في اللغة، لكنها دالة عادية داخل الـ DSL.
  • احتواء الفوضى: عملية البناء (الميوتنبل) محصورة داخل البلوك. المنتج النهائي (NotificationSettings) ثابت وآمن.
🎯 مبدأ احتواء الفوضى

في كل الحلول الفعّالة، كانت هناك خطوة أخيرة حاسمة: الـ build. عملية البناء بطبيعتها فوضوية ومتغيرة. المبدأ يقول: احتوِ الفوضى في صندوق صغير ومؤقت (Builder أو بلوك buildList). وبمجرد إغلاق الصندوق، يخرج منتج مثالي ثابت. بقية النظام يتعامل مع المنتج المثالي وهو مطمئن أنه لن يتغير.

7 مبادئ SOLID

رحلة تصليح كود واحد من دالة واحدة معقدة إلى نظام مرن ومُفصل. نبدأ بـ loginUser التي تفعل ثلاثة أشياء: مصادقة Firebase، تسجيل الأخطاء في ملف، وعرض رسالة ترحيب.

S — Single Responsibility Principle

المبدأ لا يقول "دالة واحدة لكل شيء"، بل يقول "سبب واحد للتغيير". الدالة الحالية لها ثلاثة أسباب للتغيير: تغيير منطق المصادقة، تغيير طريقة تسجيل الأخطاء، أو تغيير شكل رسالة الترحيب.

Kotlin 
// قبل: دالة واحدة تعمل كل شيء
fun loginUser(email: String, password: String) {
    val result = FirebaseAuth.signIn(email, password) // مصادقة
    if (result.isFailure) {
        File("errors.txt").appendText(result.exception.toString()) // تسجيل
        return
    }
    showWelcomeMessage(result.user) // واجهة مستخدم
}

// بعد: فصل المسؤوليات
class FileLogger {
    fun logError(error: Throwable) {
        File("errors.txt").appendText("$error\n")
    }
}

class LoginUseCase(private val logger: FileLogger) {
    fun execute(email: String, password: String): User? {
        return try {
            FirebaseAuth.signIn(email, password).getOrThrow()
        } catch (e: Exception) {
            logger.logError(e)
            null
        }
    }
}

🔍 شرح الكود

  • FileLogger: مسؤولية واحدة — تسجيل الأخطاء. إذا قررنا لاحقًا الانتقال لـ Sentry أو قاعدة بيانات، نعدل هنا فقط.
  • LoginUseCase: مسؤولية واحدة — منطق المصادقة. لا يعرف شيئًا عن الواجهة الرسومية أو تفاصيل التسجيل.

O — Open/Closed Principle

قسم التسويق يطلب تسجيل أخطاء الحملات في ملف منفصل (campaign_errors.txt). الغريزة تقول: افتح FileLogger وغيّره. لكن هذا يكسر الكود القديم. الحل: التوسع بدل التعديل.

Kotlin 
open class FileLogger(private val fileName: String = "errors.txt") {
    open fun logError(error: Throwable) {
        File(fileName).appendText("$error\n")
    }
}

// توسيع بدون تعديل الكلاس الأصلي
class CampaignFileLogger : FileLogger("campaign_errors.txt")
✅ المبدأ

الكود القديم فضل مغلقًا (لم نلمسه). النظام كان مفتوحًا لإضافة السلوك الجديد عبر الوراثة.

L — Liskov Substitution Principle

ماذا لو كتبت في CampaignFileLogger دالة جديدة اسمها logCampaignError بدل override لـ logError؟

Kotlin 
// ❌ خطأ: كسر العقد
class CampaignFileLogger : FileLogger() {
    fun logCampaignError(error: Throwable) { // دالة جديدة!
        File("campaign_errors.txt").appendText("$error\n")
    }
}

// الكود المستهلك لا يعرف عن الدالة الجديدة
fun processError(logger: FileLogger, error: Throwable) {
    logger.logError(error) // سيسجل في errors.txt وليس campaign_errors.txt!
}
⚠️ كسر الثقة

الكلاس الأب يُعد بسلوك معين (logError). أي ابن يجب أن يكون بديلًا كاملًا للأب في أي مكان. إنشاء دالة جديدة باسم مختلف يُخفي السلوك عن الكود الذي يتعامل مع FileLogger عامةً. الـ Override يحافظ على العقد؛ إعادة التسمية تكسره.

I — Interface Segregation Principle

ظهرت أنواع جديدة من اللوجرز: واحد يُرسل إيميلات، وآخر يطبع للـ Debugging. صنعنا واجهة ضخمة اسمها ILogger تحتوي على logError و sendErrorEmail. FileLogger أُجبر على تنفيذ sendErrorEmail وتركها فارغة. هذا Fat Interface يُلوث الكود.

Kotlin 
// ✅ واجهات صغيرة متخصصة
interface ErrorLogger {
    fun logError(error: Throwable)
}

interface EmailNotifier {
    fun sendErrorEmail(error: Throwable)
}

// كل كلاس ينفذ ما يحتاجه فقط
class FileLogger : ErrorLogger {
    override fun logError(error: Throwable) { /* ... */ }
}

class AlertService : ErrorLogger, EmailNotifier {
    override fun logError(error: Throwable) { /* ... */ }
    override fun sendErrorEmail(error: Throwable) { /* ... */ }
}

🔍 شرح الكود

  • ErrorLogger: للتسجيل فقط.
  • EmailNotifier: للإيميلات فقط.
  • الكلاس الذي يفعل الاثنين ينفذ الواجهتين معًا. لا أحد يُجبر على تنفيذ ما لا يحتاجه.

D — Dependency Inversion Principle

في قلب كود تسجيل الدخول، لا يزال هناك سطر: FirebaseAuth.signIn(...). نحن مرتبطون بشكل مباشر بخدمة Firebase. إذا غيّرنا نظام المصادقة غدًا، يجب فتح الكلاس وتعديله.

Kotlin 
// التجريد: "أحتاج أي شيء يُجري المصادقة"
interface Authenticator {
    fun signIn(email: String, password: String): Result<User>
}

// التفاصيل تعتمد على التجريد
class FirebaseAuthenticator : Authenticator {
    override fun signIn(email: String, password: String): Result<User> {
        return FirebaseAuth.signIn(email, password)
    }
}

class CustomApiAuthenticator : Authenticator {
    override fun signIn(email: String, password: String): Result<User> {
        return apiClient.login(email, password)
    }
}

// الكود الرئيسي يعتمد على التجريد فقط
class LoginUseCase(private val authenticator: Authenticator) {
    fun execute(email: String, password: String): User? {
        return authenticator.signIn(email, password).getOrNull()
    }
}

// في مكان واحد فقط نحدد التفصيلة
val loginUseCase = LoginUseCase(FirebaseAuthenticator())

🔍 شرح الكود

  • Authenticator: التجريد. يحدد "ما" المطلوب لا "كيف".
  • FirebaseAuthenticator: تفصيل منخفض المستوى يعتمد على التجريد.
  • LoginUseCase: كود عالي المستوى يعتمد على التجريد فقط. تغيير Firebase إلى API خاص يتطلب تعديل سطر واحد خارجي فقط.
  • اختبار: يمكن إعطاء LoginUseCase FakeAuthenticator في الاختبارات.
🎯 ملخص الرحلة

S فكّك الزحمة. O أضف بأمان. L احترم العقود. I اجعل الواجهات دقيقة. D اقلب الاعتمادية: التفاصيل تعتمد على المفاهيم المجردة، لا العكس. الكود الناتج أرخص صيانة، وأسرع تطويرًا، وأكثر متعة في العمل.
