أساسيات حقن التبعيات (Dependency Injection 101)

المفاهيم الأساسية التي يجب على كل مهندس Android إتقانها

ما هو Dependency Injection ولماذا هو إلزامي؟

Dependency Injection (DI) هو نمط تصميم معماري (Design Pattern) يهدف إلى تقليل الارتباط الوثيق (Tight Coupling) بين الكائنات في التطبيق. بدلاً من أن يقوم الكائن بإنشاء تبعياته بنفسه (عبر new أو Factory methods)، يتم "حقن" هذه التبعيات من الخارج عبر Constructor أو Field أو Method Injection.

في عالم Android، حيث تتعقد الأنظمة بشكل هائل مع نمو التطبيقات، يصبح DI إلزامياً وليس اختيارياً. التطبيقات التي لا تستخدم DI تعاني من كود صعب الاختبار (Untestable)، وصيانة مكلفة، وتكرار غير ضروري. مع DI، يصبح كل مكون مستقلاً، ويمكن اختباره بمعزول، ويمكن استبدال تبعياته بسهولة.

💡 المبدأ الأساسي

Dependency Inversion Principle (DIP) — أحد مبادئ SOLID — ينص على أن الكائنات عالية المستوى لا يجب أن تعتمد على كائنات منخفضة المستوى، بل يجب أن تعتمد كلاهما على Abstractions. DI هو الآلية العملية لتطبيق هذا المبدأ.

الفوائد الجوهرية لـ DI

🔗
Decoupling (فك الارتباط)

يفصل الكود عن التفاصيل التنفيذية. يمكن تغيير Database implementation من Room إلى Realm دون تعديل ViewModels أو Repositories.

🧪
Testability (قابلية الاختبار)

يمكن استبدال الـ Dependencies الحقيقية بـ Mocks أو Fakes أثناء Unit Testing. لا حاجة لـ Robolectric في كل اختبار.

🔧
Maintainability (قابلية الصيانة)

تغيير في مكان واحد (Module) ينعكس على كل التطبيق. لا حاجة لتعديل عشرات الملفات عند تغيير Constructor.

⏳
Lifecycle Management

إدارة دورة حياة الكائنات تلقائياً. Singleton يعيش مع التطبيق، ActivityScoped يُدمَر مع الـ Activity، وهكذا.

⚠ تحذير هام

Koin يُصنف أحياناً كـ "Lightweight DI" لكنه في جوهره يستخدم Service Locator Pattern مع DSL. الفرق أنه يخفي ذلك عن المطور. Hilt يستخدم Pure DI مع Code Generation أثناء Compile-time.

أنواع Injection في Kotlin

1. Constructor Injection (الأفضل والأكثر تفضيلاً):

class UserRepository @Inject constructor(
    private val apiService: ApiService,
    private val database: AppDatabase
) {
    // Dependencies are immutable and available immediately
}

2. Field Injection (يُستخدم فقط عند الضرورة):

class MainActivity : AppCompatActivity() {
    @Inject
    lateinit var viewModel: MainViewModel
    // Used when constructor injection is impossible (e.g., Android framework classes)
}
✅ أفضل الممارسات

دائماً استخدم Constructor Injection كلما كان ذلك ممكناً. Field Injection يُستخدم فقط في Android Components (Activity, Fragment, Service) لأن Framework لا يسمح بـ Constructor Injection فيها. حتى في ViewModels، استخدم @HiltViewModel مع Constructor Injection.

الدليل العميق والمتقدم لـ Dagger Hilt

Hilt Masterclass — كل ما تحتاج معرفته عن Compile-time DI

ما هو Dagger Hilt؟

Dagger Hilt هو إطار عمل (Framework) لحقن التبعيات مبني أعلى Dagger 2، طورته Google خصيصاً لتبسيط DI في Android. Hilt يقوم بتوليد كود Java/Kotlin أثناء Compile-time باستخدام Annotation Processing Tool (APT) أو Kotlin Symbol Processing (KSP)، مما يضمن:

  • Compile-time Validation: أي خطأ في Graph يُكتشف أثناء Build وليس في Runtime.
  • Zero Reflection: لا يستخدم Reflection أبداً، مما يعني أداءً ممتازاً في Startup.
  • Android-aware Components: يفهم دورة حياة Android (Activity, Fragment, ViewModel) بشكل أصلي.

الإعداد والتهيئة

أضف الـ Dependencies في build.gradle.kts:

// Project level build.gradle.kts
plugins {
    id("com.google.dagger.hilt.android") version "2.51" apply false
}

// App level build.gradle.kts
plugins {
    id("com.google.dagger.hilt.android")
    id("com.google.devtools.ksp") // Recommended over kapt
}

dependencies {
    implementation("com.google.dagger:hilt-android:2.51")
    ksp("com.google.dagger:hilt-compiler:2.51")

    // For ViewModel support
    implementation("androidx.hilt:hilt-navigation-compose:1.2.0")

    // For Worker support
    implementation("androidx.hilt:hilt-work:1.2.0")
    ksp("androidx.hilt:hilt-compiler:1.2.0")
}

ثم أنشئ Application class مع @HiltAndroidApp:

@HiltAndroidApp
class MyApplication : Application() {
    // Hilt generates the necessary Dagger components automatically
}
📌 دور @HiltAndroidApp

هذه الـ Annotation تُنشئ ApplicationComponent (المعروف الآن بـ SingletonComponent) تلقائياً. هذا هو الجذر (Root) لـ Dependency Graph في التطبيق. بدونها، لن يعمل Hilt.

@AndroidEntryPoint — نقاط الدخول

أي Android Component (Activity, Fragment, Service, BroadcastReceiver, View) يريد استقبال Injection يجب أن يحمل @AndroidEntryPoint. هذا يُعلم Hilt بأن يولد Component فرعي مرتبط بدورة حياة هذا الـ Component. 

@AndroidEntryPoint
class MainActivity : AppCompatActivity() {

    @Inject
    lateinit var analytics: AnalyticsTracker

    private val viewModel: MainViewModel by viewModels()

    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        // analytics is injected automatically before onCreate
    }
}
⚠ قاعدة مهمة

إذا كان Fragment يستخدم @AndroidEntryPoint، يجب أن يكون الـ Activity المضيف أيضاً يحمل @AndroidEntryPoint. وإذا كان View يستخدمها، يجب أن يكون الـ Fragment أو Activity المضيف يحملها.

Modules & Provider Bindings

Module في Hilt هو Class يُعلم Hilt كيفية توفير (Provide) instances لأنواع لا يمكن حقنها تلقائياً (مثل مكتبات الطرف الثالث: Retrofit, Room, OkHttp).

@Provides — للمكتبات الخارجية:

@Module
@InstallIn(SingletonComponent::class)
object NetworkModule {

    @Provides
    @Singleton
    fun provideOkHttpClient(): OkHttpClient {
        return OkHttpClient.Builder()
            .addInterceptor(HttpLoggingInterceptor().apply {
                level = HttpLoggingInterceptor.Level.BODY
            })
            .build()
    }

    @Provides
    @Singleton
    fun provideRetrofit(okHttpClient: OkHttpClient): Retrofit {
        return Retrofit.Builder()
            .baseUrl("https://api.example.com/")
            .client(okHttpClient)
            .addConverterFactory(GsonConverterFactory.create())
            .build()
    }

    @Provides
    @Singleton
    fun provideApiService(retrofit: Retrofit): ApiService {
        return retrofit.create(ApiService::class.java)
    }
}

@Binds — لتنفيذات Interfaces (أكثر كفاءة):

@Module
@InstallIn(SingletonComponent::class)
abstract class RepositoryModule {

    @Binds
    @Singleton
    abstract fun bindUserRepository(
        impl: UserRepositoryImpl
    ): UserRepository

    @Binds
    @Singleton
    abstract fun bindAuthRepository(
        impl: AuthRepositoryImpl
    ): AuthRepository
}
✅ @Provides مقابل @Binds

استخدم @Binds دائماً عند ربط Interface بتنفيذ. لماذا؟ لأن @Binds يولد كود أقل وأسرع لأنه لا يحتاج إلى Instance Provider. @Provides يُستخدم فقط عندما تحتاج إلى Logic إضافي (مثل إنشاء Retrofit أو Room).

Multiple Implementations & Qualifiers

عندما يكون لديك أكثر من تنفيذ لنفس Interface (مثل ImageLoader مع تنفيذين: Glide و Coil)، يجب استخدام Qualifiers لتمييزها.

1. باستخدام @Named (الأسهل لكن أقل أماناً):

@Module
@InstallIn(SingletonComponent::class)
object ImageLoaderModule {

    @Provides
    @Singleton
    @Named("glide")
    fun provideGlideLoader(context: Context): ImageLoader = GlideImageLoader(context)

    @Provides
    @Singleton
    @Named("coil")
    fun provideCoilLoader(context: Context): ImageLoader = CoilImageLoader(context)
}

// Usage
class ProfileViewModel @Inject constructor(
    @Named("coil") private val imageLoader: ImageLoader
)

2. باستخدام Custom Qualifier (الأفضل والأكثر أماناً):

@Qualifier
@Retention(AnnotationRetention.RUNTIME)
annotation class GlideLoader

@Qualifier
@Retention(AnnotationRetention.RUNTIME)
annotation class CoilLoader

@Module
@InstallIn(SingletonComponent::class)
object ImageLoaderModule {

    @Provides
    @Singleton
    @GlideLoader
    fun provideGlide(context: Context): ImageLoader = GlideImageLoader(context)

    @Provides
    @Singleton
    @CoilLoader
    fun provideCoil(context: Context): ImageLoader = CoilImageLoader(context)
}

// Usage — Type-safe, no string literals
class ProfileViewModel @Inject constructor(
    @CoilLoader private val imageLoader: ImageLoader
)
✅ نصيحة Senior

تجنب @Named قدر الإمكان. Custom Qualifiers توفر Type Safety وتمنع أخطاء الكتابة (Typos) التي لا يكتشفها Compiler مع @Named.

Predefined Context Bindings

Hilt يوفر Context bindings جاهزة لا تحتاج إلى Module. يمكنك حقن Context مباشرة مع تحديد نوعه: 

class AnalyticsTracker @Inject constructor(
    @ApplicationContext private val appContext: Context
) {
    // Application-wide Context
}

class DialogHelper @Inject constructor(
    @ActivityContext private val activityContext: Context
) {
    // Activity-specific Context — only available in ActivityComponent scope
}

السيناريوهات المتقدمة

1. توفير Retrofit و Room Database:

@Module
@InstallIn(SingletonComponent::class)
object DatabaseModule {

    @Provides
    @Singleton
    fun provideDatabase(
        @ApplicationContext context: Context
    ): AppDatabase {
        return Room.databaseBuilder(
            context,
            AppDatabase::class.java,
            "app_database.db"
        )
        .addMigrations(Migrations.MIGRATION_1_2)
        .build()
    }

    @Provides
    fun provideUserDao(db: AppDatabase): UserDao = db.userDao()
}

2. @EntryPoint — للـ Classes التي لا يدعمها Hilt أصلاً:

بعض الـ Android Components لا تدعم @AndroidEntryPoint بشكل أصلي، مثل ContentProvider، Custom Views المُنشأة برمجياً، أو الـ Classes التي تُنشأ من قبل Framework. 

@EntryPoint
@InstallIn(SingletonComponent::class)
interface AnalyticsEntryPoint {
    fun analyticsTracker(): AnalyticsTracker
}

// Usage in ContentProvider
class MyContentProvider : ContentProvider() {

    private lateinit var analytics: AnalyticsTracker

    override fun onCreate(): Boolean {
        val appContext = context?.applicationContext ?: return false
        val entryPoint = EntryPointAccessors.fromApplication(
            appContext,
            AnalyticsEntryPoint::class.java
        )
        analytics = entryPoint.analyticsTracker()
        return true
    }
}
📌 متى تستخدم @EntryPoint؟

استخدم @EntryPoint فقط عندما لا يمكنك استخدام @AndroidEntryPoint. أمثلة: ContentProvider، BroadcastReceiver مع android:directBootAware="true"، Custom Views التي تُنشأ بـ new، أو الـ EntryPoints للـ Tests.

3. Hilt Worker — WorkManager Integration:

@HiltWorker
class SyncWorker @AssistedInject constructor(
    @Assisted context: Context,
    @Assisted params: WorkerParameters,
    private val repository: UserRepository,
    private val apiService: ApiService
) : CoroutineWorker(context, params) {

    override suspend fun doWork(): Result {
        return try {
            repository.syncWithRemote()
            Result.success()
        } catch (e: Exception) {
            Result.retry()
        }
    }
}

// In Application class
@HiltAndroidApp
class MyApplication : Application(), Configuration.Provider {

    @Inject
    lateinit var workerFactory: HiltWorkerFactory

    override val workManagerConfiguration: Configuration
        get() = Configuration.Builder()
            .setWorkerFactory(workerFactory)
            .build()
}

Hilt في Jetpack Compose

Hilt يتكامل بسلاسة مع Jetpack Compose عبر مكتبة hilt-navigation-compose. يمكنك حقن ViewModels بسهولة: 

@Composable
fun ProfileScreen(
    viewModel: ProfileViewModel = hiltViewModel()
) {
    val uiState by viewModel.uiState.collectAsStateWithLifecycle()

    Column(
        modifier = Modifier.fillMaxSize(),
        horizontalAlignment = Alignment.CenterHorizontally
    ) {
        Text(text = uiState.userName)
        Button(onClick = { viewModel.refresh() }) {
            Text("Refresh")
        }
    }
}

// ViewModel with SavedStateHandle
@HiltViewModel
class ProfileViewModel @Inject constructor(
    private val repository: UserRepository,
    savedStateHandle: SavedStateHandle
) : ViewModel() {

    private val userId: String = savedStateHandle["userId"] ?: ""

    val uiState = repository.getUser(userId)
        .stateIn(viewModelScope, SharingStarted.WhileSubscribed(5000), UiState.Loading)
}
✅ نصيحة Compose

استخدم دائماً hiltViewModel() بدلاً من viewModel() في Compose. hiltViewModel() يتأكد من أن الـ ViewModel يتم إنشاؤه مع الـ Dependencies المحقونة بشكل صحيح ويربطه بدورة حياة الـ Navigation Back Stack.

الدليل الشامل لـ Koin

Koin DSL & Lightweight DI — حقن التبعيات بدون Code Generation

ما هو Koin وكيف يعمل؟

Koin هو إطار عمل لحقن التبعيات مكتوب بالكامل بلغة Kotlin، ويعتمد على Kotlin DSL (Domain Specific Language) بدلاً من Annotation Processing. Koin لا يولد كود أثناء Compile-time، بل يبني Dependency Graph في Runtime باستخدام Reflection خفيف أو Kotlin Compiler Plugin (Koin Annotations).

الفلسفة الأساسية لـ Koin: "Just DSL, no magic". كل شيء صريح ومرئي في الكود. لا توجد Annotations مخفية، ولا Generated Code غامض، ولا Build Errors معقدة.

💡 آلية عمل Koin

Koin يستخدم Service Locator Pattern تحت الغطاء. عند استدعاء by inject() أو get()، يبحث Koin في الـ Registry الداخلية عن Definition مطابق، ثم يُنشئ Instance (أو يعيد Instance موجود) بناءً على النوع (single, factory, scoped).

التهيئة والإعداد

أضف الـ Dependencies في build.gradle.kts:

dependencies {
    // Core Koin
    implementation("io.insert-koin:koin-android:3.5.6")

    // For Jetpack Compose
    implementation("io.insert-koin:koin-androidx-compose:3.5.6")

    // For Navigation Compose
    implementation("io.insert-koin:koin-androidx-navigation:3.5.6")

    // For KMP (Kotlin Multiplatform)
    implementation("io.insert-koin:koin-core:3.5.6")
}

ثم ابدأ Koin في Application class:

class MyApplication : Application() {

    override fun onCreate() {
        super.onCreate()

        startKoin {
            // Bind Android Context
            androidContext(this@MyApplication)

            // Load modules
            modules(
                networkModule,
                databaseModule,
                repositoryModule,
                viewModelModule
            )
        }
    }
}

Modules & Definitions

في Koin، تُعرّف الـ Dependencies داخل module { ... } blocks باستخدام دوال مثل single، factory، و viewModel.

single — Singleton (نفس Instance لكل التطبيق):

val networkModule = module {
    // Singleton: same instance everywhere
    single { OkHttpClient.Builder().build() }

    single {
        Retrofit.Builder()
            .baseUrl("https://api.example.com/")
            .client(get()) // get() resolves OkHttpClient
            .addConverterFactory(GsonConverterFactory.create())
            .build()
    }

    single { get<Retrofit>().create(ApiService::class.java) }
}

factory — New Instance في كل مرة:

val useCaseModule = module {
    // Factory: new instance every time it's requested
    factory { ValidateEmailUseCase() }
    factory { ValidatePasswordUseCase() }
}

viewModel / viewModelOf — لـ Android ViewModels:

val viewModelModule = module {
    // Method 1: Explicit DSL
    viewModel { MainViewModel(get(), get()) }

    // Method 2: viewModelOf (Kotlin 1.8+, cleaner)
    viewModelOf(::ProfileViewModel)
    viewModelOf(::SettingsViewModel)
}
✅ متى تستخدم كل نوع؟

استخدم single للـ Repositories، Databases، Retrofit Instances. استخدم factory للـ UseCases أو الـ Objects التي لا تحتاج إلى State مشترك. استخدم viewModel للـ ViewModels (تُدار دورة حياةها تلقائياً).

Injection Resolution: Lazy vs Eager

Koin يوفر طريقتين لاسترجاع Dependencies: Lazy (التقييم الكسول) و Eager (التقييم الفوري).

Lazy Evaluation — by inject():

class MainActivity : AppCompatActivity() {
    // Lazy: resolved only when first accessed
    private val viewModel: MainViewModel by inject()
    private val analytics: AnalyticsTracker by inject()

    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        // viewModel is resolved here, not before
        viewModel.loadData()
    }
}

Eager Evaluation — get():

class UserRepository(
    private val apiService: ApiService,
    private val database: AppDatabase
) {
    // Both are resolved immediately at construction time
}

// In a module:
single { UserRepository(get(), get()) }

// Or directly:
val repository: UserRepository = getKoin().get()
📌 الفرق الأساسي

by inject() مثالي للـ Properties في Activity/Fragment لأنه يؤجل الـ Resolution إلى وقت الاستخدام. get() مثالي داخل Modules أو Constructor Parameters حيث تحتاج إلى الـ Instance فوراً.

Koin في Jetpack Compose

Koin يتكامل مع Jetpack Compose عبر koin-androidx-compose. يمكنك حقن ViewModels باستخدام koinViewModel(): 

@Composable
fun ProfileScreen(
    viewModel: ProfileViewModel = koinViewModel()
) {
    val uiState by viewModel.uiState.collectAsStateWithLifecycle()

    Column(modifier = Modifier.fillMaxSize()) {
        Text(text = uiState.userName)
    }
}

// With parameters
@Composable
fun DetailScreen(userId: String) {
    val viewModel: DetailViewModel = koinViewModel(
        parameters = { parametersOf(userId) }
    )
}

تمرير Parameters ديناميكية:

val viewModelModule = module {
    viewModel { (userId: String) ->
        DetailViewModel(userId, get())
    }
}

Koin في Kotlin Multiplatform (KMP)

Koin هو الخيار الأول لـ Kotlin Multiplatform، وهذا أحد أبرز مميزاته مقارنة بـ Hilt. بينما Hilt مرتبط بـ Android JVM-only، Koin يعمل على:

  • Android — عبر koin-android
  • iOS — عبر koin-core مع Kotlin/Native
  • Desktop (JVM) — عبر koin-core
  • JavaScript / WASM — عبر koin-core

مثال على Module مشترك في KMP:

// commonMain — shared across all platforms
val sharedModule = module {
    single<HttpClient> { createHttpClient() }
    single<UserRepository> { UserRepositoryImpl(get()) }
    factory { GetUserUseCase(get()) }
}

// androidMain
fun initKoin(context: Context) {
    startKoin {
        androidContext(context)
        modules(sharedModule, androidModule)
    }
}

// iosMain
fun initKoin() {
    startKoin {
        modules(sharedModule, iosModule)
    }
}
✅ لماذا Koin هو الأفضل لـ KMP؟

Hilt يعتمد على Java Annotation Processing (APT) و Dagger 2، اللذان يعملان فقط على JVM. Koin مكتوب بالكامل بلغة Kotlin ويعتمد على Kotlin DSL، مما يجعله Portable عبر كل المنصات التي تدعمها Kotlin Multiplatform.

Koin Annotations (الجيل الجديد)

Koin 3.2+ يقدم Koin Annotations التي تسمح باستخدام Annotations مشابهة لـ Hilt مع الاحتفاظ ببساطة Koin:

المقارنة المعمارية الحاسمة: Hilt مقابل Koin

Hilt vs. Koin Showdown — قرار معماري يحدد مستقبل مشروعك

الجدول الشامل للمقارنة

المعيار Dagger Hilt Koin
Core Paradigm Compile-time Code Generation
يستخدم APT/KSP لتوليد كود Java أثناء Build. الـ Dependency Graph يُبنى ويُتحقق بالكامل قبل تشغيل التطبيق.		 Runtime DSL / Service Locator
يستخدم Kotlin DSL لبناء Graph في Runtime. لا يوجد Code Generation (إلا مع Koin Annotations اختيارياً).
Performance Impact Build Time: أعلى بسبب Code Generation والـ Annotation Processing.
Runtime: صفر Reflection. أداء ممتاز في Startup.		 Build Time: أقل بكثير. لا يوجد Annotation Processing.
Runtime: يستخدم Reflection خفيف (أو Kotlin Compiler Plugin). Startup أبطأ قليلاً.
Safety & Bug Catching ✅ Compile-time Validation
أي Dependency مفقود أو Cycle أو Scope غير صحيح يُكتشف أثناء Build. لا يمكن تشغيل تطبيق به Errors.		 ⚠ Runtime Crashes
أخطاء الـ Missing Dependencies تظهر فقط عند الاستخدام الأول. يتطلب اختبار شامل (Integration Tests) لاكتشاف الأخطاء.
Learning Curve متوسط إلى عالٍ. يتطلب فهم Annotations (@Module, @Provides, @Binds, Scopes, Components). الأخطاء في Build قد تكون غامضة للمبتدئين. منخفض جداً. DSL بسيط وبديهي. أي مطور Kotlin يمكنه فهمه في دقائق. الأخطاء Runtime أسهل في الفهم.
Boilerplate Code أقل من Dagger 2 لكن أكثر من Koin. يتطلب Modules، Annotations، وربما EntryPoints. أقل بكثير. Module واحد بسيط يمكن أن يغطي كل التطبيق. لا حاجة لـ Annotations في معظم الحالات.
KMP Compatibility ❌ Android JVM Only
Hilt مبني على Dagger 2 و Java APT. لا يعمل إلا على Android JVM. لا يمكن استخدامه في iOS أو JS.		 ✅ Full KMP Support
يعمل على Android، iOS (Kotlin/Native)، Desktop (JVM)، و JavaScript/WASM. الخيار الوحيد لـ KMP DI.
Google Support ✅ Official Google
مدعوم رسمياً من Google. مدمج في Android Architecture Components. توثيق رسمي وتحديثات مستمرة.		 Community-Driven
مشروع Open Source قوي بقيادة InsertKoinIO. لكنه ليس Official Google. الدعم من المجتمع والشركات التي تستخدمه.
Jetpack Compose hiltViewModel() مع Navigation Integration ممتاز. SavedStateHandle مدعوم أصلاً. koinViewModel() مع Compose Integration ممتاز. Parameters ديناميكية أسهل في Koin.
Testing Hilt Testing Framework مع @HiltAndroidTest، HiltTestApplication، و @BindValue للـ Mocks. بسيط جداً: startKoin { modules(testModule) } أو loadKoinModules() / unloadKoinModules().
Debugging أخطاء Build معقدة (ComponentProcessor Errors). لكنها تمنع Runtime Crashes. أخطاء Runtime واضحة (StackTrace يوضح أي Dependency مفقود). لكنها تحدث عند المستخدم النهائي إذا لم تُختبر.

متى تختار Hilt؟ ومتى تختار Koin؟

🏆
اختر Hilt إذا...
  • تبني تطبيق Android Enterprise كبير الحجم مع فريق متعدد المطورين.
  • الـ Compile-time Safety أولوية قصوى (Banking, Healthcare, Fintech).
  • تريد دعماً رسمياً من Google مع ضمان الاستمرارية.
  • لا تحتاج إلى Kotlin Multiplatform — Android فقط.
  • تريد أداءً ممتازاً في Startup مع Zero Reflection.
  • تفضل أخطاء Build واضحة على Crashes في Production.
🚀
اختر Koin إذا...
  • تبني مشروع Kotlin Multiplatform (Android + iOS + Desktop).
  • تريد سرعة في التطوير مع أقل Boilerplate ممكن.
  • المشروع صغير إلى متوسط الحجم (MVVM بسيط).
  • فريقك يفضل Kotlin DSL على Annotations.
  • تريد Build Time سريع دون Annotation Processing.
  • تبني Prototype أو MVP وتحتاج إلى Velocity عالية.
🌟 نصيحة معمارية Senior
🏠
التطبيقات المؤسسية (Enterprise Android Apps)
اختر Hilt دائماً. الـ Compile-time Safety تمنع أخطاء Production مكلفة. في المؤسسات الكبيرة، يكون الـ Build Time أقل أهمية من الـ Runtime Safety. Hilt مدمج مع Android Architecture Components ويوفر تجربة موحدة للفريق.
🌐
مشاريع Kotlin Multiplatform (KMP)
اختر Koin دون تردد. هو الخيار الوحيد العملي لـ KMP DI. يمكنك مشاركة Modules بين Android و iOS و Desktop بسهولة. مع Koin Annotations، تحصل على تجربة قريبة من Hilt مع الحفاظ على Portability.
⚡
المشاريع السريعة (Fast-Paced / MVPs)
اختر Koin للـ Velocity. Setup في دقائق، DSL بديهي، ولا يوجد Build Errors معقدة. عندما ينمو المشروع وتحتاج إلى Compile-time Safety، يمكنك الترحيل إلى Hilt (أو الاستمرار مع Koin Annotations).
💡
الاستراتيجية الهجينة (Hybrid Strategy)
في المشاريع الكبيرة، يمكنك استخدام Hilt للـ Android Module و Koin للـ Shared KMP Module. Define Interfaces في commonMain مع Koin، وImplementها في Android بـ Hilt. هذا يتطلب Bridge صغير لكنه يعطيك أفضل ما في العالمين.

الخلاصة النهائية

لا يوجد "إطار أفضل" بشكل مطلق — الاختيار يعتمد على السياق. Hilt هو الخيار الأكثر أماناً وأداءً للـ Android Native. Koin هو الخيار الأكثر مرونة وسرعةً للـ KMP والمشاريع الخفيفة. المهندس Senior يختار الأداة بناءً على احتياجات المشروع، لا بناءً على الترند أو التفضيل الشخصي.

المهم أن تفهم المبادئ وراء DI — Decoupling, Inversion of Control, و Lifecycle Management — لأن هذه المبادئ تنطبق بغض النظر عن الإطار. إطار العمل مجرد أداة؛ المعمارية الصحيحة هي الهدف.
