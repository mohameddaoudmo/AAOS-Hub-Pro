منهجية إدارة مقابلة تصميم أنظمة الهواتف

How to Approach a Mobile System Design Interview
🎯
الهدف الاستراتيجي: مقابلة تصميم النظام ليست اختباراً للحفظ، بل هي محاكاة لتصميم منتج حقيقي ضمن قيود Battery و Memory و Network و Storage. نجاحك يعتمد على قدرتك على التنقل بين المستويات المختلفة للتصميم بسلاسة.

C — Clarify Requirements الدقائق 0-5
Clarification & Scope Definition

لا تبدأ بالحل أبداً. ابدأ بطرح الأسئلة التوضيحية لتحديد نطاق المشكلة. حدد:

  • Constraints: App size budget، API rate limits، Local DB storage limit

D — Discuss Trade-offs الدقائق 30-40
Architectural Decision Records (ADRs)

ناقش الخيارات البديلة بوضوح. لا يوجد تصميم "مثالي" — كل قرار له ثمن:

  • REST vs gRPC: Readability & Caching vs Performance & Payload Size
  • Room vs MMKV: Structured Queries vs Ultra-Low Latency Key-Value
  • Polling vs SSE vs WebSocket: Battery efficiency vs Real-time guarantees
  • SQLite vs Realm: Maturity & Ecosystem vs Ease of Use
S — Summarize & Handle Follow-ups الدقائق 40-45

  • ما هي استراتيجية Security (Encryption at Rest & in Transit)؟
  • كيف يتوسع النظام عند 10x Scale؟

طرح الأسئلة التوضيحية الصحيحة

Asking the Right Clarifying Questions
💡
القاعدة الذهبية: أول 5 دقائق من المقابلة تحدد 50% من نتيجتها. المهندس الذي يطرح أسئلة توضيحية دقيقة يُظهر System Thinking و Product Sense — وهما صفتان لا تُقدران بثمن في المستويات Senior+.
📋
Functional Requirements
المتطلبات الوظيفية
  • ما هي رحلات المستخدم الأساسية (Core User Journeys)؟
  • هل هناك Views ديناميكية تتغير حسب السياق؟
  • ما هي صيغ الـ Payload (JSON, Protobuf, XML)؟
  • ما هي آلية الـ Authentication (OAuth2, JWT, API Key)؟
  • هل يوجد Push Notifications أم In-App فقط؟
  • هل يدعم التطبيق Multiple Languages / RTL؟
⚡
Non-Functional Requirements
المتطلبات غير الوظيفية
  • ما هو Latency Tolerance المقبول (P50, P95, P99)؟
  • هل التطبيق يجب أن يعمل Offline-first أم Network-dependent؟
  • ما هو App Size Budget المستهدف (MB)؟
  • ما هو تأثير البطارية المقبول (Battery Impact)؟
  • ما هي معدلات تحديث الشاشة المستهدفة (60Hz vs 120Hz FPS)؟
  • هل هناك Accessibility requirements (TalkBack / VoiceOver)؟

🔷 تفصيل كل طبقة

🎨
UI Layer
Presentation & State Rendering
  • Views: Activities/Fragments (Android) أو ViewControllers (iOS)
  • Composables: Jetpack Compose (Android) أو SwiftUI (iOS)
  • ViewModels: يحتفظ بالـ State أثناء تغييرات الـ Configuration
  • StateHolders: MVI Pattern — State واحد غير قابل للتعديل (Immutable)
⚙️
Business Layer
Domain Logic & Use Cases
  • Use Cases: كل Use Case = عملية واحدة (مثال: GetUserProfileUseCase)
  • Domain Models: POJOs/Kotlin Data Classes خالصة — لا تعتمد على Android SDK
  • Repository Contracts: Interfaces تُحدد ما يمكن فعله، لا كيفية فعله
💾
Data Layer
Repositories, Storage & Caching
  • Repositories: تُقرر: Local أم Remote؟ أم الاثنين (Repository Pattern)
  • Local Storage: Room (SQL) / DataStore (Key-Value) / MMKV (High-perf KV)
  • Cache Manager: LruCache (Memory) + DiskLruCache (Disk) للصور
  • Remote Service: Retrofit + OkHttp (Android) / Alamofire (iOS)
🌐
Network Layer
HTTP Engine, Serialization & Sockets
  • HTTP Engine: OkHttp Connection Pooling, HTTP/2, QUIC
  • Interceptors: Auth Token Refresh, Retry Logic, Logging
  • Serializer: Moshi (Codegen) / Kotlinx Serialization (MPP)
  • Socket Client: WebSocket للـ Real-time, SSE للـ Server Push

🔷 حدود HLD مقابل LLD

المحور ينتمي إلى HLD يُؤجل إلى LLD
System Boundaries أين يبدأ Mobile Client وينتهي؟ ما هي الـ External APIs؟ —
Data Flow كيف تنتقل البيانات بين الطبقات؟ —
Data Models — حقول الـ JSON الـ Exact، Types، Validations
Interface Contracts — توقيعات الـ Functions، Parameters، Return Types
Algorithm Details — Pagination Logic، Sorting Strategy، Diffing Algorithm
External Dependencies هل نستخدم Firebase, AWS, MapBox, Stripe؟ كيف نُهيئ الـ SDK (Initialization Config)

نصيحة Staff Engineer: عند رسم HLD، ابدأ دائماً بسؤال: "What is the single source of truth for data in this system?" — الإجابة تُحدد إذا كنت بحاجة لـ Offline-first Architecture (Local DB = SSOT) أم Network-dependent (Server = SSOT).

🔷 تطبيق مبادئ SOLID في تصميم Mobile

S
Single Responsibility Principle
One Reason to Change

كل Class له سبب واحد للتغيير. لا تجعل UserRepository يتعامل مع Caching AND Networking AND Serialization AND Analytics.

Before (Anti-pattern)
class UserManager {
    fun fetchFromNetwork() { ... }
    fun saveToDatabase() { ... }
    fun showNotification() { ... }   // ❌ 3+ responsibilities
    fun logAnalytics() { ... }       // ❌ Analytics mixed in
}
After (SRP)
class UserRemoteDataSource(private val api: UserApi) { 
    suspend fun fetch(): UserDto 
}
class UserLocalDataSource(private val db: UserDao) { 
    suspend fun save(user: UserEntity) 
}
class NotificationManager { 
    fun show(title: String, body: String) 
}
class UserRepository(
    private val remote: UserRemoteDataSource,
    private val local: UserLocalDataSource
) { ... }
O
Open/Closed Principle
Open for Extension, Closed for Modification

عند إضافة نوع جديد من الـ API Responses، لا تعدل الـ Parser الحالي. استخدم Polymorphism.

Implementation
interface ResponseParser<T> {
    fun parse(json: String): T
}

class UserParser : ResponseParser<User> { 
    override fun parse(json: String): User = ... 
}
class OrderParser : ResponseParser<Order> { 
    override fun parse(json: String): Order = ... 
}
// Adding ProductParser requires ZERO changes to existing code
D
Dependency Inversion
Depend on Abstractions

الطبقات العليا لا تعتمد على التفاصيل. تعتمد على Abstractions. هذا يُسهّل الـ Unit Testing بشكل كبير.

Constructor Injection (Hilt / Koin)
class FeedViewModel(
    private val getFeedUseCase: GetFeedUseCase,  // Interface
    private val imageLoader: ImageLoader,         // Interface
    private val analytics: AnalyticsTracker       // Interface
) : ViewModel() { ... }

// In tests:
class FakeImageLoader : ImageLoader { 
    override fun load(url: String) = mockBitmap 
}
L/I
Liskov Substitution & Interface Segregation
Fat Interface Anti-pattern

لا تجبر الـ Client على تنفيذ Methods لا يحتاجها. اجزئ الـ Interfaces إلى وحدات صغيرة متخصصة.

Interface Segregation
// ❌ Bad: One fat interface
interface Storage {
    fun read(): ByteArray
    fun write(data: ByteArray)
    fun encrypt()
    fun compress()
    fun syncToCloud()
}

// ✓ Good: Segregated interfaces
interface Readable { fun read(): ByteArray }
interface Writable { fun write(data: ByteArray) }
interface Encryptable { fun encrypt() }

class SecureCache : Readable, Writable, Encryptable { ... }
class PublicCache : Readable, Writable { ... }

🔷 مناقشة المقايضات والحالات الحافة (Trade-offs & Edge Cases)

Battery Drain vs Real-time Precision

في تطبيقات التتبع (Uber)، كلما زادت دقة تحديث الموقع، زاد استهلاك البطارية.

✓ الحل الأمثل:
  • Adaptive GPS: دقة عالية أثناء الرحلة، منخفضة أثناء الانتظار
  • Fused Location Provider (GPS + Network + Sensors)
  • Batch Updates: إرسال كل 5-10 ثوانٍ بدلاً من Real-time
  • Geofencing: إيقاف التتبع عند مغادرة منطقة العمل
Memory Pressure vs Cache Size

في تطبيقات الصور (Instagram)، حجم الـ Cache يؤثر على الأداء والاستقرار.

✓ الحل الأمثل:
  • LruCache بحجم ديناميكي يعتمد على Runtime.getRuntime().maxMemory()
  • Disk LRU Cache للصور المضغوطة (JPEG 80% quality)
  • Downsampling: تحميل الصور بحجم الـ View فقط
  • Bitmap Pool لإعادة استخدام الذاكرة (Glide / Coil)
🚨
Edge Cases لا تُنسى في LLD:
  • Process Death: ما يحدث عندما يقتل النظام التطبيق بسبب Low Memory؟ هل تُحفظ الـ State في SavedStateHandle؟
  • Network Switch: الانتقال من Wi-Fi إلى Cellular — هل يُعاد الاتصال تلقائياً؟ هل نُعيد المحاولة فوراً؟
  • Doze Mode / App Standby: كيف يتصرف Background Sync على Android 6+؟
  • Low Battery Mode: هل نُقلل من Background Operations وGPS Polling؟
  • Configuration Change: دوران الشاشة — هل يُعاد إنشاء الـ ViewModel؟ (لا، إذا استخدمت Architecture Components)

الأخطاء الشائعة الواجب تجنبها
Common Mistakes to Avoid

الأنماط المضادة (Anti-patterns) التالية هي الأسباب الأكثر شيوعاً لرسوب المرشحين — حتى لو كانوا مهندسين تقنيين ممتازين. تجنبها يعني أنك تفهم Mobile System Design كمنظور هندسي وليس كمجرد كتابة كود.

🚫
فخ المهندس المتسرع
The "Rushing Engineer" Trap

الخطأ: البدء برسم Architecture diagram في الدقيقة الأولى دون طرح أي سؤال توضيحي.

✗ لماذا هذا خطأ فادح؟
  • يُظهر أنك لا تفهم Product Context
  • قد تبني حلاً لمسألة غير موجودة (Over-engineering)
  • تفوتك Constraints حاسمة (Battery, Offline, Scale)
✓ الحل: ابدأ دائماً بـ "دعني أتأكد من فهمي للمتطلبات..." ثم اطرح 3-5 أسئلة توضيحية.
💻
تجاهل قيود الهاتف المحمول
Treating Mobile like a Server

الخطأ: التصرف وكأن الهاتف لديه Infinite RAM/CPU و Unlimited Battery و Always-On Network.

✗ أمثلة على هذا الخطأ:
  • "سأُبقي WebSocket مفتوحاً دائماً" — بدون Battery Impact analysis
  • "سأخزن كل البيانات في الذاكرة" — بدون Memory Pressure handling
  • "سأجلب كل Feed دفعة واحدة" — بدون Pagination أو Lazy Loading
✓ الحل: اذكر دائماً Mobile Constraints كأولوية: Battery, Memory, Network, Storage, Thermal Throttling.
🏗️
الإفراط في التعقيد
Over-Engineering

الخطأ: إضافة Micro-frameworks أو Abstractions غير ضرورية لتطبيق بسيط (مثال: Event Bus + RxJava + Dagger + 5 Libraries لـ To-Do App).

✗ لماذا هذا خطأ؟
  • يزيد App Size (APK/IPA) بلا داعٍ
  • يُعقد الـ Build Time و Debugging
  • يُظهر أنك لا تفهم YAGNI (You Aren't Gonna Need It)
✓ الحل: ابدأ بأبسط حل يُلبي المتطلبات. أضف Complexity فقط عندما تُبرهن الحاجة إليها.
⚖️
عدم مناقشة المقايضات
Presenting "Perfect" Design

الخطأ: تقديم تصميم كأنه "مثالي" بدون عيوب. كل قرار معماري له ثمن (Trade-off).

✗ أمثلة:
  • "WebSocket أفضل دائماً" — بدون مناقشة Battery Drain
  • "Room أفضل دائماً" — بدون مناقشة Write Latency
  • "Offline-first أفضل دائماً" — بدون مناقشة Conflict Complexity
✓ الحل: لكل قرار تقوله، اذكر: "اخترت X لأنه يُعطيني A، لكن الثمن هو B. في سياق هذا التطبيق، A أهم من B لأن..."
🔄
خلط مستويات HLD و LLD
Mixing Abstraction Levels

الخطأ: الدخول في تفاصيل الـ Function Parameters أثناء رسم الـ High-Level Architecture، أو البقاء في مستوى المربعات والأسهم عندما يطلب المقابل الـ Code.

✗ المشكلة:
  • يُظهر عدم وضوح في التفكير المُنظم (Structured Thinking)
  • يُضيع الوقت في تفاصيل لا تهم في المرحلة الحالية
  • يُربك المقابل — لا يعرف في أي مستوى أنت
✓ الحل: استخدم عبارة: "في مستوى HLD، نرى أن... والآن دعني أتعمق في LLD للمكون X..."
🔒
تجاهل الأمان والخصوصية
Ignoring Security

الخطأ: عدم ذكر Security حتى يُسأل عنها. في تطبيقات الهاتف، الأمان ليس "إضافة" — هو متطلب أساسي.

✗ ما يُفترض ذكره تلقائياً:
  • Data Encryption at Rest (SQLCipher / Keychain / Keystore)
  • HTTPS / TLS 1.3 for Data in Transit
  • Certificate Pinning لمنع MITM attacks
  • OAuth2 / JWT Token Management (Refresh logic)
  • Input Validation و Protection against SQL Injection

class OfflineMessageQueue(
    private val db: PendingMessageDao,
    private val networkMonitor: NetworkMonitor,
    private val syncEngine: SyncEngine
) {
    // Queue message when offline
    suspend fun enqueue(message: Message) {
        db.insert(PendingMessage(
            id = generateUUID(),
            payload = message.encrypt(),
            priority = Priority.HIGH,
            retryCount = 0,
            createdAt = System.currentTimeMillis()
        ))
    }

    // Auto-sync when network returns
    init {
        networkMonitor.isOnline
            .filter { it }
            .flatMapConcat { db.getPending() }
            .collect { pending ->
                pending.forEach { msg ->
                    try {
                        syncEngine.send(msg.decrypt())
                        db.delete(msg.id)
                    } catch (e: NetworkException) {
                        if (msg.retryCount < MAX_RETRIES) {
                            db.incrementRetry(msg.id)
                        } else {
                            db.markFailed(msg.id)
                        }
                    }
                }
            }
    }
}

🚨 الحالات الحافة

  • Message Duplication: استخدام Idempotency Keys (UUID لكل رسالة) لمنع الإرسال المزدوج عند إعادة المحاولة
  • Device Switch: مزامنة الرسائل عبر أجهزة متعددة باستخدام Multi-Device Protocol
  • Key Rotation: تدوير مفاتيح التشفير كل N رسالة

class ImageUploadManager(
    private val api: MediaApi,
    private val compressor: ImageCompressor,
    private val workManager: WorkManager
) {
    fun uploadImage(uri: Uri, metadata: PostMetadata): UUID {
        // 1. Compress locally first
        val compressed = compressor.compress(
            input = uri,
            maxWidth = 1080,
            maxHeight = 1080,
            quality = 85
        )

        // 2. Schedule background upload with WorkManager
        val uploadWork = OneTimeWorkRequestBuilder<ImageUploadWorker>()
            .setInputData(workDataOf(
                "file_path" to compressed.path,
                "caption" to metadata.caption,
                "filter_id" to metadata.filterId
            ))
            .setConstraints(Constraints.Builder()
                .setRequiredNetworkType(NetworkType.CONNECTED)
                .build())
            .setBackoffCriteria(
                BackoffPolicy.EXPONENTIAL,
                WorkRequest.MIN_BACKOFF_MILLIS,
                TimeUnit.MILLISECONDS
            )
            .build()

        workManager.enqueue(uploadWork)
        return uploadWork.id
    }
}

// Chunked upload for large files / poor network
class ChunkedUploader(private val api: MediaApi) {
    suspend fun upload(file: File, chunkSize: Int = 256 * 1024) {
        val totalChunks = ceil(file.length() / chunkSize.toDouble()).toInt()
        val uploadId = api.initiateUpload(file.name, file.length())

        file.inputStream().use { stream ->
            val buffer = ByteArray(chunkSize)
            var chunkIndex = 0

            while (stream.read(buffer) > 0) {
                api.uploadChunk(uploadId, chunkIndex, totalChunks, buffer)
                chunkIndex++
            }
        }

        api.finalizeUpload(uploadId)
    }
}

🚨 الحالات الحافة

  • Upload Interruption: WorkManager يضمن إعادة المحاولة حتى 3 مرات مع Exponential Backoff
  • Memory Pressure during Filter: استخدام GPU Rendering (OpenGL / Metal) بدلاً من CPU Bitmap manipulation
  • Duplicate Upload: Content-Addressable Storage (Hash-based deduplication)
  • Storage Quota: LruDiskCache يحذف الصور القديمة تلقائياً عند امتلاء الذاكرة

sealed class RideState {
    object IDLE : RideState()
    object SEARCHING : RideState()      // Looking for drivers
    data class MATCHED(val driverId: String) : RideState()
    data class DRIVER_ARRIVING(val eta: Int) : RideState()
    object ON_TRIP : RideState()
    data class PAYMENT_PENDING(val amount: Double) : RideState()
    object COMPLETED : RideState()
    data class CANCELLED(val reason: String) : RideState()
}

class RideStateMachine {
    private val _state = MutableStateFlow<RideState>(RideState.IDLE)
    val state: StateFlow<RideState> = _state.asStateFlow()

    fun transition(event: RideEvent): Result<Unit> {
        val newState = when (_state.value to event) {
            is (IDLE to RequestRide) -> SEARCHING
            is (SEARCHING to DriverAccepted) -> MATCHED(event.driverId)
            is (MATCHED to DriverArrived) -> DRIVER_ARRIVING(event.eta)
            is (DRIVER_ARRIVING to TripStarted) -> ON_TRIP
            is (ON_TRIP to TripEnded) -> PAYMENT_PENDING(event.fare)
            is (PAYMENT_PENDING to PaymentSuccess) -> COMPLETED
            else -> return Result.failure(IllegalStateException(
                "Invalid transition: ${_state.value} -> $event"
            ))
        }
        _state.value = newState
        return Result.success(Unit)
    }
}

  • GPS Drift: Kalman Filtering لتنعيم إشارات GPS الضعيفة
  • App Kill during Trip: Foreground Service + Notification لضمان استمرار التتبع

class AdaptiveBitrateSelector {
    fun selectTrack(availableTracks: List<Track>, 
                    bandwidth: Long, 
                    bufferHealth: Long): Track {
        return when {
            // If buffer is healthy and bandwidth allows, upgrade quality
            bufferHealth > BUFFER_THRESHOLD_HIGH && 
            bandwidth > availableTracks[currentIndex + 1].bitrate -> 
                availableTracks[currentIndex + 1]

            // If bandwidth drops or buffer is low, downgrade immediately
            bandwidth < availableTracks[currentIndex].bitrate * 0.8 ||
            bufferHealth < BUFFER_THRESHOLD_LOW -> 
                availableTracks.find { it.bitrate <= bandwidth * 0.7 } 
                    ?: availableTracks.first()

            else -> availableTracks[currentIndex]
        }
    }
}

        val token = queue.enqueue(userId, productId, priority = System.currentTimeMillis())

        // Poll for queue position
        return pollForTurn(token)
    }

    // Step 2: When token is active, reserve inventory
    suspend fun attemptCheckout(token: Token, payment: PaymentInfo): Result<Order> {
        // Optimistic inventory reservation (holds item for 5 minutes)
        val reservation = inventoryService.reserve(token.productId, quantity = 1)

        if (!reservation.success) {
            return Result.failure(SoldOutException())
        }

        // Step 3: Process payment within reservation window
        return try {
            val order = paymentService.charge(payment)
            inventoryService.confirmReservation(reservation.id)
            Result.success(order)
        } catch (e: PaymentException) {
            inventoryService.releaseReservation(reservation.id)
            Result.failure(e)
        }
    }
}

// Client-side: Show queue position with WebSocket updates
class FlashSaleViewModel : ViewModel() {
    private val _queuePosition = MutableStateFlow<Int>(0)
    val queuePosition: StateFlow<Int> = _queuePosition

    fun observeQueue(token: Token) {
        webSocketManager.observe("queue:${token.id}")

// WebSocket connection with binary protocol (Protobuf) for minimal overhead
class StockTickerManager(
    private val webSocket: WebSocketClient,
    private val protobufParser: ProtobufParser
) {
    private val _prices = MutableStateFlow<Map<String, StockPrice>>(emptyMap())
    val prices: StateFlow<Map<String, StockPrice>> = _prices

    fun connect(symbols: List<String>) {
        webSocket.connect("wss://ticker.broker.com/stream")

        // Subscribe to symbols
        val subscribeMsg = SubscribeMessage(
            symbols = symbols,
            fields = listOf(PRICE, VOLUME, CHANGE, BID, ASK)
        )
        webSocket.send(subscribeMsg.toProtobuf())

        webSocket.onMessage { bytes ->
            val tick = protobufParser.parse<TickUpdate>(bytes)
            _prices.update { current ->
                current + (tick.symbol to tick.toStockPrice())
            }
        }
    }

    // Throttle UI updates to 16ms (60 FPS) to prevent jank
    val throttledPrices = prices
        .sample(16)  // Kotlin Flow sample operator
        .distinctUntilChanged()
}

class BookingValidator {
    fun validate(checkIn: Date, checkOut: Date, availability: AvailabilityCalendar): ValidationResult {
        val nights = ChronoUnit.DAYS.between(checkIn, checkOut)

        return when {
            nights < 1 -> ValidationResult.Error("Minimum stay is 1 night")
            nights > 30 -> ValidationResult.Error("Maximum stay is 30 nights")
            checkIn.isBefore(LocalDate.now()) -> ValidationResult.Error("Check-in cannot be in the past")
            !availability.isAvailable(checkIn, checkOut) -> 
                ValidationResult.Error("Selected dates are not available")
            else -> ValidationResult.Success(nights = nights, totalPrice = availability.calculatePrice(checkIn, checkOut))
        }
    }
}
