01

لماذا تُعتبر دورة الحياة الأهم في مقابلات Android؟

لأن النظام هو من يقرر متى تُنشأ الـ Activity ومتى تُدمَّر — ليس المطور. فهم هذه الدورة يحدد إن كان تطبيقك يفقد بيانات المستخدم، يتسرب في الذاكرة، أو ينهار عند تدوير الشاشة.

Activity Lifecycle هو نظام حالات (state machine) تديره الـ ActivityThread استجابةً لأحداث النظام: فتح تطبيق آخر، تدوير الشاشة، الضغط على Home، نفاد الذاكرة، أو رجوع المستخدم.

المبدأ الأساسي

الـ Activity لا "تتحكم" في متى تُدمَّر — هي فقط تستجيب. أي كود يفترض أن onDestroy() ستُستدعى دائمًا (لتنظيف موارد حرجة مثلًا) هو افتراض خاطئ؛ النظام قد يقتل العملية بأكملها دون استدعاء أي دالة.

02

الحالات السبع بالتفصيل

onCreate(savedInstanceState: Bundle?)

تُستدعى مرة واحدة عند إنشاء الـ Activity. هنا: inflate الـ layout، تهيئة ViewModel، استرجاع الحالة المحفوظة من Bundle. الـ Activity ليست مرئية بعد.

onStart()

الـ Activity أصبحت مرئية للمستخدم لكن لم تحصل على التفاعل (focus) بعد. مناسبة لبدء تحديثات UI الخفيفة.

onResume()

الـ Activity في المقدمة بالكامل وتستقبل تفاعل المستخدم. مناسبة لبدء الكاميرا، المستشعرات (sensors)، أو أي مورد يحتاج تفاعلًا مباشرًا.

onPause()

تُستدعى عندما تفقد الـ Activity الـ focus جزئيًا (مثلًا حوار شفاف يظهر فوقها، أو Activity أخرى في وضع multi-window). يجب أن تكون سريعة جدًا — النظام ينتظرها لإكمال الانتقال.

onStop()

الـ Activity لم تعد مرئية بالكامل. مناسبة لإيقاف عمليات مكلفة (تحديثات موقع، مزامنة). قد يليها onDestroy() أو onRestart() حسب سلوك المستخدم.

onRestart()

تُستدعى فقط عندما يعود المستخدم لـ Activity متوقفة (stopped) قبل تدميرها — تُستدعى قبل onStart() مباشرة.

onDestroy()

الاستدعاء الأخير قبل زوال الـ Activity — إما بسبب finish() أو تدوير الشاشة أو تدمير النظام لها. تنظيف الموارد النهائي (إن استُدعيت أصلًا).

الحالات المُشتقة (Derived States)

الحالةالوصف
Foreground (Resumed)مرئية وتستقبل التفاعل. أولوية قتل منخفضة جدًا من النظام.
Visible (Started/Paused)مرئية جزئيًا أو كليًا لكن دون تفاعل كامل. أولوية قتل متوسطة.
Background (Stopped)غير مرئية إطلاقًا. أول مرشح للقتل عند نقص الذاكرة.
03

Configuration Changes وإعادة الإنشاء

تدوير الشاشة، تغيير اللغة، أو وضع تقسيم الشاشة (multi-window) تُعتبر جميعها "تغييرات تهيئة" — والسلوك الافتراضي للنظام هو تدمير الـ Activity بالكامل وإعادة إنشائها من الصفر.

// السلسلة الكاملة عند تدوير الشاشة:
// onPause() → onStop() → onSaveInstanceState() → onDestroy()
// ثم: onCreate() → onStart() → onRestoreInstanceState() → onResume()

لماذا هذا السلوك موجود أصلًا؟

لأن موارد مختلفة (layout-land، layout قيم مختلفة للغات) قد تحتاج تحميلًا كاملًا مختلفًا بناءً على التهيئة الجديدة — إعادة الإنشاء تضمن تحميل الموارد الصحيحة تلقائيًا.

التحكم اليدوي (نادرًا ما يُنصح به)

<activity
    android:name=".MainActivity"
    android:configChanges="orientation|screenSize|keyboardHidden" />
تحذير

استخدام android:configChanges يمنع النظام من إعادة إنشاء الـ Activity، لكنه يعني عليك تحديث الموارد يدويًا عبر onConfigurationChanged(). غالبية الفرق تتجنب هذا وتعتمد على ViewModel بدلًا منه.

04

onSaveInstanceState مقابل ViewModel

أداتان مختلفتان تمامًا لمشكلتين مختلفتين، وخلطهما من أكثر أخطاء المقابلات شيوعًا.

المعيارonSaveInstanceState (Bundle)ViewModel
ينجو من تدوير الشاشة؟نعمنعم
ينجو من قتل النظام للعملية (process death)؟نعملا (إلا مع SavedStateHandle)
ينجو من الضغط على زر الرجوع (finish)؟لالا
حجم البيانات المناسبصغير جدًا (كيلوبايتات) — يُسلسَل عبر Binderأي حجم — يبقى في الذاكرة كـ object
الغرضحفظ حالة UI بسيطة (نص مكتوب، موضع تمرير)الاحتفاظ بحالة الشاشة ومنطق الأعمال عبر إعادة الإنشاء
override fun onSaveInstanceState(outState: Bundle) {
    super.onSaveInstanceState(outState)
    outState.putString("query", currentQuery)
}

override fun onCreate(savedInstanceState: Bundle?) {
    super.onCreate(savedInstanceState)
    val restoredQuery = savedInstanceState?.getString("query")
}
الحل الحديث الموصى به

SavedStateHandle داخل ViewModel يدمج الميزتين: يعيش عبر تدوير الشاشة (كـ ViewModel عادي) وينجو أيضًا من process death (لأنه مبني فوق onSaveInstanceState داخليًا).

05

Tasks و Back Stack و launchMode

الـ Task هو مجموعة Activities مرتّبة كـ stack. launchMode يحدد كيف تُضاف Activity جديدة لهذا الـ stack.

launchModeالسلوك
standardالافتراضي. كل استدعاء لـ startActivity ينشئ instance جديدة دائمًا، حتى لو كانت موجودة أصلًا.
singleTopإن كانت الـ Activity الهدف بالفعل في أعلى الـ stack، يُعاد استخدام نفس الـ instance عبر onNewIntent() بدل إنشاء واحدة جديدة.
singleTaskinstance واحدة فقط في الـ task بالكامل. إن كانت موجودة في مكان ما بالـ stack، تُزال كل الـ Activities فوقها ويُعاد استخدامها.
singleInstanceمثل singleTask، لكن الـ Activity تعيش في task منفصل تمامًا لا تشاركه أي Activity أخرى.
مثال شائع في المقابلات

شاشة تسجيل الدخول (Login) غالبًا تُستخدم بـ singleTask مع flags مثل FLAG_ACTIVITY_CLEAR_TASK عند تسجيل الخروج، لمنع المستخدم من الرجوع لشاشات محمية عبر زر الرجوع.

06

onNewIntent ولماذا يُنسى غالبًا

عند إعادة استخدام instance موجودة (singleTop/singleTask)، لا تُستدعى onCreate() مجددًا — بل onNewIntent() فقط، وهذا فخ شائع في المقابلات.

override fun onNewIntent(intent: Intent) {
    super.onNewIntent(intent)
    // يجب تحديث الـ intent المخزن يدويًا
    setIntent(intent)
    handleDeepLink(intent)
}
خطأ شائع

الاعتماد فقط على intent الأصلي (المُمرَّر لـ onCreate) دون تحديثه في onNewIntent() يجعل التطبيق يتعامل مع بيانات قديمة عند deep link ثانٍ لنفس الـ Activity.

07

Process Death مقابل الإغلاق العادي

أهم فرق يخلط فيه أغلب المرشحين في المقابلات المتقدمة.

السيناريوما الذي يحدث
الضغط على زر الرجوع (finish)onPause → onStop → onDestroy. الـ Activity تُزال من الـ back stack نهائيًا. isFinishing() = true.
الضغط على HomeonPause → onStop فقط. الـ Activity تبقى في الذاكرة (instance حي) بانتظار العودة.
تدوير الشاشةonPause → onStop → onSaveInstanceState → onDestroy → إعادة إنشاء كاملة فورية.
Process Death (نظام يقتل العملية في الخلفية)لا تُستدعى أي دالة على الإطلاق! العملية تُقتل مباشرة. عند العودة: onCreate يُستدعى مع Bundle محفوظ مسبقًا (إن وُجد).
كيف تختبرها فعليًا

عبر Developer Options → "Don't keep activities"، أو أمر adb shell am kill <package> بعد وضع التطبيق في الخلفية — هذا يحاكي process death الحقيقي وليس مجرد onStop.

أسئلة المقابلات الصعبة

أسئلة حقيقية تُطرح في مقابلات Android للمستويات المتوسطة والمتقدمة، مرتّبة حسب الموضوع، مع إجابات مفصّلة يمكنك البناء عليها بأسلوبك الخاص.

مجموعة أ — الأساسيات العميقة
هل يمكن أن تُستدعى onPause() بدون أن يليها onStop()؟ اشرح متى ولماذا.صعب

نعم. إذا ظهرت فوق الـ Activity الحالية نافذة حوار (Dialog) أو Activity شفافة لا تغطي الشاشة بالكامل، تُستدعى onPause() فقط لأن الـ Activity الأصلية ما زالت مرئية جزئيًا — لكنها فقدت الـ focus. onStop() لا تُستدعى إلا عندما تصبح الـ Activity غير مرئية بالكامل.

ما الفرق بين isFinishing() و isDestroyed()؟ ولماذا نحتاج لفحصهما قبل عمليات معينة؟دقيق

isFinishing() تصبح true بمجرد استدعاء finish() أو حدوث إنهاء طبيعي — حتى قبل onDestroy(). أما isDestroyed() فتصبح true فقط بعد اكتمال onDestroy() فعليًا.

الفحص مهم قبل عمليات async (مثل عرض Dialog بعد استجابة شبكة متأخرة) لتفادي WindowManager.BadTokenException عند محاولة عرض UI على Activity في طريقها للزوال.

لماذا onPause() يجب أن تكون سريعة جدًا؟ ماذا يحدث إن أبطأتها؟صعب

لأن النظام لا يسمح للـ Activity الجديدة (التي ستظهر فوقها) بالانتقال إلى onResume() حتى تنتهي onPause() للـ Activity الحالية بالكامل. أي عملية بطيئة (I/O متزامن، حسابات ثقيلة) هنا تجمّد الانتقال البصري بالكامل وقد تسبب ANR.

مجموعة ب — Configuration Changes وViewModel
ViewModel ينجو من تدوير الشاشة — كيف تقنيًا، وما الآلية الداخلية؟صعب

عند تدمير Activity بسبب تغيير تهيئة (وليس finish حقيقي)، يحتفظ النظام بـ NonConfigurationInstances الذي يحمل مرجع ViewModelStore. الـ Activity الجديدة (بعد إعادة الإنشاء) تسترجع نفس ViewModelStore بدل إنشاء واحد جديد — لذا نفس instances الـ ViewModel تبقى حية دون إعادة تهيئة.

الفرق الجوهري: هذا يعمل فقط عبر onRetainNonConfigurationInstance() الداخلي، وهو مختلف تمامًا عن process death حيث يُفقد كل شيء في الذاكرة.

لديك تحميل صورة كبيرة (Bitmap) قيد التنفيذ عند تدوير الشاشة. أين يجب أن يعيش هذا الكود، ولماذا وضعه في Activity مباشرة خطأ؟صعب

يجب أن يعيش في ViewModel (عبر viewModelScope) وليس في Activity. لأن الـ Activity تُدمَّر فعليًا عند التدوير، فأي coroutine أو callback مرتبط بها مباشرة سيُلغى أو يُشير إلى context ميت (memory leak إن لم يُلغَ). ViewModel ينجو من التدوير، فتستمر العملية دون انقطاع ودون تكرارها من جديد.

ما هو Diamond Problem في LiveData عند التدوير السريع المتكرر (rapid rotation)؟دقيق

عند تدوير الشاشة بسرعة عدة مرات متتالية، قد تُنشأ عدة Activities/observers بينما القديمة لم تُنظَّف بعد بالكامل، ما قد يؤدي لاستدعاء observer قديم على View مُدمَّر. الحل: استخدام viewLifecycleOwner بدل this عند المراقبة داخل Fragment، والتأكد من أن الـ observer يُزال تلقائيًا مع ربطه بـ LifecycleOwner الصحيح بدل إدارته يدويًا.

مجموعة ج — Tasks و Back Stack
الفرق بين FLAG_ACTIVITY_CLEAR_TOP و FLAG_ACTIVITY_CLEAR_TASK — ومتى تستخدم كل واحد؟صعب

CLEAR_TOP: إن كانت الـ Activity الهدف موجودة في الـ stack، تُزال كل الـ Activities الموجودة فوقها فقط، وتُعاد نفس instance (عبر onNewIntent).

CLEAR_TASK: أقوى بكثير — يمسح الـ task بالكامل ويبدأ الـ Activity الهدف كجذر جديد تمامًا للـ stack. يُستخدم غالبًا مع تسجيل الخروج لمنع أي رجوع لشاشات محمية.

لديك singleTask Activity، وفتحتها من تطبيق آخر بينما كانت بالفعل تعمل في الخلفية ضمن task خاص بها. ماذا يحدث لدورة الحياة بالتفصيل؟صعب

النظام يجلب الـ task بالكامل (الذي يحتوي على هذه الـ Activity) إلى المقدمة بدل إنشاء instance جديدة. يحدث: onNewIntent() ثم onRestart() → onStart() → onResume() على نفس instance القديمة. لا يُستدعى onCreate() إطلاقًا لأن الـ instance لم تُدمَّر أصلًا — فقط كانت في الخلفية.

مجموعة د — Process Death والذاكرة
كيف تفرّق فعليًا بين "Activity في stopped state" و"process تم قتلها بالكامل" عمليًا في الكود؟دقيق

لا توجد طريقة مباشرة للتمييز من داخل onCreate نفسها — كلا الحالتين تنتهيان بنفس المسار الظاهري (onCreate مع أو بدون savedInstanceState). لكن الفرق العملي: في الحالة الأولى كل الكائنات في الذاكرة (Application class, singletons, statics) بقيت كما هي. في الحالة الثانية، Application.onCreate() يُستدعى من جديد بالكامل — فحص متغير static تم تعيينه في onCreate الخاص بالـ Application هو أحد الطرق العملية لتتبع ذلك أثناء debugging.

لماذا لا يُعتبر onDestroy() مكانًا موثوقًا لتنظيف موارد حرجة (مثل إغلاق اتصال قاعدة بيانات أو رفع بيانات analytics مهمة)؟صعب

لأن النظام قد يقتل العملية مباشرة (Process Death) دون استدعاء أي دورة حياة على الإطلاق، خصوصًا تحت ضغط ذاكرة عالٍ أو عند وضع "Don't keep activities". أي عملية حرجة يجب أن تُنفَّذ بشكل استباقي (مثل WorkManager لعمليات مضمونة التنفيذ) بدل الاعتماد على onDestroy كنقطة تنظيف مضمونة.

ما دور ActivityManager وoom_adj في تحديد أي Activity/عملية تُقتل أولًا عند نقص الذاكرة؟دقيق

يمنح النظام كل عملية "oom_adj score" بناءً على أهميتها الحالية: العمليات في المقدمة (foreground) تحصل على أدنى قيمة (أولوية قتل شبه معدومة)، بينما العمليات في الخلفية التي لا تملك أي مكون نشط (لا Service، لا Activity مرئية) تحصل على أعلى قيمة وتكون أول مرشح للقتل عند الحاجة لتحرير ذاكرة لتطبيقات أخرى.

مجموعة هـ — أسئلة سيناريو تطبيقية
مستخدم يملأ فورمًا طويلًا، ثم يستقبل مكالمة هاتفية (تطبيق آخر يظهر فوق تطبيقك)، ثم يعود. ما الاستراتيجية الصحيحة لضمان عدم فقدان بياناته؟صعب

الاعتماد فقط على onSaveInstanceState محفوف بالمخاطر إن كانت البيانات كبيرة (حدود حجم Bundle عبر Binder محدودة، عادة أقل من 1MB إجمالًا لكل الـ transaction). الحل الأصح: تخزين حالة الفورم في ViewModel مع SavedStateHandle بشكل مستمر أثناء الكتابة (debounced)، بحيث تنجو من كل من تدوير الشاشة وProcess Death دون الاعتماد الكامل على لحظة onPause/onStop فقط.

لماذا يُنصح بعدم بدء عمليات طويلة (مثل رفع ملف) داخل onResume() مباشرة في كل مرة؟دقيق

onResume() تُستدعى في كل مرة تعود فيها الـ Activity للمقدمة — ليس فقط عند الإنشاء الأول. بدء عملية رفع ملف هناك مباشرة (دون فحص إن كانت جارية بالفعل) يعني تكرارها في كل انتقال بسيط (مثل فتح إشعار والعودة)، ما يهدر بيانات المستخدم وموارد الخادم. الحل: تتبع الحالة في ViewModel والتحقق قبل البدء، أو استخدام WorkManager للعمليات الطويلة غير المرتبطة مباشرة بدورة حياة الشاشة.

Activity A تفتح Activity B لأخذ نتيجة (Activity Result API). صف بالتفصيل كل استدعاءات دورة الحياة على A وB من لحظة الفتح حتى العودة بالنتيجة.صعب

عند فتح B: A.onPause() → B.onCreate() → B.onStart() → B.onResume() → (بعد اكتمال انتقال B) A.onStop().

عند إغلاق B وإرجاع نتيجة: B.onPause() → A.onRestart() → A.onStart() → A.onResume() (وهنا يصل الـ callback المسجّل عبر registerForActivityResult) → B.onStop() → B.onDestroy().

الملاحظة المهمة: نتيجة الـ callback تصل بعد onResume في A، وليس فورًا — لذلك لا يجب الاعتماد على ترتيب تنفيذ فوري متزامن مع دورة الحياة.

كيف تختبر يدويًا أن تطبيقك يتعافى بشكل صحيح من Process Death، بدون انتظار حدوثها عشوائيًا؟دقيق

عبر تفعيل "Don't keep activities" في خيارات المطور، والتي تجعل النظام يدمّر كل Activity بمجرد مغادرتها (onStop مباشرة onDestroy) — هذا يحاكي أسوأ سيناريو ممكن لضغط الذاكرة، ويكشف بسرعة أي بيانات لا تُحفظ بشكل صحيح عبر SavedStateHandle أو onSaveInstanceState.

نصيحة أخيرة للمقابلة

أفضل إجابة على أي سؤال دورة حياة ليست حفظ الترتيب فقط — بل شرح لماذا يوجد هذا الترتيب، وما المشكلة الهندسية التي يحلها. هذا ما يفرّق بين إجابة حفظ وإجابة فهم حقيقي.
