1. تطور طبقة العتاد في أندرويد (The Evolution of Android HAL)

تمثل طبقة تجريد العتاد (Hardware Abstraction Layer) الحاجز البرمجي الفاصل بين نواة نظام التشغيل (Kernel) والفريمورك العلوي (Android Framework). تطورت هذه الطبقة عبر ثلاث مراحل رئيسية لتحقيق فصل كامل بين نظام Google والتعديلات الخاصة بمصنعي الأجهزة (OEMs).

Legacy HAL (ما قبل Android 8.0)

كانت مكتبات مشتركة (Shared Libraries بصيغة .so) يتم تحميلها مباشرة داخل عملية System Server عبر dlopen(). هذا الرابط المباشر أدى إلى:

  • ترابط شديد (Tight Coupling) بين نظام Google والتعديلات الخاصة بالمُصنّع.
  • استحالة تحديث النظام (OTA) دون إعادة بناء كامل لل Vendor Partition.
  • تعارضات في رموز الكيرنيل (Kernel Symbol Collisions) عبر تحديثات النظام.

Project Treble & HIDL (Android 8.0+)

أطلقت Google مشروع Treble لإعادة هيكلة HAL بالكامل باستخدام لغة HIDL (HAL Interface Definition Language) ونقلها إلى Binderized HALs:

  • فصل System Partition عن Vendor Partition عبر واجهات Binder IPC.
  • تشغيل HALs كخدمات مستقلة في عمليات Vendor.
  • إدخال VINTF (Vendor Interface) لضمان التوافقية بين النظام والمُصنّع.

Stable AIDL HAL (Android 11+)

المرحلة الحالية والمستقبلية: توحيد آلية IPC بين Framework وHAL باستخدام AIDL (Android Interface Definition Language) بدلاً من HIDL:

  • استخدام نفس آلية IPC للفريمورك والعتاد (Unified IPC).
  • دعم أصلي للغات Java وC++ وRust عبر Backend واحد.
  • تقليل التعقيد: ملف AIDL واحد يولد Java Stub وC++ Backend.
  • الاستقرار عبر @VintfStability لضمان عدم تغيير الواجهة عبر التحديثات.

2. معمارية VINTF وفصل النظام عن المُصنّع (VINTF & The Vendor Boundary)

ما هو VINTF؟

يُعدّ VINTF (Vendor Interface Object) آلية التحقق من التوافقية بين قسم النظام (System Partition) وقسم المُصنّع (Vendor Partition) في وقت الإقلاع (Boot Time) وعند تثبيت تحديثات OTA.

🔧 الغرض من VINTF

ضمان أن النظام المحدّث (System Image) يستطيع التواصل مع HALs الموجودة في Vendor Image دون حدوث أعطال في IPC أو عدم تطابق في إصدارات الواجهات.

ملفات VINTF الأساسية

device/<vendor>/<device>/manifest.xml

يُعلن المُصنّع في هذا الملف عن جميع HALs التي يوفرها في Vendor Partition، بما في ذلك إصدار الواجهة واسم المثيل (Instance Name).

<!-- VINTF Manifest: إعلان خدمة AIDL HAL -->
<manifest type="device" version="6.0">
    <hal format="aidl">
        <name>android.hardware.custom</name>
        <version>1</version>
        <fqname>ICustomHardware/default</fqname>
    </hal>
</manifest>
device/<vendor>/<device>/compatibility_matrix.xml

يحدد هذا الملف متطلبات النظام من HALs: أي واجهات يتطلب Framework وجودها في Vendor Partition للتمكن من الإقلاع.

<!-- Compatibility Matrix: متطلبات النظام من HALs -->
<compatibility-matrix version="6.0" type="framework">
    <hal format="aidl" optional="false">
        <name>android.hardware.custom</name>
        <version>1</version>
        <interface>
            <name>ICustomHardware</name>
            <instance>default</instance>
        </interface>
    </hal>
</compatibility-matrix>

⚠️ حدود System/Vendor و SELinux

يُمنع SELinux بشكل افتراضي أي تواصل IPC بين عمليات System (domain: system_server) وعمليات Vendor (domain: vendor_hal_custom_hw). يجب تعريف Policy صريح في ملف *.te للسماح بـ binder_call بين المجالين.

3. تعريف واجهة AIDL للعتاد (Step 1: Defining the AIDL HAL)

1

إنشاء بنية المجلدات في AOSP

يتم وضع واجهات HAL المخصصة ضمن شجرة hardware/interfaces/ وفقاً للتسلسل الهرمي التالي:

hardware/interfaces/custom_hardware/aidl/Android.bp
hardware/interfaces/custom_hardware/aidl/ICustomHardware.aidl
// ICustomHardware.aidl — واجهة العتاد المخصصة
// يجب وضع التعليق التالي لضمان استقرار الواجهة عبر التحديثات

package android.hardware.custom;

import android.hardware.custom.CustomResult;

// @VintfStability: يضمن أن هذه الواجهة لن تتغير وستُعرّف في VINTF
@VintfStability
interface ICustomHardware {
    // العملية الأساسية: إرسال أمر إلى العتاد واستلام النتيجة
    CustomResult sendCommand(in String command, in int param);

    // استعلام عن حالة العتاد
    boolean isReady();

    // الحصول على معلومات إصدار العتاد
    String getHardwareVersion();
}
hardware/interfaces/custom_hardware/aidl/CustomResult.aidl
package android.hardware.custom;

@VintfStability
parcelable CustomResult {
    int statusCode;
    String data;
    long timestamp;
}

يستخدم aidl_interface module لبناء الواجهة وتوليد الأكواد للغات Java وC++ وRust.

aidl_interface {
    name: "android.hardware.custom",

    stability: "vintf",  // يُفعّل @VintfStability
    imports: ["android.hardware.common"],

        java: {
            enabled: true,
            sdk_version: "module_current",
        },
        cpp: {
            enabled: true,
        },
        ndk: {
            enabled: true,  // NDK Backend مُستحسن للـ Vendor Services
        },
    },
}

4. برمجة خدمة العتاد بلغة C++ في قسم المُصنّع (Step 2: C++ Vendor Implementation)

3

تنفيذ الواجهة: BnCustomHardware

تُنشّئ خدمة العتاد (Vendor Service) بامتداد الفئة الأساسية المولدة تلقائياً BnCustomHardware من AIDL Compiler.

vendor/<vendor>/<device>/hardware/custom_hw/CustomHardware.cpp
// CustomHardware.cpp — تنفيذ خدمة العتاد في Vendor Partition

#include "CustomHardware.h"
#include <android-base/logging.h>
#include <android/binder_manager.h>
#include <android/binder_process.h>

namespace aidl {
namespace android {
namespace hardware {
namespace custom {

// تنفيذ العملية: إرسال الأمر إلى العتاد الفعلي عبر sysfs أو ioctl
ndk::ScopedAStatus CustomHardware::sendCommand(
        const std::string& command,
        int32_t param,
        CustomResult* result) {

    // التحقق من جاهزية العتاد
    if (!mDeviceReady) {
        return ndk::ScopedAStatus::fromServiceSpecificError(-1);
    }

    // محاكاة تفاعل مع العتاد (في الواقع: كتابة على /dev/custom_hw)
    result->statusCode = 0;  // SUCCESS
    result->data = "ACK: " + command;
    result->timestamp = time(nullptr);

    return ndk::ScopedAStatus::ok();
}

// التحقق من حالة العتاد
ndk::ScopedAStatus CustomHardware::isReady(bool* ready) {
    *ready = mDeviceReady;
    return ndk::ScopedAStatus::ok();
}

// الحصول على إصدار العتاد
ndk::ScopedAStatus CustomHardware::getHardwareVersion(std::string* version) {
    *version = "Custom-HW-v2.1.0";
    return ndk::ScopedAStatus::ok();
}

} // namespace custom
} // namespace hardware
} // namespace android
} // namespace aidl

نقطة الدخول: main.cpp وخدمة Vendor

تُسجّل الخدمة في Service Manager عبر AServiceManager_addService وتُشغّل حلقة Binder Thread Pool.

vendor/<vendor>/<device>/hardware/custom_hw/main.cpp
// main.cpp — نقطة إقلاع خدمة العتاد (Vendor Daemon)

#include "CustomHardware.h"
#include <android-base/logging.h>
#include <android/binder_manager.h>
#include <android/binder_process.h>

using namespace aidl::android::hardware::custom;

int main() {
    // 1. إنشاء كائن الخدمة
    std::shared_ptr<CustomHardware> service = 
        ndk::SharedRefBase::make<CustomHardware>();

    // 2. تسجيل الخدمة في AServiceManager
    //    الاسم يجب أن يتطابق مع FQNAME في manifest.xml
    const char* instance = "android.hardware.custom.ICustomHardware/default";

    binder_status_t status = AServiceManager_addService(
        service->asBinder().get(),  // IBinder object
        instance                     // Instance name
    );

    if (status != STATUS_OK) {
        LOG(FATAL) << "فشل في تسجيل خدمة العتاد: " << status;
        return -1;
    }

    LOG(INFO) << "تم تسجيل خدمة العتاد المخصصة بنجاح";

    // 3. تشغيل حلقة معالجة الطلبات (ThreadPool)
    //    يبدأ 16 خيطاً (Threads) لمعالجة IPC الواردة
    ABinderProcess_setThreadPoolMaxThreadCount(16);
    ABinderProcess_startThreadPool();

    // 4. الانتظار إلى ما لانهاية
    ABinderProcess_joinThreadPool();

    return 0;  // لا يُ reached أبداً
}

6. الربط مع الفريمورك واستكشاف الأخطاء (Step 4: Framework Invocation & Diagnostics)

استدعاء HAL من System Service (Java)

// CustomSystemService.java — خدمة النظام التي تستهلك HAL

package com.android.server.custom;

import android.hardware.custom.ICustomHardware;
import android.hardware.custom.CustomResult;
import android.os.ServiceManager;
import android.os.IBinder;
import android.os.RemoteException;
import android.util.Slog;

public class CustomSystemService {
    private static final String TAG = "CustomSystemService";
    private static final String HAL_INSTANCE = 
        "android.hardware.custom.ICustomHardware/default";

    private ICustomHardware mHal;

    public void connectToHal() {
        try {
            // الانتظار حتى تكون الخدمة مسجلة في ServiceManager
            IBinder binder = ServiceManager.waitForDeclaredService(HAL_INSTANCE);

            if (binder == null) {
                throw new IllegalStateException("HAL غير متوفر");
            }

            // ربط الواجهة
            mHal = ICustomHardware.Stub.asInterface(binder);

            // اختبار الاتصال
            CustomResult result = mHal.sendCommand("INIT", 0);
            Slog.i(TAG, "نتيجة العتاد: " + result.data);

        } catch (RemoteException e) {
            Slog.e(TAG, "فشل الاتصال بـ HAL", e);
        }
    }

    public boolean isHardwareReady() {
        try {
            return mHal != null && mHal.isReady();
        } catch (RemoteException e) {
            return false;
        }
    }
}

الاستدعاء من System Service (C++)

// CustomFrameworkClient.cpp

#include <android/hardware/custom/ICustomHardware.h>
#include <android/binder_manager.h>
#include <android-base/logging.h>

using namespace android::hardware::custom;

void initializeHardware() {
    const char* instance = "android.hardware.custom.ICustomHardware/default";

    // الحصول على واجهة AIDL عبر NDK ServiceManager
    AIBinder* binder = AServiceManager_waitForService(instance);

    if (binder == nullptr) {
        LOG(ERROR) << "فشل في الحصول على خدمة العتاد";
        return;
    }

    // تحويل IBinder إلى واجهة مكتوبة
    std::shared_ptr<ICustomHardware> hal = 
        ICustomHardware::fromBinder(ndk::SpAIBinder(binder));

    CustomResult result;
    auto status = hal->sendCommand("TEST", 42, &result);

    if (status.isOk()) {
        LOG(INFO) << "الحالة: " << result.statusCode 
                  << " البيانات: " << result.data;
    }
}

🔍 تشخيص SELinux Denials

إذا فشل الاتصال بصمت (Silent Failure) أو تلقيت SecurityException، افحص سجلات SELinux:

adb shell dmesg | grep avc          # Kernel denials
adb shell logcat | grep audit       # Userspace audit

مثال على خطأ شائع: avc: denied { call } for pid=1234 comm="system_server" scontext=u:r:system_server:s0 tcontext=u:r:vendor_hal_custom_hw:s0

الحل: إضافة binder_call(system_server, vendor_hal_custom_hw) في ملف *.te.

✅ قائمة التحقق قبل الإقلاع (Boot Checklist)

  1. تأكد من وجود vendor: true في aidl_interface و cc_binary.
  2. تحقق من تطابق FQNAME في الكود و manifest.xml و init.rc.
  3. تأكد من تضمين compatibility_matrix.xml في DEVICE_FRAMEWORK_COMPATIBILITY_MATRIX_FILE.
  4. افحص SELinux Policy باستخدام audit2allow إذا ظهرت denials.
  5. تأكد من تشغيل الخدمة تلقائياً عبر init.rc ضمن class hal.
  6. استخدم lshal للتأكد من ظهور الواجهة بعد الإقلاع.

8. أفضل الممارسات والتوصيات الإنتاجية

🔒 الأمان و SELinux

  • لا تُسند أبداً Domain system_server لعمليات Vendor — استخدم vendor_hal_<name> منفصلاً.
  • استخدم neverallow Rules لمنع Vendor من الوصول المباشر إلى System Data.
  • جميع ملفات العتاد في /dev/ يجب أن تحمل تسمية SELinux (dev_type) صريحة.

⚡ الأداء والاستقرار

  • لا تنفّذ عمليات حجب (Blocking Operations) داخل دوال Binder مباشرة — استخدم Thread Pool منفصل.
  • حدد ABinderProcess_setThreadPoolMaxThreadCount() بما يتناسب مع الحمل المتوقع (الافتراضي: 16).
  • استخدم @VintfStability فقط للواجهات التي لن تتغير؛ للتجارب استخدم @JavaDerive أو غير مستقر.

🔧 البناء والصيانة

  • احتفظ بـ AIDL Interface في hardware/interfaces/ وليس في vendor/ لضمان مراجعته من Google.
  • استخدم aidl_api/ Snapshots لقفل إصدارات الواجهة عند إصدار النظام.
  • أضف api_levels في Android.bp إذا كنت تدعم إصدارات AOSP متعددة.
