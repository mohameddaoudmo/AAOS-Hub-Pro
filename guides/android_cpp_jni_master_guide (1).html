أساسيات C++ الحديثة لمهندسي أندرويد
Modern C++ Smart Pointers & Memory Ownership
📦
مفهوم الملكية والموارد (Memory Ownership & RAII)

في تطوير أنظمة أندرويد منخفضة المستوى، يعد فهم ملكية الذاكرة أمرًا حيويًا. يوفر C++ الحديث نموذجًا واضحًا لإدارة الموارد عبر RAII (Resource Acquisition Is Initialization).

🔒 Value Semantics

النسخة تملك بياناتها بشكل مستقل. عند التعيين، يتم نسخ البيانات فعليًا. آمن لكن مكلف للكائنات الكبيرة.

🔗 Reference Semantics

المتغيرات تشير إلى نفس الكائن في الذاكرة. يتطلب إدارة صريحة للحياة لتجنب use-after-free أو double-free.

💡 Move Semantics

تسمح std::move بنقل الملكية بدلاً من النسخ، مما يحسن الأداء بشكل كبير مع الكائنات الثقيلة مثل std::vector أو مؤشرات الملفات. في AOSP، يُستخدم بكثرة في HAL interfaces.

Smart Pointers: الغوص العميق

std::unique_ptr<T> — الملكية الفريدة

يضمن وجود مالك واحد فقط للمورد. لا يمكن نسخه، يمكن فقط نقله. تكلفة زمنية صفرية تقريبًا (O(1) overhead).

C++ 
// إنشاء unique_ptr مع custom deleter لملفات AOSP
auto fileDeleter = [](FILE* fp) {
    if (fp) fclose(fp);
};

std::unique_ptr<FILE, decltype(fileDeleter)> safeFile(
    fopen("/data/local/tmp/log.txt", "w"), 
    fileDeleter
);

// نقل الملكية إلى دالة أخرى
void processBuffer(std::unique_ptr<uint8_t[]> buffer, size_t size) {
    // buffer سيُحرر تلقائيًا عند الخروج من النطاق
}

auto rawBuffer = std::make_unique<uint8_t[]>(4096);
processBuffer(std::move(rawBuffer), 4096);
// rawBuffer الآن nullptr — آمن تمامًا

    }

Android RefBase, sp<T>, and wp<T>
⚠️ لماذا AOSP لا يستخدم std::shared_ptr؟

يستخدم AOSP نظام intrusive reference counting عبر RefBase لأسباب تاريخية وأدائية: (1) حجم أصغر للكائن — لا يحتاج control block منفصل، (2) كفاءة أعلى في cache locality، (3) تكامل عميق مع Binder IPC ومراحل تحميل المكتبات في AOSP.

💪
Strong Pointers (sp<T>)
  • تزيد mStrong عند الإنشاء
  • تنقصه عند التدمير
  • عندما يصل إلى صفر: يُستدعى destructor
  • الكائن يعيش طالما هناك sp
🔓
Weak Pointers (wp<T>)
  • تزيد mWeak فقط
  • لا تمنع تدمير الكائن
  • تُستخدم لكسر الاعتماديات الدائرية
  • الترويج عبر .promote() مع فحص nullptr
C++ — AOSP RefBase Module 
// include/utils/RefBase.h
#include <utils/RefBase.h>
#include <utils/StrongPointer.h>
using namespace android;

class DisplayEngine : public RefBase {
public:
    DisplayEngine() { ALOGD("DisplayEngine created"); }
    ~DisplayEngine() { ALOGD("DisplayEngine destroyed"); }
    void renderFrame() { /* ... */ }
};

// ==================== Usage in System Service ====================
class SurfaceFlinger {
    sp<DisplayEngine> mPrimaryDisplay;
    wp<DisplayEngine> mSecondaryDisplay; // weak — لا يمنع التدمير
public:
    void initDisplays() {
        mPrimaryDisplay = new DisplayEngine();
        sp<DisplayEngine> sec = new DisplayEngine();
        mSecondaryDisplay = sec; // يُحول تلقائيًا إلى weak
        // sec يخرج من النطاق — mSecondaryDisplay لا يمنع التدمير
    }
    void renderSecondary() {
        sp<DisplayEngine> engine = mSecondaryDisplay.promote();
        if (engine != nullptr) {
            engine->renderFrame(); // ✅ آمن
        } else {
            ALOGW("Secondary display already destroyed!");
        }
    }
};
🚨 خطأ شائع: Creating sp from raw pointer

لا تُنشئ sp<T> يدويًا من مؤشر خام إذا كان الكائن يستخدم RefBase، لأن ذلك قد يؤدي إلى double-free أو use-after-free. استخدم دائمًا new مباشرة في sp أو استخدم sp::make<T>() إن توفرت.

⚡
مؤشر JNIEnv* وقواعد السلامة

JNIEnv* هو مؤشر على بيئة تنفيذ JNI الخاصة بالـ Thread. يحتوي على جدول دوال غير مباشر (indirect function table) يُستخدم لاستدعاء جميع عمليات JNI.

⛝ لا تشارك JNIEnv* عبر Threads!

JNIEnv* خاص بـ Thread واحد. إذا احتاج Thread أصلي (C++) في الخلفية إلى استدعاء Java، يجب عليه:

C++ — Attach/Detach Pattern 
JavaVM* g_vm = nullptr; // يُحفظ في JNI_OnLoad

JNIEXPORT jint JNI_OnLoad(JavaVM* vm, void* reserved) {
    g_vm = vm;
    return JNI_VERSION_1_6;
}

void backgroundWorker() {
    JNIEnv* env;
    jint attachResult = g_vm->AttachCurrentThread(&env, nullptr);
    if (attachResult != JNI_OK) {
        return; // فشل الربط
    }
    // ✅ استخدم env بأمان هنا
    // ... JNI calls ...
    g_vm->DetachCurrentThread(); // ✅ لا تنسَ الفصل!
}

إدارة الذاكرة وتفادي التسريبات في JNI
JNI Memory & References Management
⚠️ الفجوة الحرجة

جامع القمامة في JVM (Garbage Collector) لا يستطيع إطلاقًا تحرير الذاكرة المخصصة في C++ عبر malloc أو new. هذه الذاكرة خارج نطاق JVM تمامًا. يجب عليك إدارتها يدويًا.

📍
Local References
  • تُنشأ تلقائيًا
  • صالحة فقط داخل إطار الدالة الأصلية
  • تُحرر تلقائيًا عند العودة إلى Java
  • خطر Local Reference Table Overflow
  • الحد الأقصى: 512 مرجع (افتراضي)
// Explicit cleanup
env->DeleteLocalRef(jobj);
🌎
Global References
  • تدوم عبر استدعاءات متعددة
  • تُشارك بين Threads
  • لا تُحرر تلقائيًا — تسريب مؤكد
  • تمنع GC من تدمير الكائن
  • يجب استدعاء DeleteGlobalRef
jobject global = env->NewGlobalRef(local);
// ... use across calls ...
env->DeleteGlobalRef(global);
👻
Weak Global References
  • تدوم عبر استدعاءات
  • لا تمنع GC من التدمير
  • يُرجع NULL إذا تُدمّر
  • مثالية للـ caches
  • يجب فحصها قبل الاستخدام
jweak wref = env->NewWeakGlobalRef(obj);
jobject strong = env->NewLocalRef(wref);
if (strong) { /* use */ }
env->DeleteWeakGlobalRef(wref);

C++ — RAII Wrapper for JNI Strings 
class JniString {
    JNIEnv* mEnv;
    jstring mJstr;
    const char* mCstr;
public:
    JniString(JNIEnv* env, jstring jstr) 
        : mEnv(env), mJstr(jstr), mCstr(env->GetStringUTFChars(jstr, nullptr)) {}

    ~JniString() {
        mEnv->ReleaseStringUTFChars(mJstr, mCstr);
    }

    const char* c_str() const { return mCstr; }
    operator const char*() const { return mCstr; }
};

// Usage: يُحرر تلقائيًا عند الخروج من النطاق
void processPath(JNIEnv* env, jstring path) {
    JniString cPath(env, path);
    ALOGD("Processing: %s", cPath.c_str());
} // ✅ ReleaseStringUTFChars called automatically

تسجيل الدوال المتقدم في JNI
Static vs Dynamic JNI Registration
📜
Static Native Registration (Legacy)
  • يعتمد على name mangling (Java_com_example_package_Class_method)
  • يتطلب تطابق اسم الحزمة والفئة تمامًا
  • بطيء في البحث عند التحميل الأول
  • يُعرقل obfuscation وإعادة البناء
  • صعب في الصيانة عند تغيير الحزم
C++ — Static
extern "C" JNIEXPORT void JNICALL
Java_com_android_server_DisplayService_nativeInit(
    JNIEnv* env, jobject thiz, jint displayId
) {
    // ...
}
⚙️
Dynamic Native Registration (Best Practice)
  • يستخدم JNI_OnLoad وJNINativeMethod
  • أسرع في التنفيذ — لا يوجد بحث runtime
  • يدعم obfuscation وإعادة البناء بحرية
  • أسهل في الصيانة والاختبار
  • مُوصى به رسميًا في AOSP
C++ — Dynamic
static JNINativeMethod gMethods[] = {
    {"nativeInit", "(I)V", (void*)nativeInit},
    {"nativeProcess", "([B)Z", (void*)nativeProcess},
};

JNIEXPORT jint JNI_OnLoad(JavaVM* vm, void* reserved) {
    JNIEnv* env;
    vm->GetEnv((void**)&env, JNI_VERSION_1_6);
    jclass clazz = env->FindClass("com/android/server/DisplayService");
    env->RegisterNatives(clazz, gMethods, NELEM(gMethods));
    return JNI_VERSION_1_6;
}

مكتبة أصلية كاملة: Dynamic Registration + Exception Safety
C++ — Complete Native Module 
// native_sensor.cpp
#include <jni.h>
#include <android/log.h>
#include <vector>
#include <stdexcept>

#define LOG_TAG "NativeSensor"
#define LOGE(...) __android_log_print(ANDROID_LOG_ERROR, LOG_TAG, __VA_ARGS__)

static void throwJavaException(JNIEnv* env, const char* msg) {
    jclass exClass = env->FindClass("java/lang/RuntimeException");
    env->ThrowNew(exClass, msg);
}

static jboolean nativeProcessBuffer(JNIEnv* env, jobject thiz, jbyteArray buffer) {
    jboolean isCopy = JNI_FALSE;
    jsize len = env->GetArrayLength(buffer);

    if (len == 0) {
        throwJavaException(env, "Empty buffer provided");
        return JNI_FALSE;
    }

    jbyte* raw = env->GetByteArrayElements(buffer, &isCopy);
    if (!raw) {
        throwJavaException(env, "Failed to access buffer");
        return JNI_FALSE;
    }

    try {
        std::vector<uint8_t> data(raw, raw + len);
        // Process data...

        env->ReleaseByteArrayElements(buffer, raw, JNI_ABORT);
        return JNI_TRUE;
    } catch (const std::exception& e) {
        env->ReleaseByteArrayElements(buffer, raw, JNI_ABORT);
        throwJavaException(env, e.what());
        return JNI_FALSE;
    }
}

static JNINativeMethod gSensorMethods[] = {
    {"nativeProcessBuffer", "([B)Z", (void*)nativeProcessBuffer},
};

JNIEXPORT jint JNI_OnLoad(JavaVM* vm, void* reserved) {
    JNIEnv* env;
    if (vm->GetEnv((void**)&env, JNI_VERSION_1_6) != JNI_OK) {
        return JNI_ERR;
    }
    jclass clazz = env->FindClass("com/example/SensorManager");
    if (!clazz) return JNI_ERR;

    if (env->RegisterNatives(clazz, gSensorMethods, 
        sizeof(gSensorMethods)/sizeof(gSensorMethods[0])) < 0) {
        return JNI_ERR;
    }
    return JNI_VERSION_1_6;
}

📦 قراءة Native Crash Tombstones

عند حدوث crash أصلي، يُنشئ Android ملف tombstone في /data/tombstones/. يحتوي على:

Signal number (SIGSEGV, SIGABRT) Fault address Backtrace (unwind) Register dump Memory maps
🔴
SIGSEGV (Segmentation Fault)
  • الوصول إلى ذاكرة غير مصرح بها
  • dereferencing nullptr أو مؤشر مُتلف
  • use-after-free مع RefBase
  • buffer overflow في native heap
$ adb shell cat /data/tombstones/tombstone_01 | grep "signal"
signal 11 (SIGSEGV), code 1 (SEGV_MAPERR)
fault addr 0x00000000
🟡
SIGABRT (Abort)
  • استدعاء abort() أو __assert_fail
  • double-free في الذاكرة
  • heap corruption detected
  • JNI Local Reference Table Overflow
$ adb shell cat /data/tombstones/tombstone_02 | grep "signal"
signal 6 (SIGABRT), code -1 (SI_QUEUE)
abort message: 'JNI ERROR: local reference table overflow'
🧬
AddressSanitizer (ASan) في AOSP

ASan أداة قوية لاكتشاف أخطاء الذاكرة في الوقت الفعلي. يُمكن تفعيله في بناء AOSP عبر:

Android.bp / CMake 
// Android.bp
cc_binary {
    name: "my_native_service",
    srcs: ["main.cpp"],
    sanitize: {
        address: true,
    },
}

// CMakeLists.txt
set(CMAKE_CXX_FLAGS "${CMAKE_CXX_FLAGS} -fsanitize=address -fno-omit-frame-pointer")
set(CMAKE_LINKER_FLAGS "${CMAKE_LINKER_FLAGS} -fsanitize=address")
✅ ما يكتشفه ASan

use-after-free · heap-buffer-overflow · stack-buffer-overflow · global-buffer-overflow · use-after-return · initialization-order bugs · memory leaks (مع LSan)

💡 نصيحة أخيرة من المهندس الأول

عند العمل على طبقات النظام في AOSP، اتبع دائمًا مبدأ defensive programming: افحص كل مؤشر قبل الاستخدام، استخدم sp<T> وwp<T> بدلاً من المؤشرات الخامة، ولا تثق أبدًا بمدخلات JNI القادمة من Java. اختبر كل مسار للأخطاء، واستخدم ASan في البيئة التطويرية قبل دمج الكود.
