1 عزل العمليات وفلسفة مشغل Binder
نموذج عزل العمليات في Linux مقابل نموذج أمان Android

يُعدّ عزل العمليات (Process Isolation) من الركائز الأساسية التي تبنى عليها أنظمة التشغيل الحديثة. في نواة Linux، يتم تخصيص مساحة عنوان (Address Space) منفصلة لكل عملية (Process)، مما يضمن أن ذاكرة العملية A لا يمكنها الوصول المباشر إلى ذاكرة العملية B إلا عبر آليات IPC (Inter-Process Communication) مراقبة من النواة.

في Android، يتم ترقية هذا النموذج عبر مفهوم Sandboxing: كل تطبيق يعمل بـ UID فريد (User ID) ومجموعة GID خاصة به، ويتم تشغيله في عملية zygote منفصلة. هذا يعني أن حتى لو تم اختراق تطبيق واحد، فإن الوصول إلى بيانات تطبيق آخر يتطلب تجاوز آليات IPC والأمان في النواة.

لماذا آليات IPC التقليدية غير كافية لنظام تشغيل متنقل؟

تدعم Linux عدة آليات IPC تقليدية مثل Unix Domain Sockets، Shared Memory (shm)، و System V Message Queues. لكن هذه الآليات تواجه تحديات جوهرية في بيئة Android:

  • الأمان (Security): لا تُجري Sockets التحقق من هوية المرسل (UID/PID) بشكل موثوق على كل رسالة، مما يُسهّل هجمات انتحال الهوية (Identity Spoofing).
  • استهلاك الطاقة (Power Consumption): آليات النسخ المزدوج (Double-Copy) في Sockets تُرهق وحدة المعالجة والذاكرة، مما يقلل عمر البطارية.
  • تأخير الاستجابة (Latency): في نظام متنقل، يجب أن تكتمل مكالمات IPC في أجزاء من الميلي ثانية. آليات System V IPC تتطلب سياقات تبديل (Context Switches) مكلفة.
  • إدارة دورة الحياة (Lifecycle Management): Android يحتاج إلى آلية IPC تدعم "الموت الودي" (Graceful Death) لعمليات الخدمة وإعادة تشغيلها تلقائياً عند الطلب.
💡 الفلسفة الأساسية لـ Binder: بدلاً من أن تكون IPC مجرد "أنبوب نقل بيانات"، صمّم Binder ليكون إطار عمل موجه للكائنات (Object-Oriented IPC Framework). يمكن للعميل استدعاء طرق (Methods) على كائن بعيد كما لو كان محلياً، مع ضمانات أمان مدمجة على مستوى النواة.
دور مشغل /dev/binder في فضاء النواة

يعمل Binder Kernel Driver كـ وسيط موثوق به (Trusted Middleman) بين جميع عمليات Android. عند فتح أي عملية لملف الجهاز /dev/binder، تقوم النواة بتسجيل:

  • PID (معرّف العملية) الخاص بالمتصل.
  • UID (معرّف المستخدم) الخاص بالتطبيق.
  • حجم المخزن المؤقت (Buffer) المخصص عبر mmap().

عند وصول أي معاملة (Transaction)، يتحقق Binder Driver من هوية المرسل ويُرفقها كبيانات وصفية (Metadata) في الرسالة الواردة إلى الخادم، مما يتيح للخادم اتخاذ قرارات أمان دقيقة عبر Binder.getCallingUid().

تكلفة النسخ المزدوج في IPC التقليدي

في آليات IPC الكلاسيكية مثل Pipes أو Sockets، تمر البيانات عبر مسار يتضمن نسختين:

  1. النسخة الأولى: نسخ البيانات من مساحة عنوان العميل (User Space) إلى مخزن مؤقت داخل النواة (Kernel Space).
  2. النسخة الثانية: نسخ البيانات من مخزن النواة إلى مساحة عنوان الخادم (User Space).

تحسين Binder عبر mmap() وآلية النسخة الواحدة

يستخدم Binder تقنية ذكية تعتمد على mmap() لتقليل النسخ إلى نسخة واحدة فقط (Single-Copy):

  • عند بدء تشغيل العملية، يستدعي Binder User-Space دالة mmap() على /dev/binder لتخصيص منطقة ذاكرة مشتركة بين العملية والنواة.
  • عندما يريد العميل إرسال بيانات، يكتبها مباشرة في هذه المنطقة المشتركة (نسخة واحدة فقط من User Space إلى Kernel-Mapped Buffer).
  • الخادم يقرأ البيانات من نفس المنطقة المشتركة دون الحاجة إلى نسخ ثانٍ — يتم فقط تعديل جدول صفحات الذاكرة (Page Table) ليُظهر أن هذه الصفحات تنتمي الآن إلى مساحة عنوان الخادم.

🔬 التفاصيل التقنية لـ mmap(): عند استدعاء mmap(NULL, size, PROT_READ, MAP_PRIVATE, fd, 0) على واصف ملف /dev/binder، تقوم النواة بتخصيص صفحات ذاكرة افتراضية (Virtual Pages) لا تُحجز فعلياً إلا عند الكتابة (Copy-on-Write). هذا يعني أن العملية لا تستهلك ذاكرة فعلية إلا عند الحاجة، مما يُحسّن كثافة الذاكرة (Memory Density) في الأنظمة ذات الموارد المحدودة.
حدود مخزن Binder وفهم TransactionTooLargeException

يأتي التحسين السابق مع قيود صارمة. يتم تخصيص مخزن Binder بسعة 1 ميغابايت (1MB) افتراضياً لكل عملية تطبيق، وهذا المخزن مشترك بين جميع المعاملات النشطة (Active Transactions) في نفس الوقت.

⚠️ خطر TransactionTooLargeException: إذا حاولت إرسال Parcel يتجاوز الحجم المتاح (مثلاً قائمة كبيرة من الكائنات أو Bitmap ضخم)، يرمي Binder Driver استثناء TransactionTooLargeException. هذا ليس عيباً — بل آلية حماية لمنع عملية واحدة من احتكار كل موارد IPC في النظام.

3 ميكانيكية عمل الـ Parcel وتشريح البيانات
ما هو Parcel في ذاكرة Android؟

Parcel هو حاوية تسلسل خفيفة الوزن (Lightweight Serialization Container) تُستخدم لنقل البيانات بين العمليات عبر Binder. على عكس Serializable في Java الذي يعتمد على انعكاس (Reflection) وبطيء، يستخدم Parcel تسلسلاً ثنائياً مباشراً (Binary Flattening) إلى ذاكرة متجاورة (Contiguous Memory).

يتم تخزين بيانات Parcel في مخزن مؤقت خام (Raw Buffer) يُديره Native Code عبر فئة C++ android::Parcel، بينما يعرض Java/Kotlin واجهة عالية المستوى تُترجم المكالمات إلى هذه الطبقة الأصلية.

التخطيط الثنائي (Binary Layout) للبيانات المُسلّسة

يتم ترتيب البيانات داخل Parcel بشكل مسطح (Flat) مع مراعاة محاذاة 4 بايت (32-bit Alignment). إليك التخطيط الداخلي:

Offset 0x00 00 00 00 00 │ 00 00 00 00 Header (8 bytes)
Offset 0x08 2A 00 00 00 │ 00 00 00 00 int32_t value = 42
Offset 0x10 48 00 00 00 │ 65 00 00 00 UTF-16 'H' 'e'
Offset 0x18 6C 00 00 00 │ 6C 00 00 00 UTF-16 'l' 'l'
Offset 0x20 6F 00 00 00 │ 00 00 00 00 UTF-16 'o' + null
Offset 0x28 00 00 00 00 │ 00 00 00 00 IBinder Ref (handle)
Offset 0x30 00 00 00 00 │ 00 00 00 00 File Descriptor (fd)
Offset 0x38 FF FF FF FF │ 00 00 00 00 Object Null Marker
📐 قواعد المحاذاة (Alignment Rules):
  • جميع الأعداد الصحيحة (int32, int64) تُحاذى على حدود 4 بايت.
  • النصوص (Strings) تُخزن بترميز UTF-16 مع بايتات طول مسبق (Length Prefix).
  • مراجع IBinder تُخزن كـ Handles (أعداد صحيحة) في العملية البعيدة، ويتم ترجمتها بواسطة Binder Driver.
  • واصفات الملفات (File Descriptors) تُمرر عبر آلية SCM_RIGHTS في النواة.
مؤشرات الإزاحة (Offset Pointers) وإدارة الذاكرة

تحتفظ فئة Parcel بمؤشرين رئيسيين:

  • mData: مؤشر إلى بداية المخزن المؤقت (Buffer Start).
  • mDataPos: موضع الكتابة/القراءة الحالي (Current Read/Write Position).
  • mDataSize: إجمالي حجم البيانات المكتوبة.
  • mDataCapacity: السعة القصوى للمخزن المؤقت قبل إعادة التخصيص.

عند كتابة بيانات جديدة، يتم التحقق أولاً من توفر مساحة كافية. إذا لم تكن كافية، يتم استدعاء realloc() لتوسيع المخزن المؤقت مع الحفاظ على المحتوى السابق. هذا يعني أن Parcel يُعدّ مخزناً مؤقتاً ديناميكياً (Dynamic Buffer) يتكيف مع حجم البيانات.

4 تتبع مسار التواصل بين عمليتين (End-to-End Trace)
بناء Parcel وإصدار ioctl(BINDER_WRITE_READ)

في العملية العميلة، يقوم التطبيق بإنشاء كائن Parcel وكتابة البيانات (Primitives, Strings, IBinder refs) بترتيب محدد. ثم يتم تمرير هذا Parcel إلى طبقة Native عبر IBinder::transact()، والتي تُنشئ هيكل binder_write_read وتستدعي ioctl(fd, BINDER_WRITE_READ, &bwr).

// Client Side — C++ Native Binder
// إنشاء Parcel فارغ وتعبئته بالبيانات
Parcel data;
data.writeInterfaceToken("android.app.IActivityManager");
data.writeInt32(1001);          // كتابة int32_t
data.writeString16(u"hello");   // كتابة String16 (UTF-16)

// إعداد هيكل binder_write_read
struct binder_write_read bwr;
memset(&bwr, 0, sizeof(bwr));

// كتابة أمر BC_TRANSACTION في مخزن الكتابة
uint32_t cmd[2];
cmd[0] = BC_TRANSACTION;
cmd[1] = (uint32_t)data.ipcData();  // مؤشر إلى بيانات Parcel

bwr.write_buffer = (binder_uintptr_t)cmd;
bwr.write_size   = sizeof(cmd);
bwr.write_consumed = 0;

// الاستدعاء النظامي — الانتقال إلى فضاء النواة
int res = ioctl(mProcess->mDriverFD, BINDER_WRITE_READ, &bwr);
الانتقال إلى فضاء النواة والتحقق من بيانات الاعتماد

عند استلام النواة لاستدعاء ioctl، يُنفّذ Binder Driver التحققات التالية:

  • التحقق من صلاحية واصف الملف (FD) المرتبط بـ /dev/binder.
  • استخراج UID و PID للعملية المتصلة من هيكل task_struct الخاص بالنواة.
  • التحقق من أن المعاملة موجهة إلى Service مسجلة (عبر Context Manager إذا كانت أول معاملة).
🔐 التحقق من الأمان: لا يمكن تزوير UID/PID لأن Binder Driver يقرأها مباشرة من نواة Linux (current->cred->uid) وليس من User Space. هذا يضمن أن هوية المرسل موثوقة بنسبة 100%.
ترجمة مراجع الكائنات المحلية إلى مقابض بعيدة

إذا احتوى Parcel على مراجع IBinder محلية (مثل BpBinder)، يقوم Binder Driver بـ ترجمة العناوين (Address Translation):

  • الكائنات المحلية (Local Objects) تُحوّل إلى Handles (أرقام صحيحة) يفهمها العملية البعيدة.
  • الكائنات البعيدة (Remote Handles) تُحوّل إلى مؤشرات كائنات محلية إذا كانت موجودة في جدول الترجمة.
  • يتم تحديث refs->desc (File Descriptor) عبر آلية SCM_RIGHTS.

إيقاظ تجمع خيوط العملية الخادمة (IPCThreadState)

بعد التحقق والترجمة، يضع Binder Driver المعاملة في قائمة الانتظار (Work Queue) الخاصة بالعملية الهدف. إذا كانت العملية نائمة، يتم إرسال إشارة wake_up_interruptible() لإيقاظ أحد خيوط IPCThreadState في تجمع الخيوط (Thread Pool).

يستخدم Android نموذج تجمع خيوط IPC (IPC Thread Pool) بدلاً من إنشاء خيط جديد لكل معاملة. يتم تسجيل الخيوط عبر BC_REGISTER_LOOPER و BC_ENTER_LOOPER.

// Server Thread Pool Registration
// تسجيل الخيط الحالي كـ IPC Thread في Binder Driver
Parcel reply;
IPCThreadState* self = IPCThreadState::self();

// إرسال أمر BC_ENTER_LOOPER لإعلام النواة
uint32_t cmd = BC_ENTER_LOOPER;
self->writeInParcel(&cmd, sizeof(cmd));

// الدخول في حلقة الاستماع (Event Loop)
while (1) {
    // انتظار ioctl(BINDER_WRITE_READ) واردة
    self->talkWithDriver(true);

    // معالجة المعاملات الواردة
    while (self->executeCommand(cmd) == NO_ERROR) {
        // تنفيذ الأمر وإرسال الرد
    }
}
فك تسلسل Parcel وإرجاع رد الاستجابة

يستقبل الخادم Parcel عبر BBinder::onTransact()، ويقوم بفك تسلسل البيانات بالترتيب الدقيق نفسه الذي كُتبت به. أي خطأ في ترتيب القراءة (مثلاً قراءة String قبل int) سيؤدي إلى فساد الذاكرة (Memory Corruption) أو Parcel mismatch crash.

بعد معالجة الطلب، يُنشئ الخادم Parcel رد (reply) ويرسله عبر sendReply()، والذي يُصدر ioctl(BINDER_WRITE_READ) بالاتجاه المعاكس.

// Server Side — BBinder::onTransact()

#include "IMyService.h"

status_t BpMyService::addUser(int32_t userId, const String16& name) {
    // إنشاء Parcel للبيانات (Input) والرد (Output)
    Parcel data, reply;

    // كتابة Interface Token للتحقق من الهوية
    data.writeInterfaceToken(IMyService::getInterfaceDescriptor());

    // ───────────────────────────────────────────────
    // التسلسل الصريح — يجب أن يتطابق مع ترتيب القراءة
    // في BnMyService::onTransact() بالضبط
    // ───────────────────────────────────────────────
    data.writeInt32(userId);    // 4 bytes, aligned
    data.writeString16(name);   // UTF-16 with length prefix

    // إرسال المعاملة عبر Binder — TF_ONE_WAY = غير متزامن
    status_t status = remote()->transact(
        TRANSACT_ADD_USER,   // رمز المعاملة
        data,                // Parcel الدخل
        &reply,              // Parcel الرد
        0                    // flags (0 = متزامن)
    );

    if (status != NO_ERROR) {
        ALOGE("addUser transaction failed: %d", status);
        return status;
    }

    // قراءة نتيجة الاستجابة
    return reply.readInt32();
}

status_t BpMyService::getUser(int32_t userId, String16* outName) {
    Parcel data, reply;
    data.writeInterfaceToken(IMyService::getInterfaceDescriptor());
    data.writeInt32(userId);

    status_t status = remote()->transact(
        TRANSACT_GET_USER, data, &reply, 0
    );

    if (status == NO_ERROR) {
        *outName = reply.readString16();
    }
    return status;
}

// ============================================================
// BnMyService.cpp — تنفيذ الهيكل الأساسي على جانب الخادم
// يُظهر فك التسلسل بالترتيب الدقيق لتجنب Parcel Mismatch
// ============================================================
#include "IMyService.h"

namespace android {

status_t BnMyService::onTransact(
    uint32_t code,
    const Parcel& data,
    Parcel* reply,
    uint32_t flags
) {
    // التحقق من Interface Token — يمنع استدعاءات غير مصرح بها
    data.checkInterface(this);

    switch (code) {
        case TRANSACT_ADD_USER: {
            // ───────────────────────────────────────────────
            // فك التسلسل بالترتيب الدقيق نفسه الذي كُتبت به
            // أي خطأ هنا = Parcel Mismatch Crash!
            // ───────────────────────────────────────────────
            int32_t userId = data.readInt32();
            String16 name = data.readString16();

            // استدعاء التنفيذ الفعلي (Implemented by subclass)
            status_t result = addUser(userId, name);

            // كتابة الرد
            reply->writeInt32(result);
            return NO_ERROR;
        }

        case TRANSACT_GET_USER: {
            int32_t userId = data.readInt32();
            String16 name;

            status_t result = getUser(userId, &name);

            reply->writeInt32(result);
            reply->writeString16(name);
            return NO_ERROR;
        }

        default:
            // تمرير إلى BBinder للمعاملات غير المعروفة
            return BBinder::onTransact(code, data, reply, flags);
    }
}

⚠️ تحذير Parcel Mismatch: يجب أن يتطابق ترتيب readXxx() في الخادم تماماً مع ترتيب writeXxx() في العميل. إذا كتبت writeInt32() ثم writeString16() في العميل، يجب أن تقرأ readInt32() ثم readString16() في الخادم. أي انحراف يؤدي إلى قراءة بيانات خاطئة من الذاكرة.
تطبيق Kotlin باستخدام Parcelable

في طبقة التطبيق (Application Layer)، يستخدم Android واجهة Parcelable لتسلسل الكائنات عبر Binder. على عكس Serializable، يتطلب Parcelable كتابة تعليمات التسلسل يدوياً، مما يوفر أداءً أعلى بكثير لأنه يتجنب الانعكاس (Reflection).

// Kotlin — Parcelable Data Class Implementation
package com.example.binderdemo

import android.os.Parcel
import android.os.Parcelable

/**
 * كيان بيانات يُستخدم في IPC عبر Binder
 * يُظهر التسلسل والاستعادة الصريحة لتجنب Parcel Mismatch
 *
 * ⚠️  مهم جداً: يجب أن يتطابق ترتيب writeString() / writeInt()
 *     مع ترتيب readString() / readInt() بالضبط!
 */
data class UserProfile(
    val userId: Int,
    val userName: String,
    val email: String,
    val isActive: Boolean,
    val score: Double
) : Parcelable {

    /**
     * المنشئ الثانوي — يُستخدم لفك التسلسل من Parcel
     * ترتيب القراءة يجب أن يتطابق مع ترتيب الكتابة في writeToParcel()
     */
    constructor(parcel: Parcel) : this(
        // 1. قراءة Int (4 bytes, aligned)
        parcel.readInt(),

        // 2. قراءة String (UTF-16 مع طول مسبق)
        parcel.readString() ?: "",

        // 3. قراءة String ثانية
        parcel.readString() ?: "",

        // 4. قراءة Boolean (يُخزن كـ Int: 1 = true, 0 = false)
        parcel.readByte() != 0.toByte(),

        // 5. قراءة Double (8 bytes, aligned to 4)
        parcel.readDouble()
    )

    /**
     * التسلسل الصريح — يجب أن يتطابق مع ترتيب القراءة في المنشئ
     */
    override fun writeToParcel(parcel: Parcel, flags: Int) {
        // 1. كتابة Int
        parcel.writeInt(userId)

        // 2. كتابة String
        parcel.writeString(userName)

        // 3. كتابة String
        parcel.writeString(email)

        // 4. كتابة Boolean كـ Byte
        parcel.writeByte(if (isActive) 1 else 0)

        // 5. كتابة Double
        parcel.writeDouble(score)
    }

    /**
     * وصف المحتوى — يُستخدم في Binder لتحديد ما إذا كان
     * Parcel يحتوي على File Descriptors (FDs)
     */
    override fun describeContents(): Int = 0

    /**
     * الكائن المُنشئ (CREATOR) — مطلوب من واجهة Parcelable
     */
    companion object CREATOR : Parcelable.Creator<UserProfile> {
        override fun createFromParcel(parcel: Parcel): UserProfile {
            return UserProfile(parcel)
        }

        override fun newArray(size: Int): Array<UserProfile?> {
            return arrayOfNulls(size)
        }
    }
}

package com.example.binderdemo

import android.app.Service

/**
 * خدمة AIDL مع التحقق من صلاحيات العملية المتصلة
 * يُظهر كيفية استخدام Binder.getCallingUid() لمنع
 * هجمات تصعيد الصلاحيات (Privilege Escalation)

class SecureUserService : Service() {

    companion object {
        private const val TAG = "SecureUserService"

        // قائمة UID مسموح لها بالوصول (Whitelist)
        private val ALLOWED_UIDS = setOf(
            1000,   // System Server
            1001,   // Phone
            2000    // Shell (ADB)
        )
    }

    /**
     * تنفيذ AIDL Interface — يتضمن التحقق من الأمان
     */
    private val binder = object : IUserService.Stub() {

        override fun getUserProfile(userId: Int): UserProfile {
            // ───────────────────────────────────────────────
            // التحقق من الأمان: من الذي يطلب هذه البيانات؟
            // ───────────────────────────────────────────────
            val callingUid = Binder.getCallingUid()
            val callingPid = Binder.getCallingPid()

            Log.d(TAG, "getUserProfile called by UID=$callingUid, PID=$callingPid")

            // رفض الوصول إذا لم يكن UID في القائمة المسموحة
            if (callingUid !in ALLOWED_UIDS) {
                Log.w(TAG, "Access denied for UID=$callingUid")
                throw SecurityException(
                    "Permission denied: UID $callingUid not authorized"
                )
            }

            // ───────────────────────────────────────────────
            // المنطق التجاري — يُنفذ فقط بعد التحقق من الأمان
            // ───────────────────────────────────────────────
            return UserProfile(
                userId = userId,
                userName = "User_$userId",
                email = "user$userId@example.com",
                isActive = true,
                score = 95.5
            )
        }

            code: Int,
            data: Parcel,
            reply: Parcel?,
            flags: Int

    override fun onBind(intent: Intent): IBinder {
        Log.i(TAG, "Service bound by: ${intent.`package`}")

المراقبة عبر /d/binder/proc وتحليل الاختناقات

يُعدّ نظام الملفات الافتراضي /d/binder/ (DebugFS) مصدراً غنياً لمعلومات التشخيص. يمكن للمطورين المخضرمين قراءة هذه الملفات لفهم:

  • الاختناقات (Bottlenecks): عمليات ذات معاملات معلقة لفترات طويلة تشير إلى خدمة بطيئة أو حالة Deadlock.
  • تسريبات الذاكرة (Memory Leaks): زيادة مستمرة في عدد Local Nodes دون انخفاض تشير إلى عدم تحرير Binder Objects.
  • هجمات الحرمان (DoS): عملية واحدة تستهلك نسبة عالية من المخزن المؤقت (Buffer) تشير إلى محاولة استنزاف الموارد.
// C++ — قراءة معلومات Binder من DebugFS برمجياً
// ============================================================
// BinderDiagnostics.cpp — قراءة معلومات التشخيص برمجياً
// ============================================================
#include <fstream>
#include <sstream>
#include <string>
#include <android/log.h>

class BinderDiagnostics {
public:
    /**
     * قراءة إحصائيات Binder لعملية محددة
     */
    static bool checkBufferPressure(pid_t pid, float& usagePercent) {
        std::string path = "/d/binder/proc/" + std::to_string(pid);
        std::ifstream file(path);

        if (!file.is_open()) {
            ALOGE("Failed to open %s", path.c_str());
            return false;
        }

        std::string line;
        size_t used = 0, total = 0;

        while (std::getline(file, line)) {
            if (line.find("buffer:") != std::string::npos) {
                // تحليل السطر: "buffer: 256KB / 1024KB"
                std::sscanf(line.c_str(), 
                    "buffer: %zuKB / %zuKB", &used, &total);
            }
        }

        if (total > 0) {
            usagePercent = (float)used / total * 100.0f;

            if (usagePercent > 80.0f) {
                ALOGW("Binder buffer at %.1f%% — Risk of TransactionTooLarge!", 
                      usagePercent);
            }
            return true;
        }

        return false;
    }
};
تدقيق الأمان: التحقق من UID/PID ومنع تصعيد الصلاحيات

يُعدّ التحقق من هوية المتصل (Caller Identity) من أهم آليات الأمان في Android IPC. يجب على كل خدمة Binder (سواءً Native أو Java) التحقق من UID و PID قبل تنفيذ أي عملية حساسة.

        val result = pm.checkUidPermission(permission, callingUid)

    fun enforceSameApp(expectedUid: Int) {

        if (callingUid != expectedUid) {

الممارسة الوصف التأثير
تقليل حجم Parcel تجنب إرسال Bitmap كاملة؛ استخدم URI أو Thumbnail يمنع TransactionTooLargeException
استخدام ONE_WAY للعمليات غير المتزامنة (Fire-and-Forget)، استخدم TF_ONE_WAY يقلل تأخير الانتظار (Blocking Time)
