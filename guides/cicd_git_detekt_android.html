مفاهيم CI/CD في AndroidCI/CD Concepts in Android

CI اختصار لـ Continuous Integration، وCD ممكن تعني Continuous Delivery أو Continuous Deployment. الفكرة الأساسية إنك بدل ما تدمج التعديلات وتبني وتختبر التطبيق يدويًا كل شوية، بتخلي السيرفر يعمل ده أوتوماتيك في كل مرة حد يعمل push للكود.

Continuous Integration (CI)

كل مرة يتعمل push أو Pull Request، السيرفر بيسحب الكود أوتوماتيك، يبنيه، يشغل الـ Unit Tests والـ Static Analysis (زي Detekt وktlint) عشان يتأكد إن الكود الجديد ملوش تعارض أو أخطاء قبل ما يتدمج.

Continuous Delivery

بعد نجاح الـ CI، التطبيق بيتجهز كـ APK/AAB جاهز للنشر في أي وقت، لكن الـ deploy الفعلي لسه بيحتاج موافقة يدوية (زر واحد فقط).

Continuous Deployment

خطوة أبعد من الـ Delivery — التطبيق بينزل أوتوماتيك على Play Store (غالبًا على قناة Internal Testing أو Beta) من غير أي تدخل بشري، طالما كل الاختبارات نجحت.

ليه مهم في Android بالذات؟

تعدد الأجهزة والـ API Levels، وقت بناء الـ Gradle الطويل، تعقيد الـ Signing، وتعدد الـ Product Flavors — كل ده بيخلي الأتمتة ضرورة مش رفاهية في أي مشروع فيه أكتر من مطور.

الفايدة الحقيقية في فريق Android

  • اكتشاف الأخطاء بدري: لو حد كسر الـ build أو فشل test، تعرف في نفس الدقيقة مش بعد أسبوع.
  • ثبات بيئة البناء: الـ build بيحصل على سيرفر نظيف كل مرة، مش على جهاز مطور فيه إعدادات مختلفة (No "works on my machine").
  • سرعة الإصدار: تقدر تنزل نسخة جديدة لأي قناة اختبار في دقايق بدل ساعات من الخطوات اليدوية.
  • ثقة أعلى في الدمج: فريق كبير يقدر يدمج Pull Requests كتير في اليوم من غير خوف إنهم يكسروا بعض.
💡

قاعدة ذهبية: لو خطوة بتتعمل يدويًا أكتر من مرتين، اعتبرها مرشحة للأتمتة داخل الـ Pipeline.

on:
  pull_request:
    branches: [ main ]

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: 17
      - name: Run Detekt
        run: ./gradlew detekt
      - name: Run Unit Tests
        run: ./gradlew testDebugUnitTest
      - name: Assemble Debug APK
        run: ./gradlew assembleDebug

تقنيات أتمتة الإصدارRelease Automation Techniques

الهدف من أتمتة الإصدار إنك توصل لمرحلة تقدر فيها تنزل نسخة جديدة بـ Trigger واحد (زر أو Tag) من غير أي خطوة يدوية عرضة للخطأ.

1. الترقيم الدلالي — Semantic Versioning

نظام MAJOR.MINOR.PATCH (مثال: 2.4.1) — MAJOR لما يبقى فيه Breaking Change، MINOR لميزة جديدة متوافقة مع القديم، PATCH لإصلاح باگ. في Android بنربطها بـ:

app/build.gradle.kts
android {
    defaultConfig {
        versionCode = generateVersionCode()  // رقم داخلي متزايد، إلزامي لكل رفعة على Play Store
        versionName = "2.4.1"          // الاسم الظاهر للمستخدم
    }
}

2. أتمتة زيادة رقم الإصدار

بدل ما تزود versionCode يدويًا، بتخليه يعتمد على عدد الـ commits أو على CI build number أوتوماتيك، أو تستخدم بلجن زي gradle-versioner.

3. Fastlane Lanes

fastlane/Fastfile
lane :beta do
  gradle(task: "bundleRelease")
  upload_to_play_store(
    track: "beta",
    aab: "app/build/outputs/bundle/release/app-release.aab"
  )
  slack(message: "نسخة Beta جديدة اتنزلت 🚀")
end

4. النشر التدريجي — Staged Rollouts

Play Console بيسمحلك تنزل النسخة على نسبة صغيرة من المستخدمين الأول (زي 10%)، وتراقب الـ Crash rate وANR قبل ما توسّع النسبة تدريجيًا لحد 100%، وده بتقدر تؤتمته بـ Fastlane أو Google Play Developer API.

5. توليد الـ Changelog أوتوماتيك

باستخدام Conventional Commits (زي feat:, fix:, chore:) تقدر تولّد ملاحظات الإصدار أوتوماتيك بأدوات زي git-cliff أو release-please.

تحسين البناء متعدد الموديولاتMulti-module Build Optimization

في مشاريع كبيرة مقسّمة لـ Modules (زي :core, :feature:home, :feature:profile)، وقت البناء ممكن يبقى مشكلة حقيقية. أهم التقنيات لتسريع الـ build:

  • Gradle Build Cache: بيحفظ نتائج المهام (outputs) ويعيد استخدامها لو نفس المدخلات ماتغيّرتش — محلي أو Remote Cache مشترك بين الفريق والـ CI.
  • Configuration Cache: بيحفظ نتيجة مرحلة الـ configuration نفسها (قبل التنفيذ)، فبيقلل وقت البداية بشكل كبير في المشاريع الكبيرة.
  • Parallel Execution: org.gradle.parallel=true — بيخلي Gradle يبني الموديولات المستقلة عن بعض بالتوازي.
  • Convention Plugins: بدل ما تكرر نفس إعدادات build.gradle.kts في كل موديول، بتعمل Plugin مشترك (في build-logic module) يطبّق نفس الإعدادات بشكل موحّد.
  • Module Graph الصحيح: تجنب الاعتماديات الدائرية (Circular Dependencies) واستخدم api vs implementation بذكاء عشان تقلل إعادة الترجمة غير الضرورية عند تغيير موديول واحد.
  • Build Scan: ./gradlew build --scan بيديك تقرير تفصيلي يوضح أبطأ المهام والاعتماديات اللي بتعطل الـ parallelism.
gradle.properties
org.gradle.caching=true
org.gradle.parallel=true
org.gradle.configuration-cache=true
org.gradle.jvmargs=-Xmx4g -XX:+UseParallelGC
💡

نصيحة عملية: في CI، فعّل Remote Build Cache (زي Gradle Enterprise أو حل بديل مجاني على S3) عشان كل الفريق والـ pipeline يستفيدوا من نفس نتائج البناء المحفوظة.

إدارة الأسرار وتوقيع التطبيقSecrets and Signing Management

ملف الـ Keystore ومفاتيح الـ API من أخطر الأشياء اللي لازم متتسربش. القواعد الأساسية:

  1. خزّن الـ Keystore كـ Base64 داخل GitHub Secrets أو GitLab CI/CD Variables — مش أبدًا في الكود أو ملف مرفوع على الـ repo.
  2. استخدم متغيرات بيئة للـ passwords بدل كتابتها في build.gradle مباشرة.
  3. فعّل Play App Signing عشان جوجل تدير مفتاح التوقيع النهائي، وإنت بس تحتاج مفتاح الرفع (Upload Key) اللي أسهل استبداله لو اتسرب.
  4. استخدم .gitignore لاستبعاد *.jks وlocal.properties و.env من الرفع نهائيًا.
GitHub Actions — فك تشفير الـ Keystore
- name: Decode Keystore
  env:
    KEYSTORE_BASE64: ${{'{{'}} secrets.KEYSTORE_BASE64 }}
  run: |
    echo $KEYSTORE_BASE64 | base64 -d > app/release.keystore
app/build.gradle.kts
signingConfigs {
    create("release") {
        storeFile = file(System.getenv("KEYSTORE_PATH") ?: "release.keystore")
        storePassword = System.getenv("KEYSTORE_PASSWORD")
        keyAlias = System.getenv("KEY_ALIAS")
        keyPassword = System.getenv("KEY_PASSWORD")
    }
}
🔒

خطأ شائع جدًا: رفع local.properties فيه API keys بالغلط على GitHub Public Repo. لو حصل، غيّر المفتاح فورًا — مسحه من الكود مش كافي لأنه لسه موجود في الـ Git history.

أفضل ممارسات CI/CDCI/CD Best Practices

  • Fail Fast: رتّب المراحل السريعة (lint/unit tests) قبل البطيئة (instrumented tests/build) عشان توفر وقت ومصاريف.
  • Cache كل حاجة ممكنة: Gradle dependencies، Gradle wrapper، وحتى الـ Docker layers لو بتستخدم Containers.
  • Matrix Builds: شغّل نفس الـ tests على أكتر من API level أو device config بالتوازي بدل التسلسل.
  • احتفظ بالـ Artifacts: ملفات الـ APK/AAB، تقارير الاختبارات، وتقارير Detekt تتحفظ كـ build artifacts لفترة محددة عشان الرجوع ليها وقت الحاجة.
  • Branch Protection Rules: اربط قواعد الحماية على الـ main branch بنجاح الـ CI checks — محدش يقدر يعمل merge لو الـ pipeline فشل.
  • إشعارات فورية: ربط الـ pipeline بـ Slack/Teams عشان الفريق يعرف فورًا لو حصل فشل، مش يكتشفوا بعد يوم.
  • Pipeline كملف واحد قابل للقراءة: تجنب الـ scripts المبعثرة، خلي الـ workflow file نفسه موثّق وواضح الخطوات.
  • Timeouts: حدد وقت أقصى لكل job عشان لو حصل تعليق (hang) ما يفضلش الـ runner شغال لساعات بلاش.

أساسيات GitGit Essentials

Git نظام تحكم بالإصدارات موزّع (Distributed Version Control System) — كل مطور عنده نسخة كاملة من تاريخ المشروع على جهازه، مش بس على سيرفر مركزي.

الأوامر الأساسية

الأمرالوظيفة
git initإنشاء repository جديد في المجلد الحالي.
git clone <url>نسخ repository موجود من سيرفر بعيد.
git statusعرض حالة الملفات (متغيّرة/مضافة/غير متتبّعة).
git add <file>إضافة التعديلات لمنطقة الـ Staging.
git commit -m "msg"حفظ التعديلات المضافة كـ commit جديد بالتاريخ.
git pushرفع الـ commits المحلية للـ remote repository.
git pullسحب ودمج آخر تعديلات من الـ remote.
git branch <name>إنشاء فرع جديد.
git checkout -b <name>إنشاء فرع جديد والانتقال له مباشرة.
git merge <branch>دمج فرع تاني في الفرع الحالي.
git rebase <branch>إعادة تطبيق الـ commits فوق فرع تاني (تاريخ أنظف من merge).
git stashتخزين مؤقت للتعديلات غير المحفوظة من غير commit.

Merge vs Rebase — الفرق العملي

git merge

بيحافظ على التاريخ الحقيقي كامل، لكن بيضيف "merge commits" بتخلي الـ log مليان تفريعات. آمن للاستخدام دايمًا حتى على فروع مشتركة.

git rebase

بيدي تاريخ خطي نظيف (linear history) بدون merge commits، لكن بيغيّر الـ commit hashes — خطير لو استخدمته على فرع الفريق مشترك بيشتغل عليه ناس تانية.

استراتيجيات الـ Pull RequestPull Request (PR) Strategies

الـ Pull Request مش بس وسيلة لدمج الكود، ده أهم أداة لمراجعة الجودة ونقل المعرفة داخل الفريق.

استراتيجيات التفريع الشائعة

الاستراتيجيةالوصفمناسبة لـ
Trunk-Based Developmentفروع صغيرة عمرها ساعات، بتتدمج على main بسرعة وباستمرار، مع Feature Flags لإخفاء الميزات الغير مكتملة.فرق CI/CD ناضجة، إصدار مستمر.
Git Flowفروع منظمة: main, develop, feature/*, release/*, hotfix/*.مشاريع بإصدارات مجدولة (App Store releases).
GitHub Flowفرع واحد رئيسي + فروع feature قصيرة تتدمج مباشرة بعد المراجعة.فرق صغيرة/متوسطة، نشر مستمر.

نصائح لـ PR فعّال

  • حجم صغير: PR أقل من 400 سطر أسهل بكتير في المراجعة من PR ضخم بـ 3000 سطر.
  • وصف واضح: استخدم PR Template فيه: الهدف، طريقة الاختبار، Screenshots لو UI، وربط بالـ Issue.
  • Conventional Commits: feat:, fix:, refactor:, chore:, docs: — بتسهّل توليد الـ changelog وفهم التاريخ.
  • Draft PRs: افتح PR كـ Draft وإنت لسه بتشتغل عشان تاخد Feedback مبكر من غير ما تطلب موافقة نهائية.
  • CI Checks إلزامية: امنع الـ merge لو الـ Detekt أو الـ Tests فشلوا (Required Status Checks في GitHub).

Git لإدارة الإصداراتGit for Release Management

إدارة الإصدار بشكل صحيح في Git بتخليك تقدر ترجع لأي نسخة نزلت للمستخدمين وقت ما تحتاج، وتتعامل مع Hotfixes بسرعة من غير ما تكسر التطوير الجاري.

Tags للإصدارات

Terminal
git tag -a v2.4.1 -m "Release 2.4.1 - إصلاح مشكلة تسجيل الدخول"
git push origin v2.4.1

# عرض كل الإصدارات
git tag -l "v2.*"

فرع الـ Release

لما التطوير على develop يوصل لمرحلة الاستقرار، بتعمل فرع release/2.5.0 — عليه بس إصلاحات صغيرة وتجهيزات النشر (رقم الإصدار، الـ changelog)، مفيش ميزات جديدة تتضاف عليه، وبعد ما ينزل بيتدمج في main وdevelop مع بعض.

فروع الـ Hotfix

لو ظهر باگ حرج في نسخة الإنتاج، بتعمل فرع hotfix/2.4.2 مباشرة من main، تصلحه، تنزله بسرعة، وبعدين تدمجه في كل من main وdevelop عشان الإصلاح ميضيعش في الإصدار الجاي.

💡

نصيحة: اربط كل Tag إصدار بـ GitHub Release فيه ملاحظات الإصدار (Release Notes) وملف الـ APK/mapping.txt الخاص بالـ ProGuard/R8، عشان تقدر تفك أي Crash Report بعدين بسهولة.

Detached HEAD مش مفهومأي commit جديد ممكن يضيع لو عملت checkout لفرع تاني.لو عايز تحتفظ بالتعديلات، اعمل فرع جديد فورًا: git checkout -b fix-branch.
Commit messages غامضة زي "fix"بيصعّب فهم التاريخ وقت الـ debugging أو الـ git blame.استخدم Conventional Commits ووصف واضح للسبب مش بس للفعل.
⚠️

لو حصل غلط فعلاً: git reflog بيحتفظ بسجل كل حركة عملتها حتى لو مسحت commit بالغلط — غالبًا تقدر تسترجعه منه قبل ما تدخل في حالة هلع.

Pre-commit Hooks في AndroidPre-commit Hooks for Android

Git Hooks سكريبتات بتتشغل أوتوماتيك عند حدث معين (زي قبل الـ commit أو قبل الـ push)، وبتساعدك تمسك المشاكل محليًا قبل ما توصل للـ CI أصلاً.

الأنواع الشائعة

الـ Hookيتشغل متىاستخدام نموذجي
pre-commitقبل حفظ الـ commitتشغيل ktlintFormat وDetekt على الملفات المتغيّرة فقط.
commit-msgبعد كتابة الرسالةالتأكد إن الرسالة متوافقة مع Conventional Commits.
pre-pushقبل رفع الكود للـ remoteتشغيل Unit Tests سريعة قبل ما توصل التعديلات للفريق.

مثال Hook بسيط بـ Shell Script

.git/hooks/pre-commit
#!/bin/sh
echo "⏳ Running Detekt before commit..."
./gradlew detekt --daemon

if [ $? -ne 0 ]; then
  echo "❌ Detekt found issues. Commit aborted."
  exit 1
fi

echo "✅ Detekt passed."
exit 0

بما إن Hooks المحلية العادية متتشاركش أوتوماتيك مع الفريق، الحل الأفضل هو استخدام أداة زي Husky (لو المشروع فيه Node) أو Gradle plugin زي gradle-git-hooks-plugin اللي بينسخ الـ hooks لكل مطور أول ما يعمل sync للمشروع.

💡

نصيحة أداء: شغّل Detekt على الملفات المتغيّرة فقط في الـ pre-commit (باستخدام --input على الملفات من git diff) عشان الـ hook يفضل سريع ومايضايقش المطور في كل commit.

ما هو Detekt؟What is Detekt?

Detekt أداة تحليل ساكن (Static Code Analysis) مخصصة للغة Kotlin، بتفحص الكود من غير ما تشغّله فعليًا، وبتكتشف: الأكواد المعقدة زيادة، مشاكل الأسلوب (style)، الأخطاء المحتملة (potential bugs)، ومشاكل الأداء — كل ده قبل ما توصل للمراجعة البشرية أصلاً.

ليه Detekt مش مجرد "linter عادي"؟

  • بيبني Abstract Syntax Tree (AST) كامل للكود Kotlin، فبيقدر يفهم البنية مش بس يقارن نصوص.
  • قابل للتوسعة بالكامل — تقدر تكتب Rules خاصة بمعايير فريقك.
  • بيدعم Type Resolution (فحص الأنواع الفعلية) مش بس تحليل نصي سطحي.
  • بيتكامل مباشرة مع Gradle وAndroid Studio وGitHub Actions.

Detekt مقابل أدوات تانية

الأداةتركيزها
Detektجودة الكود، التعقيد، الأخطاء المحتملة، الـ code smells في Kotlin.
ktlintتنسيق الكود (formatting) فقط — مسافات، ترتيب imports، أسلوب الكتابة الرسمي لـ Kotlin.
Android Lintمشاكل خاصة بـ Android SDK نفسه — resources غير مستخدمة، مشاكل accessibility، API compatibility.

في الغالب بتستخدم الثلاثة مع بعض — كل واحدة بتغطي زاوية مختلفة، ومفيش تعارض بينهم.

namingمخالفة قواعد تسمية Kotlin (camelCase, PascalCase للـ classes).
commentsTODO/FIXME متروكة، تعليقات فاضية أو زايدة عن الحاجة.
exceptionscatch(Exception) عام جدًا، throw generic exceptions، ابتلاع الأخطاء بصمت.
formatting(عبر تكامل ktlint) مسافات، أقواس، ترتيب استيراد.

Detekt بيقدر يطلّع تقارير بصيغ متعددة في نفس الوقت — HTML لمراجعة بصرية سريعة، XML/Checkstyle للتكامل مع أدوات تانية، وSARIF لعرض النتائج مباشرة كتعليقات على الـ Pull Request في GitHub.

إعداد الـ BaselineDetekt Baseline Setup

لو Detekt بيتضاف على مشروع قديم فيه آلاف المشاكل الموجودة بالفعل، مش منطقي تطلب من الفريق يصلحهم كلهم قبل ما يقدروا يعملوا commit. الحل هو Baseline: ملف بيسجل كل المشاكل الحالية ويستثنيها من الفحص، وأي مشكلة جديدة بعد كده هي اللي بتوقّف الـ build.

Terminal — توليد الـ Baseline
./gradlew detektBaseline
build.gradle.kts
detekt {
    baseline = file("config/detekt/baseline.xml")
}

استراتيجية التبني التدريجي

  1. ولّد الـ baseline أول مرة عشان تجمّد المشاكل الموجودة حاليًا.
  2. خلي الـ CI يفشل بس على المشاكل الجديدة (مش الموجودة في الـ baseline).
  3. خصص وقت دوري (Sprint واحد كل شهر مثلاً) لتقليل حجم الـ baseline تدريجيًا وإصلاح الديون القديمة.
  4. لما الـ baseline يوصل صفر، احذف الملف نهائيًا وخلي المشروع نظيف 100%.
✅

الفايدة: الفريق بيقدر يبدأ فرض جودة الكود من النهاردة على أي كود جديد، من غير ما يتوقف التطوير أسابيع عشان يصلّح تاريخ قديم كامل.

قواعد مخصصة في DetektCustom Rules in Detekt

لو فريقك عنده معايير خاصة (زي منع استخدام LiveData لصالح StateFlow في مشروع بيهاجر تدريجيًا)، تقدر تكتب Rule مخصصة بنفسك.

1. إنشاء موديول Rules منفصل

بتعمل موديول Gradle مستقل (مثلاً :detekt-rules) فيه الكلاسات دي، وبيتصدّر كـ jar يتحمّل في مرحلة الـ Detekt.

2. كتابة Rule بسيطة

NoLiveDataRule.kt
class NoLiveDataRule(config: Config) : Rule(config) {

    override val issue = Issue(
        id = "NoLiveData",
        severity = Severity.Defect,
        description = "استخدم StateFlow بدل LiveData في الكود الجديد",
        debt = Debt.TWENTY_MINS
    )

    override fun visitImportDirective(importDirective: KtImportDirective) {
        super.visitImportDirective(importDirective)
        if (importDirective.importedFqName?.asString() == "androidx.lifecycle.LiveData") {
            report(CodeSmell(issue, Entity.from(importDirective), issue.description))
        }
    }
}

3. تسجيل الـ RuleSetProvider

CustomRuleSetProvider.kt
class CustomRuleSetProvider : RuleSetProvider {
    override val ruleSetId = "custom-rules"
    override fun instance(config: Config): RuleSet =
        RuleSet(ruleSetId, listOf(NoLiveDataRule(config)))
}

4. تفعيلها في build.gradle.kts

app/build.gradle.kts
dependencies {
    detektPlugins(project(":detekt-rules"))
}

لازم كمان تعمل ملف resources/META-INF/services/io.gitlab.arturbosch.detekt.api.RuleSetProvider فيه اسم الكلاس الكامل عشان Detekt يقدر يكتشف الـ Rule تلقائيًا (Service Loader mechanism).

دمج Detekt في CI/CDIntegrating Detekt in CI/CD

هنا بنقفل الدايرة — بندمج المحورين التانيين مع بعض: Detekt كـ Quality Gate جوه Pipeline الـ CI/CD.

.github/workflows/detekt.yml
name: Code Quality
on: [pull_request]

jobs:
  detekt:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Run Detekt
        run: ./gradlew detekt

      - name: Upload SARIF report
        if: always()
        uses: github/codeql-action/upload-sarif@v3
        with:
          sarif_file: build/reports/detekt/detekt.sarif

      - name: Upload HTML report as artifact
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: detekt-report
          path: build/reports/detekt/detekt.html

لماذا SARIF مهم؟

رفع تقرير SARIF (Static Analysis Results Interchange Format) بيخلي GitHub يعرض كل مشكلة Detekt كتعليق مباشر على السطر بالظبط جوه الـ Pull Request نفسه — المراجع (Reviewer) بيشوف المشكلة جنب الكود من غير ما يفتح تقرير منفصل.

خلي الفشل واضح ومفيد

  • خلي الـ job يفشل (exit code 1) لو فيه أي مشكلة جديدة خارج الـ baseline — ده اللي بيمنع الـ merge أصلاً عبر Branch Protection.
  • ارفع تقرير HTML كـ artifact دايمًا (if: always()) حتى لو الخطوة فشلت، عشان المطور يقدر يفتحه ويشوف التفاصيل كاملة.
  • لو عندك موديولات كتير، شغّل Detekt بالتوازي مع باقي الفحوصات (unit tests, lint) مش بالتسلسل، عشان توفر وقت.
🎯

الخلاصة: لما تجمع CI/CD وGit Workflow وDetekt مع بعض بالشكل ده، بتضمن إن أي كود يوصل لـ main يكون: مبني بنجاح، معدّى الاختبارات، وموافق لمعايير جودة الفريق — كل ده أوتوماتيك وبدون تدخل بشري بعد لحظة الـ push.
