معماريات أندرويد — Android Architecture Patterns

فهم تطور المعماريات من MVC إلى MVI وكيفية اختيار النمط المناسب لكل مشروع

ما هو الفرق بين MVC و MVP و MVVM و MVI، وكيف تطورت معماريات أندرويد عبر هذه الأنماط؟

Architecture Evolution Kotlin Jetpack

تطورت معماريات أندرويد بشكل تدريجي لحل مشكلة Coupling العالي بين واجهة المستخدم (UI) ومنطق الأعمال (Business Logic). فيما يلي رحلة التطور:

1. MVC (Model-View-Controller)

في MVC، يتحكم Controller في كل شيء. المشكلة في أندرويد أن Activity أو Fragment يُجبر على أن يكون Controller وView في آن واحد، مما يؤدي إلى God Activity ضخمة يصعب اختبارها.

⟷

⟷

⚠️

لماذا MVC لم يعد مستحسناً في أندرويد؟

لأن Activity تتحمل مسؤولية تحديث UI ومعالجة الأحداث والتحكم في البيانات في آن واحد. اختبار الوحدات (Unit Testing) يصبح شبه مستحيل.

2. MVP (Model-View-Presenter)

في MVP، نفصل Presenter عن Activity عبر Interface. الـ Presenter يحتوي على المنطق ويُعلم الـ View بالتحديثات عبر Contract.

KOTLIN 
// MVP Contract
interface LoginContract {
    interface View {
        fun showLoading()
        fun hideLoading()
        fun showError(message: String)
        fun navigateToHome()
    }
    interface Presenter {
        fun login(username: String, password: String)
    }
}

// Presenter Implementation
class LoginPresenter(
    private val view: LoginContract.View,
    private val repository: UserRepository
) : LoginContract.Presenter {
    override fun login(username: String, password: String) {
        view.showLoading()
        repository.authenticate(username, password)
            .enqueue(object : Callback<User> {
                override fun onResponse(call: Call<User>, response: Response<User>) {
                    view.hideLoading()
                    if (response.isSuccessful) view.navigateToHome()
                    else view.showError("Invalid credentials")
                }
                override fun onFailure(call: Call<User>, t: Throwable) {
                    view.hideLoading()
                    view.showError(t.message ?: "Unknown error")
                }
            })
    }
}
⚡

عيب MVP الكبير

الـ Presenter يحتفظ بـ Reference للـ View (Activity) مما يسبب Memory Leaks إذا لم تُدير دورة الحياة (Lifecycle) بعناية. كما أن كل تحديث للبيانات يتطلب استدعاءً صريحاً للـ View.

3. MVVM (Model-View-ViewModel)

في MVVM، يحل ViewModel محل Presenter. الفرق الجوهري: الـ ViewModel لا يعرف الـ View! بدلاً من ذلك، يُعرض البيانات عبر Observable patterns مثل LiveData أو StateFlow.

KOTLIN 
class LoginViewModel(
    private val loginUseCase: LoginUseCase
) : ViewModel() {

    private val _uiState = MutableStateFlow(LoginUiState())
    val uiState: StateFlow<LoginUiState> = _uiState.asStateFlow()

    fun login(username: String, password: String) {
        viewModelScope.launch {
            _uiState.value = _uiState.value.copy(isLoading = true)
            val result = loginUseCase(username, password)
            _uiState.value = when (result) {
                is Result.Success -> _uiState.value.copy(isLoading = false, isLoggedIn = true)
                is Result.Error -> _uiState.value.copy(isLoading = false, error = result.message)
            }
        }
    }
}

data class LoginUiState(
    val isLoading: Boolean = false,
    val isLoggedIn: Boolean = false,
    val error: String? = null
)

4. MVI (Model-View-Intent)

MVI يأخذ MVVM إلى مستوى أعلى من Predictability عبر Unidirectional Data Flow. كل تغيير في الـ State يتم عبر Intent (Action) واحد، والـ State دائماً Immutable.

KOTLIN 
// MVI: Single Immutable State + Sealed Class for Intents
sealed class LoginIntent {
    data class EnterUsername(val value: String) : LoginIntent()
    data class EnterPassword(val value: String) : LoginIntent()
    object SubmitLogin : LoginIntent()
    object DismissError : LoginIntent()
}

data class LoginState(
    val username: String = "",
    val password: String = "",
    val isLoading: Boolean = false,
    val error: String? = null,
    val isSuccess: Boolean = false
) {
    val isSubmitEnabled: Boolean
        get() = username.isNotBlank() && password.length >= 6
}

class LoginViewModel : ViewModel() {
    private val _state = MutableStateFlow(LoginState())
    val state = _state.asStateFlow()

    fun processIntent(intent: LoginIntent) {
        when (intent) {
            is LoginIntent.EnterUsername ->
                _state.value = _state.value.copy(username = intent.value)
            is LoginIntent.EnterPassword ->
                _state.value = _state.value.copy(password = intent.value)
            is LoginIntent.SubmitLogin -> performLogin()
            is LoginIntent.DismissError ->
                _state.value = _state.value.copy(error = null)
        }
    }
}
النمط اتجاه البيانات قابلية الاختبار التعقيد الحالة (State)
MVC ثنائي الاتجاه صعب جداً بسيط غير محددة
MVP ثنائي الاتجاه متوسط متوسط غير محددة
MVVM أحادي الاتجاه تقريباً سهل متوسط متعددة (LiveData/Flow)
MVI أحادي الاتجاه صارم سهل جداً معقد حالة واحدة غير قابلة للتغيير (Single Immutable State)
▼

ما هو Unidirectional Data Flow (UDF) في MVVM/MVI، ولماذا يُعتبر حاسماً لـ Jetpack Compose؟

UDF Jetpack Compose State Management

Unidirectional Data Flow (UDF) يعني أن البيانات تتدفق في اتجاه واحد فقط: Event → Update State → Recompose UI. لا يوجد تدفق معاكس من UI إلى ViewModel مباشرةً عبر تعديل State.

User Event
→
ViewModel
→
New State
→
UI Recomposition

لماذا UDF ضروري لـ Jetpack Compose؟

  • Recomposition هو دالة State: Compose يُعيد رسم UI تلقائياً عند تغير State. إذا كان State متعدد المصادر (Multiple Sources of Truth)، تصبح Recomposition غير متوقعة.
  • Predictability: كل State يأتي من مصدر واحد (Single Source of Truth) وهو الـ ViewModel.
  • Time-Travel Debugging: يمكنك تسجيل كل State وتشغيله للخلف/الأمام لأن State دائماً Immutable.
  • Testability: اختبار ViewModel يصبح اختبار دالة State خالصة: f(intent) = newState.
KOTLIN — Jetpack Compose + UDF 
@Composable
fun LoginScreen(
    viewModel: LoginViewModel = viewModel()
) {
    val state by viewModel.state.collectAsState()

    Column(modifier = Modifier.padding(16.dp)) {
        OutlinedTextField(
            value = state.username,
            onValueChange = { viewModel.processIntent(LoginIntent.EnterUsername(it)) },
            label = { Text("Username") }
        )
        Button(
            onClick = { viewModel.processIntent(LoginIntent.SubmitLogin) },
            enabled = state.isSubmitEnabled
        ) {
            if (state.isLoading) {
                CircularProgressIndicator(modifier = Modifier.size(20.dp))
            } else {
                Text("Login")
            }
        }
        state.error?.let { error ->
            Text(text = error, color = Color.Red)
        }
    }
}
💡

نصيحة Senior Architect

في Compose، تجنب استخدام rememberSaveable لحالة معقدة. دع الـ ViewModel يملك الـ State ودع Compose يُعيد الرسم فقط. هذا يحميك من فقدان البيانات عند تغيير الإعدادات (Configuration Changes).

كيف تُطبق Clean Architecture في أندرويد (Presentation, Domain, Data Layers)؟

Clean Architecture Layered Architecture Dependency Rule

Clean Architecture (من Robert C. Martin) تُفصل التطبيق إلى طبقات متحدة المركز (Concentric Layers)، حيث تُشير Dependencies دائماً للداخل. القاعدة الذهبية: "Inner layers know nothing about outer layers."

Presentation Layer
(UI, ViewModel, Compose)
⟵
Domain Layer
(UseCases, Entities, Repository Interfaces)
⟵
Data Layer
(Repository Impl, Room, Retrofit, DTOs)

1. Domain Layer — قلب التطبيق

هذه الطبقة خالصة من أي إطار عمل (Framework-agnostic). تحتوي على:

  • Entities: كائنات العمل الأساسية (مثل User, Product)
  • UseCases (Interactors): كل UseCase يمثل عملية واحدة في الأعمال (مثل GetUserProfileUseCase)
  • Repository Interfaces: عقود (Contracts) فقط بدون Implementation
KOTLIN — Domain Layer 
// domain/model/User.kt — Pure Kotlin, no Android dependencies
data class User(
    val id: String,
    val name: String,
    val email: String,
    val profileUrl: String?
)

// domain/repository/UserRepository.kt — Interface only
interface UserRepository {
    suspend fun getUser(id: String): Result<User>
    fun observeUsers(): Flow<List<User>>
}

// domain/usecase/GetUserProfileUseCase.kt
class GetUserProfileUseCase(
    private val repository: UserRepository
) {
    suspend operator fun invoke(userId: String): Result<User> {
        return repository.getUser(userId)
    }
}

2. Data Layer — Implementation & Frameworks

تحتوي على Implementation للـ Repository Interfaces وتتعامل مع:

  • Remote Data Source: Retrofit APIs
  • Local Data Source: Room Database
  • DTOs (Data Transfer Objects): نماذج JSON الخام
  • Mappers: تحويل DTOs إلى Domain Models
KOTLIN — Data Layer 
// data/remote/dto/UserDto.kt
data class UserDto(
    @SerializedName("user_id") val userId: String,
    @SerializedName("full_name") val fullName: String,
    @SerializedName("email_address") val emailAddress: String,
    @SerializedName("avatar_url") val avatarUrl: String?
)

// data/remote/mapper/UserMapper.kt
object UserMapper {
    fun toDomain(dto: UserDto): User = User(
        id = dto.userId,
        name = dto.fullName,
        email = dto.emailAddress,
        profileUrl = dto.avatarUrl
    )
}

// data/repository/UserRepositoryImpl.kt
class UserRepositoryImpl(
    private val remoteDataSource: UserRemoteDataSource,
    private val localDataSource: UserLocalDataSource,
    private val mapper: UserMapper
) : UserRepository {

    override suspend fun getUser(id: String): Result<User> {
        return try {
            val localUser = localDataSource.getUserById(id)
            if (localUser != null) {
                Result.success(localUser)
            } else {
                val dto = remoteDataSource.fetchUser(id)
                val domainUser = mapper.toDomain(dto)
                localDataSource.saveUser(domainUser)
                Result.success(domainUser)
            }
        } catch (e: Exception) {
            Result.failure(e)
        }
    }

    override fun observeUsers(): Flow<List<User>> {
        return localDataSource.observeAllUsers()
    }
}

3. DTOs vs Domain Models vs Entities

النوع الموقع الغرض مثال
DTO Data Layer تعكس هيكل JSON الخام من API UserDto مع @SerializedName
Domain Model Domain Layer كيان العمل النظيف بدون annotations User بحقول نظيفة
Entity Data Layer (Room) تعكس هيكل الجدول في قاعدة البيانات UserEntity مع @Entity
ℹ️

لماذا نفصل Domain Model عن DTO؟

لأن هيكل API قد يتغير (تغيير أسماء الحقول، إضافة/حذف حقول) دون أن يؤثر على منطق الأعمال. الـ Domain Model يبقى مستقراً بينما Mappers يتعاملون مع التغييرات.

متى تستخدم MVVM مقابل MVI مقابل Clean Architecture؟ ما هي عتبات تعقيد التطبيق؟

Decision Making Complexity Thresholds

اختيار المعمارية ليس ديناً، بل هو توازن بين التعقيد والفائدة. إليك العتبات العملية:

حجم التطبيق الشاشات الفريق النمط المُوصى به السبب
صغير جداً 1-3 شاشات 1 مطور MVVM بسيط Over-engineering يقتل السرعة
صغير-متوسط 4-10 شاشات 2-3 مطورين MVVM + Repository Pattern توازن جيد بين التنظيم والسرعة
متوسط 10-20 شاشة 3-5 مطورين Clean Architecture + MVVM فصل UseCases يُسهل التعاون
كبير 20+ شاشة 5+ مطورين Clean Architecture + MVI State مركزي يُسهل Debugging والتنسيق
Enterprise Multi-module فريقان+ Clean Architecture + MVI + Modularization كل Module يملك Domain Layer خاص
💡

قاعدة الذهب للمهندس المعماري

ابدأ بـ أبسط نمط يحل المشكلة. لا تُطبق Clean Architecture لتطبيق To-Do بسيط. لكن إذا رأيت أن ViewModel يتضخم (Fat ViewModel) أو أن اختبار الأعمال يصعب، فهذه إشارة لإدخال UseCases.

أنماط التصميم الإنشائية — Creational Patterns

أنماط تتحكم في آلية إنشاء الكائنات لضمان مرونة وإعادة استخدام الكود

Singleton Pattern

ضمان وجود نسخة واحدة فقط من الكائن

السؤال: كيف تضمن أن يكون لديك نسخة واحدة فقط من كائن مثل قاعدة البيانات أو عميل HTTP؟

الموقف الحقيقي: Room Database و Retrofit يجب أن يكونا Singletons لتجنب تسرب الذاكرة وضمان Thread Safety.

KOTLIN — Thread-Safe Singleton 
// Method 1: Kotlin 'object' (eager, thread-safe)
object RetrofitClient {
    val apiService: ApiService by lazy {
        Retrofit.Builder()
            .baseUrl("https://api.example.com/")
            .addConverterFactory(GsonConverterFactory.create())
            .build()
            .create(ApiService::class.java)
    }
}

// Method 2: Double-Check Locking (when you need parameters)
class DatabaseManager private constructor(context: Context) {
    companion object {
        @Volatile
        private var instance: DatabaseManager? = null

        fun getInstance(context: Context): DatabaseManager {
            return instance ?: synchronized(this) {
                instance ?: DatabaseManager(context.applicationContext).also {
                    instance = it
                }
            }
        }
    }
}
⚠️

تحذير: Overusing Singleton هو Anti-Pattern

Singletons يصعبون Unit Testing لأنها Global State. استخدم Dependency Injection (Hilt/Koin) بدلاً من الوصول المباشر للـ Singletons.

Factory & Abstract Factory

إنشاء كائنات ديناميكياً بناءً على السياق

السؤال: كيف تُنشئ كائنات مختلفة من نفس النوع بناءً على runtime conditions؟

الموقف الحقيقي: بوابات دفع مختلفة حسب المنطقة (Stripe, PayPal, Tap)، أو إنشاء ViewModel عبر ViewModelProvider.Factory.

KOTLIN — Factory Pattern 
// Payment Strategy Interface
interface PaymentProcessor {
    suspend fun processPayment(amount: Double): Result<String>
}

class StripeProcessor : PaymentProcessor { ... }
class PayPalProcessor : PaymentProcessor { ... }

// Factory
object PaymentFactory {
    fun createProcessor(region: String): PaymentProcessor {
        return when (region) {
            "US" -> StripeProcessor()
            "EU" -> PayPalProcessor()
            "MENA" -> TapProcessor()
            else -> throw IllegalArgumentException("Unsupported region")
        }
    }
}

// ViewModelProvider.Factory (Android built-in)
class MyViewModelFactory(
    private val repository: UserRepository
) : ViewModelProvider.Factory {
    override fun <T : ViewModel> create(modelClass: Class<T>): T {
        return when {
            modelClass.isAssignableFrom(UserViewModel::class.java) ->
                UserViewModel(repository) as T
            else -> throw IllegalArgumentException("Unknown ViewModel")
        }
    }
}

Builder Pattern

بناء كائنات معقدة خطوة بخطوة

السؤال: كيف تُنشئ كائنات ذات عدد كبير من الإعدادات الاختيارية دون Constructor معقد؟

الموقف الحقيقي: AlertDialog.Builder، NotificationCompat.Builder، أو طلبات HTTP معقدة.

KOTLIN — Builder with DSL 
// Custom HTTP Request Builder
class HttpRequest private constructor(
    val url: String,
    val method: String,
    val headers: Map<String, String>,
    val body: String?,
    val timeout: Int
) {
    class Builder(private val url: String) {
        private var method = "GET"
        private var headers = mutableMapOf<String, String>()
        private var body: String? = null
        private var timeout = 30_000

        fun method(method: String) = apply { this.method = method }
        fun header(key: String, value: String) = apply { headers[key] = value }
        fun body(body: String) = apply { this.body = body }
        fun timeout(ms: Int) = apply { this.timeout = ms }

        fun build() = HttpRequest(url, method, headers, body, timeout)
    }
}

// Usage
val request = HttpRequest.Builder("https://api.example.com/user")
    .method("POST")
    .header("Authorization", "Bearer token")
    .header("Content-Type", "application/json")
    .body("{\"name\":\"Ahmed\"}")
    .timeout(10_000)
    .build()
💡

أنماط التصميم الهيكلية — Structural Patterns

أنماط تُنظم العلاقات بين الكائنات والكلاسات لبناء هياكل مرنة وقابلة للتوسع

Adapter Pattern

توحيد واجهات غير متوافقة

السؤال: كيف تُستخدم كلاس/واجهة قديمة أو طرف ثالث لا تتوافق مع كودك الحالي؟

الموقف الحقيقي: RecyclerView.Adapter يُحوّل Domain Models إلى ViewHolders. أو ربط API قديم بتطبيقك الجديد.

KOTLIN — Adapter Pattern 
// Legacy Payment API (3rd party SDK)
class LegacyPaymentSdk {
    fun makePayment(amountInCents: Int, currencyCode: String) { ... }
}

// Our modern interface
interface ModernPaymentGateway {
    fun pay(amount: Double, currency: Currency)
}

// Adapter bridges the gap
class LegacyPaymentAdapter(
    private val legacySdk: LegacyPaymentSdk
) : ModernPaymentGateway {
    override fun pay(amount: Double, currency: Currency) {
        val cents = (amount * 100).toInt()
        legacySdk.makePayment(cents, currency.currencyCode)
    }
}

// RecyclerView.Adapter is the most common Android Adapter
class ProductAdapter(
    private val onItemClick: (Product) -> Unit
) : ListAdapter<Product, ProductViewHolder>(ProductDiffCallback()) {

    override fun onCreateViewHolder(parent: ViewGroup, viewType: Int): ProductViewHolder {
        val binding = ItemProductBinding.inflate(
            LayoutInflater.from(parent.context), parent, false
        )
        return ProductViewHolder(binding, onItemClick)
    }

    override fun onBindViewHolder(holder: ProductViewHolder, position: Int) {
        holder.bind(getItem(position))
    }
}

Decorator Pattern

إضافة وظائف ديناميكياً دون تعديل الكلاس الأصلي

السؤال: كيف تُضيف وظائف (Logging, Auth, Caching) لكائن موجود دون وراثته؟

الموقف الحقيقي: إضافة Interceptors لـ Retrofit (Logging, Authentication Headers, Retry Logic).

KOTLIN — Decorator Pattern 
// Base interface
interface HttpClient {
    suspend fun execute(request: HttpRequest): HttpResponse
}

// Concrete implementation
class OkHttpClientWrapper : HttpClient {
    override suspend fun execute(request: HttpRequest): HttpResponse { ... }
}

// Decorator: Logging
class LoggingHttpClient(
    private val wrapped: HttpClient
) : HttpClient {
    override suspend fun execute(request: HttpRequest): HttpResponse {
        Log.d("HTTP", "→ ${request.method} ${request.url}")
        val response = wrapped.execute(request)
        Log.d("HTTP", "← ${response.statusCode}")
        return response
    }
}

// Decorator: Auth Header
class AuthHttpClient(
    private val wrapped: HttpClient,
    private val tokenProvider: () -> String
) : HttpClient {
    override suspend fun execute(request: HttpRequest): HttpResponse {
        val authenticated = request.copy(
            headers = request.headers + ("Authorization" to "Bearer ${tokenProvider()}")
        )
        return wrapped.execute(authenticated)
    }
}

// Compose decorators
val client = LoggingHttpClient(
    AuthHttpClient(
        OkHttpClientWrapper(),
        tokenProvider = { TokenManager.getToken() }
    )
)

Facade Pattern

تبسيط واجهة معقدة عبر واجهة موحدة

السؤال: كيف تُبسط تفاعل مطوريك مع SDK معقد أو نظام فرعي كبير؟

الموقف الحقيقي: MediaPlayer Manager، CameraX Wrapper، أو Biometric Auth Helper.

KOTLIN — Facade Pattern 
// Complex subsystem: CameraX + ML Kit + Storage
class CameraManager(private val context: Context) { ... }
class BarcodeAnalyzer { ... }
class ImageStorage(private val context: Context) { ... }

// Facade: Simple unified interface
class ScannerFacade(context: Context) {
    private val camera = CameraManager(context)
    private val analyzer = BarcodeAnalyzer()
    private val storage = ImageStorage(context)

    fun startScanning(
        lifecycleOwner: LifecycleOwner,
        previewView: PreviewView,
        onBarcodeDetected: (String) -> Unit
    ) {
        camera.initialize(lifecycleOwner, previewView)
        camera.setAnalyzer { imageProxy ->
            val barcode = analyzer.scan(imageProxy)
            barcode?.let { onBarcodeDetected(it) }
        }
    }

    fun captureAndSave(onSaved: (Uri) -> Unit) {
        camera.takePicture { bitmap ->
            val uri = storage.save(bitmap)
            onSaved(uri)
        }
    }

    fun release() {
        camera.shutdown()
    }
}
ℹ️

الفائدة

مطورو الفريق لا يحتاجون لمعرفة تعقيد CameraX أو ML Kit. يستخدمون ScannerFacade البسيط فقط.

Proxy Pattern

التحكم في الوصول أو التحميل الكسول

السؤال: كيف تتحكم في الوصول لكائن مكلف (Heavy Object) أو تحميله كسولاً (Lazy Loading)؟

الموقف الحقيقي: Lazy initialization لصور عالية الدقة، أو التحقق من الصلاحيات قبل الوصول لخدمة حساسة.

KOTLIN — Proxy Pattern 
// Subject interface
interface ImageLoader {
    fun loadImage(url: String): Bitmap
}

// Real subject: Heavy operation
class RealImageLoader(private val context: Context) : ImageLoader {
    override fun loadImage(url: String): Bitmap {
        // Expensive: network + decode + resize
        return BitmapFactory.decodeStream(URL(url).openStream())
    }
}

// Proxy: Lazy loading + Caching
class CachedImageLoader(
    private val realLoader: ImageLoader
) : ImageLoader {
    private val cache = LruCache<String, Bitmap>(50)

    override fun loadImage(url: String): Bitmap {
        cache.get(url)?.let { return it }
        val bitmap = realLoader.loadImage(url)
        cache.put(url, bitmap)
        return bitmap
    }
}

// Protection Proxy: Access control
class SecureImageLoader(
    private val realLoader: ImageLoader,
    private val isPremium: () -> Boolean
) : ImageLoader {
    override fun loadImage(url: String): Bitmap {
        if (!isPremium()) {
            throw SecurityException("Premium feature required")
        }
        return realLoader.loadImage(url)
    }
}

أنماط التصميم السلوكية والمعمارية — Behavioral & Architectural Patterns

أنماط تُدير التواصل بين الكائنات وتُنظم سلوك التطبيق وردود الفعل

Observer Pattern

الإشعار التلقائي بتغييرات الحالة

السؤال: كيف تُعلم مكونات متعددة بتغيّر في البيانات دون ربطها ببعضها؟

الموقف الحقيقي: StateFlow، SharedFlow، LiveData — كلها تطبيقات حديثة للـ Observer Pattern في أندرويد.

KOTLIN — StateFlow & SharedFlow 
class NewsViewModel(
    private val repository: NewsRepository
) : ViewModel() {

    // StateFlow: Hot observable with initial value, replays last value
    private val _articles = MutableStateFlow<List<Article>>(emptyList())
    val articles: StateFlow<List<Article>> = _articles.asStateFlow()

    // SharedFlow: Events that should not be replayed (one-time events)
    private val _events = MutableSharedFlow<NewsEvent>(extraBufferCapacity = 1)
    val events = _events.asSharedFlow()

    fun loadNews() {
        viewModelScope.launch {
            repository.fetchLatest()
                .catch { e ->
                    _events.tryEmit(NewsEvent.ShowError(e.message ?: "Unknown"))
                }
                .collect { list ->
                    _articles.value = list
                }
        }
    }
}

// In Compose: UI observes automatically
@Composable
fun NewsScreen(viewModel: NewsViewModel = viewModel()) {
    val articles by viewModel.articles.collectAsState()
    val context = LocalContext.current

    // Collect one-time events
    LaunchedEffect(Unit) {
        viewModel.events.collect { event ->
            when (event) {
                is NewsEvent.ShowError ->
                    Toast.makeText(context, event.message, Toast.LENGTH_SHORT).show()
            }
        }
    }

    LazyColumn {
        items(articles) { article ->
            ArticleItem(article)
        }
    }
}
ℹ️

StateFlow vs SharedFlow

استخدم StateFlow للحالة التي يجب الاحتفاظ بها (UI State). استخدم SharedFlow للأحداث لمرة واحدة (Navigation, Snackbar, Toast) لأنها لا تُعاد تشغيلها عند تغيير الإعدادات.

Repository Pattern

مصدر واحد للحقيقة للبيانات

السؤال: كيف تُدّرج البيانات من مصادر متعددة (Local + Remote) بشكل موحد؟

الموقف الحقيقي: جلب المقالات من Room (Offline) وتحديثها من Retrofit (Remote) بشكل شفاف.

KOTLIN — Repository with Single Source of Truth 
class ArticleRepositoryImpl(
    private val remote: ArticleRemoteDataSource,
    private val local: ArticleLocalDataSource,
    private val networkMonitor: NetworkMonitor
) : ArticleRepository {

    override fun getArticles(): Flow<Resource<List<Article>>> = flow {
        emit(Resource.Loading)

        // 1. Emit cached data immediately (fast UI)
        val cached = local.getArticles().first()
        if (cached.isNotEmpty()) {
            emit(Resource.Success(cached))
        }

        // 2. Fetch from remote if online
        if (networkMonitor.isOnline()) {
            try {
                val remoteArticles = remote.fetchArticles()
                local.saveArticles(remoteArticles)
                emit(Resource.Success(remoteArticles))
            } catch (e: Exception) {
                emit(Resource.Error(e.message ?: "Network error", cached))
            }
        } else if (cached.isEmpty()) {
            emit(Resource.Error("No internet and no cache", null))
        }
    }.flowOn(Dispatchers.IO)
}

sealed class Resource<out T> {
    object Loading : Resource<Nothing>()
    data class Success<out T>(val data: T) : Resource<T>()
    data class Error<out T>(
        val message: String,
        val data: T? = null
    ) : Resource<T>()
}

Strategy Pattern

تبديل الخوارزميات ديناميكياً

السؤال: كيف تُبدل سلوك الكائن في Runtime دون تعديل الكود الأصلي؟

الموقف الحقيقي: خوارزميات ترتيب مختلفة، Feature Flags، أو حسابات ضريبة متعددة حسب الدولة.

KOTLIN — Strategy Pattern 
// Strategy interface
interface SortingStrategy {
    fun sort(products: List<Product>): List<Product>
}

// Concrete strategies
class PriceAscendingStrategy : SortingStrategy {
    override fun sort(products: List<Product>) =
        products.sortedBy { it.price }
}

class PriceDescendingStrategy : SortingStrategy {
    override fun sort(products: List<Product>) =
        products.sortedByDescending { it.price }
}

class RatingStrategy : SortingStrategy {
    override fun sort(products: List<Product>) =
        products.sortedByDescending { it.rating }
}

// Context
class ProductSorter(private var strategy: SortingStrategy) {
    fun setStrategy(newStrategy: SortingStrategy) {
        this.strategy = newStrategy
    }
    fun sort(products: List<Product>) = strategy.sort(products)
}

// Usage in ViewModel
class ProductViewModel : ViewModel() {
    private val sorter = ProductSorter(PriceAscendingStrategy())

    fun onSortSelected(sortType: SortType) {
        val strategy = when (sortType) {
            SortType.PRICE_ASC -> PriceAscendingStrategy()
            SortType.PRICE_DESC -> PriceDescendingStrategy()
            SortType.RATING -> RatingStrategy()
        }
        sorter.setStrategy(strategy)
        // Re-sort and emit new state...
    }
}

State Pattern

إدارة آلة الحالة (State Machine)

السؤال: كيف تُدير حالات UI معقدة (Loading, Success, Error, Empty) دون if-else متداخلة؟

الموقف الحقيقي: مشغل الموسيقى (Idle, Playing, Paused, Buffering)، أو خطوات معالجة الطلب.

KOTLIN — State Pattern with Sealed Interface 
sealed interface PlaybackState {
    val isPlaying: Boolean
    fun play(): PlaybackState
    fun pause(): PlaybackState
    fun stop(): PlaybackState
}

data object IdleState : PlaybackState {
    override val isPlaying = false
    override fun play() = PlayingState(System.currentTimeMillis())
    override fun pause() = this
    override fun stop() = this
}

data class PlayingState(val startTime: Long) : PlaybackState {
    override val isPlaying = true
    override fun play() = this
    override fun pause() = PausedState(elapsedTime())
    override fun stop() = IdleState
    private fun elapsedTime() = System.currentTimeMillis() - startTime
}

data class PausedState(val elapsedMs: Long) : PlaybackState {
    override val isPlaying = false
    override fun play() = PlayingState(System.currentTimeMillis() - elapsedMs)
    override fun pause() = this
    override fun stop() = IdleState
}

class MediaPlayer {
    private var state: PlaybackState = IdleState

    fun play() { state = state.play() }
    fun pause() { state = state.pause() }
    fun stop() { state = state.stop() }
    fun isPlaying() = state.isPlaying
}

Command Pattern

تغليف الطلبات ككائنات

السؤال: كيف تُغلّف عملية ككائن لتُنفذ لاحقاً، أو تُلغي، أو تُجدول؟

الموقف الحقيقي: Undo/Redo في محرر نصوص، أو Queue للطلبات في حالة Offline.

KOTLIN — Command Pattern 
// Command interface
interface Command {
    suspend fun execute()
    suspend fun undo()
}

// Concrete command: Sync when back online
class SyncArticleCommand(
    private val article: Article,
    private val remote: ArticleRemoteDataSource,
    private val local: ArticleLocalDataSource
) : Command {
    private var previousSyncStatus: Boolean = false

    override suspend fun execute() {
        previousSyncStatus = article.isSynced
        val response = remote.createArticle(article)
        local.markAsSynced(article.id, response.serverId)
    }

    override suspend fun undo() {
        local.updateSyncStatus(article.id, previousSyncStatus)
    }
}

// Invoker: Command Queue for offline support
class OfflineCommandQueue(
    private val networkMonitor: NetworkMonitor
) {
    private val queue = ArrayDeque<Command>()
    private val history = ArrayDeque<Command>()

    fun enqueue(command: Command) {
        queue.addLast(command)
        processQueue()
    }

    private fun processQueue() {
        if (!networkMonitor.isOnline()) return
        CoroutineScope(Dispatchers.IO).launch {
            while (queue.isNotEmpty()) {
                val cmd = queue.removeFirst()
                try {
                    cmd.execute()
                    history.addLast(cmd)
                } catch (e: Exception) {
                    queue.addFirst(cmd) // Retry later
                    break
                }
            }
        }
    }

    suspend fun undoLast() {
        history.removeLastOrNull()?.undo()
    }
}

🎯 نصائح Senior Architect — خلاصة ذهبية

  • ✓
    تجنب Over-Engineering: لا تُطبق Clean Architecture لتطبيق To-Do بسيط. ابدأ بأبسط نمط يحل المشكلة، ثم طوّر عندما يتضخم الكود.
  • ✓
    State هو الملك: في عالم Jetpack Compose، اجعل State مركزياً في ViewModel ولا تُنشئ Multiple Sources of Truth. كل State يجب أن يكون Immutable.
  • ✓
    Dependency Injection ضروري: استخدم Hilt أو Koin من اليوم الأول. Singletons المباشرة تجعل الاختبار مستحيلاً.
  • ✓
    فصل Domain عن Framework: Domain Layer يجب أن يكون Pure Kotlin. لا تُدخل Android SDK أو Retrofit في UseCases.
  • ✓
    اختبر المنطق لا الـ UI: 80% من اختباراتك يجب أن تكون Unit Tests للـ UseCases و ViewModels. UI Tests مكلفة وبطيئة.
  • ✓
    Sealed Classes هي صديقك: استخدم sealed interface لتمثيل State و Events. هذا يُجبر Compiler على التعامل مع كل الحالات (Exhaustive when).
  • ✓
    Repository Pattern للبيانات: دائماً استخدم Repository كـ Single Source of Truth. لا تدع ViewModel يتحدث مباشرةً مع Retrofit أو Room.
  • ✓
    Flow على LiveData: في Compose و Kotlin Coroutines، StateFlow و SharedFlow هما المعيار الحديث. LiveData مفيد فقط في XML Views.
