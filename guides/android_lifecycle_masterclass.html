المقدمة الاستراتيجية: لماذا تُعد Lifecycle و State Management المقياس الأول؟

عندما تجلس في مقابلة تقنية صارمة في إحدى كبرى الشركات الأوروبية — سواء كانت Spotify في ستوكهولم، أو Booking.com في أمستردام، أو N26 في برلين — فإن أول ما يختبره المقابل هو مدى فهمك العميق لنظام التشغيل أندرويد ذاته، لا مجرد معرفتك بمكتبات الطرف الثالث.

الفرق بين مطور Mid-level ومطور Senior لا يكمن في عدد المكتبات التي يعرفها، بل في قدرته على الإجابة عن الأسئلة التالية بثقة مطلقة:

  • ماذا يحدث تحت الغطاء عندما يقرر نظام أندرويد قتل عملية تطبيقك بسبب ضغط الذاكرة؟
  • لماذا يمتلك Fragment دورة حياة منفصلة لكائنه (Instance Lifecycle) ودورة حياة أخرى لواجهته (View Lifecycle)؟
  • ما الفرق الدقيق بين onPause() و onStop()، ومتى تفقد الـ Activity القدرة على التفاعل مع المستخدم فعلياً؟
  • لماذا يؤدي استخدام commitAllowingStateLoss() بشكل أعمى إلى فقدان حالة المستخدم بصمت؟
  • كيف تتجنب تسريب الذاكرة عند تمرير Context إلى ViewModel أو خيوط الخلفية؟
لماذا يهتم المقابلون الأوروبيون بهذه المواضيع بشكل مفرط؟

الشركات الأوروبية الكبرى تبني تطبيقات بملايين المستخدمين النشطين يومياً. أي خلل في إدارة الحالة أو تسريب للذاكرة يترجم مباشرة إلى:

  • تقييمات سلبية على Google Play (انخفاض التقييم من 4.5 إلى 3.2 بسبب الأعطال المتكررة)
  • تكاليف دعم فني هائلة (فريق دعم يتعامل مع آلاف الشكاوى يومياً)
  • خسارة المستخدمين (Churn Rate) بسبب تجربة استخدام غير موثوقة
  • مخالفات قانونية في ظل قوانين GDPR الصارمة (فقدان بيانات المستخدمين بسبب Process Death غير المُدار)

ما الذي يميز هذا المرجع؟

لن نقتصر على شرح "ماذا" يحدث، بل سنغوص في "لماذا" يحدث و "كيف" يعمل ذلك داخلياً في نظام أندرويد. كل فقرة في هذا المرجع مصممة لتُجيب عن سؤال مقابلة محتمل، وكل مثال برمجي قابل للنسخ واللصق مباشرة في مشروع إنتاجي.

سنبدأ بتشريح Activity Lifecycle بأدق تفاصيله، ثم ننتقل إلى متاهة Fragment Lifecycle التي تُعدّ المقصلة الحقيقية للمطورين في المقابلات، فنتعمق في آليات FragmentManager الداخلية، ونختتم ببنك الأسئلة الخادعة التي تُطرح في مقابلات الشركات الأوروبية الكبرى.

1. onCreate() — لحظة الولادة

تُستدعى onCreate() مرة واحدة فقط خلال عمر كائن Activity. هذه هي اللحظة التي يُنشئ فيها النظام الكائن، ويُرفق به Bundle يحتوي على الحالة المحفوظة سابقاً (إن وُجدت).

Kotlin 
class MainActivity : AppCompatActivity() {

    private lateinit var viewModel: MainViewModel
    private var userId: String? = null

    override fun onCreate(savedInstanceState: Bundle?) {
        // يجب استدعاء super.onCreate() أولاً دائماً
        // لأن AppCompatActivity تقوم بتهيئة FragmentManager والموارد
        super.onCreate(savedInstanceState)

        // تحميل التخطيط — في هذه اللحظة لا يزال الـ View غير مرتبط بالشاشة
        setContentView(R.layout.activity_main)

        // استعادة الحالة المحفوظة — هذه الحالة قادمة من:
        // 1. Process Death ثم استعادة النظام للعملية
        // 2. Configuration Change (مثل تدوير الشاشة)
        userId = savedInstanceState?.getString("USER_ID_KEY")
            ?: intent.getStringExtra("USER_ID_EXTRA")

        // تهيئة ViewModel — يجب أن تتم هنا لأن Activity قد تُعاد إنشاؤها
        viewModel = ViewModelProvider(this)[MainViewModel::class.java]

        // ربط الملاحظات — لكن احذر! لا تربط LiveData هنا إذا كانت
        // تعتمد على View Lifecycle. سنشرح ذلك لاحقاً.
    }

    override fun onSaveInstanceState(outState: Bundle) {
        super.onSaveInstanceState(outState)
        // حفظ الحالة الحرجة قبل أن يقرر النظام قتل العملية
        outState.putString("USER_ID_KEY", userId)
    }
}
الفخاخ الشائعة في onCreate()
  • الخطأ الأول: استدعاء supportFragmentManager.beginTransaction() قبل super.onCreate() — سيؤدي هذا إلى IllegalStateException لأن FragmentManager لم يُهيأ بعد.
  • الخطأ الثاني: افتراض أن savedInstanceState غير فارغ يعني Process Death فقط. في الواقع، يُمرر Bundle أيضاً عند Configuration Changes.
  • الخطأ الثالث: تهيئة ViewBinding قبل setContentView() — سيؤدي إلى NullPointerException لأن الـ View غير موجود بعد.

2. onStart() — الظهور المرئي

عندما تصل Activity إلى حالة STARTED، تصبح مرئية للمستخدم لكنها لا تزال غير قادرة على استقبال التفاعلات. هذا هو الوقت المثالي لبدء عمليات تتطلب مرئية الواجهة دون تفاعل مباشر:

Kotlin 
override fun onStart() {
    super.onStart()
    // بدء تحديثات الموقع الجغرافي — المستخدم يرى التغييرات على الخريطة
    locationManager.requestLocationUpdates(
        LocationManager.GPS_PROVIDER,
        5000L, // 5 ثوانٍ
        10f,   // 10 أمتار
        locationListener
    )

    // بدء Animation خفيف — المستخدم سيراه لأن الواجهة مرئية
    binding.loadingIndicator.startAnimation(rotateAnimation)
}

3. onResume() — جاهزية التفاعل الكاملة

عند onResume()، تكون Activity في مقدمة الشاشة وقادرة على استقبال جميع التفاعلات. هذا هو المكان المناسب لـ:

  • بدء الكاميرا أو الميكروفون
  • استئناف تشغيل الوسائط (Media Playback)
  • تسجيل مستمعي أحداث الحساسات (Sensors)
  • بدء عدادات الأداء (Performance Tracking)
Kotlin 
override fun onResume() {
    super.onResume()
    // استئناف الكاميرا — يجب أن تكون في onResume وليس onStart
    // لأن الكاميرا تستهلك موارد كبيرة ولا نريد تشغيلها
    // إذا كان هناك Dialog يغطي جزءاً من الشاشة
    if (cameraPermissionGranted) {
        cameraDevice?.startPreview()
    }

    // تسجيل دخول المستخدم في Analytics
    analyticsTracker.trackScreenView("MainScreen")
}

4. onPause() — فقدان التركيز (وليس الاختفاء)

هذه هي النقطة الأكثر خطورة في دورة الحياة. onPause() تُستدعى عندما يفقد التطبيق التركيز، لكنه قد يظل مرئياً جزئياً. السيناريوهات:

  • فتح Dialog شفاف أو شبه شفاف
  • فتح Activity شفاف (android:theme="@android:style/Theme.Translucent")
  • ظهور نافذة الأذونات (Permission Dialog)
  • سحب شريط الإشعارات (Notification Shade)
  • فتح Picture-in-Picture
الفخ الخطير: onPause() ≠ onStop()

المطورون يخلطون بينهما باستمرار. القاعدة الذهبية:

  • onPause(): الواجهة قد تظل مرئية لكن غير قابلة للتفاعل. لا تقم بإطلاق موارد ثقيلة هنا (مثل إيقاف الكاميرا بالكامل).
  • onStop(): الواجهة غير مرئية بالكامل. هذا هو المكان الآمن لإطلاق الموارد الثقيلة.

في المقابلات: "لماذا نحفظ البيانات في onPause() وليس onStop()؟" — الإجابة: لأن onStop() قد لا تُستدعى إذا قرر النظام قتل العملية فوراً بعد onPause() بسبب ضغط الذاكرة الحاد.

Kotlin 
override fun onPause() {
    super.onPause()
    // إيقاف التفاعلات الحساسة — لكن لا تُطلق الكاميرا بعد!
    // في onPause، قد يظل المستخدم يرى واجهتنا (مثل Dialog شفاف)

    // إيقاف معالجة اللمس المستمر (Long-press gestures)
    gestureDetector.stop()

    // حفظ البيانات الحرجة — قد لا نصل إلى onStop()
    saveDraftToLocalStorage()

    // إيقاف الـ Animation — لا نريد استهلاك CPU والواجهة غير نشطة
    binding.loadingIndicator.clearAnimation()
}

5. onStop() — الاختفاء الكامل

تُستدعى onStop() عندما تصبح Activity غير مرئية بالكامل. هذا هو المكان الآمن لإطلاق الموارد الثقيلة:

Kotlin 
override fun onStop() {
    super.onStop()
    // إطلاق الموارد الثقيلة — الآن الواجهة غير مرئية بالكامل
    cameraDevice?.stopPreview()
    cameraDevice?.close()

    // إيقاف تحديثات الموقع
    locationManager.removeUpdates(locationListener)

    // إيقاف الاستماع لتغييرات الشبكة
    connectivityManager.unregisterNetworkCallback(networkCallback)

    // إلغاء الاشتراكات في Real-time listeners (Firebase, etc.)
    firestoreListener?.remove()
}

6. onDestroy() — النهاية

تُستدعى onDestroy() قبل تدمير كائن Activity. لكن احذر: لا يُضمن استدعاؤها دائماً. إذا قتل النظام العملية بشكل مفاجئ (Process Death)، فلن تصل إلى onDestroy() أبداً.

Kotlin 
override fun onDestroy() {
    super.onDestroy()
    // تنظيف الموارد التي لا تُدار تلقائياً
    // لكن لا تعتمد على هذه الدالة لحفظ البيانات الحرجة!

    // إلغاء CoroutineScope المرتبط بالـ Activity
    activityScope.cancel()

    // تدمير الـ Presenter إذا كنت تستخدم MVP
    presenter?.onDestroy()

    // إلغاء الاشتراكات في RxJava
    compositeDisposable.clear()
}

سلوك دورة الحياة عند ظهور Dialog أو Transparent Activity

هذا هو السؤال المفضل في مقابلات الشركات الأوروبية. لنحلل السيناريوهات بدقة:

السيناريو ما يحدث للـ Activity الأسفل الدوال المستدعاة
ظهور Dialog عادي لا شيء — الـ Dialog جزء من نفس الـ Window لا شيء
ظهور Dialog من تطبيق آخر (System Alert) يفقد التركيز لكنه يظل مرئياً onPause() فقط
فتح Transparent Activity يفقد التركيز ويظل مرئياً جزئياً onPause() فقط
فتح Activity عادي (غير شفاف) يختفي بالكامل onPause() → onStop()
طلب صلاحية (Runtime Permission) يفقد التركيز — الـ Dialog نظامي onPause() فقط

سؤال مقابلة: "ماذا يحدث عندما يفتح المستخدم شريط الإشعارات فوق Activity؟"

الإجابة الصحيحة: لا شيء في الغالب. Notification Shade لا يُعتبر Window يفقد التركيز. لكن إذا كان التطبيق يستخدم FLAG_NOT_FOCUSABLE أو إذا كان النظام يعالج الحدث بشكل خاص (مثل Android 12+ مع One-handed mode)، فقد يُستدعى onPause().

الفخ: بعض المقابلين يخلطون بين Notification Shade و System Dialogs. الإجابة المثالية تتضمن التمييز بين "فقدان التركيز" (Focus Loss) و "الاختفاء" (Visibility Loss).

الموت المفاجئ للعملية (Process Death)

يُعدّ Process Death من أخطر التحديات في تطوير أندرويد. يحدث عندما يقرر نظام التشغيل قتل عملية تطبيقك بسبب:

  • ضغط الذاكرة الحاد (Low Memory Killer)
  • تفعيل وضع توفير الطاقة الصارم (Doze Mode / App Standby)
  • قيود البطارية من الشركة المصنعة (OEM Battery Optimizations)
  • الانتقال السريع بين تطبيقات كثيرة (Recent Apps Pressure)
الكارثة: onDestroy() لا تُستدعى أبداً في Process Death!

عندما يقتل النظام العملية، يُزيلها من الذاكرة فوراً دون إنذار. هذا يعني:

  • جميع المتغيرات في الذاكرة (RAM) تُفقد للأبد
  • لا تُستدعى onStop() أو onDestroy()
  • المستخدم سيعيد فتح التطبيق متوقعاً نفس الحالة
  • إذا لم تُدير الحالة بشكل صحيح، سيختفي تقدمه بالكامل

كيف يختبر نظام أندرويد قدرة تطبيقك على البقاء؟

يستخدم النظام آلية SavedStateRegistry لحفظ واستعادة الحالة. هذه الآلية تعمل على مستوى Activity و Fragment و حتى View المخصصة:

Kotlin 
class ProcessDeathResilientActivity : AppCompatActivity() {

    companion object {
        private const val KEY_SCROLL_POSITION = "scroll_position"
        private const val KEY_USER_INPUT = "user_input"
        private const val KEY_SELECTED_TAB = "selected_tab"
    }

    private var scrollPosition: Int = 0
    private var userInput: String = ""
    private var selectedTab: Int = 0

    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        setContentView(R.layout.activity_resilient)

        // استعادة الحالة — هذه هي خط الدفاع الأول
        savedInstanceState?.let { bundle ->
            scrollPosition = bundle.getInt(KEY_SCROLL_POSITION, 0)
            userInput = bundle.getString(KEY_USER_INPUT, "")
            selectedTab = bundle.getInt(KEY_SELECTED_TAB, 0)

            // تطبيق الحالة المستعادة فوراً
            binding.editText.setText(userInput)
            binding.recyclerView.scrollToPosition(scrollPosition)
            binding.tabLayout.getTabAt(selectedTab)?.select()
        }
    }

    override fun onSaveInstanceState(outState: Bundle) {
        super.onSaveInstanceState(outState)

        // حفظ الحالة الحرجة — يجب أن تكون خفيفة جداً!
        // لا تحفظ كائنات كبيرة هنا — استخدم ViewModel + SavedStateHandle
        outState.putInt(KEY_SCROLL_POSITION, scrollPosition)
        outState.putString(KEY_USER_INPUT, userInput)
        outState.putInt(KEY_SELECTED_TAB, selectedTab)
    }

    // التحديث المستمر للمتغيرات
    private fun setupListeners() {
        binding.editText.doAfterTextChanged { text ->
            userInput = text?.toString() ?: ""
        }

        binding.recyclerView.addOnScrollListener(
            object : RecyclerView.OnScrollListener() {
                override fun onScrolled(rv: RecyclerView, dx: Int, dy: Int) {
                    scrollPosition = (rv.layoutManager as LinearLayoutManager)
                        .findFirstVisibleItemPosition()
                }
            }
        )

        binding.tabLayout.addOnTabSelectedListener(
            object : TabLayout.OnTabSelectedListener {
                override fun onTabSelected(tab: TabLayout.Tab?) {
                    selectedTab = tab?.position ?: 0
                }
                override fun onTabUnselected(tab: TabLayout.Tab?) {}
                override fun onTabReselected(tab: TabLayout.Tab?) {}
            }
        )
    }
}

SavedStateHandle — الأسلوب الحديث والموصى به

بدءاً من ViewModel 2.3.0، يوفر SavedStateHandle آلية أكثر أماناً لحفظ الحالة. الفائدة الرئيسية: يتكامل مع ViewModel ويبقى على قيد الحياة عبر Configuration Changes و Process Death:

Kotlin 
class MainViewModel(savedStateHandle: SavedStateHandle) : ViewModel() {

    companion object {
        private const val KEY_SEARCH_QUERY = "search_query"
        private const val KEY_FILTER_STATE = "filter_state"
    }

    // LiveData backed by SavedStateHandle — تبقى حية عبر Process Death!
    val searchQuery: MutableLiveData = savedStateHandle
        .getLiveData(KEY_SEARCH_QUERY, "")

    val filterState: MutableLiveData = savedStateHandle
        .getLiveData(KEY_FILTER_STATE, FilterState.DEFAULT)

    // StateFlow backed by SavedStateHandle
    private val _uiState = MutableStateFlow(
        savedStateHandle.get<UiState>("ui_state") ?: UiState()
    )
    val uiState: StateFlow<UiState> = _uiState.asStateFlow()

    fun updateSearchQuery(query: String) {
        searchQuery.value = query
        // SavedStateHandle يحفظ القيمة تلقائياً
    }

    fun updateFilter(filter: FilterState) {
        filterState.value = filter
    }

    // عند تغيير StateFlow، نُحدث SavedStateHandle يدوياً
    fun updateUiState(newState: UiState) {
        _uiState.value = newState
        savedStateHandle["ui_state"] = newState
    }
}
الفرق بين ViewModel و SavedStateHandle
  • ViewModel وحده: يبقى حياً خلال Configuration Changes فقط. عند Process Death، يُدمر ويُعاد إنشاؤه بدون بيانات.
  • SavedStateHandle: يستخدم onSaveInstanceState تحت الغطاء. يبقى حياً خلال Configuration Changes و Process Death.
  • القيود: SavedStateHandle يخضع لنفس قيود Bundle — لا يمكن حفظ كائنات غير Serializable/Parcelable، والحجم الإجمالي محدود (~1MB تقريباً).

تغيير الإعدادات (Configuration Changes)

يُعدّ تدوير الشاشة (Orientation Change) أكثر Configuration Change شيوعاً، لكن هناك أنواع أخرى:

  • تغيير اللغة (locale)
  • تغيير حجم الخط (fontScale)
  • تغيير وضع العرض الليلي/النهاري (uiMode)
  • تغيير حجم الشاشة (screenSize)
  • تغيير الكثافة (density)
  • تغيير لوحة المفاتيح المتصلة (keyboard)
AndroidManifest.xml 
<!-- الطريقة الأولى: منع إعادة الإنشاء (غير موصى بها في الإنتاج) -->
<activity
    android:name=".MainActivity"
    android:configChanges="orientation|screenSize|keyboardHidden"
    android:screenOrientation="portrait" />

<!-- الطريقة الثانية: السماح بإعادة الإنشاء مع إدارة الحالة الصحيحة -->
<activity
    android:name=".MainActivity"
    android:configChanges="orientation|screenSize" />
تحذير: android:configChanges ليست حلاً سحرياً!

استخدام android:configChanges لمنع إعادة إنشاء Activity يُعتبر مضاداً للأنماط في معظم الحالات لأنه:

  • يمنع النظام من تحميل الموارد المناسبة للإعداد الجديد (مثل layout-land)
  • يُعقد اختبار الوحدة (Unit Testing) لأنك تتجاوز سلوك النظام الطبيعي
  • لا يحميك من Process Death — فقط من Configuration Changes

الإجابة تكمن في آلية Back Stack و FragmentManager. عندما تُضيف Fragment إلى Back Stack باستخدام addToBackStack()، يبقى كائن Fragment حياً في الذاكرة بينما يُدمر View الخاص به. هذا يسمح بـ:

الفخ القاتل: عدم إلغاء Binding في onDestroyView()

عند استخدام View Binding في Fragment، يجب إلغاء مرجع Binding في onDestroyView(). إذا لم تفعل ذلك:

  • الـ View تحتفظ بمرجع إلى Fragment عبر Binding
  • عند إضافة Fragment إلى Back Stack، يبقى View في الذاكرة
  • يُسبب Memory Leak لأن Garbage Collector لا يستطيع تحرير Fragment
  • مع كل انتقال، تتراكم الـ Views القديمة في الذاكرة حتى OutOfMemoryError

متى نستخدم LifecycleOwner ومتى ViewLifecycleOwner؟

هذا السؤال يُفصل بين المطور المتوسط والمطور المتقدم. لنحلل الفرق بأمثلة حقيقية:

❌ خطأ قاتل — استخدام this (LifecycleOwner)
override fun onViewCreated(view: View, savedInstanceState: Bundle?) {
    super.onViewCreated(view, savedInstanceState)

    // ❌ خطأ فادح!
    // عندما يُضاف Fragment إلى Back Stack،
    // يبقى Fragment حياً لكن View يُدمر.
    // LiveData سيستمر بإرسال التحديثات إلى View مدمر!
    viewModel.data.observe(this) { data ->
        binding.textView.text = data
    }
}
✅ صحيح — استخدام viewLifecycleOwner
override fun onViewCreated(view: View, savedInstanceState: Bundle?) {
    super.onViewCreated(view, savedInstanceState)

    // ✅ صحيح!
    // viewLifecycleOwner يُلغي الاشتراك تلقائياً
    // عند onDestroyView().
    viewModel.data.observe(viewLifecycleOwner) { data ->
        binding.textView.text = data
    }
}
القاعدة الذهبية: Fragment Lifecycle vs View Lifecycle
this (LifecycleOwner):حياة الكائن — من onAttach() إلى onDetach(). استخدمها فقط للعمليات التي لا تعتمد على View (مثل ViewModel initialization).
viewLifecycleOwner:حياة الـ View — من onCreateView() إلى onDestroyView(). استخدمها دائماً لربط LiveData، StateFlow، أو أي مستمع يتفاعل مع View.

الحل النهائي: repeatOnLifecycle

بدءاً من Lifecycle 2.4.0، يوفر repeatOnLifecycle الحل الأكثر أماناً لجمع Flow في Fragments:

  • يُلغي الـ Flow تلقائياً عندما ينتقل Lifecycle إلى STOPPED
  • يعيد تشغيل الـ Flow عندما يعود إلى STARTED
  • يمنع تسريب الذاكرة بشكل كامل
  • يُستخدم مع viewLifecycleOwner دائماً في Fragments
Kotlin — Production-Ready Pattern 
class ProductionFragment : Fragment() {

    private var _binding: FragmentProductionBinding? = null
    private val binding get() = _binding!!
    private val viewModel: ProductionViewModel by viewModels()

    override fun onCreateView(
        inflater: LayoutInflater,
        container: ViewGroup?,
        savedInstanceState: Bundle?
    ): View {
        _binding = FragmentProductionBinding.inflate(inflater, container, false)
        return binding.root
    }

    override fun onViewCreated(view: View, savedInstanceState: Bundle?) {
        super.onViewCreated(view, savedInstanceState)
        setupUi()
        observeData()
    }

    private fun setupUi() {
        binding.retryButton.setOnClickListener {
            viewModel.refresh()
        }
    }

    private fun observeData() {
        // ✅ LiveData مع viewLifecycleOwner
        viewModel.uiState.observe(viewLifecycleOwner) { state ->
            binding.progressBar.isVisible = state.isLoading
            binding.contentGroup.isVisible = !state.isLoading && state.error == null
            binding.errorGroup.isVisible = state.error != null

            state.data?.let { binding.textView.text = it }
        }

        // ✅ StateFlow مع repeatOnLifecycle
        viewLifecycleOwner.lifecycleScope.launch {
            viewLifecycleOwner.repeatOnLifecycle(Lifecycle.State.STARTED) {
                viewModel.events.collect { event ->
                    when (event) {
                        is Event.ShowSnackbar -> {
                            Snackbar.make(binding.root, event.message, Snackbar.LENGTH_SHORT).show()
                        }
                        is Event.Navigate -> {
                            findNavController().navigate(event.direction)
                        }
                    }
                }
            }
        }
    }

    override fun onDestroyView() {
        super.onDestroyView()
        _binding = null // ⚠️ لا تنسَ هذا أبداً!
    }
}

الإدارة المتقدمة للتنقل ومكدس الرجوع

يُعدّ فهم آليات FragmentManager و Back Stack من أهم المهارات التي تُميّز مهندس Senior عن مهندس Mid-level. في هذا الفصل، سنغوص في الآليات الداخلية حتى مستوى الكود المصدري لأندرويد.

الآلية الداخلية لعمل FragmentManager

FragmentManager هو المسؤول عن إدارة دورة حياة Fragments، ومعالجة الـ Transactions، والحفاظ على Back Stack. لفهم كيف يعمل، يجب أن نفهم ثلاثة مفاهيم أساسية:

1. FragmentTransaction: القلب النابض للتنقل

كل عملية على Fragment (إضافة، إزالة، استبدال) تتم عبر FragmentTransaction. لكن ما يجعل الأمر معقداً هو أن هذه الـ Transactions غير متزامنة بشكل افتراضي.

Kotlin 
// ═══════════════════════════════════════════════════════════
// الآلية الداخلية لـ FragmentTransaction
// ═══════════════════════════════════════════════════════════

// كل ما تكتبه هنا لا يُنفذ فوراً — يُخزن في قائمة انتظار!
supportFragmentManager.beginTransaction()
    .replace(R.id.container, DetailFragment::class.java, bundle, "detail")
    .addToBackStack("detail_transaction") // اسم اختياري للـ Back Stack
    .setReorderingAllowed(true) // تحسين الأداء — يسمح بإعادة ترتيب الـ Transactions
    .commit() // ✅ الطريقة الصحيحة

// ⚠️ ما الذي يحدث تحت الغطاء؟
// 1. تُخزن الـ Transaction في FragmentManager.mPendingActions
// 2. FragmentManager يسجل طلباً للتنفيذ في Handler الرئيسي
// 3. في الحلقة الرئيسية (Main Looper)، تُنفذ الـ Transaction
// 4. يتم تحديث Back Stack وتغيير حالات Lifecycle

// commitNow() — تنفيذ فوري متزامن (احذر من الاستخدام الخاطئ!)
supportFragmentManager.beginTransaction()
    .replace(R.id.container, DetailFragment())
    .commitNow() // تنفيذ فوري — يتجاوز قائمة الانتظار

// commitNow() مفيد فقط في حالات محددة:
// 1. عندما تحتاج إلى الوصول إلى Fragment فوراً بعد الإنشاء
// 2. في اختبارات الوحدة (Unit Tests)
// 3. عندما تريد ضمان ترتيب التنفيذ

2. الفرق بين add() و replace() وأثرهما على Lifecycle والذاكرة

هذا هو السؤال الأكثر شيوعاً في مقابلات Senior Android في أوروبا. الفرق ليس مجرد "إضافة" مقابل "استبدال" — الفرق يمتد إلى كيفية إدارة الذاكرة ودورة الحياة.

الجانب add() replace()
السلوك يُضيف Fragment فوق Fragment موجود يُزيل جميع Fragments في الـ Container ويضيف الجديد
دورة الحياة الـ Fragment السابق يبقى في onPause() أو onStop() الـ Fragments السابقة تمر بـ onDestroyView()
استهلاك الذاكرة أعلى — جميع الـ Views تبقى في الذاكرة أقل — الـ Views القديمة تُحرر
العودة (Back) يعود إلى الـ Fragment السابق مع استعادة View يعود إلى الـ Fragment السابق مع إعادة إنشاء View
الاستخدام المثالي Tabs، Master-Detail، BottomNavigation Flows متسلسلة، Wizard، Onboarding

class MainActivity : AppCompatActivity() {

    private val fragmentTags = listOf("home", "search", "profile")
    private var currentTag: String = "home"

    private fun switchTab(targetTag: String) {
        if (targetTag == currentTag) return

        val transaction = supportFragmentManager.beginTransaction()

        // إخفاء الـ Fragment الحالي
        supportFragmentManager.findFragmentByTag(currentTag)?.let {
            transaction.hide(it)
            // ⚠️ hide() لا تُدمر View — تبقى في الذاكرة
            // لكنها تصل إلى onPause() → onStop()
        }

        // إظهار أو إنشاء الـ Fragment الجديد
        var targetFragment = supportFragmentManager.findFragmentByTag(targetTag)
        if (targetFragment == null) {
            targetFragment = when (targetTag) {
                "home" -> HomeFragment()
                "search" -> SearchFragment()
                "profile" -> ProfileFragment()
                else -> throw IllegalArgumentException()
            }
            transaction.add(R.id.container, targetFragment, targetTag)
        } else {
            transaction.show(targetFragment)
            // show() تُعيد Fragment إلى onStart() → onResume()
        }

        transaction.commit()
        currentTag = targetTag
    }
}
تحذير: hide()/show() لا تُدير Back Stack!

عند استخدام hide() و show()، لا تُضاف الـ Transactions إلى Back Stack بشكل افتراضي. هذا يعني أن ضغط زر الرجوع لن يُرجع المستخدم بين التبويبات. لإدارة Multiple Back Stacks بشكل صحيح، استخدم Jetpack Navigation Component أو قم بتنفيذ Back Stack يدوي لكل تبويب.

الجدل التاريخي: commit() vs commitAllowingStateLoss()

هذا الموضوع يُثير جدلاً كبيراً في مجتمع أندرويد. لنحلل الأمر بموضوعية:

لماذا يوجد commitAllowingStateLoss()؟

عندما يكون Activity في حالة onSaveInstanceState() أو بعدها (أي State Saved)، لا يُسمح بإجراء Fragment Transactions جديدة. السبب: إذا قُتلت العملية بعد هذه اللحظة واستُعيدت، فإن FragmentManager سيحاول استعادة Fragments من الحالة المحفوظة. إذا كانت هناك Transactions جديدة لم تُحفظ، ستفقدها.

متى يكون commitAllowingStateLoss() مقبولاً؟

هناك حالات نادرة يكون فيها الاستخدام مبرراً:

  • DialogFragments غير حرجة: إذا كان DialogFragment يعرض معلومات ثانوية (مثل "تم التحديث بنجاح") ولا يؤثر على حالة التطبيق.
  • Analytics أو Logging: إذا كنت تضيف Fragment خفيفاً لتتبع حدث لا يؤثر على واجهة المستخدم.
  • Workarounds مؤقتة: في مكتبات الطرف الثالث التي لا تتحكم فيها.

القاعدة الذهبية: إذا كان Fragment يحتوي على حالة مهمة أو بيانات يدخلها المستخدم، لا تستخدم commitAllowingStateLoss() أبداً.

احتراف Jetpack Navigation Component

يُعدّ Jetpack Navigation Component الحل الرسمي والموصى به لإدارة التنقل في تطبيقات أندرويد الحديثة. لكن الاحتراف يتطلب فهم أعمق من مجرد ربط NavGraph.

1. التعامل مع Multiple Back Stacks

في التطبيقات الكبيرة (مثل Instagram أو Spotify)، يحتاج كل تبويب في BottomNavigationView إلى Back Stack خاص به. هذا يعني أن الانتقال بين التبويبات لا يُفقد تاريخ التنقل داخل كل تبويب.

// Multiple Back Stacks مع Navigation Component
// ═══════════════════════════════════════════════════════════

class MainActivity : AppCompatActivity() {

    private lateinit var binding: ActivityMainBinding
    private lateinit var navController: NavController

    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        binding = ActivityMainBinding.inflate(layoutInflater)
        setContentView(binding.root)

        val navHostFragment = supportFragmentManager
            .findFragmentById(R.id.nav_host_container) as NavHostFragment

        navController = navHostFragment.navController

        // ✅ setupWithNavController مع restoreState = true
        // يُنشئ Back Stack منفصلة لكل تبويب!
        binding.bottomNav.setupWithNavController(navController)

        // لمنع إعادة إنشاء الـ Destination نفسه عند النقر المكرر
        binding.bottomNav.setOnItemSelectedListener { item ->
            val currentDestination = navController.currentDestination?.id
            if (currentDestination == item.itemId) {
                // النقر على التبويب الحالي — اذهب إلى Root
                navController.popBackStack(item.itemId, inclusive = false)
                true
            } else {
                // ✅ الانتقال مع استعادة حالة التبويب السابق
                navController.navigate(item.itemId, null, navOptions {
                    popUpTo(navController.graph.findStartDestination().id) {
                        saveState = true
                    }
                    launchSingleTop = true
                    restoreState = true
                })
                true
            }
        }
    }
}

class SafeActivity : AppCompatActivity() {

    // ✅ استخدام WeakReference للتخلص من الـ Implicit Reference
    private val activityScope = CoroutineScope(SupervisorJob() + Dispatchers.Main)

    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        setContentView(R.layout.activity_safe)

        // ✅ CoroutineScope مرتبط بـ Lifecycle — يُلغى تلقائياً
        lifecycleScope.launch {
            delay(10_000)
            // lifecycleScope يتحقق تلقائياً من أن Activity لا تزال حية
            if (isActive && !isFinishing) {
                textView.text = "Done"
            }
        }

        // ✅ أو باستخدام viewLifecycleOwner في Fragment
        viewLifecycleOwner.lifecycleScope.launch {
            delay(10_000)
            // يُلغى تلقائياً عند onDestroyView()
        }
    }

    override fun onDestroy() {
        super.onDestroy()
        // ✅ إلغاء الـ Scope يدوياً إذا لم تستخدم lifecycleScope

السؤال: "كيف تشارك البيانات بين Fragment و Activity و Fragment آخر متداخل (Nested Fragment) دون حدوث Tight Coupling؟"

هذا السؤال يختبر فهمك لـ Communication Patterns في أندرويد. الحلول الخاطئة (مثل Direct Casting أو Static References) تُسبب Memory Leaks و Tight Coupling. الحل الصحيح يعتمد على ViewModel المشترك مع Scoped صحيح.

// 1. ViewModel مشترك — يعيش طوال عمر Activity
class SharedViewModel : ViewModel() {

    private val _selectedItem = MutableLiveData<Item>()
    val selectedItem: LiveData<Item> = _selectedItem

الفرق بين viewModels() و activityViewModels()
by viewModels():يُنشئ ViewModel مرتبطاً بالـ Fragment الحالي. يُدمر عندما يُدمر الـ Fragment. مناسب للبيانات الخاصة بالـ Fragment.
by activityViewModels():يستخدم ViewModel مرتبطاً بالـ Activity. يبقى حياً طوال عمر Activity. مناسب للبيانات المشتركة بين Fragments متعددة.
by viewModels({requireParentFragment()}):يستخدم ViewModel مرتبطاً بالـ Parent Fragment. مناسب للتواصل بين Nested Fragments دون إشراك Activity.

class FormViewModel(
    private val savedStateHandle: SavedStateHandle,
    private val formRepository: FormRepository
) : ViewModel() {

    companion object {
        private const val KEY_FORM_STATE = "form_state"
    }

    // ✅ SavedStateHandle يبقى حياً عبر Process Death!
    private val _formState = MutableStateFlow(
        savedStateHandle.get<FormState>(KEY_FORM_STATE) ?: FormState()
    )
    val formState: StateFlow<FormState> = _formState.asStateFlow()

    // ✅ LiveData backed by SavedStateHandle
    val currentStep: MutableLiveData<Int> = savedStateHandle
        .getLiveData("current_step", 0)

    fun updateFirstName(name: String) {
        val current = _formState.value
        val updated = current.copy(firstName = name)
        _formState.value = updated
        savedStateHandle[KEY_FORM_STATE] = updated // حفظ فوري!
    }

    fun updateEmail(email: String) {
        val current = _formState.value
        val updated = current.copy(email = email)
        _formState.value = updated
        savedStateHandle[KEY_FORM_STATE] = updated
    }

    fun updateStep(step: Int) {
        currentStep.value = step
    }

    fun submitForm() {
        viewModelScope.launch {
            val state = _formState.value
            formRepository.submit(state)
        }
    }

    // ✅ حفظ في Repository (خط الدفاع الثاني — Persistent Storage)
    fun saveDraft() {
        viewModelScope.launch {
            formRepository.saveDraft(_formState.value)
        }
    }
}

class FormRepository(
    private val draftDao: DraftDao, // Room Database
    private val dataStore: DataStore<Preferences> // Preferences DataStore
) {
    suspend fun saveDraft(state: FormState) {
        draftDao.insertDraft(state.toEntity())
    }

    suspend fun getDraft(): FormState? {
        return draftDao.getLatestDraft()?.toFormState()
    }

    suspend fun submit(state: FormState): Result<Unit> {
        return try {
            apiService.submitForm(state)
            draftDao.clearDrafts() // نجاح — امسح المسودة
            Result.success(Unit)
        } catch (e: Exception) {
            saveDraft(state) // فشل — احفظ المسودة
            Result.failure(e)
        }
    }
}

class FormFragment : Fragment() {

    private val viewModel: FormViewModel by viewModels()

    override fun onViewCreated(view: View, savedInstanceState: Bundle?) {
        super.onViewCreated(view, savedInstanceState)

        // ✅ استعادة الحالة من ViewModel (SavedStateHandle)
        viewLifecycleOwner.lifecycleScope.launch {
            viewLifecycleOwner.repeatOnLifecycle(Lifecycle.State.STARTED) {
                viewModel.formState.collect { state ->
                    binding.firstNameInput.setText(state.firstName)
                    binding.emailInput.setText(state.email)
                    binding.stepIndicator.currentStep = state.currentStep
                }
            }
        }

        // ✅ حفظ تلقائي عند كل تغيير
        binding.firstNameInput.doAfterTextChanged { text ->
            viewModel.updateFirstName(text?.toString() ?: "")
        }

        // ✅ حفظ مسودة عند مغادرة Fragment
        // onPause() — آخر فرصة قبل Process Death
    }

    override fun onPause() {
        super.onPause()
        // ✅ حفظ المسودة في Persistent Storage
        // لأن Process Death قد يحدث بعد onPause()
        viewModel.saveDraft()
    }
}
استراتيجية الدفاع المتعدد الطبقات (Defense in Depth)

لضمان عدم فقدان البيانات في أي ظرف، نستخدم ثلاثة خطوط دفاع:

  • الخط الأول — SavedStateHandle: يحفظ الحالة في onSaveInstanceState. يبقى حياً خلال Configuration Changes و Process Death. لكنه محدود بالحجم (~1MB).
  • الخط الثاني — Persistent Storage (Room/DataStore): يحفظ المسودة في قاعدة البيانات المحلية. يبقى حياً حتى إذا أغلق المستخدم التطبيق يدوياً.
  • الخط الثالث — Remote Backup: في التطبيقات الحرجة، يُرفع النموذج تلقائياً إلى السحابة كل بضع ثوانٍ (Auto-save).

الخلاصة: ViewModel يُدمر في Process Death!

هذه هي النقطة التي يُخطئ فيها معظم المطورين. ViewModel لا يبقى حياً في Process Death. يبقى حياً فقط خلال Configuration Changes. الفرق:

  • Configuration Change: Activity تُدمر وتُعاد إنشاؤها، لكن ViewModel يبقى حياً (يُدار عبر ViewModelStore).
  • Process Death: العملية بأكملها تُقتل. ViewModelStore يُدمر. ViewModel يُنشأ من جديد.

لذلك: لا تعتمد أبداً على متغيرات الذاكرة في ViewModel للبيانات الحرجة. استخدم SavedStateHandle أو Persistent Storage.

الخلاصة النهائية للمقابلات

عند الإجابة على أي سؤال متعلق بدورة الحياة في المقابلات الأوروبية، تذكر دائماً هذه النقاط:

  • اميز بين Configuration Change و Process Death: هما سيناريوهان مختلفان تماماً في كيفية إدارة الحالة.
  • Fragment له View Lifecycle منفصلة: استخدم viewLifecycleOwner دائماً لربط الملاحظات.
  • commitAllowingStateLoss() خطر: استخدم isStateSaved للتحقق قبل أي Transaction.
  • Memory Leaks تُقاس بالإنتاج: لا تعتمد على اختباراتك المحلية فقط — استخدم LeakCanary و Firebase Performance.
  • Context نوعه مهم: ActivityContext للواجهة، ApplicationContext للعمليات طويلة الأمد.
