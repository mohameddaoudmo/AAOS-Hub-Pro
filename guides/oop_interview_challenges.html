🎯 الفلسفة وراء الأسئلة الخادعة في السوق الأوروبي

عندما تتقدم لوظيفة مطور أندرويد في شركة كبرى مثل Zalando في برلين، أو BMW في ميونخ، أو Delivery Hero، فإنك لا تجيب فقط على أسئلة تقنية، بل تخضع لاختبار فهمك العميق لآليات عمل اللغة من الداخل. هذه الشركات لا تبحث عن من يكتب الكود فحسب، بل عن من يفهم Memory Model وRuntime Behavior وDesign Trade-offs.

💡 لماذا OOP تحديداً؟

لأن البرمجة كائنية التوجه هي اللبنة الأساسية التي تبنى عليها كل منصة أندرويد. فهمك العميق لها يعكس قدرتك على:

  • تجنب تسريبات الذاكرة في التطبيقات المعقدة
  • تصميم أنظمة قابلة للاختبار والتوسع
  • قراءة وفهم أكواد المكتبات الكبرى مثل Jetpack
  • اتخاذ قرارات تصميمية سليمة تحت الضغط

تستخدم الشركات الأوروبية ما يُعرف بـ Tricky Questions لاختبار ثلاثة محاور رئيسية:

🎭 تشبيه واقعي: امتحان رخصة القيادة الألمانية

كما أن امتحان القيادة في ألمانيا لا يختبر فقط قدرتك على التحرك بالسيارة، بل يختبر فهمك للقوانين في المواقف الحرجة (مثل الأولوية في التقاطعات غير المنظمة)، كذلك أسئلة الـ OOP تختبر سلوكك في المواقف الحرجة البرمجية.

المحور الأول: فهم دورة حياة الكائن (Object Lifecycle Understanding)

عندما يسألك المقابل: "ماذا يحدث عندما تستدعي دالة افتراضية من داخل المشيد الأساسي؟"، فإنه لا يريد الإجابة السطحية. يريد أن يعرف هل تفهم أن:

  • الكائن لا يزال في حالة غير مكتملة أثناء تنفيذ المشيد
  • الـ vtable لم يكتمل بناؤه بعد
  • هذا يؤدي إلى سلوك غير متوقع قد يسبب أخطاء فادحة في الإنتاج

المحور الثاني: الوعي بتكاليف الأداء (Performance Awareness)

في عالم الأجهزة المحمولة، كل ملي ثانية تهم. فهمك لـ Dynamic Dispatch وMethod Overhead يعكس وعيك بتأثير قرارات التصميم على أداء التطبيق.

المحور الثالث: القدرة على التصميم المعماري (Architectural Design Skills)

أسئلة مثل "كيف تمنع كسر Encapsulation عند تمرير كائنات قابلة للتعديل داخل كائنات غير قابلة للتعديل؟" تختبر قدرتك على التفكير في عقود الكائنات وImmutability وDefensive Copying.

⚠️ تحذير مهم

في المقابلات الألمانية تحديداً، يُنظر بعين الريبة إلى الإجابات الحافية. المقابلون يقدرون الصراحة في الاعتراف بعدم المعرفة أكثر من التخمين. لكنهم يتوقعون أن تكون إجاباتك دقيقة ومدعومة بأمثلة كودية عندما تكون واثقاً.

🔧 الترتيب الدقيق للتهيئة في الهرميات المعقدة

تُعد مسألة ترتيب التهيئة في الهرميات الوراثية المتعددة المستويات من أكثر الأسئلة شيوعاً في المقابلات الأوروبية. لماذا؟ لأن فهمها يعكس إدراكك العميق لكيفية بناء الكائنات في الذاكرة.

🏗️ تشبيه واقعي: بناء ناطحة سحاب

تخيل أنك تبني ناطحة سحاب. لا يمكنك أن تبدأ بالطابق العشرين قبل إكمال الأساسات. كذلك في البرمجة كائنية التوجه، لا يمكن إكمال تهيئة الكائن الفرعي قبل الانتهاء من تهيئة الكائن الأساسي. لكن التعقيد يكمن في الترتيب الدقيق داخل كل طبقة.

القواعد الذهبية لترتيب التهيئة في جافا وكوتلن

عند إنشاء كائن جديد، يتبع الـ JVM الترتيب التالي بدقة:

  1. تحميل الصنف (Class Loading): يقوم ClassLoader بتحميل الصنف إلى الذاكرة إذا لم يكن محملاً من قبل
  2. تنفيذ الكتل الساكنة (Static Initializers): من الأعلى إلى الأسفل في شجرة الوراثة، بدءاً من java.lang.Object
  3. تخصيص الذاكرة (Memory Allocation): يخصص الـ JVM مساحة في Heap للكائن
  4. التهيئة الافتراضية (Default Initialization): تهيئة الحقول بقيمها الافتراضية (صفر، null، false)
  5. تنفيذ كتل التهيئة (Instance Initializers): من الأعلى إلى الأسفل
  6. تنفيذ المشيد (Constructor): بدءاً من المشيد الأساسي ثم المتفرع
Java 
public class InitializationOrderDemo {

    static class GrandParent {
        static { System.out.println("GrandParent: Static Block"); }
        { System.out.println("GrandParent: Instance Initializer"); }
        public GrandParent() {
            System.out.println("GrandParent: Constructor");
        }
    }

    static class Parent extends GrandParent {
        static { System.out.println("Parent: Static Block"); }
        { System.out.println("Parent: Instance Initializer"); }
        public Parent() {
            System.out.println("Parent: Constructor");
        }
    }

    static class Child extends Parent {
        static { System.out.println("Child: Static Block"); }
        { System.out.println("Child: Instance Initializer"); }
        public Child() {
            System.out.println("Child: Constructor");
        }
    }

    public static void main(String[] args) {
        new Child();
    }
}
// Output
GrandParent: Static Block Parent: Static Block Child: Static Block GrandParent: Instance Initializer GrandParent: Constructor Parent: Instance Initializer Parent: Constructor Child: Instance Initializer Child: Constructor
🚨 الفخ الخادع: الاستدعاء الافتراضي داخل المشيد

من أخطر الأنماط في البرمجة كائنية التوجه هو استدعاء دالة overridable داخل المشيد. لماذا؟ لأن الكائن الفرعي لم يُهيأ بعد!

Java 
public class DangerousInitialization {

    static class Parent {
        public Parent() {
            // ⚠️ خطير جداً! الكائن الفرعي لم يُبنَ بعد
            initialize();
        }

        protected void initialize() {
            System.out.println("Parent.initialize()");
        }
    }

    static class Child extends Parent {
        private final String criticalData = "Initialized";

        public Child() {
            // super() يُستدعى ضمنياً هنا
            System.out.println("Child constructor: " + criticalData);
        }

        @Override
        protected void initialize() {
            // ❌ criticalData لا تزال null هنا!
            System.out.println("Child.initialize(): " + criticalData);
        }
    }

    public static void main(String[] args) {
        new Child();
    }
}
// Output المُحيّر
Child.initialize(): null Child constructor: Initialized

ما الذي حدث هنا؟ عندما استدعى المشيد الأساسي initialize()، كان الـ vtable قد اكتمل ربطه بالفعل (لأن الـ JVM يحدد الأصناف الفعلية عند new)، لكن حقول الكائن الفرعي لم تُهيأ بعد. هذا يعني أن criticalData لا تزال تحمل قيمتها الافتراضية null!

⚔️ Method Hiding مقابل Method Overriding

يُعد التمييز بين Method Hiding وMethod Overriding من أكثر نقاط الالتباس شيوعاً. الفرق ليس مجرد نظري، بل له تأثيرات عملية على الأداء والسلوك.

الخاصية Method Overriding Method Hiding
ينطبق على الدوال غير الساكنة (Instance Methods) الدوال الساكنة (Static Methods)
آلية الربط (Binding) Late Binding (Dynamic Dispatch) Early Binding (Static Dispatch)
يعتمد على النوع الفعلي للكائن (Runtime Type) نوع المرجع (Reference Type)
يستخدم vtable نعم ✓ لا ✗
يمكن أن يكون final نعم (يمنع الـ Overriding) لا معنى له
Kotlin 
open class Parent {
    open fun instanceMethod() = println("Parent instanceMethod")

    companion object {
        fun staticMethod() = println("Parent staticMethod")
    }
}

class Child : Parent() {
    override fun instanceMethod() = println("Child instanceMethod")

    companion object {
        fun staticMethod() = println("Child staticMethod") // Hiding, not overriding
    }
}

fun main() {
    val ref: Parent = Child()

    ref.instanceMethod() // Output: Child instanceMethod (Late Binding)
    Parent.staticMethod()  // Output: Parent staticMethod (Early Binding)

    // ⚠️ Even if we call through Child reference:
    Child.staticMethod()   // Output: Child staticMethod
}

💎 معضلة الوراثة المتعددة (Diamond Problem)

في جافا وكوتلن، لا يُسمح بالوراثة المتعددة من أصناف (Multiple Class Inheritance)، لكن يُسمح بتنفيذ واجهات متعددة (Multiple Interface Implementation). ما الذي يحدث عندما تحتوي واجهتان على نفس الدالة الافتراضية؟

Java 
interface Printer {
    default void print() {
        System.out.println("Printer: printing document");
    }
}

interface Scanner {
    default void print() {
        System.out.println("Scanner: scanning output");
    }
}

// ❌ Compilation Error: class MultiFunctionDevice inherits unrelated 
// defaults for print() from types Printer and Scanner
class MultiFunctionDevice implements Printer, Scanner {
    // MUST override to resolve conflict
    @Override
    public void print() {
        Printer.super.print(); // Explicitly choose Printer's implementation
        // OR: Scanner.super.print();
        // OR: provide completely new implementation
    }
}
✅ الحل في كوتلن

في كوتلن، يُعالج هذا الأمر بشكل أنيق عبر الكلمة المفتاحية super<InterfaceName>:

Kotlin 
interface Printer {
    fun print() = println("Printer: printing")
}

interface Scanner {
    fun print() = println("Scanner: scanning")
}

class MultiFunctionDevice : Printer, Scanner {
    override fun print() {
        super<Printer>.print()  // Explicitly call Printer's implementation
        super<Scanner>.print()  // Explicitly call Scanner's implementation
    }
}

🧬 Generics و Type Erasure وتأثيرها على Method Signature

تُعد Type Erasure من أخفى المفاهيم في جافا. عندما تُترجم الشيفرة، يُحذف معلومات النوع العام (Generic Type Information) ويُستبدل بحدوده العليا (Upper Bound). هذا يخلق مواقف خادعة في الـ Method Overloading.

Java 
import java.util.*;

public class TypeErasureTrap {

    // After erasure: void process(List list)
    public void process(List<String> strings) {
        System.out.println("Processing Strings");
    }

    // After erasure: void process(List list)  
    // ❌ COMPILATION ERROR: both methods have same erasure
    // public void process(List<Integer> integers) {
    //     System.out.println("Processing Integers");
    // }

    // ✅ Valid overload because raw types differ after erasure
    public void process(Set<String> strings) {
        System.out.println("Processing Set");
    }

    public static void main(String[] args) {
        TypeErasureTrap trap = new TypeErasureTrap();

        // ⚠️ Dangerous: Raw type bypasses generic safety
        List rawList = new ArrayList<Integer>();
        trap.process(rawList); // Compiles, but may cause ClassCastException at runtime
    }
}
⚠️ الفخ في كوتلن

في كوتلن، يُحافظ على معلومات النوع العام في وقت التشغيل عبر Reified Type Parameters باستخدام الكلمة المفتاحية reified في الدوال المضمنة (Inline Functions):

Kotlin 
inline fun <reified T> isType(value: Any): Boolean {
    return value is T  // ✅ Works because T is reified at compile time
}

// Usage
val result = isType<String>(42)  // Returns false
val result2 = isType<String>("hello")  // Returns true

// Without reified, this would not be possible in generic functions
// because type information is erased at runtime

⚙️ كيف ينفذ الـ JVM جدول الطرق الافتراضية (vtable)

vtable (Virtual Method Table) هو الهيكل البيانات الذي يُمكّن الـ JVM من تحديد الدالة الصحيحة لاستدعائها في وقت التشغيل. فهمه العميق يُعد فارقاً بين المطور المتوسط والمطور الخبير.

📞 تشبيه واقعي: دليل الهاتف الذكي

تخيل أن لديك دليل هاتف تقليدي (Early Binding) مقابل مساعد ذكي يتعرف على صوت المتصل ويحول المكالمة للشخص المناسب تلقائياً (Late Binding). الـ vtable هو ذلك "المساعد الذكي" داخل الـ JVM.

تكلفة Dynamic Dispatch

📊 التكلفة الزمنية

كل استدعاء دالة افتراضية يتطلب:

  1. قراءة مؤشر الصنف من كائن الهيدر (~1-2 clock cycles)
  2. الوصول إلى vtable عبر مؤشر الصنف (~1-2 cycles)
  3. قراءة مؤشر الدالة من vtable (~1-2 cycles)
  4. القفز إلى الدالة (indirect jump)

الإجمالي: ~3-5 clock cycles إضافية مقارنة بالاستدعاء المباشر. في التطبيقات الأندرويدية التي تُعالج آلاف الأحداث في الثانية، يمكن أن يتراكم هذا.

🎭 الفخاخ عند استخدام Polymorphism مع الحقول والدوال الساكنة

أكبر خطأ يقع فيه المطورون هو الاعتقاد بأن Polymorphism ينطبق على الحقول أو الدوال الساكنة. لا ينطبق!

Java 
public class FieldHidingTrap {

    static class Parent {
        String name = "Parent";
        static String staticName = "Parent Static";

        void printName() {
            System.out.println("Method: " + name);
        }
    }

    static class Child extends Parent {
        String name = "Child";           // Hides Parent.name, NOT overrides
        static String staticName = "Child Static"; // Hides Parent.staticName

        @Override
        void printName() {
            System.out.println("Method: " + name);
        }
    }

    public static void main(String[] args) {
        Parent p = new Child();

        // ⚠️ Field access uses reference type (Early Binding)
        System.out.println(p.name);           // "Parent" (surprising!)
        System.out.println(p.staticName);     // "Parent Static"

        // ✅ Method call uses actual type (Late Binding)
        p.printName();                        // "Method: Child"

        // Direct access through Child reference
        Child c = new Child();
        System.out.println(c.name);           // "Child"
    }
}

🚀 تحسين JIT: Devirtualization

في JVMs الحديثة (HotSpot, ART في أندرويد)، يقوم الـ JIT Compiler بتحليل المسارات الساخنة (Hot Paths). إذا لاحظ أن دالة افتراضية تُستدعى دائماً على نفس الصنف، يقوم بـ Devirtualization: استبدال الاستدعاء الافتراضي باستدعاء مباشر، وحتى Inlining للدالة إذا كانت صغيرة.

مبادئ التصميم الصلبة تحت الاختبار العملي

📐 مبدأ استبدال ليزكوف (Liskov Substitution Principle - LSP)

يُعد Liskov Substitution Principle من أصعب المبادئ فهماً وتطبيقاً. ينص على أنه يجب أن نتمكن من استبدال أي صنف فرعي بصنفه الأساسي دون تغيير سلوك البرنامج. لكن ما الذي يعنيه "تغيير السلوك" فعلياً؟

🦅 تشبيه واقعي: مربع وطويل

في الهندسة، كل مربع هو مستطيل. لكن في البرمجة كائنية التوجه، إذا ورث صنف Square من Rectangle وغيّر سلوك setWidth() ليضبط الارتفاع أيضاً، فإنه ينتهك LSP. لماذا؟ لأن الكود الذي يتوقع أن setWidth() لا تؤثر على الارتفاع سيتعطل.

Kotlin 
// ❌ ANTI-PATTERN: Violates LSP
open class Rectangle {
    open var width: Int = 0
    open var height: Int = 0

    fun area(): Int = width * height
}

class Square : Rectangle() {
    override var width: Int = 0
        set(value) {
            field = value
            height = value  // Violates expectation!
        }

    override var height: Int = 0
        set(value) {
            field = value
            width = value   // Violates expectation!
        }
}

    rectangle.width = 5
    rectangle.height = 10

    // Client expects area = 50, but Square returns 100!
    assert(rectangle.area() == 50) { "LSP Violation!" }
}

    testRectangle(Rectangle())  // ✅ Passes
    testRectangle(Square())     // ❌ Fails! LSP Violated

🔄 مبدأ عكس التبعيات (Dependency Inversion Principle - DIP)

ينص على أن الوحدات العليا لا يجب أن تعتمد على الوحدات الدنيا. يجب أن تعتمد كلاهما على التجريدات. في أندرويد، يُعد هذا المبدأ حجر الزاوية في Clean Architecture وMVVM.

🏠 تشبيه واقعي: نظام المنزل الذكي

  2. جميع الحقول تُهيأ بقيمها الافتراضية (null, 0, false)
  3. يُستدعى مشيد Animal عبر super(name)
  4. داخل مشيد Animal، يُستدعى makeSound()
  5. الـ vtable يشير بالفعل إلى Dog.makeSound() (صحيح!)
  6. لكن breed لم تُهيأ بعد! لا تزال null
  7. بعد انتهاء Animal()، تُهيأ breed = "Golden Retriever"
  8. ينتهي مشيد Dog

public final class ImmutablePerson {
    private final List<String> hobbies;
    private final Date birthDate;

    public ImmutablePerson(List<String> hobbies, Date birthDate) {
        // Defensive copy in constructor
        this.hobbies = new ArrayList<>(hobbies);
        this.birthDate = new Date(birthDate.getTime());
    }

    public List<String> getHobbies() {
        // Defensive copy on access
        return new ArrayList<>(hobbies);
    }

    public Date getBirthDate() {
        return new Date(birthDate.getTime());
    }
}

Kotlin 
// ✅ KOTLIN: Declaration-site variance
interface Producer<out T> {  // Covariant
    fun produce(): T  // Can only produce T, not consume
}

interface Consumer<in T> {   // Contravariant
    fun consume(item: T)  // Can only consume T, not produce
}

interface Storage<T> {       // Invariant
    fun produce(): T
    fun consume(item: T)
}

// Usage:
val stringProducer: Producer<String> = StringProducer()
val anyProducer: Producer<Any> = stringProducer  // ✅ OK: out T

val anyConsumer: Consumer<Any> = AnyConsumer()
val stringConsumer: Consumer<String> = anyConsumer  // ✅ OK: in T
المفهوم Java Syntax Kotlin Syntax المعنى
Covariance ? extends T out T يمكن إسناد Producer<Child> إلى Producer<Parent>
Contravariance ? super T in T يمكن إسناد Consumer<Parent> إلى Consumer<Child>
Invariance T T لا يمكن إسناد إلا لنفس النوع بالضبط
🐕 تشبيه واقعي: سلسلة الكلاب

إذا كان Animal هو الصنف الأساسي وDog هو الصنف الفرعي:

  • Covariance (out): يمكنك إسناد List<Dog> إلى List<? extends Animal> لأنك تستخرج حيوانات (قد تكون كلاباً)
  • Contravariance (in): يمكنك إسناد List<Animal> إلى List<? super Dog> لأنك تضيف كلاباً إلى قائمة حيوانات
  • Invariance: List<Dog> ليست List<Animal> لأنك قد تضيف قطة إلى قائمة حيوانات!

🎪 السؤال الثامن: equals() و hashCode() Contract

ما هي العقدة (Contract) بين equals() و hashCode()؟ وما الذي يحدث عند كسرها في HashMap؟
Java 
// ❌ BROKEN: Violates equals/hashCode contract
public class BrokenKey {
    private final String id;
    private String mutableData;

    public BrokenKey(String id) { this.id = id; }
    public void setMutableData(String data) { this.mutableData = data; }

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;
        if (o == null || getClass() != o.getClass()) return false;
        BrokenKey that = (BrokenKey) o;
        return Objects.equals(id, that.id) &&
               Objects.equals(mutableData, that.mutableData);  // ❌ Uses mutable field!
    }

    @Override
    public int hashCode() {
        return Objects.hash(id, mutableData);  // ❌ Uses mutable field!
    }
}

// Dangerous usage:
Map<BrokenKey, String> map = new HashMap<>();
BrokenKey key = new BrokenKey("123");
key.setMutableData("initial");
map.put(key, "value");

key.setMutableData("changed");  // ❌ hashCode changes!
// key is now in the WRONG bucket of HashMap!
String value = map.get(key);  // Returns null! Key "lost" in HashMap
Kotlin 
// ✅ CORRECT: Immutable data class (auto-generates proper equals/hashCode)
data class SafeKey(
    val id: String,           // val = immutable
    val createdAt: Long       // val = immutable
) {
    // Kotlin data class automatically:
    // 1. Uses only primary constructor properties in equals()
    // 2. Uses same properties in hashCode()
    // 3. Both are based on immutable fields only
}

// ✅ Or manual implementation for Java compatibility:
class ManualKey private constructor(
    private val id: String,
    private val timestamp: Long
) {
    override fun equals(other: Any?): Boolean {
        if (this === other) return true
        if (other !is ManualKey) return false
        return id == other.id && timestamp == other.timestamp
    }

    override fun hashCode(): Int {
        var result = id.hashCode()
        result = 31 * result + timestamp.hashCode()
        return result
    }

    companion object {
        fun create(id: String) = ManualKey(id, System.currentTimeMillis())
    }
}
📐 العقدة (Contract)
  1. Reflexive: x.equals(x) == true
  2. Symmetric: x.equals(y) == y.equals(x)
  3. Transitive: إذا x.equals(y) وy.equals(z) فـ x.equals(z)
  4. Consistent: النتيجة لا تتغير إذا لم يتغير الكائن
  5. hashCode contract: إذا x.equals(y) فـ x.hashCode() == y.hashCode()

🏛️ السؤال التاسع: Decorator Pattern في أندرويد

كيف تُطبق Decorator Pattern لإضافة وظائف (Logging, Caching, Encryption) لـ Repository بدون تعديل الكود الأصلي؟
Kotlin 
// Core interface
interface UserRepository {
    suspend fun getUser(id: String): User
    suspend fun saveUser(user: User)
}

// Base implementation
class UserRepositoryImpl(
    private val api: UserApi,
    private val dao: UserDao
) : UserRepository {
    override suspend fun getUser(id: String): User {
        return dao.getUser(id) ?: api.fetchUser(id).also { dao.insert(it) }
    }

    override suspend fun saveUser(user: User) {
        dao.insert(user)
        api.updateUser(user)
    }
}

// ✅ DECORATOR: Logging
class LoggingUserRepository(
    private val delegate: UserRepository
) : UserRepository {

    override suspend fun getUser(id: String): User {
        Log.d("Repository", "Getting user: $id")
        val start = System.currentTimeMillis()
        val user = delegate.getUser(id)
        Log.d("Repository", "Got user in ${System.currentTimeMillis() - start}ms")
        return user
    }

    override suspend fun saveUser(user: User) {
        Log.d("Repository", "Saving user: ${user.id}")
        delegate.saveUser(user)
    }
}

// ✅ DECORATOR: Caching with TTL
class CachingUserRepository(
    private val delegate: UserRepository,
    private val cache: LruCache<String, Pair<User, Long>>,
    private val ttlMillis: Long = 60_000
) : UserRepository {

    override suspend fun getUser(id: String): User {
        val cached = cache.get(id)
        if (cached != null && System.currentTimeMillis() - cached.second < ttlMillis) {
            return cached.first
        }
        val user = delegate.getUser(id)
        cache.put(id, user to System.currentTimeMillis())
        return user
    }

    override suspend fun saveUser(user: User) {
        cache.remove(user.id)
        delegate.saveUser(user)
    }
}

// ✅ Composition: Stack decorators
val repository = CachingUserRepository(
    LoggingUserRepository(
        UserRepositoryImpl(api, dao)
    ),
    LruCache(100)
)
🧅 تشبيه واقعي: البصلة المتدرجة

كل Decorator هو طبقة حول الطبقة الداخلية. كالبصلة، يمكنك إضافة طبقات (Logging, Caching, Encryption) حول النواة (Repository الأساسي) دون تعديل أي طبقة داخلية. هذا هو جوهر Open/Closed Principle.

🎨 السؤال العاشر: Strategy Pattern مع Lambdas في كوتلن

كيف تُبسط Strategy Pattern باستخدام Lambdas/Function Types في كوتلن؟ وما هي ميزة هذا النهج في أندرويد؟
Kotlin 
// ❌ VERBOSE: Traditional Strategy Pattern with interfaces
interface SortStrategy {
    fun <T : Comparable<T>> sort(list: List<T>): List<T>
}

class QuickSort : SortStrategy {
    override fun <T : Comparable<T>> sort(list: List<T>): List<T> {
        // Implementation...
        return list.sorted()
    }
}

class MergeSort : SortStrategy {
    override fun <T : Comparable<T>> sort(list: List<T>): List<T> {
        // Implementation...
        return list.sorted()
    }
}

// ✅ ELEGANT: Function types as strategies
typealias SortStrategy<T> = (List<T>) -> List<T>

class Sorter<T : Comparable<T>> {
    fun sort(list: List<T>, strategy: SortStrategy<T>): List<T> {
        return strategy(list)
    }
}

// Usage with lambdas
val sorter = Sorter<Int>()

val quickSort: SortStrategy<Int> = { it.sorted() }
val reverseSort: SortStrategy<Int> = { it.sortedDescending() }

val sorted = sorter.sort(listOf(3, 1, 4), quickSort)
val reversed = sorter.sort(listOf(3, 1, 4), reverseSort)

// ✅ Even more elegant: Inline with SAM conversion
fun <T : Comparable<T>> List<T>.customSort(
    strategy: (List<T>) -> List<T> = { it.sorted() }
): List<T> = strategy(this)

val result = listOf(3, 1, 4).customSort { it.shuffled() }
