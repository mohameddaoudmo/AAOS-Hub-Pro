المقدمة: فلسفة بنية AOSP والفرق الجوهري مع أندرويد التجاري

عندما نتحدث عن AOSP (Android Open Source Project)، نتحدث عن المصدر المفتوح لنظام التشغيل أندرويد. لكن ما يجهله الكثيرون هو أن أندرويد التجاري الذي يعمل على هاتفك الذكي ليس مجرد AOSP خام - بل هو AOSP مُعدّل ومُغلّف بخدمات Google (GMS). هذا الفرق الجوهري هو البوابة التي تفصل بين "مبرمج التطبيقات" و"مهندس المنصة".

AOSP vs GMS: المصدر المفتوح مقابل النظام التجاري

AOSP هو المشروع المفتوح المصدر الذي تديره Google وتُساهم فيه شركات أخرى (Samsung, Qualcomm, Sony, إلخ). يتضمن: نواة لينكس، مكتبات C/C++، Android Runtime (ART)، Framework APIs، وتطبيقات النظام الأساسية (Dialer, Contacts, Messaging). لكنه لا يتضمن تطبيقات Google (Gmail, Maps, Play Store) ولا خدمات Google Play Services.

GMS (Google Mobile Services) هو الطبقة التجارية التي تضيفها Google فوق AOSP. يتضمن: Google Play Store، Google Play Services (Push Notifications, Location, Maps API)، Google Apps (Gmail, YouTube, Drive)، وشهادات Google للأمان. بدون GMS، لا يمكنك تحميل التطبيقات من Play Store ولا استخدام خرائط Google.

التمثيل الحياتي: السيارة الأساسية مقابل السيارة الفاخرة

AOSP كهيكل سيارة أساسي: يحتوي على المحرك، الهيكل، العجلات، والمقاعد. يمكنك قيادتها والتنقل بها. لكنها لا تحتوي على نظام تكييف، نظام ملاحة، راديو فاخر، أو مساعد ذكي.

GMS كالإضافات الفاخرة: نظام الملاحة (Google Maps)، المساعد الصوتي (Google Assistant)، متجر التطبيقات (Play Store)، والخدمات السحابية. هذه الإضافات تجعل السيارة "مريحة" لكنها ليست ضرورية للعمل.

الشركات المصنعة (Samsung, Xiaomi, Huawei) تأخذ هيكل AOSP، تضيف GMS (إذا كان لديهم ترخيص)، ثم تضيف طبقاتهم الخاصة (One UI, MIUI, HarmonyOS).

فهم AOSP يعني فهم كيف يعمل أندرويد حقاً تحت الغطاء. عندما يتجمد تطبيقك (ANR)، أو يتسرب ذاكرة، أو يفشل في الاتصال بالشبكة - فهم Binder IPC و Zygote و SystemServer يمكّنك من تشخيص المشكلة على مستوى النظام، لا مجرد مستوى التطبيق.

في عالم السيارات (AAOS)، يصبح هذا أكثر أهمية لأنك تتعامل مع: عتاد مخصص (CAN Bus، أجهزة استشعار، أنظمة تكييف)، متطلبات أمان صارمة (لا يمكن للسائق أن يتشتت)، وإدارة طاقة معقدة (السيارة تدخل وضع السكون).

Linux Kernel: الأساس الذي يقوم عليه كل شيء

في قلب كل جهاز أندرويد يوجد نواة لينكس مُعدّلة. لكن هذه ليست نواة لينكس قياسية. Google قامت بإضافة تعديلات جوهرية تجعلها مناسبة للأجهزة المحمولة والسيارات.

Low Memory Killer (LMK): القاتل الذكي للذاكرة

في أنظمة لينكس التقليدية، عندما تنفد الذاكرة، يُفعّل Out-Of-Memory (OOM) Killer الذي يقتل العمليات بشكل عشوائي. لكن في أندرويد، هذا غير مقبول - لا يمكنك قتل تطبيق الهاتف أثناء مكالمة طوارئ! لذا أضافت Google Low Memory Killer (LMK).

LMK يعمل على مستوى kernel space ويُراقب مستوى الذاكرة الحررة. عندما تنخفض الذاكرة، يبدأ في قتل العمليات حسب أولوية مُحددة مسبقاً (OomAdj Scores). العمليات غير المهمة (Background Apps) تُقتل أولاً، بينما العمليات الحيوية (System Server, Phone App) تُحفظ حتى النهاية.

LMK كمدير طوارئ في مبنى مزدحم. عندما يمتلئ المبنى (تنفد الذاكرة)، لا يطلب من الجميع الخروج بشكل عشوائي. بدلاً من ذلك، يبدأ بطرد الزوار غير الضروريين (Background Apps) أولاً. إذا استمر الازدحام، يطرد الموظفين في الأقسام الثانوية (Cached Services). يبقى فريق الطوارئ والإدارة (System Server, Phone) حتى النهاية. هذا يضمن أن النظام يبقى مستقراً حتى في أسوأ الظروف.

Wakelocks: منع النوم عند الحاجة

في أنظمة لينكس التقليدية، عندما لا يكون هناك عمل، يدخل النظام في وضع السكون (Sleep/Suspend) لتوفير الطاقة. لكن في الهواتف، قد تحتاج إلى إبقاء WiFi نشطاً لتلقي رسائل Push، أو إبقاء الشاشة مضاءة أثناء مشاهدة فيديو.

Wakelocks هي آلية أضافتها Google إلى نواة لينكس تسمح للعمليات (في kernel space) بـ "طلب الإبقاء على الاستيقاظ". عندما يحتفظ برنامج تشغيل (Driver) بـ Wakelock، لا يستطيع النظام الدخول في وضع السكون العميق. 

// استخدام Wakelock في kernel driver
#include <linux/wakelock.h>

static struct wake_lock my_wakelock;

void init_driver() {
    wake_lock_init(&my_wakelock, WAKE_LOCK_SUSPEND, "my_driver_wakelock");
}

void start_important_operation() {
    wake_lock(&my_wakelock); // منع النظام من النوم
    // ... إجراء العملية الحرجة ...
}

void finish_operation() {
    wake_unlock(&my_wakelock); // السماح بالنوم مرة أخرى
}
⚠️
مشكلة Wakelocks: تسريب الطاقة

إذا نسي برنامج تشغيل (Driver) استدعاء wake_unlock()، فإن الجهاز لن يدخل في وضع السكون أبداً، مما يؤدي إلى استنزاف البطارية خلال ساعات. في Android Automotive، هذا يعني أن السيارة قد تفقد طاقة البطارية بالكامل بين عشية وضحاها. لذا، تُراقب Google Wakelocks بصرامة في تطبيقات النظام.

Binder Driver: القلب النابض للاتصال بين العمليات

Binder هو أهم إضافة قامت بها Google على نواة لينكس. في أنظمة لينكس التقليدية، العمليات تتواصل عبر IPC (Inter-Process Communication) باستخدام Pipes أو Sockets أو Shared Memory. لكن هذه الآليات بطيئة ومعقدة للاستخدام اليومي.

Binder يُقدّم آلية IPC خفيفة وفعالة مصممة خصيصاً لأندرويد. يسمح لعملية (Client) باستدعاء دوال في عملية أخرى (Server) كأنها دوال محلية. هذا يُعرف بـ Remote Procedure Call (RPC).

التمثيل الحياتي: نظام الأنابيب في المبنى

تخيل مبنىً به شقق متعددة (عمليات). كل شقة لديها أنابيب مياه خاصة (ذاكرة خاصة) لا يمكن للشقق الأخرى الوصول إليها. إذا أراد ساكن في الشقة 5 (تطبيقك) الحصول على ماء ساخن من الشقة 1 (System Server)، فإنه لا يذهب بنفسه. بدلاً من ذلك، يرسل رسالة عبر نظام أنابيب مركزي (Binder Driver) يديره حارس المبنى (Kernel). الحارس يأخذ الرسالة، يتحقق من هوية المرسل (Security)، يذهب إلى الشقة 1، يحضر الماء الساخن، ويعيده إلى الشقة 5. هذا النظام المركزي أسرع من أن يذهب كل ساكن بنفسه، وأكثر أماناً لأن الحارس يتحقق من الهويات. 

// البنية الداخلية لـ Binder Transaction
// kernel/drivers/android/binder.c

struct binder_transaction_data {
    // معرف العملية المستهدفة
    union {
        __u32 handle;       // معامل في العملية الحالية
        binder_uintptr_t ptr; // مؤشر في العملية المستهدفة
    } target;

    // معرف الدالة المطلوب استدعاؤها
    __u32 code;

    // البيانات المرسلة
    binder_uintptr_t buffer;

    // حجم البيانات
    binder_size_t data_size;
};

آلية عمل Binder:

  1. التسجيل (Registration): الخدمة (مثلاً ActivityManagerService) تُسجّل نفسها مع ServiceManager عبر Binder.
  2. البحث (Lookup): العميل (تطبيقك) يطلب من ServiceManager عنوان الخدمة.
  3. الاستدعاء (Transaction): العميل يُرسل Binder Transaction يحتوي على: معرف الخدمة، معرف الدالة (code)، والبيانات (arguments).
  4. التنفيذ: الـ Kernel ينسخ البيانات من مساحة العميل إلى مساحة الخادم، ويستدعي الدالة المطلوبة.
  5. الإرجاع: النتيجة تُنسخ بالعكس عبر نفس الآلية.
🔒 الأمان في Binder: التحقق من الهوية

Binder لا ينقل البيانات فقط - بل ينقل هوية المرسل أيضاً. عندما يستدعي تطبيقك ActivityManager، يعرف ActivityManager بالضبط من هو التطبيق الذي يستدعيه (عبر Binder.getCallingUid()). هذا يمكّن النظام من:

  • فرض Permissions على مستوى النظام.
  • منع التطبيقات من انتحال هوية تطبيقات أخرى.
  • تتبع أي عملية تستهلك موارد كثيرة.

HAL: طبقة تجريد العتاد (Hardware Abstraction Layer)

HAL هي الطبقة التي تفصل إطار العمل (Framework) عن العتاد الفعلي. الفكرة: إطار العمل يتحدث لغة موحدة (Java APIs)، بينما HAL يترجم هذه اللغة إلى أوامر خاصة بكل جهاز.

مثال: عندما تضغط على زر رفع الصوت في هاتفك، يحدث التالي:

  1. إطار العمل (Framework) يستدعي AudioManager.setStreamVolume().
  2. Framework يتحدث إلى HAL عبر JNI (Java Native Interface).
  3. HAL يستدعي برنامج تشغيل (Driver) خاص بشركة Qualcomm أو MediaTek.
  4. الـ Driver يتحدث إلى العتاد الفعلي (Audio Codec) عبر I2C أو SPI.
// مثال: HAL للكاميرا (Camera HAL)
// hardware/interfaces/camera/...

// Camera HAL Interface (HIDL/AIDL)
interface ICameraDevice {
    // فتح الكاميرا
    openDevice() generates (Status status);

    // التقاط صورة
    captureRequest(Request request) generates (Status status);

    // إغلاق الكاميرا
    closeDevice() generates (Status status);
};

// Samsung قد تستخدم معالج Exynos
// Qualcomm تستخدم Snapdragon ISP

HIDL vs AIDL: التحول في HAL

في أندرويد 8 (Oreo)، قدمت Google HIDL (HAL Interface Definition Language) لفصل HAL عن Framework. لكن في أندرويد 11+، بدأ التحول إلى AIDL (Android Interface Definition Language) لأنه أبسط وأكثر أداءً. الفرق: HIDL يستخدم hwbinder (نسخة من Binder مخصصة للعتاد)، بينما AIDL يستخدم binder العادي. في AAOS الحديث، معظم HALs تستخدم AIDL.

الآلية الداخلية للاتصال بين العمليات عبر Binder IPC

Binder IPC هو العمود الفقري لكل عملية اتصال في أندرويد. عندما تفتح تطبيقاً، أو تلتقط صورة، أو تستلم إشعاراً - فإن Binder يعمل في الخلفية. فهم هذه الآلية يفصل بين "مبرمج التطبيقات العادي" و"مهندس المنصة المتمرس".

Binder: لماذا لا نستخدم Sockets أو Pipes؟

في أنظمة لينكس التقليدية، العمليات تتواصل عبر Unix Domain Sockets أو Pipes. لكن هذه الآليات بطيئة لأنها تتطلب:

  • نسخ البيانات مرتين: من مساحة العميل إلى Kernel Buffer، ثم من Kernel Buffer إلى مساحة الخادم.
  • تسلسل (Serialization) مكلف: يجب تحويل البيانات إلى بايتات ثم إعادة بنائها.
  • لا يوجد هوية: الخادم لا يعرف من هو العميل بدون آليات إضافية.

Binder يحل هذه المشاكل عبر آلية مُحسّنة:

  • نسخ واحد فقط (One-Copy): Binder يستخدم mmap() لإنشاء ذاكرة مشتركة (Shared Memory) بين العمليات. البيانات تُنسخ مرة واحدة فقط من العميل إلى Kernel، ثم يُعطى الخادم مؤشراً (Pointer) إلى نفس البيانات دون نسخ إضافي.
  • تسلسل Parcellable: أندرويد يستخدم Parcel - تنسيق تسلسل مُحسّن يعرف بالضبط كيف يُرتّب البيانات في الذاكرة لتجنب إعادة الترتيب.
  • هوية مُدمجة: كل Transaction يحمل UID و PID للعميل تلقائياً.
التمثيل الحياتي: خدمة توصيل الطرود بين الشركات

تخيل شركتين في مبنى واحد. الشركة أ (العميل) تريد إرسال مستندات إلى الشركة ب (الخادم).

Socket (الطريقة القديمة): الشركة أ تضع المستندات في صندوق، تُغلّفه، تكتب عنوان الشركة ب، وتعطيه لساعي البريد (Kernel). الساعي يأخذ الصندوق إلى مستودع بريد مركزي، ثم يأخذه إلى الشركة ب. الشركة ب تفتح الصندوق، تُزيل التغليف، وتقرأ المستندات. بطيء لأن هناك تغليف وفك تغليف ونقل عبر مستودع مركزي.

Binder (الطريقة الذكية): الشركة أ تضع المستندات في صندوق بريد مشترك (Shared Memory via mmap) في الردهة. الشركة أ تكتب رسالة قصيرة: "الشركة ب: مستنداتك في الصندوق رقم 7". الساعي (Kernel) يأخذ الرسالة القصيرة فقط (وليس المستندات!) ويُسلمها للشركة ب. الشركة ب تذهب إلى الصندوق رقم 7 وتقرأ المستندات مباشرة دون نسخ. أسرع بكثير لأن المستندات الثقيلة لم تُنقل أبداً.

ServiceManager: دفتر عناوين النظام

ServiceManager هو أول خدمة تعمل في النظام بعد إقلاع kernel. يعمل كـ دفتر عناوين مركزي (Registry). كل خدمة نظام (System Service) تُسجّل نفسها مع ServiceManager عند بدء التشغيل. عندما يحتاج تطبيق إلى خدمة، يسأل ServiceManager عن عنوانها (Handle). 

// ServiceManager في Native Code

SystemServer: قلب النظام النابض

SystemServer هو العملية الأهم في أندرويد. يُطلق بواسطة Zygote (عملية "الأم" التي تُنشأ جميع تطبيقات Java) أثناء إقلاع النظام. SystemServer يُطلق جميع خدمات النظام:

  • ActivityManagerService - إدارة دورة حياة التطبيقات
  • WindowManagerService - إدارة النوافذ والشاشات
  • PackageManagerService - إدارة التطبيقات المثبتة
  • PowerManagerService - إدارة الطاقة والشاشة
  • InputManagerService - معالجة اللمس والأزرار
  • AudioService - إدارة الصوت
  • CarService (في AAOS) - خدمات السيارة

private void startOtherServices() {

Zygote هي عملية خاصة تُطلق أثناء إقلاع النظام. تقوم بتحميل جميع مكتبات Java الأساسية (Android Framework classes) في الذاكرة. عندما تُطلق تطبيقاً جديداً، لا يُنشأ من الصفر - بل يُنسخ (Fork) من Zygote. هذا يعني:

الدخول إلى عالم السيارات: Android Automotive OS

Android Automotive OS (AAOS) هو نظام التشغيل الكامل الذي يعمل على وحدة المعلومات والترفيه في السيارة (IVI - In-Vehicle Infotainment). هذا يختلف تماماً عن Android Auto الذي يعمل على هاتفك الذكي ويُعرض على شاشة السيارة.

AAOS vs Android Auto: الفرق الجوهري

البُعد Android Automotive OS (AAOS) Android Auto

التخصيص عالي (UI/UX خاص بكل شركة) محدود (قوالب Google)
أمثلة Volvo XC40, Polestar 2, GM Ultifi, Ford SYNC 4 أي سيارة تدعم Android Auto
التمثيل الحياتي: التلفزيون المدمج مقابل Chromecast

AAOS كالتلفزيون الذكي (Smart TV): نظام التشغيل موجود داخل التلفزيون. يمكنك تثبيت تطبيقات عليه مباشرة. الشركة المصنعة للتلفزيون تتحكم في الواجهة والميزات.

Android Auto كـ Chromecast: الهاتف هو المصدر، والشاشة مجرد "مرآة". التلفزيون لا يفعل شيئاً - كل المعالجة تحدث على الهاتف. إذا فقدت الهاتف الإشارة، توقف كل شيء.

هندسة AAOS: ما الذي يُضاف فوق AOSP؟

AAOS ليس نظاماً منفصلاً - بل هو AOSP مُعدّل مع إضافات خاصة بالسيارات. هذه الإضافات تتركز في عدة مجالات:

  1. Car Service Layer: خدمات جديدة في SystemServer تتعامل مع عتاد السيارة.
  2. Vehicle HAL: طبقة تجريد جديدة تترجم بين إشارات CAN Bus وواجهات Java.
  3. Car UI Toolkit: مكتبات واجهة مستخدم مُحسّنة للقيادة (أزرار كبيرة، تباين عالٍ، دعم عجلة القيادة).
  4. Power Management: إدارة طاقة مُحسّنة للسيارات (Garage Mode, Suspend-to-RAM).
  5. Security: نموذج أمان صارم يمنع تشتت السائق (Driver Distraction).
  6. Multi-Display: دعم شاشات متعددة (Cluster, IVI, Rear Seat Entertainment).

            CarSensorManager.SENSOR_RATE_NORMAL

            mSensorListener,
            CarSensorManager.SENSOR_TYPE_FUEL_LEVEL,
            CarSensorManager.SENSOR_RATE_NORMAL

        new CarSensorManager.OnSensorChangedListener() {

                    case CarSensorManager.SENSOR_TYPE_FUEL_LEVEL:
                        float fuelPercent = event.floatValues[0];
                        updateFuelGauge(fuelPercent);
                        break;
                }
            }
        };
}

🔊 Audio Focus في السيارة: Ducking vs Muting

في AAOS، نظام Audio Focus أكثر تعقيداً من الهاتف:

  • Ducking: خفض مستوى مصدر صوتي (مثلاً الموسيقى) عند وصول مصدر أعلى أولوية (مثلاً الملاحة).
  • Muting: كتم مصدر صوتي بالكامل عند وصول مصدر حرج (مثلاً تحذير تصادم).
  • Parallel Playback: تشغيل مصدرين في آن واحد في مناطق مختلفة (موسيقى للسائق، فيلم للأطفال).

CarAudioService يستخدم AudioPolicy و AudioMix في AudioManager لتحقيق هذا التوجيه المعقد.

القلب النابض للسيارة: Vehicle Hardware Abstraction Layer (VHAL)

إذا كان Car Service Layer هو "وزارة المواصلات"، فإن VHAL (Vehicle HAL) هو شبكة الطرق والجسور التي تربط الوزارة بالمدن (عتاد السيارة). VHAL هو الطبقة التي تترجم بين لغة البرمجيات (Java/Kotlin) ولغة العتاد (CAN Bus frames, Ethernet packets).

من CAN Bus إلى Java: رحلة الإشارة

CAN Bus (Controller Area Network) هو الشبكة الداخلية للسيارة. جميع الأجهزة الإلكترونية في السيارة (ECUs - Electronic Control Units) تتواصل عبر CAN Bus باستخدام إطارات (Frames) صغيرة (8 بايتات كحد أقصى لكل رسالة).

التمثيل الحياتي: شبكة الهاتف الداخلي في المستشفى

تخيل مستشفىً كبيراً. كل قسم (ECU) لديه هاتف داخلي (CAN Bus). عندما يحتاج قسم الطوارئ (Airbag ECU) إلى إبلاغ قسم الاستقبال (IVI System) بحادث، لا يتصل بهاتف خارجي - بل يستخدم شبكة الهاتف الداخلي. الرسالة قصيرة: "حادث في الطابق 3، سرعة 60 كم/س، رقم المريض 4729". هذه الرسالة صغيرة ومحددة - ليست مكالمة فيديو طويلة.

CAN Bus Frame كرسالة قصيرة على الشبكة الداخلية:

  • ID (11 أو 29 بت): يُحدد نوع الرسالة (مثلاً: سرعة السيارة، درجة الحرارة).
  • Data (0-8 بايت): البيانات الفعلية (مثلاً: 0x00 0x3C = 60 كم/س).
  • CRC (15 بت): للتحقق من صحة الرسالة.
  • Ack (1 بت): تأكيد الاستلام.
// هيكل إطار CAN Bus
struct can_frame {
    canid_t can_id;  // 11-bit أو 29-bit ID
    __u8    can_dlc; // ح length البيانات (0-8)
    __u8    data[8]; // البيانات الفعلية (8 بايت كحد أقصى)
};

// مثال: إطار يحمل سرعة السيارة
// can_id = 0x123 (معرف سرعة السيارة)
// can_dlc = 2 (بايتان)
// data[0] = 0x00, data[1] = 0x3C (60 كم/س)

VHAL: الترجمة بين CAN Bus و Android Properties

VHAL يعمل كـ مترجم ثنائي الاتجاه:

  1. من العتاد إلى البرمجيات (Read): يستلم إطارات CAN Bus، يفك تغليفها (Parse)، ويحولها إلى VehiclePropertyValue objects.
  2. من البرمجيات إلى العتاد (Write): يستلم VehiclePropertyValue من Car Service، يُغلّفها في إطارات CAN Bus، ويُرسلها إلى ECU المناسب.
// Vehicle HAL Interface (AIDL)

                               int32_t maxSharedMemoryFileCount);

    float maxSampleRate;       // أقصى معدل أخذ عينات (Hz)
}

HIDL vs AIDL في VHAL: التحول الهندسي

في أندرويد 8-10، كان VHAL يستخدم HIDL (HAL Interface Definition Language). لكن بدءاً من أندرويد 11+، بدأ التحول إلى AIDL. لماذا؟

  • HIDL يستخدم hwbinder - نسخة من Binder مخصصة للعتاد. هذا يتطلب عملية منفصلة (hwbinder daemon) وتسلسل إضافي.
  • AIDL يستخدم binder العادي - أسرع وأبسط وأقل استهلاكاً للذاكرة.
// HIDL (القديم) - يتطلب hwbinder
interface IVehicle @1.0 {
    getAllPropConfigs() generates (vec propConfigs);
    get(VehiclePropValue requestedProp) generates 
        (StatusCode status, VehiclePropValue propValue);
};

// AIDL (الجديد) - يستخدم binder العادي
interface IVehicle {
    VehiclePropConfig[] getAllPropConfigs();
    VehiclePropValue get(in VehiclePropValue requestedProp);
}

إدارة الطاقة، الأمان، وبدء التشغيل في السيارات

السيارة ليست هاتفاً ذكياً. عندما تُطفئ السيارة، لا يمكنك "إغلاق النظام" بالكامل كما تفعل مع الهاتف. يجب أن يبقى بعض الأنظمة نشطة (إنذار، تحديثات، تسجيل البيانات)، بينما يدخل البعض الآخر في وضع السكون. هذا يتطلب نموذج إدارة طاقة معقد يُعرف بـ CarPowerManagement.

Garage Mode: العمل الخفي عند إطفاء المحرك

Garage Mode هو وضع خاص في AAOS يُفعّل عندما يُطفئ السائق المحرك. في هذا الوضع:

  • الشاشة الرئيسية مُطفأة (لتوفير الطاقة).
  • التطبيقات لا تستطيع تشغيل واجهة المستخدم.
  • لكن المهام الخلفية مسموح بها: تحديثات النظام (OTA)، تسجيل بيانات الصيانة، تحميل الخرائط، تحديث التطبيقات.
// الاستماع لتغييرات حالة الطاقة
public class PowerStateListener implements CarPowerManager.CarPowerStateListener {

    @Override
    public void onStateChanged(int state) {
        switch (state) {
            case CarPowerManager.STATE_ON:
                // السيارة في وضع التشغيل الكامل
                enableAllFeatures();
                break;

            case CarPowerManager.STATE_SHUTDOWN_PREPARE:
                // التحضير للإغلاق
                saveCriticalData();
                break;

            case CarPowerManager.STATE_SUSPEND:
                // الدخول في وضع السكون (Suspend-to-RAM)
                releaseNonCriticalResources();
                break;

            case CarPowerManager.STATE_HIBERNATION:
                // السبات الكامل (Suspend-to-Disk)
                // يستغرق الإقلاع أطول لكن يوفر أكثر
                break;

            case CarPowerManager.STATE_POST_SUSPEND:
                // الاستيقاظ من وضع السكون
                restoreState();
                break;
        }
    }
}

// التسجيل في CarPowerManager
CarPowerManager powerManager = (CarPowerManager) car.getCarManager(Car.POWER_SERVICE);
powerManager.setListener(AsyncTask.THREAD_POOL_EXECUTOR, new PowerStateListener());
التمثيل الحياتي: حارس الليل في المبنى

Garage Mode كحارس ليل في مبنى مكتبي. عندما يغير جميع الموظفون (تُطفئ السيارة)، لا يُغلق المبنى بالكامل. بدلاً من ذلك:

  • الأضواء الرئيسية تُطفأ (الشاشة تُطفأ).
  • نظام الأمان يبقى نشطاً (إنذار، كاميرات).
  • فريق الصيانة يعمل (تحديثات OTA، تنظيف).
  • المولد الاحتياطي جاهز (البطارية تحافظ على الطاقة الحرجة).

عندما يأتي أول موظف صباحاً (تُشغل السيارة)، يستيقظ المبنى بالكامل خلال ثوانٍ.

تحسين زمن الإقلاع (Boot Time Optimization)

في عالم السيارات، زمن الإقلاع (Boot Time) هو مسألة حياة أو موت - ليس مجرد راحة. السائق يتوقع أن تر ven النظام خلال 2 ثوانٍ من فتح الباب، لا 30 ثانية. لتحقيق هذا، يستخدم AAOS عدة تقنيات:

  • Zygote Preloading: تحميل جميع مكتبات Framework في الذاكرة أثناء إقلاع النظام الأولي.
  • Parallel Service Initialization: تشغيل خدمات النظام بالتوازي بدلاً من التسلسل.
  • Lazy HAL Initialization: تهيئة HALs فقط عند الحاجة (مثلاً لا تُهيئ Bluetooth حتى يُفتح شاشة Bluetooth).
  • Suspend-to-RAM: بدلاً من الإغلاق الكامل، يُحفظ حالة النظام في RAM. الاستيقاظ أسرع بـ 10x من الإقلاع البارد.
  • Read-Ahead Optimization: تحميل ملفات النظام المتوقعة إلى الذاكرة مسبقاً.

منع تشتيت الانتباه: Driver Distraction Optimization

الأمان هو الأولوية القصوى في AAOS. لا يمكن أن يُشغل السائق فيديو على الشاشة أثناء القيادة، أو يكتب رسالة نصية طويلة. CarUxRestrictions هو النظام الذي يُقيّد واجهة المستخدم بناءً على حالة السيارة. 

// CarUxRestrictionsManager - التحقق من القيود
public class DistractionManager {
    private CarUxRestrictionsManager mUxRestrictionsManager;

    public void init(Context context) {
        Car car = Car.createCar(context);
        mUxRestrictionsManager = (CarUxRestrictionsManager) 
            car.getCarManager(Car.CAR_UX_RESTRICTION_SERVICE);

        mUxRestrictionsManager.registerListener(
            new CarUxRestrictionsManager.OnUxRestrictionsChangedListener() {
                @Override
                public void onUxRestrictionsChanged(CarUxRestrictions restrictions) {
                    if (restrictions.isRequiresDistractionOptimization()) {
                        // السيارة في حركة - تفعيل القيود
                        applyDrivingRestrictions(restrictions);
                    } else {
                        // السيارة متوقفة - إلغاء القيود
                        removeRestrictions();
                    }
                }
            }
        );
    }

    private void applyDrivingRestrictions(CarUxRestrictions restrictions) {
        // التحقق من أنواع القيود
        boolean noVideo = restrictions.isVideoRestricted();
        boolean noKeyboard = restrictions.isKeyboardRestricted();
        boolean limitedStringLength = restrictions.getMaxStringLength() > 0;

        if (noVideo) {
            hideVideoPlayer();
        }

        if (noKeyboard) {
            disableKeyboardInput();
        }

        if (limitedStringLength) {
            int maxLength = restrictions.getMaxStringLength();
            limitTextInputLength(maxLength);
        }
    }
}

CarUxRestrictions يدعم مستويات متدرجة من القيود:

  • BASELINE: القيود الأساسية (لا يوجد).
  • NO_VIDEO: منع تشغيل الفيديو.
  • NO_KEYBOARD: منع لوحة المفاتيح (Voice Input فقط).
  • LIMIT_STRING_LENGTH: تقييد طول النصوص المعروضة.
  • NO_SETUP: منع إعدادات النظام المعقدة.
  • NO_TEXT_MESSAGE: منع الرسائل النصية الطويلة.

SELinux: الجدار الناري للنواة

SELinux (Security-Enhanced Linux) هو نظام تحكم في الوصول إلزامي (MAC) يعمل على مستوى kernel. في AAOS، SELinux يُحدد بالضبط أي عملية يمكنها الوصول إلى أي ملف أو socket أو Binder service. مثلاً: تطبيق الملاحة لا يستطيع الوصول إلى /dev/can0 (CAN Bus device) لأن SELinux policy تمنع ذلك. فقط VehicleHAL و CarService لديهم إذن الوصول. هذا يمنع تطبيقات خبيثة من التحكم في عتاد السيارة.

أسئلة المقابلات الشخصية المتقدمة

هذه الأسئلة تغطي العمق الهندسي لبنية AOSP و AAOS وهي شائعة في مقابلات Senior AOSP Platform Engineer و Android Automotive Architect.

Senior Level

السؤال ١: ما الفرق بين Binder IPC و Unix Domain Sockets في أندرويد؟ ولماذا اختارت Google Binder؟

الإجابة الهندسية:

Unix Domain Sockets تتطلب نسخ البيانات مرتين: من مساحة العميل (User Space) إلى Kernel Buffer، ثم من Kernel Buffer إلى مساحة الخادم (User Space). بالإضافة إلى ذلك، لا تحمل هوية المرسل تلقائياً - يجب إرسالها كجزء من البيانات. هذا يعني تكلفة عالية لكل Transaction.

Binder يستخدم mmap() لإنشاء ذاكرة مشتركة (Shared Memory) بين العمليات. البيانات تُنسخ مرة واحدة فقط من العميل إلى Kernel. ثم يُعطى الخادم وصف ملف (File Descriptor) يشير إلى نفس الذاكرة دون نسخ إضافي. هذا يُقلل من تكلفة النسخ بمقدار النصف.

بالإضافة إلى ذلك، Binder يحمل UID و PID للعميل تلقائياً في كل Transaction. هذا يمكّن النظام من:

  • فرض Permissions على مستوى النظام (مثلاً android.permission.CAMERA).
  • منع انتحال الهوية (Identity Spoofing).
  • تتبع استهلاك الموارد لكل تطبيق.

الخلاصة: Binder أسرع (One-Copy vs Two-Copy)، أكثر أماناً (هوية مُدمجة)، ومصمم خصيصاً لنموذج خدمات أندرويد.

Senior Level

السؤال ٢: كيف يعمل Low Memory Killer (LMK) في أندرويد؟ وما الفرق بينه وبين OOM Killer في لينكس القياسي؟

الإجابة الهندسية:

OOM Killer في لينكس القياسي يُفعّل عندما تنفد الذاكرة تماماً. يختار الضحية بناءً على oom_score الذي يعتمد على استهلاك الذاكرة والـ CPU. المشكلة: يمكن أن يقتل أي عملية - حتى System Server أو Phone App - مما يسبب عدم استقرار.

LMK في أندرويد يعمل قبل نفاد الذاكرة تماماً. يُراقب free memory و file-backed pages بشكل مستمر. عندما تصل الذاكرة إلى عتبات (Thresholds) مُحددة مسبقاً، يبدأ في قتل العمليات حسب أولوية مُحددة:

  • Background Apps (OomAdj > 900): تُقتل أولاً.
  • Previous App (OomAdj ~ 700): تُقتل ثانياً.
  • Home App (OomAdj ~ 600): تُقتل ثالثاً.
  • Services (OomAdj ~ 500): تُقتل رابعاً.
  • Foreground App (OomAdj ~ 0): تُحفظ حتى النهاية.
  • System Server (OomAdj = -1000): لا تُقتل أبداً (يؤدي إلى reboot).

في AAOS، LMK مُحسّن إضافياً لأن السيارة لا يمكنها إعادة الإقلاع أثناء القيادة. لذا يتم تخصيص minfree levels بشكل أكثر تحفظاً.

Staff Level

السؤال ٣: ما هو الفرق بين Android Auto و Android Automotive OS (AAOS) من حيث الهندسة المعمارية؟

الإجابة الهندسية:

Android Auto: يعمل على الهاتف الذكي. يُعرض واجهة مستخدم مُبسّطة على شاشة السيارة عبر USB/WiFi (بروتوكول Android Auto Protocol). الهاتف هو المصدر الوحيد للمعالجة والبيانات. السيارة مجرد "شاشة عرض" و"لوحة لمس". لا يوجد وصول مباشر إلى عتاد السيارة (CAN Bus). Google تتحكم بالتجربة بالكامل.

AAOS: يعمل على وحدة IVI في السيارة. هو نظام تشغيل كامل يشمل Linux Kernel، Android Framework، وخدمات السيارة (CarService, VHAL). يتواصل مباشرة مع CAN Bus عبر VHAL. الشركة المصنعة تتحكم في UI/UX والتخصيص. يدعم شاشات متعددة (Cluster + IVI + Rear). يتطلب ترخيص Google Automotive Services (GAS) لاستخدام Maps و Play Store.

الخلاصة: Android Auto = "Remote Desktop" من الهاتف. AAOS = "نظام تشغيل مدمج" في السيارة.

Staff Level

السؤال ٤: كيف يعمل VHAL (Vehicle HAL) في قراءة بيانات CAN Bus وتحويلها إلى Vehicle Properties؟

الإجابة الهندسية:

الرحلة من CAN Bus إلى Java:

  1. CAN Bus Frame: ECU (مثلاً وحدة المحرك) تُرسل إطار CAN بـ can_id = 0x123 و data = [0x00, 0x3C] (سرعة = 60 كم/س).
  2. SocketCAN Driver: برنامج تشغيل CAN Bus في Linux Kernel يستلم الإطار ويضعه في /dev/can0.
  3. VehicleHAL (Native): يقرأ من /dev/can0 عبر SocketCAN API. يفك تغليف الإطار (Parse) باستخدام DBC (Database CAN) file الذي يُعرّف: "can_id 0x123 = سرعة السيارة، بايت 0-1 = القيمة × 0.1 كم/س".
  4. VehicleHAL (AIDL): يُنشئ VehiclePropValue object: {prop: PERF_VEHICLE_SPEED, areaId: GLOBAL, value: 60.0}.
  5. Binder IPC: يرسل VehiclePropValue عبر Binder إلى CarService (Java).
  6. CarService: يستلم القيمة، يُحدث حالته الداخلية، ويُبلّغ جميع المستمعين (Listeners) المسجلين.
  7. Application: CarSensorManager يستدعي onSensorChanged() في التطبيق.

العكس (كتابة): عندما يضغط السائق على زر "رفع درجة الحرارة"، تسير الرحلة بالعكس: تطبيق → CarHvacManager → CarService → VHAL → SocketCAN → CAN Bus → ECU HVAC.

Senior Level

السؤال ٥: ما هو Garage Mode في AAOS؟ وكيف يختلف عن Doze Mode في الهاتف؟

الإجابة الهندسية:

Doze Mode (الهاتف): يُفعّل عندما يكون الهاتف ثابتاً وغير مستخدم لفترة. يُقيّد الوصول إلى الشبكة (JobScheduler, Alarms, Network). الهدف: توفير البطارية. المستخدم يمكنه إلغاء Doze ببساطة بتحريك الهاتف.

Garage Mode (السيارة): يُفعّل عندما يُطفئ السائق المحرك (AP_POWER_STATE_REQ = OFF). في هذا الوضع:

  • الشاشة تُطفأ (Display OFF).
  • التطبيقات لا تستطيع تشغيل Activities.
  • المهام الخلفية مسموحة: OTA Updates، تسجيل بيانات الصيانة، تحميل الخرائط.
  • CarService يبقى نشطاً لمراقبة حالة السيارة.
  • النظام قد يدخل Suspend-to-RAM بعد فترة.

الفرق الجوهري: Doze يهدف إلى توفير البطارية بتقييد كل شيء. Garage Mode يهدف إلى التوازن: إطفاء UI لتوفير الطاقة، لكن السماح بمهام الصيانة الحرجة. السيارة ليست هاتفاً - لا يمكن "إغلاقها" بالكامل.

Architect

السؤال ٦: كيف يتم تأمين VHAL بحيث لا يستطيع تطبيق عشوائي التحكم في أبواب السيارة أو المكابح؟

الإجابة الهندسية:

هناك أربع طبقات أمان تحمي VHAL:

  1. Signature Permissions: أذونات مثل android.car.permission.CAR_CABIN و android.car.permission.CAR_HVAC تتطلب أن يكون التطبيق موقعاً بنفس مفتاح النظام (System Signature). تطبيقات Play Store العادية لا تستطيع الحصول عليها.
  2. SELinux Policy: vehicle_hal.te يُحدد أن vehicle_hal process يمكنه الوصول فقط إلى /dev/can* و car_service. تطبيقات المستخدم (u:r:untrusted_app:s0) لا يمكنها التحدث إلى VHAL مباشرة.
  3. CarService as Gatekeeper: التطبيقات لا تتحدث إلى VHAL مباشرة. بل تتحدث إلى CarService عبر Binder. CarService يتحقق من UID و Permission قبل تمرير الطلب إلى VHAL.
  4. Property Access Control: بعض الخصائص (مثلاً DOOR_LOCK) تُعرّف في VehiclePropConfig كـ READ_WRITE فقط لعمليات النظام. VHAL نفسه يرفض الكتابة من عمليات غير موثوقة.

# VHAL يمكنه التحدث إلى CarService فقط
allow vehicle_hal car_service:binder call;

# تطبيقات المستخدم لا يمكنها الوصول إلى VHAL
neverallow untrusted_app vehicle_hal:binder call;

السؤال ٧: كيف تُصمم نظام Audio في AAOS يدعم شاشات متعددة ومناطق صوتية مختلفة؟

CarAudio Architecture:

السؤال ٨: ما هي مشكلة Boot Time في AAOS وكيف تُحل؟

الإجابة الهندسية:

المشكلة: السائق يتوقع أن تر ven النظام خلال 2 ثوانٍ من فتح الباب. لكن إقلاع Linux Kernel + Android Framework + CarService + VHAL قد يستغرق 20-40 ثانية.

الحلول:

  • Suspend-to-RAM (S3): بدلاً من الإغلاق الكامل، يُحفظ حالة النظام في RAM. عند فتح الباب، يستيقظ النظام خلال 1-3 ثوانٍ. هذا هو الحل الأساسي.
  • Zygote Preloading: تحميل جميع مكتبات Framework في الذاكرة أثناء إقلاع النظام الأولي. التطبيقات تبدأ عبر fork() من Zygote (Copy-On-Write).
  • Parallel Service Initialization: في SystemServer، خدمات النظام تُطلق بالتوازي بدلاً من التسلسل. AAOS يضيف CarService إلى startOtherServices() مع أولوية عالية.
  • Lazy HAL Initialization: HALs مثل Bluetooth أو WiFi لا تُهيأ حتى يُفتح الإعدادات. فقط HALs الحرجة (Display, Audio, VHAL) تُهيأ فوراً.
  • Read-Ahead: init.rc يستخدم readahead لتحميل ملفات النظام المتوقعة إلى Page Cache.
  • A/B Partitioning: يُقلل من وقت التحقق من OTA Updates أثناء الإقلاع.

السؤال ٩: كيف يعمل HIDL vs AIDL في HALs؟ ولماذا تحولت Google من HIDL إلى AIDL في أندرويد 11+؟

الإجابة الهندسية:

HIDL (Android 8-10): صُمم لفصل HAL عن Framework عبر Stable Interface. يستخدم hwbinder - نسخة من Binder مخصصة للعتاد. يتطلب عملية منفصلة (hwbinder daemon) وتسلسل إضافي (HIDL uses its own serialization format). هذا يعني تكلفة إضافية في كل Transaction.

AIDL (Android 11+): يستخدم binder العادي مباشرة. لا يتطلب hwbinder daemon. يستخدم Parcel serialization المُحسّن بالفعل. أسرع وأقل استهلاكاً للذاكرة. بالإضافة إلى ذلك، AIDL يدعم Java backends مباشرة (HIDL يتطلب C++ backend).

لماذا التحول؟

  • الأداء: AIDL أسرع بنسبة 20-30% في معظم السيناريوهات.
  • البساطة: مطور واحد يمكنه كتابة AIDL interface و Java implementation. HIDL يتطلب C++ implementation + Java wrapper.
  • الصيانة: AIDL أقرب إلى "كود أندرويد العادي" - أسهل في التصحيح والصيانة.
  • التوحيد: بدلاً من Binder + hwbinder، يوجد Binder واحد فقط.

السؤال ١٠: كيف تُصمم نظام OTA (Over-The-Air) Updates في AAOS يعمل بأمان أثناء Garage Mode؟

الإجابة الهندسية:

A/B Partitioning (Seamless Updates): AAOS يستخدم A/B partitioning حيث يوجد نسختان من كل قسم (System, Vendor, Boot). أثناء Garage Mode:

  1. Download: يُحمّل التحديث إلى القسم غير النشط (B) أثناء Garage Mode.
  2. Verification: يُتحقق من توقيع التحديث (Verified Boot / dm-verity).
  3. Switch: عند الإقلاع التالي، يُحوّل Bootloader إلى القسم B.
  4. Rollback: إذا فشل الإقلاع 3 مرات، يُرجع Bootloader تلقائياً إلى القسم A.

الأمان:

  • Verified Boot: كل قسم يُتحقق منه عبر dm-verity (hash tree) قبل التحميل.
  • AVB (Android Verified Boot) يضمن أن Bootloader نفسه لم يُعدّل.
  • Encryption: partitions تُشفّر بـ File-Based Encryption (FBE).
  • SELinux: OTA Daemon يعمل في u:r:ota_daemon:s0 context محدود.
// Garage Mode + OTA
public class OtaUpdateService extends Service {
    @Override
    public void onCreate() {
        CarPowerManager powerManager = ...;
        powerManager.setListener(executor, state -> {
            if (state == CarPowerManager.STATE_ON) {
                // السيارة في وضع التشغيل - لا تقم بـ OTA
                cancelOtaDownload();
            } else if (state == CarPowerManager.STATE_SHUTDOWN_PREPARE) {
                // السيارة تُطفأ - Garage Mode قادم
                if (isWifiConnected() && batteryAboveThreshold()) {
                    startOtaDownload();
                }
            }
        });
    }
}
